智能合约与 EVM

合约在链上到底是什么、怎么部署、地址怎么来；调用一个函数时交易里写了什么；链下服务怎么靠事件知道链上发生了什么；EVM 怎么一步步执行、为什么写存储那么贵；以及“EVM 等价”和“EVM 兼容”到底差在哪。

一句话

智能合约 = 链上一个地址里存着的一段字节码，加上它自己的一块存储；EVM 是执行这段字节码的虚拟机

你写的 Solidity 会被编译成字节码，部署后放在链上某个地址里。之后谁给这个地址发交易，所有节点都会用 EVM 执行同一段字节码，得出同一个结果，改同一块存储。USDC、桥、CCTP、CCIP，前面所有章节里的“合约”都是这个东西。

常见说法里，对的部分

  • 合约代码公开，任何人都能看、都能验证执行结果
  • 合约按代码执行，没有人能在执行中途插手
  • 同一份 Solidity 能部署到 Ethereum、Base、OP、BSC，Qtum 上大体也行

需要纠正的部分

  • 合约不会自己运行。没有定时器，必须有人发交易调用它，代码才会执行
  • 合约看不到链外的世界，也看不到别的链。ethereum.org 原话：合约“不能从链外来源获取数据”，这是设计如此。所以需要预言机、需要桥
  • 链上存的不是 Solidity 源码，是编译后的字节码。区块浏览器上的源码，是开发者自己上传、再由浏览器重新编译核对的
  • “部署后不能改”只对单个合约成立。用代理合约可以换逻辑（入门章、第 02 章）
  • “EVM 兼容”不等于完全一样：opcode 版本、gas 价格、地址规则、区块字段的含义，各链都可能不同（见下文）

合约在链上

两种账户，一套字段

以太坊上的每个地址都是一个账户，有四个字段：nonce、balance、codeHash、storageRoot。普通账户（EOA）由私钥控制，codeHash 是空串的哈希；合约账户由代码控制，codeHash 指向它的字节码，storageRoot 是它那块存储的默克尔根。

普通账户（EOA）合约账户
由谁控制私钥代码
能主动发交易吗能不能，只能在被调用时再去调用别的合约
有代码吗没有（Pectra 后可以通过 EIP-7702 临时指向一段合约代码）有，部署时写入
有存储吗没有有：2256 个槽，每个槽 32 字节

部署：一笔没有收款人的交易

部署交易的 data 里放的是“初始化代码”：它执行一次（跑构造函数），返回值才是存进链上的“运行时代码”。新合约的地址在部署前就能算出来：

方式地址怎么算说明
CREATEkeccak256(rlp([部署者, 部署者的 nonce])) 的后 20 字节普通部署
CREATE2keccak256(0xff ‖ 部署者 ‖ salt ‖ keccak256(初始化代码)) 的后 20 字节EIP-1014。和 nonce 无关，所以能在多条链上部署到同一个地址。CCTP V2 的合约仓库里就有一个 Create2Factory，各链地址相同
QtumRIPEMD160(SHA256(txid ‖ 输出序号))没有账户 nonce，规则完全不同（第 01 章）
EIP-170

合约有大小上限

运行时代码最多 0x6000 = 24,576 字节；初始化代码最多 49,152 字节（EIP-3860）。链上读到：USDC 的实现合约 FiatToken 2.2 是 23,464 字节，已经很接近上限；它的代理合约只有 2,186 字节；CCTP 的 TokenMessengerV2 代理 2,175 字节；WBTC 4,582 字节。

Verify

怎么确认链上跑的就是那份源码

用同样的编译器版本和参数重新编译源码，比对字节码。第 02 章提到，Bridged USDC Standard 要求第三方用 Solidity 0.6.12 编译、把编译元数据交给 Circle 核对，就是这个原因。

调用

操作码执行谁的代码改谁的存储被调用方看到的 msg.sender常见用途
CALL被调用合约 BB 的A普通调用；转 ETH
STATICCALLB不允许改任何状态Aview / pure 函数，比如查余额
DELEGATECALLBA 的原来调用 A 的那个人代理合约：数据在代理里，逻辑在实现合约里

被调用的合约 revert 时，它这一层的修改全部撤销；调用方如果不专门处理（Solidity 默认会把错误继续往上抛），整笔交易回滚，gas 照付。第 03 章说桥“先标记已领、再铸币”是安全的，靠的就是这一点。

ABI

合约之间、钱包和合约之间，按 ABI（Application Binary Interface）约定的格式传数据。调用数据（calldata）的前 4 字节是函数选择器：函数签名（如 transfer(address,uint256)）的 Keccak-256 哈希的前 4 字节；后面每个参数占 32 字节。

Tool

选择器、事件 topic、calldata

输入函数或事件签名（只写类型，不写参数名和空格），算出选择器和 topic。下面再按 transfer(address,uint256) 拼一段完整的 calldata。Keccak-256 在浏览器里计算。

如果签名里写错一个字符（比如 uint 没写成 uint256），选择器就完全不同，调用会落到合约的“找不到函数”分支。

事件

合约用 emit 写日志（底层是 LOG0–LOG4 操作码）。日志不进合约存储，合约自己也读不到，但节点会保存，链下服务可以用 eth_getLogs 按条件查。桥的 Validator、区块浏览器、钱包的余额变动提醒，全都靠这个。

部分内容一条真实的 USDC Transfer 日志（以太坊区块 26,292,306）
address发出日志的合约0xA0b8…eB48（USDC）
topics[0]事件签名的 Keccak-2560xddf252ad…b3ef = keccak256("Transfer(address,address,uint256)")
topics[1]、[2]标了 indexed 的参数，可以按它过滤from、to，各补齐到 32 字节
data没标 indexed 的参数，ABI 编码0x…04c1 = 1217，按 6 位小数是 0.001217 USDC
Qtum Bridge

Qtum 桥的存款事件

DepositedERC20(address token, uint256 amount, string receiver, string network, ERC20BridgingType operationType)。topic0 是 0xda9a7442…0684（枚举在 ABI 里按 uint8 算）。它的参数都没有标 indexed，所以 Validator 只能按“桥合约地址 + topic0”查出全部存款，再在链下解码 data 逐条处理。

Caution

日志也会被重组掉

日志属于区块。区块被重组掉，日志也就不存在了，eth_getLogs 的结果会变。所以链下服务不能看到日志就签名，要等区块达到足够的确认程度（第 05 章）。

EVM 内部

ethereum.org：EVM 是一台深度 1024 的栈机器，每项 256 位。执行时有三类地方放数据，价格差别非常大。

位置生命周期读 / 写的 gas
栈一次调用内大多数运算 3 gas（如 ADD、PUSH1）
内存（memory）一次调用内，按字节寻址MSTORE 3 gas + 内存扩展费
临时存储（transient）一笔交易内，结束后清空TSTORE / TLOAD 各 100 gas（Cancun，EIP-1153）
存储（storage）永久，属于这个合约SLOAD：首次 2100，再读 100（EIP-2929）；SSTORE 把 0 改成非 0：20,000 + 首次访问 2,100

这就是为什么“转一笔 USDC”要 4 万多 gas、“转 ETH”只要 21,000：ERC-20 转账至少要读写两个存储槽（双方余额），还要写一条日志。

版本

EVM 也在升级：编译目标要和链对得上

每次以太坊硬分叉都可能给 EVM 加新操作码或预编译。Solidity 编译时有个 evmVersion 参数，决定能用哪些操作码。当前文档里默认是 osaka。如果目标链还没支持某个操作码，按新版本编译的合约部署上去就会失败或行为异常。

“等价”指尽量做到和以太坊逐项一致，以太坊上能跑的合约和工具，不改就能用；“兼容”指能跑 EVM 合约，但在某些地方行为不同。下面这张表把前面各章讲过的差异放在一起。
