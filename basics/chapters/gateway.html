EthGateway

一座 ETH ↔ Qtum 托管桥在以太坊这一侧的合约：用户的 USDC 存进来，用户提现时从这里付出去。它里面装着哪些规则、为什么这样设计、和冷钱包、签名服务、Qtum 侧的 MintGateway 是什么关系，以及审计时要盯住哪些地方。

一句话

EthGateway = 一个不可升级的合约，收用户存入的 USDC，只在热余额上限内留钱，超出的同笔转进冷钱包；放款只认运营地址，并受单笔和 24 小时上限约束

它是一份托管桥设计里的合约，用来讲清楚一个托管合约该有哪些规则，不是已经部署的合约。“EthGateway”只是这份设计里的名字，不是某个现成产品或行业标准。下文的函数名和字段都是示意。

基础事实内容
在哪条链以太坊主网。Qtum 那一侧对应的合约叫 MintGateway
管什么币只管 Circle 发行的原生 USDC（以太坊上的 FiatToken 合约）。它自己不发币
钱放在哪一小部分（热余额，有上限）在 EthGateway 里；大部分在冷钱包 Safe（3/5 硬件钱包多签）里
谁能让它付钱正常放款：运营地址（钥匙在云端 HSM，由签名服务调用）。大额：冷钱包多签。退款：冷钱包多签
谁能停它守护者（看门狗和值班人员）能暂停；只有冷钱包多签能恢复
能不能升级不能。要改代码就部署新合约，再把业务迁过去

常见理解里，对的部分

  • 它是桥在以太坊这一侧的入口和出口：存入、提现到账都经过它
  • 它的规则写在合约里，任何人都能在链上查：热余额多少、今天放了多少、某个 ID 有没有执行过

需要纠正的部分

  • 不是现成的东西。Axelar 的 AxelarGateway、Arbitrum 的 Gateway 合约名字像，但和它没有关系（Axelar 的见图鉴）
  • 它不保管全部储备。热余额有上限，超过的部分在存入那一刻就进了冷钱包
  • 它不知道 Qtum 上发生了什么。合约只检查“调用者是不是运营地址”，用户在 Qtum 上有没有真的销毁，是签名服务在链下核对的。这和 Hyperlane、CCIP 那种“合约里验证另一条链的证明”不一样
  • 不可升级不等于参数不能改。上限、运营地址这些由冷钱包多签直接改
  • 不可升级也不等于更安全。它去掉了“升级换成恶意代码”这条路，代价是发现 bug 不能打补丁，只能暂停、部署新合约、迁移

在哪

加粗边框的就是 EthGateway。实线是交易（钱或指令），虚线是“读事件”，橙色虚线是暂停。注意 EthGateway 和 MintGateway 之间没有直接连线：两个合约互相看不见，靠中间的链下服务把两边对上。

两条线要分开看：钱只在以太坊内部流动（用户 ↔ EthGateway ↔ 冷钱包），从不跨链；信息靠链下服务读一边的事件、到另一边发交易。所以“跨链”这件事的安全，几乎全压在签名服务和看门狗上，EthGateway 的任务是在它们出错时把损失框住。

拆开看

合约里存了什么、有哪些函数、谁能调用

下面三张表是按职责写出的一种接口，名字是示意。看的时候重点看“谁能调”和“要检查什么”两列：一个托管合约的安全，基本就是这两列。

存的状态

状态是什么谁能改
hotCap热余额上限。存入后热余额超过它，多出来的当场转冷冷钱包多签
perTxCap、dailyCap运营地址的单笔放款上限、24 小时放款上限冷钱包多签
cold冷钱包地址，转冷只能转到这里部署时写入；要不要允许改，见文末“审计要盯的地方”
operator、guardians运营地址（只能放款和取消）、守护者（只能暂停）冷钱包多签
deposits[seq]每笔存入一条：发起人、金额、Qtum 收款地址、是否已退款。seq 是网关内的递增序号存入时写入，退款时标记
executed[id]、cancelled[id]Qtum → 以太坊方向，每个转账 ID 是否已付款、是否已取消放款、取消时写入，写入后不能撤销
booked账面余额：经过正常函数进出的钱。实际余额减去它，就是误转进来的钱每个进出钱的函数都要更新
paused、depositOpen是否暂停；存入入口是否开放（迁移时关闭）暂停：守护者；恢复和入口：冷钱包多签

转账 ID 的格式是：源链 + 源网关地址 + 网关内序号。以太坊这一侧的存入 ID 由 EthGateway 自己的地址和 seq 组成；从 Qtum 过来的 ID 由 MintGateway 的地址和它的序号组成。换了网关也不会撞号。

函数

函数（示意）谁能调做什么合约要检查
deposit(amount, qtumTo)任何用户从用户那里拉入 USDC，登记一条存入；热余额补到上限，多出的同一笔交易转冷；发出存入事件未暂停、入口开放、金额 > 0、Qtum 地址长度对（20 字节）
release(id, to, amount)运营地址Qtum → 以太坊的正常放款，从热余额付出未暂停；这个 ID 没执行过、没取消过；金额 ≤ 单笔上限；24 小时累计 ≤ 上限；热余额够
cancel(id)运营地址取消一笔 Qtum → 以太坊的转账（被拒的提现），之后 Qtum 侧才能重新铸币退给用户这个 ID 没执行过。取消只会挡住付款，动不了钱，所以运营地址就能做
releaseByCold(id, to, amount)冷钱包多签超过单笔上限的大额放款：一种做法是多签在一笔批量交易里先把钱转进来、再付出（另一种写法见文末）和 release 共用 executed / cancelled，同一个 ID 不能两条路都走
refund(seq)冷钱包多签被拒绝的以太坊 → Qtum 存入，退回原发起人这笔存入存在、没退过；金额和收款人从存入记录里取，不接受调用者传入
topUp(amount)冷钱包多签冷转热补款更新账面余额，让补进来的钱不会被当成误转
sweepToCold(amount)冷钱包多签把热余额收回冷钱包目的地只能是 cold
returnStray(to, amount)冷钱包多签把误转进来的钱人工核实后退回金额 ≤ 实际余额 − 账面余额，不能动正常储备
pause() / unpause()守护者 / 冷钱包多签暂停 / 恢复暂停要快，恢复要严
set…()、closeDeposits()冷钱包多签改上限、换运营地址和守护者；迁移时关闭存入入口每改一次都发事件，看门狗要能看到

角色：每把钥匙能做什么、不能做什么

角色能做不能做钥匙泄露，最多损失
用户存入其他一切—
运营地址（以太坊）放款、取消改参数、恢复、碰冷钱包24 小时上限和热余额，两者取小（下面有计算器）
守护者暂停恢复、付款恶意暂停，不损失资金
冷钱包多签（3/5）大额放款、退款、补款、收回、改参数、恢复—（它是最终的信任根）单把泄露凑不够门限
审核员链上什么都不能做—只是给大额签批准，由签名服务在链下校验

冷钱包多签是最终的信任根：它能付大额、能换运营地址。所以“冷钱包只能转进网关”这条限制的作用，不是让多签动不了钱，而是让多签每一笔付款都经过网关、都带 ID、都留下事件，看门狗能逐笔对账。

分步看

数字是示意值（热余额上限 20 万、单笔上限 2 万、24 小时上限 5 万），真实金额要按业务量来定。

deposit

① 存入：热余额补到上限，多出的同一笔转冷

release

② 放款：合约只认运营地址和上限，真假由签名服务判断

key leak

③ 运营密钥泄露：上限框住损失，看门狗暂停，多签换钥匙

refund

④ 退款：先在对面取消，确认后再退

算一算

三个数防的是不同的事，不能只看一个。热余额上限决定“现在网关里最多躺着多少钱”；单笔上限决定“多大的提现必须走多签”；24 小时上限决定“运营密钥被盗后，一天最多被放走多少”。

“最多损失”这里只算运营密钥泄露这一种情况、暂停之前的 24 小时。更完整的估算是：暂停前最坏损失 ≈ 这段时间的放款上限 + 剩余铸币额度。后一项在 Qtum 侧，不在 EthGateway 里。如果 24 小时上限按“滚动窗口”算，它和第 04 章 CCIP 的限速桶是同一类东西。

关系

组件关系要注意
MintGateway（Qtum）镜像：一边收存入、一边铸币；一边销毁、一边放款。两边用同一种 ID 格式两个合约互相看不见。“取消后才能退款”这种跨链的先后顺序，合约自己保证不了，要靠流程和看门狗
冷钱包 Safe + GuardEthGateway 的管理员；储备的大头。Guard 限定 Safe 只能调 USDC 的 transfer / approve 把钱给网关，以及调网关自己的管理函数Safe 官方源码的警告原话：Guard “has full power to block Safe transaction execution, a broken guard can cause a denial of service for the Safe”。Guard 必须允许多签换掉或移除 Guard 本身，否则写错一处，冷钱包就锁死了
签名服务唯一拿着运营密钥的程序。EthGateway 只检查“是不是运营地址”，所以这笔放款该不该付，完全由签名服务判断签名服务的核对逻辑，本质上就是 EthGateway 的“验签”，要和合约一起审（第 10 章）
看门狗持有守护者钥匙；读 EthGateway 的存入、放款、取消、退款、改参数事件，和 Qtum 侧对账事件里必须带齐对账要用的字段（ID、金额、收款人），否则看门狗只能去问后端，就不独立了
USDC（Circle 的 FiatToken）EthGateway 里装的币FiatToken 的 transfer 和 transferFrom 会检查发送方、接收方都不在黑名单。Circle 如果把网关或冷钱包拉黑，钱就动不了；用户的以太坊收款地址被拉黑，放款会失败，订单只能停在“待放款”。USDC 自己也能被 Circle 暂停和升级，这些都在托管桥控制之外

审计要点

第 10 章讲了跨链桥的审计要覆盖哪些层。下面只列 EthGateway 这一块里最容易出错的点。标“建议”的是一种可行的做法，不是唯一答案。

地方可能出的问题建议的做法
24 小时上限怎么算如果按自然日清零，攻击者可以在 23:59 放满一次、00:01 再放满一次，一小时内拿走两倍建议：用滚动窗口或限速桶（容量 + 每秒补充）
大额放款的“一笔批量交易”Safe 的批量交易是 delegatecall 到 MultiSend 合约来执行的。Guard 如果一律禁止 delegatecall，大额放款发不出去；如果放开，就要能检查批量里的每一条调用，Guard 会复杂很多建议：让 releaseByCold 自己用 transferFrom 从冷钱包拉钱再付出，多签只需调用一次，Guard 可以禁止 delegatecall
冷转热怎么进来多签直接转账给网关，不经过函数，账面余额不会增加，这笔补款会被当成误转建议：补款只能走 topUp；Guard 只放行这条路径
账面余额某个进出钱的函数漏了更新，误转识别就会算错，严重时 returnStray 能动正常储备把“账面余额 ≤ 实际余额”写成不变量，用模糊测试覆盖所有函数
退款的金额和收款人如果由调用者传入，多签操作失误或被骗就可能退错人、退多了从存入记录里取，每笔只能退一次
取消和执行两者用不同的记录，或检查顺序写错，同一个 ID 可能既取消又执行同一个 ID 的状态只有三种：未处理、已执行、已取消，只能从“未处理”变出去
暂停时哪些还能用全停，出事时多签也没法收回热余额；全不停，暂停就没意义待定：存入、放款、取消一定停；收回冷钱包、退款是否允许要明确写进规格
冷钱包地址能不能改能改，多签被攻破时可以把转冷目的地改成攻击者地址；不能改，冷钱包要换就得换网关建议：部署时写死；要换冷钱包按迁移流程换网关
Qtum 收款地址Qtum 地址在链上是 20 字节，前端要把用户填的地址转换过来。转换错了，铸到一个没人控制的地址合约只能检查长度；前端和签名服务都要校验，测试网逐种地址类型测试
构造参数和多签可改的参数代码审过了，部署时参数填错，等于白审列一张全部参数的表，部署后从链上读出来逐项核对（第 10 章“证明链上跑的就是审过的代码”）

设计这类网关时要先定下来的事：各项上限的金额；充值方式选 A（用户直接调合约）还是 B（每人一个专属地址、服务端归集）。选 B 时存入记录里的“发起人”是归集合约，不是用户，“退回原发起人”要重新定义：用户往往是从交易所提币进来的，交易所的提币地址通常不能直接退回。另外还有：手续费在不在网关里收；暂停期间能不能退款。
