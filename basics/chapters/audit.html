跨链安全审计

什么是安全审计、谁有资格做、具体怎么做；跨链桥的审计为什么要远远超出合约，链下系统和运营又怎么审；怎样证明链上跑的就是审过的那份代码。

一句话

安全审计 = 一支独立的团队，在约定的时间和范围内，审查某一版代码和系统设计，把发现的问题写成报告

它是对某个时间点、某个版本、某个范围的专业体检，不是安全保证，也不是执照。对跨链桥来说，要审的远不止合约：链下的 Validator 程序、私钥怎么保管、管理员能做什么、出事了怎么办，都在范围里。

常见说法里，对的部分

  • 上线前请外部团队审计，是行业的基本做法
  • 审计能找出很多开发团队自己看不出的问题
  • 大桥一般会请多家审计。Wormhole 官方文档列出 Trail of Bits、Neodyme、Kudelski、OtterSec、CertiK、Hacken、Zellic、Coinspect、Halborn、Cantina 十家

需要纠正的部分

  • “审计过”不等于安全。Nomad 2022-06 刚完成 Quantstamp 审计，报告里的 QSP-19 已经预示了类似问题；两个月后被盗约 1.9 亿美元（rekt.news）
  • 审计不是执照。智能合约审计没有政府颁发的从业资格，谁都可以自称审计方。托管和钥匙管理这一块倒有一个行业标准和个人认证（CCSS 与 CCSSA，见下文），但它也不是政府执照
  • 审计只对报告里写的那个版本有效。之后改的每一行代码都不在覆盖范围内
  • 只审合约远远不够。Ronin、Harmony、Orbit、Multichain 都不是合约漏洞，是钥匙出了问题（第 03 章）
  • “Acknowledged”不是“已修复”。它表示项目方知道这个问题，但决定不改

审什么

普通 DeFi 合约审计主要看合约。跨链桥的“证明者”在链下，资产在两条链上，所以范围要大得多。下表每一层后面都标了本板块讲过它的章节。

层要看什么历史教训本板块

⑦ 前端和依赖网页被篡改、域名被劫持、用户的无限授权、第三方库Socket（攻击者利用用户给聚合器的无限授权）图鉴

还有两条链各自的特性：确认和最终性规则不同、地址规则不同、chainId 是否唯一（Qtum 的 81 与 Japan Open Chain 重复，第 01 章）。这些都会改变“签名里该绑定什么、该等多久”。

怎么审：链下和运营

合约审计读的是代码。链下系统的风险大多不在代码里，而在“谁能碰到钥匙、谁能改配置、流程有没有真的照着做”。所以审法也不一样：审计方要读云账号的权限配置、抽查操作记录、到场见证生成钥匙，还要实际去攻击服务器。

对象要回答的问题审计方怎么查项目方要拿出的证据
签名服务的代码签名前是不是自己去链上核对了事件、金额、收款人和确认数；同一笔会不会签两次；自动放行上限是不是写死在签名服务里；签出的是不是低 S 签名代码审查，和合约审计一样逐行读；再用测试网构造伪造的“已批准”记录，看它签不签源码和 commit、部署配置、测试用例
云账号和 KMS谁能调用签名（KMS 的 Sign）、谁能改钥匙策略、谁能改签名服务的代码和配置；不同链的签名钥匙是不是真在不同账号读 IAM 策略、KMS 钥匙策略、账号结构；看 CloudTrail 日志里实际调用过 Sign 的身份，和策略对得上账号清单、策略导出、近期日志
服务器和网络后端被攻破后能走多远；管理端口、内部接口是否暴露；部署流水线谁能改渗透测试：从外网、从一台被攻破的内部机器分别打网络拓扑、测试环境、部署权限清单
多签和硬件钱包冷钱包多签的持钥人是不是真的分属不同人、不同地点；有没有两把钥匙放在同一台设备上到场见证钥匙仪式（key ceremony）：看设备开箱、生成地址、记录备份去向；核对链上的签名人地址持钥人名单、仪式记录、备份存放记录
运营流程大额审批是不是每笔都有审核员签名；换钥匙、补额度、冷转热是不是照文档做的抽样：随机挑几笔大额转账、几次补额度，逐笔对审批记录和链上交易审批记录、操作日志、值班表、演练记录
对账和储备储备是不是一直 ≥ 负债；对账是谁算的，后端被攻破了它还准不准自己按链上数据重算一遍，和项目方的结果对比对账脚本、历史对账结果、看门狗告警记录
应急发现异常后多久能暂停；守护者钥匙在谁手里；恢复要谁批准桌面推演，或在测试网实际演练一次暂停和恢复应急预案、演练记录

和合约审计最大的不同：合约审一次，代码就固定了；运营审计看的是“这段时间做得怎么样”，所以要定期重做。CCSS 的“安全审计与渗透测试”一项，Level 3 要求至少每年一次外部审计或渗透测试。

谁有资格

没有执照，只有记录：怎么判断一个审计方靠不靠谱

智能合约审计没有法定的从业资格，也没有统一的认证考试。“有资格”在这个行业里的意思是：有可以公开查验的过往记录，并且这些记录和你要审的东西相关。唯一的例外是托管和钥匙管理：这一块有 CCSS 标准和配套的个人认证 CCSSA（下面单独讲），但它只管托管运营，不管合约代码。

类型是什么适合审什么
专业审计公司固定团队，签合同、约定范围和时间，交付正式报告合约主审；有些也做链下代码和基础设施
竞争性审计平台平台组织公开竞赛，项目方出奖金池，安全研究员（Code4rena 叫 Warden）提交问题，由裁判定级和定奖合约的第二道审查，补充视角
漏洞赏金平台托管长期赏金计划，按严重程度付奖金上线后的持续覆盖
形式化验证团队专门写规格、做数学证明验签、记账这类最关键、最适合写成规则的逻辑
传统信息安全公司渗透测试、密钥管理和运营流程审查；ISO 27001、SOC 2 这类认证属于这一类服务器、Validator 运行环境、密钥保管、审批流程
独立安全研究员个人，常在竞争平台上有公开排名按个人专长

托管这一块：CCSS 标准和 CCSSA 认证

托管桥的钱放在冷热钱包和云端 HSM 里，这部分要审的是“钥匙和流程”，不是代码。行业里专门管这个的是 CCSS（CryptoCurrency Security Standard，加密货币安全标准），由非营利组织 C4（CryptoCurrency Certification Consortium）维护。

项目内容（C4 官网，2026-10-30 读取）
审的对象一个具体的“系统”，不是整个公司。CCSS 不替代 ISO 27001 这类通用信息安全标准，是在它们之上补加密资产特有的要求
审什么当前版本 v9.0 共 41 项控制。旧版公开仓库分两大类：钥匙管理（钥匙/种子生成、钱包创建、钥匙存储、钥匙使用、钥匙泄露预案、持钥人的授予和撤销）和运营（安全审计与渗透测试、数据清除、储备证明、审计日志）
等级Level 1、2、3，逐级更严。例：“钥匙使用”一项，Level 2 要求签名前通过可信渠道核对收款地址和金额，自动签名的系统要按白名单和额度上限核对后再签；Level 3 要求访问钥匙需要 3 个以上认证因素、持钥人做背景调查
谁来审CCSSA（CCSS 认证审计员）。要上 2 天基础课 + 2 天审计员课，通过 100 题、90 分钟、70 分及格的考试，每年重新认证。和被审系统有雇佣、亲属、持币或持股关系的不能审
怎么审审的是控制措施在过去一段时间里有没有真的在执行，通常每年一次、覆盖之前 12 个月；出证书前还要由另一位审计员（CCSSA-PR）做独立的同行复核
谁拿过C4 公开名单里有 Kraken、OKX、KuCoin、BitGo、Fireblocks 等的托管或冷热钱包系统，等级从 Level 1 到 Level 3 不等

两点要注意：① CCSS 看的是“过去一段时间的执行记录”，一个刚上线的系统还没有记录，第一年能做的是按 CCSS 做差距评估，把流程搭对；② 公开名单里的 CCSSA 有些就在合约审计公司任职（名单里能看到 OpenZeppelin、EY 的人），所以合约审计和托管审计可以由同一家公司的不同团队做，但要分别签范围。本页提到的公司和平台名字只作为例子，不代表推荐。

怎么审：流程

一次审计从准备到上线

阶段项目方要做的审计方做的

准备阶段最值钱的一份材料：不变量清单

不变量是“无论发生什么都必须成立的规则”。项目方自己先写出来，审计方就知道该守住什么，模糊测试也有了检查目标。以托管桥为例：

不变量被打破意味着
储备（冷 + 热）= USDC.e 总供应 + 已存入未铸币 + 已销毁未放款 + 已取消待退款 + 待处理误转超发或漏记，最大的风险
每个转账 ID 最多被执行一次；已取消的 ID 永远不能再执行；已执行的 ID 不能取消重复付款，或既退款又放款
每次存入之后，网关的热余额 ≤ 热余额上限热钱包暴露的钱超出预期
任意 24 小时内，运营密钥放出的总额 ≤ 24 小时上限钥匙泄露后的损失没有上限
只有守护者能暂停，只有多签能恢复和改参数权限被绕过

工期和费用由什么决定

没有公开的统一价格。合约审计通常按“人·周”报价，审计方要先看过代码才会报。决定工作量的主要因素：

因素为什么影响工作量
代码量（不含测试和注释的行数）报价的基础；自己先统计好，写进范围
是否涉及多条链、签名、资金托管跨链要两边一起推演，验签和记账要逐个字段核对
文档和测试是否齐全文档不全，审计员要花时间猜设计意图；测试覆盖低，审计员要自己补
范围里有没有链下组件签名服务、后端和云配置要另外的人·周，有时要另一类专业团队
要不要复查、要几轮每轮修复后复查都要单独排期
托管运营审计（CCSS）按 C4 的说明，费用由审计员和项目方自己谈，还要另付同行复核和 C4 的登记费

排期也要算进上线计划：审计方要排档期，修复和复查还要再加时间。代码还没冻结就开审，审到一半代码又变了，前面的工作就白做了。

问题怎么定级

各家写法不同，但都围绕“会不会丢钱”。两个公开的定级标准：

Code4rena

三级

High：资产可以被直接偷走、丢失或被控制（或者有不靠空想假设的间接攻击路径）。Medium：资产没有直接风险，但协议功能或可用性受影响，或在有明确前提的假设路径下会泄露价值。QA：低风险问题，以及治理和中心化风险（包括管理员权限）。

Immunefi

四级

Critical、High、Medium、Low，主要按影响定。智能合约的 Critical 包括：直接盗取用户资金（无论静止还是在途）、永久冻结资金等。

② 查源码验证在 Sourcify / Etherscan 查实现合约是否“源码与字节码一致”Sourcify：实现合约 exact match（字节码和编译元数据都一致），Solidity 0.8.9、EVM 版本 london
③ 和仓库对比把验证过的源码逐个文件和某个 commit 对比18 个合约源文件和 bridge-evm-contracts 的 commit a351a067（2024-09-30）逐字节相同
④ 和报告的 commit 对比报告应写明审计的 commit；看部署的 commit 是否就是它，或只差已复查过的修复CertiK 页面没有公开报告正文，审计的 commit 无法确认。部署的 commit 比审计日期晚半年
⑤ 审计后改了什么看审计日期到部署 commit 之间的提交记录2024-05-15 新增 upgradeToWithSigAndCall；2024-09-30 新增 BridgeV2 / USDCManager（主网没有部署这两个）
⑥ 另一条链也要核对没有验证服务的链，可以和已验证的同一份实现比字节码Qtum 桥实现 0xB4f3…2810 的运行时字节码和以太坊上那份完全相同（各 19,772 字节，只有 9 处自己的部署地址不同，编译元数据哈希一致）；也含 upgradeToWithSigAndCall 的选择器 0x3f65ca94

结论：两条链上跑的是同一份代码，就是 commit a351a067；它包含审计之后才加入的升级函数，这部分代码没有被 2024-03 的审计覆盖。
