KMS 签名：原理与落地

托管桥的运营地址要全天候自动铸币、放款，它的私钥放在 AWS KMS 的 HSM 里。前半章讲原理：KMS 替签名服务做了什么、没做什么，签名服务怎么把 KMS 给的签名变成以太坊和 Qtum 都认的交易。后半章讲落地：签名前要核对什么，账本怎么保证同一笔只签一次，权限怎么锁到“只有签名程序能签、签名程序只能经两人批准才能改”，钥匙怎么换、出事怎么办。看不懂的词，先看“先看懂”一节。

一句话

KMS 签名 = 私钥锁在 AWS 的 HSM 里，签名服务把 32 字节摘要交给它，拿回 DER 签名，再自己转成链要的格式

本章以一座 ETH ↔ Qtum 托管桥为例：桥在两条链上各有一个运营地址，私钥放在 AWS KMS 里。标已核实的结论查过官方文档、规范或源码，来源在文末；标待验证的要在 AWS 测试账号、测试网或 regtest 上实测；写“本地实测”的，是在本机用 Node.js 实际跑出来的；标已实测的，是在一个 AWS 测试账号上真的调过 KMS（见动手）；写“原型阶段的本地记录”的，是写这套方案时在本机跑过的原型测试，这次没有重跑。

这座桥做什么：用户在以太坊上把 USDC 存进网关合约 EthGateway，桥在 Qtum 上给他铸出等量的 USDC.e；反过来，用户在 Qtum 上把 USDC.e 交给网关合约 MintGateway 销毁，桥在以太坊上从 EthGateway 付给他 USDC。“铸币”“放款”这两步，要有一个地址发交易去调网关，这就是运营地址，每条链一个：以太坊的只能调放款和取消提现，Qtum 的只能调铸币和取消存入，每一笔都受链上上限约束。合约函数名在本章是示意。

基础事实内容
KMS 只做一件事用 HSM 里的私钥，对签名服务给的 32 字节摘要做 secp256k1 ECDSA 签名。私钥不出 HSM
KMS 看不到交易交易怎么组、摘要怎么算、签名怎么转格式，都是签名服务自己的代码。所以签名服务必须先核对交易内容，再算摘要交给 KMS
两条链用同一种曲线都是 secp256k1，同一种 KMS 密钥规格两边都能用。按设计，每条链各用一把钥匙，放在不同的 AWS 账号里
KMS 的签名不能直接用要补三件事：从 DER 里拆出 r、s；把 s 规范成低位；以太坊另外算出 v
以太坊一笔交易签一次。摘要 = keccak256(未签名交易)，签名放成 (yParity, r, s)
QtumUTXO 模型，每个输入单独算摘要、单独签。摘要 = 双 SHA256(按规则改写过的交易)，签名编成 DER 加一个字节 0x01，和公钥一起放进输入的 scriptSig
签名服务还要做的自己解析交易、自己读源链核对；在账本里先占位再调 KMS，保证重试拿到的是同一笔；返回前自己验一遍签名
安全靠三层① KMS 保证私钥拿不走；② 签名服务保证只签该签的交易；③ 链上额度和合约按转账 ID 去重，签名服务被攻破时损失有上限，同一笔也不会执行两次

常见理解里，对的部分

  • 私钥在硬件里，服务器被攻破也拷不走；发现入侵后收回权限，攻击者就再也签不了
  • 每次签名都留一条 CloudTrail 日志，事后能查谁在什么时候签过
  • 不用人按键，能全天候自动签，适合运营地址

需要纠正的部分

  • KMS 不是“帮你签交易”。它只签 32 字节，不知道这 32 字节是哪笔交易，也不检查发给谁、多少钱
  • “私钥在 HSM 里就安全”只对一半。收回权限之前，能调用这把钥匙的人想签什么就签什么
  • KMS 返回的签名，两条链都不能直接用。格式要转，s 要规范，以太坊还要自己算 v
  • ECDSA_SHA_256 不会再算一次 SHA256。用 DIGEST 模式时 KMS 直接签签名服务给的 32 字节，所以以太坊的 keccak256 摘要也能交给它签
  • 只让一个角色有 kms:Sign 还不够。账号管理员可以改签名程序的代码，或者新建一个程序借用同一个角色，照样想签什么签什么。所以“谁能改、谁能发布签名程序”也要锁住（见权限）
  • 同一个摘要签两次，签名不一样。所以账本不能按“签好的交易哈希”去重，要按请求号、nonce 或输入去重（见账本）

Key Pair · Signature

私钥、公钥、签名

一句话：私钥是只有你知道的一个大数；公钥由私钥算出，可以公开；签名是用私钥对一段数据算出的一组数。任何人拿着公钥都能验证两件事：这段数据确实经过私钥持有人认可，而且没被改过。

是什么谁知道在托管桥里
私钥一个 256 位的随机整数只有持有人运营密钥的私钥，存在 KMS 里
公钥由私钥算出的曲线上的一个点（见 ECDSA）任何人从 KMS 取出，用来算运营地址
地址由公钥算出的 20 字节摘要（见 地址）任何人运营地址，写在网关合约里
签名用私钥对交易摘要算出的 (r, s)随交易公开每笔铸币、放款交易都带着

常见误解：“签名就是加密”，不对。签名不隐藏任何内容，交易本来就是公开的；签名证明的是谁认可了这笔交易、交易内容有没有被改过。“有了公钥就能算出私钥”，算不出来：由私钥算公钥很快，反过来在现实中算不出来，整套体系的安全就建立在这一点上。“地址就是公钥”，不是：地址是公钥的摘要，比公钥短。

和链的关系：链上没有用户名和密码。节点判断一笔交易能不能执行，只看签名能不能用发送地址的公钥验证通过。所以谁掌握运营密钥的私钥，或者能让 KMS 用这把私钥签名，谁就能以运营地址的身份发交易。

助记词、私钥、地址的关系：入门：助记词、私钥、地址是一条单向链

Hash

摘要（哈希）：两条链用的不一样

一句话：哈希函数把任意长度的数据变成固定长度的“指纹”。本章用到的 SHA256 和 keccak256，输出都是 32 字节。它有三个性质：同样的输入永远得到同样的指纹；输入改一个字节，指纹就完全不同；从指纹反推不出原数据。

为什么签摘要，不签整笔交易：ECDSA 的签名运算要求输入是一个 256 位的数。先把交易哈希成 32 字节，再签这 32 字节，效果等于签了整笔交易：交易哪怕改一个字节，摘要就变了，原来的签名就验证不过。这也是 KMS 的 Sign 只收 32 字节摘要的原因。

名字是什么谁在用"abc" 的结果（前 8 字节）
SHA256美国 NIST 标准的哈希函数比特币、Qtum；KMS 的 ECDSA_SHA_256 名字里的就是它ba7816bf8f01cfea…
双 SHA256先算一次 SHA256，再对结果再算一次比特币和 Qtum：交易 ID、签名摘要4f8b42c22dd3729b…
keccak256Keccak 算法，后来被选为 SHA3 标准的原型以太坊：地址、交易签名摘要、合约里的 keccak256()4e03657aea45a94f…
SHA3-256NIST 定稿 SHA3 时改了填充规则的版本以太坊不用3a985da74fe225b2…

常见误解：“keccak256 就是 SHA3”，不完全是。以太坊在 SHA3 定稿前就用了 Keccak；NIST 定稿时改了填充规则，所以同样的输入结果不同（上表后两行）。有的库把 keccak256 叫作 “sha3”，用错函数会算出错误的地址和摘要。“KMS 只能签 SHA256 算出的摘要”，也不是：DIGEST 模式下，KMS 不管摘要是怎么算出来的，只要求是 32 字节。keccak256 和双 SHA256 的结果都是 32 字节，都能交给它签。

和托管桥的关系：签名服务算摘要时，以太坊用 keccak256，Qtum 用双 SHA256。用错一个，签出来的交易节点就不认。

ECDSA

ECDSA：私钥签、公钥验的那套算法

一句话：ECDSA（椭圆曲线数字签名算法）是一套具体的“私钥签、公钥验”的算法。比特币、以太坊、Qtum 的交易签名都用它。

怎么工作（只讲后面用得到的部分）：椭圆曲线是满足某个方程的所有点 (x, y)。曲线上定义了一种“点加法”：两个点相加，得到曲线上的另一个点。把一个点 G 连加 d 次，记作 d×G。已知 d 算 d×G 很快；只知道 d×G，反推 d 在现实中做不到。

步骤做什么要用什么
生成钥匙随机取一个整数 d 作为私钥；公钥 Q = d×G曲线上公认的固定点 G；所有运算都对一个公开的大整数 n（曲线的阶）取余
签名取一次性随机数 k，算点 R = k×G；r = R 的横坐标；s = (摘要 + r×d) ÷ k。签名就是 (r, s)私钥 d、摘要
验证算 u₁ = 摘要 ÷ s，u₂ = r ÷ s，再算点 P = u₁×G + u₂×Q；P 的横坐标等于 r 就通过只要公钥 Q，不要私钥

表里的“÷”都是在对 n 取余的意义下算的。

后面用到的两个结论，都来自这张表：把 s 换成 n − s，u₁、u₂ 都变成相反数，P 变成它上下翻转的那个点，横坐标不变，所以照样验证通过，这就是低位 s 问题。只知道 r，横坐标等于 r 的点有两个（一上一下），所以从签名反推公钥时有两个候选，以太坊用 v 指明是哪一个（见以太坊）。

常见误解：“ECDSA 就是 secp256k1”，不是：ECDSA 是算法，secp256k1 是它用的那条曲线，同一个算法换一条曲线，就是另一套互不相通的钥匙。“同一条消息签两次，签名一样”，通常不一样：每次的 k 不同，签名也就不同，但两个签名都能验证通过。用 Node 对同一条消息签两次就能看到，两次结果不同（本地实测）；让 KMS 对同一个摘要签两次，结果也不同已实测。有一种做法（RFC 6979）用私钥和摘要算出 k，同样的输入签名就固定，但 KMS 的文档没有承诺它用哪种。所以设计不能依赖“签名固定”：同一笔交易重签一次，交易哈希就可能变，账本要按 nonce 或输入去重（见账本）。

k 必须保密，而且每次都不同：用同一个 k 签过两条不同的消息，别人就能直接算出私钥。2010 年索尼 PS3 的签名私钥就是这样泄露的。HSM 在内部生成 k，外面碰不到，这也是签名交给 HSM、不自己写代码实现的原因之一。

合约怎么从签名算出签名者地址（ecrecover）：第 03 章：一份签名是怎么被验证的

secp256k1

secp256k1：用的是哪条曲线

一句话：secp256k1 是一条具体的椭圆曲线，也就是上面 ECDSA 表里“曲线、G、n”这一整套公开参数。比特币选了它，以太坊和 Qtum 沿用。曲线方程是 y² = x³ + 7，所有坐标都对一个 256 位的素数取余。名字的意思：sec（SECG 组织发布的标准 SEC 2）、p（定义在素数域上）、256（256 位）、k（Koblitz 型曲线）、1（这一类里的第 1 条）。

曲线的阶 n = FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFE BAAEDCE6 AF48A03B BFD25E8C D0364141。下一张卡片的“低位 s”就是拿 s 和 n 的一半比。

常见误解：“secp256k1 是一种加密算法”，不是，它只是一组曲线参数，算法是 ECDSA。“P-256 也是 256 位，差不多”，完全不同：P-256（又叫 secp256r1）是 NIST 标准曲线，网站证书、手机安全芯片常用。同一个私钥在两条曲线上算出的公钥不同，签名互不认。

和托管桥的关系：KMS 建钥匙时必须选 ECC_SECG_P256K1。选成 ECC_NIST_P256，钥匙照样建得出、签名照样签得出，从公钥也能算出一个看起来正常的地址，但两条链都验证不过这把钥匙的签名，打到那个地址的钱永远花不出来。

Low-s

把 s 规范成低位

一句话：同一笔交易、同一把私钥，有两个都能验证通过的签名：(r, s) 和 (r, n − s)（原因见 ECDSA）。规定只用 s 较小的那个，也就是 s ≤ n/2；签出来的 s 比 n/2 大，就换成 n − s。这就叫“把 s 规范成低位”。

一个真实的例子（Node 的 secp256k1 对 "abc" 签名）值（十六进制，32 字节）
n/27fffffff…681b20a0
签出来的 sc9644549…a552e842：开头 c9 比 7f 大，是高位
n − s369bbab6…2ae358ff：开头 36 比 7f 小，是低位
验证结果原签名通过；换成 n − s 后也通过

比大小先看开头：大于 7f 的一定是高位，小于 7f 的一定是低位，正好是 7f 才需要往后比。

为什么链只认低位：两个签名都有效，会带来“交易延展性”问题。交易 ID 是对整笔交易（包括签名）算的哈希。任何人拿到一笔还没上链的交易，不用私钥，就能把 s 换成 n − s，造出一笔内容一样、交易 ID 不同的交易抢先广播。执行器按交易 ID 跟踪自己发出的交易，就会以为原来那笔没上链。所以两条链都只认低位 s：以太坊是协议规则（EIP-2），高位 s 的交易无效；Qtum 是节点的标准策略（继承自比特币），高位 s 的交易不进内存池。

签名服务怎么做：KMS 签出来的 s 大约一半是高位。签名服务拿到后比一下：s > n/2 就换成 n − s。这只是一次减法，不需要私钥，也不用再调 KMS。以太坊要注意，s 换了以后 v 也跟着变，所以先规范 s，再试 v（见以太坊）。

DER

DER：KMS 交付签名和公钥的格式

一句话：DER 是一种把结构化数据写成字节的标准编码规则，属于 ASN.1 标准。KMS 用它交付两样东西：签名和公钥。签名就是两个整数 r 和 s，公钥是曲线上的一个点，要在程序之间传，得约定怎么排成字节。DER 的办法是：每一项都写成“类型、长度、内容”三段。

字节（上一张卡片里高位 s 的那个签名，共 71 字节）意思
30类型：SEQUENCE，一个结构，里面装着 r 和 s
45长度：后面还有 0x45 = 69 字节
02 20类型 INTEGER，长度 0x20 = 32 字节：下面是 r
65bf6cee…957afar 的 32 字节

00 c9644549…a552e842s：前面补了一个 00，后面才是 32 字节

为什么有时 33 字节、有时 31 字节：DER 的整数带正负号，最高位是 1 表示负数。r、s 都是正数，所以最高字节大于等于 0x80 时，前面要补一个 00（上例的 s 开头是 c9，就补了 00）。反过来，DER 要求用最短的写法，多余的前导 00 要省掉，所以有时只有 31 字节。

两条链怎么用：以太坊不用 DER，交易里的 r、s 是两个整数，所以要从 DER 里拆出来、去掉补的 00（见签名格式）。Qtum 用 DER，沿用比特币，输入里放严格 DER 编码（BIP66）的签名，再加 1 字节 0x01。s 规范后变了，所以要重新编：上例换成 n − s 后，s 开头是 36，不用补 00，整个签名从 71 字节变成 70 字节。

公钥也是 DER：GetPublicKey 返回的 SPKI 是 88 字节的 DER 结构。前 23 字节 3056301006072a8648ce3d020106052b8104000a034200 是固定的头，里面写着“椭圆曲线公钥”（2a8648ce3d0201）和“曲线是 secp256k1”（2b8104000a）；后 65 字节才是公钥本身（见地址）。

HSM

HSM：保管私钥的专用硬件

一句话：HSM（硬件安全模块）是专门保管密钥、在内部完成签名运算的硬件。私钥在里面生成、在里面使用，不以明文离开设备；外面只能把摘要送进去，拿回签名。

和普通服务器的区别：通常有防拆机制，强行打开会清掉里面的密钥；接口只提供签名这类运算，没有“导出私钥”；要通过 FIPS 140 这类安全认证。AWS KMS 用的 HSM 通过了 FIPS 140-3 第 3 级认证已核实。

常见误解：“私钥在 HSM 里，服务器被攻破也没关系”。对的一半：私钥拷不走，发现入侵后收回权限（禁用钥匙或换掉执行角色），攻击者就再也签不了；私钥文件一旦被拷走，就永远能用。错的一半：收回权限之前，能调用这把钥匙的人想签什么就签什么，HSM 不知道它签的 32 字节是哪笔交易，也不会检查。

所以在 KMS 之外，还要让签名服务自己核对每笔交易，并在链上设额度上限。

AWS KMS

KMS：AWS 提供的、建在 HSM 上的服务

一句话：AWS KMS 是一项云服务。钥匙在 AWS 的 HSM 里生成和保管，使用者碰不到私钥，只能通过 API 让它签名。

在 HSM 之上，KMS 多提供了这些：API，GetPublicKey 取公钥，Sign 签名；权限，谁能调用哪把钥匙，由 IAM 和钥匙策略决定（见权限）；日志，每次调用都记在 CloudTrail 里；禁用和删除，钥匙可以随时禁用，删除前有一段等待期。

常见误解：“KMS 就是 HSM”，不是：HSM 是硬件，KMS 是建在 HSM 上的服务，负责权限、日志和管理。“KMS 会检查签的是什么”，不会，见上面的 HSM 卡片。

KMS 和 CloudHSM：AWS 还有一项 CloudHSM，给你一组专用的 HSM，但集群、备份、用户都要自己管。KMS 是全托管的，用起来简单得多。本章的例子用 KMS；KMS 签不出可用的 Qtum 交易时，CloudHSM 可以作为备选。

Transaction

交易、节点、区块、确认

一句话：交易是一条带签名的指令，例如转账或调用合约。签好后发给节点，节点检查签名和规则，先放进内存池；出块的人把内存池里的交易打包进区块，交易就上链了。

词意思
节点运行区块链软件的电脑：保存整条链，检查、转发交易
广播把签好的交易发给节点，节点再转给其他节点
内存池节点里“收到了、还没上链”的交易
区块打包在一起的一批交易，按顺序首尾相连成链。以太坊约 12 秒一个区块
确认数交易所在区块之后又接了几个区块。越多，越不可能被推翻
重组链偶尔会分叉，最后较短的那一支被丢掉，里面的交易要重新排队，甚至消失。确认数越多，越不怕重组
RPC程序和节点通信的接口：查数据、发交易都通过它
主网、测试网、regtest主网上的币有真实价值；测试网（Sepolia、Qtum Testnet）的币免费领、没有价值；regtest 是在自己电脑上起的私有链，什么时候出块自己说了算

最终确定：确认数只是“越来越难推翻”，以太坊另有一个硬标准。权益证明下每 12 秒一个 slot，32 个 slot 一个 epoch；区块要跨过两个 epoch（按 2 × 32 × 12 秒算约 12.8 分钟，ethereum.org 写“约 15 分钟”）才被最终确定（finalized），之后不会再被重组。RPC 可以直接用 finalized 这个标签查到最新的最终确定区块已核实。Qtum 没有最终确定，只能看确认数；主网目标出块间隔 32 秒已核实。签名服务核对源链时，以太坊以 finalized 为准，Qtum 以配置的确认数为准（见签名前的核对）。

两类规则：共识规则所有节点都必须遵守，违反了，交易或区块就是无效的，永远上不了链，以太坊的低位 s 属于这类。转发策略（也叫标准策略）是节点自己的默认规则，不符合的交易，节点不收进内存池、也不转发，但不算违反共识，Qtum 的低位 s 属于这类。对签名服务来说效果一样：不符合就发不出去。

EIP、BIP：分别是以太坊和比特币的改进提案，是规范文件的编号。本章提到的 EIP-1559、EIP-2、EIP-55、BIP66 都是。Qtum 沿用了比特币的很多 BIP。

Account · Nonce · Gas

以太坊：账户、nonce、gas

一句话：以太坊像银行账户，链上直接记着每个地址有多少钱。一笔交易就是“从这个地址扣手续费，再改某个合约的状态”。

两种账户：普通地址由私钥控制，能发交易；合约地址由代码控制，自己不能发起交易，只能被调用。合约代码在 EVM（以太坊虚拟机）里执行，用 Solidity 语言写。Qtum 内置了兼容 EVM 的虚拟机（见下面Qtum 怎么调用合约）。

nonce：每个地址发出的交易按 0、1、2…编号，每笔必须用下一个号。作用有两个：同一笔交易不能被重复执行；用同一个 nonce 再发一笔手续费更高的交易，可以替换掉还没上链的那一笔（加价重发）。

gas：执行交易要消耗计算量，用 gas 计。gasLimit 是这笔交易最多能用多少 gas，按实际用掉的收费；超过上限，交易失败，已经用掉的 gas 照样收费。手续费（EIP-1559）：每个区块有一个随拥堵自动涨落的基础费，这部分被销毁；另外给出块者一笔小费。交易里写两个上限：maxPriorityFeePerGas（每单位 gas 最多给多少小费）和 maxFeePerGas（每单位 gas 总共最多付多少）。实际每单位 gas 付“基础费 ＋ 小费”，不超过总上限。单位：1 ETH ＝ 10¹⁸ wei；gas 价格常用 gwei，1 gwei ＝ 10⁹ wei。

交易池和加价替换：一个地址的交易按 nonce 顺序上链。nonce 7 那笔手续费太低卡住了，8、9、10 全部堵在后面。解决办法是用同一个 nonce 7 签一笔手续费更高的交易，替换池里那笔。节点不是“高一点就换”：go-ethereum 默认要求新交易的两个上限（maxFeePerGas 和小费 maxPriorityFeePerGas）都严格高于旧交易，而且都不低于旧值的 110%已核实。只涨一项会被拒。

常见误解：“卡住了就给自己转 0 ETH，把 nonce 顶掉”。普通钱包可以这么做，托管桥不行：签名服务只签网关的两个函数，不签任何别的交易，这是有意的限制，否则“顶 nonce”就成了一个能签任意交易的口子。卡住了只能用同一笔调用加价重发（见以太坊的动画）。

和托管桥的关系：运营地址要预先存一些 ETH 付手续费。nonce 必须连续，所以同一时刻只能有一个执行器给运营地址分配 nonce，否则会撞号。

EIP-1559 · ABI · RLP

以太坊交易的字段、调用数据、RLP

字段意思放款交易里填什么
chainId哪条链：主网 1，Sepolia 11155111对应的链
nonce运营地址的第几笔交易下一个号
maxPriorityFeePerGas、maxFeePerGas手续费的两个上限按当时的行情
gasLimit最多用多少 gas按预估再留余量

交易里没有“发送方”字段。节点从签名恢复出公钥，再算出地址，那就是发送方（见以太坊）。

调用数据：前 4 字节是函数选择器，等于 keccak256("函数名(参数类型,…)") 的前 4 字节；后面每个参数按规则补齐到 32 字节，依次排开。这套规则叫 ABI 编码。例如 ERC20 的 transfer(address,uint256)，keccak256 的前 4 字节是 a9059cbb，调用 USDC 的 transfer 时，调用数据都以它开头。release 的参数还没定稿，选择器等合约定稿后按同样的方法算。

常见误解：“放款交易就是运营地址给用户转 USDC”。不是。运营地址发的交易调用的是 EthGateway 的 release，value 为 0；USDC 是 EthGateway 合约执行时从自己的余额里转给用户的。运营地址自己不持有 USDC，只付 ETH 手续费。

RLP：以太坊把交易字段排成字节的格式，和 DER 一样是“长度 ＋ 内容”的思路。整数按最短的大端字节写，不带前导 00。签名摘要 ＝ keccak256(0x02 ‖ RLP(未签名的 9 个字段))，开头的 0x02 表示这是 EIP-1559 交易。

msg.sender：合约里“直接调用我的是谁”。EthGateway 的 release 只允许 msg.sender 是运营地址。运营地址签名发出的交易，msg.sender 就是运营地址。

UTXO

Qtum：UTXO、找零、手续费

一句话：Qtum 和比特币一样，不记“每个地址有多少钱”，而是记一张张“还没花掉的钞票”，叫 UTXO（未花费的交易输出）。

词意思
输出交易产生的一张“钞票”：一个金额，加一段锁定脚本，规定谁能花
输入交易要花的钞票，写成“交易 ID ＋ 第几个输出”，再附上证明有权花它的签名（scriptSig）
UTXO还没被任何交易花掉的输出。一个地址的余额 ＝ 锁给它的所有 UTXO 的金额之和
找零钞票只能整张花。要付 3、手上是一张 5，就得再给自己开一个 2 的输出
手续费交易里没有手续费字段：手续费 ＝ 输入总额 − 输出总额，归出块者
单位1 QTUM ＝ 10⁸ 个最小单位，沿用比特币的叫法，叫“聪”（sat）
费率手续费按交易的字节数算，单位是“聪每字节”。Qtum 节点默认的最低转发费率是 400 聪每字节；替换一笔交易时，新交易每字节至少再多付 10 聪已核实

常见误解：“忘了写找零，多的钱会退回来”，不会，差额全部算手续费，被出块者拿走。“UTXO 链也有 nonce”，没有：一个输出只能被花一次，这就防住了重复花费，两笔交易花同一个输出，只有一笔能上链。加价重发就是靠这一点（见 Qtum）。“交易里写着每个输入多少钱”，没有：输入只写“交易 ID ＋ 第几个输出”，金额记在被引用的那笔交易里。签名服务要拿到这些前序交易，才知道每个输入多少钱（见签名前的核对的动画）。

字节顺序的坑：区块浏览器上显示的交易 ID，和交易内部引用它时存的字节顺序正好相反；金额、输出序号等字段在交易内部是小端（低位在前）。组交易时要按内部的顺序写。

和托管桥的关系：运营地址的 QTUM 是一堆 UTXO。执行器要记住哪些 UTXO 可用、哪些已经被还没上链的交易占用，不能让两笔交易抢同一个 UTXO。

Script · P2PKH · sighash

Qtum：脚本、P2PKH、sighash

一句话：每个输出带一段锁定脚本，规定花它要满足什么条件；花的人在输入里提供解锁脚本（scriptSig）。节点把两段拼起来执行，结果为“真”才允许花。脚本是一串操作，从左到右执行，用一个“栈”（一摞数据，只能从顶上放、从顶上拿）存中间结果。<数据> 表示把这段数据放到栈顶；OP_ 开头的是操作码。

P2PKH（付给公钥哈希，最常见的地址类型，运营地址就是这种）：锁定脚本 OP_DUP OP_HASH160 <hash160> OP_EQUALVERIFY OP_CHECKSIG；解锁脚本 <签名> <压缩公钥>。

步骤执行栈（右边是栈顶）
1放入签名、公钥签名 公钥
2OP_DUP：复制栈顶签名 公钥 公钥
3OP_HASH160：栈顶换成它的 hash160签名 公钥 hash160(公钥)
4放入锁定脚本里的 <hash160>签名 公钥 hash160(公钥) hash160
5OP_EQUALVERIFY：比较栈顶两项，不相等就失败签名 公钥
6OP_CHECKSIG：用公钥验证签名，对就留下“真”真

第 3–5 步证明“这个公钥就是地址对应的那个”，第 6 步证明“签名的人有这个公钥的私钥”。一步一步看栈怎么变：第 08 章的 P2PKH 动画。

sighash：签名签的是什么。签名要覆盖整笔交易，可签名本身又要放进交易的输入里，自己签不了自己。所以签之前先改写一份交易：① 正在签的输入，scriptSig 临时换成它要花的那个输出的锁定脚本，其他输入的 scriptSig 清空；② 末尾加 4 字节的 sighash 类型；③ 做双 SHA256，得到 32 字节摘要，这就是要签的东西。验证时，节点按同样的规则重新算出这个摘要，再验签名。

托管桥用的类型是 SIGHASH_ALL（值为 1）：签名覆盖全部输入和输出，签完后谁改了任何一个输出，签名就失效。签名末尾那 1 字节 0x01，就是在声明用的是这个类型。

常见误解：“一笔交易签一次就行”。不是。每个输入的摘要里，换进锁定脚本的位置不同，摘要也就不同，所以每个输入都要单独算摘要、单独签（见 Qtum 的动画）。

OP_CALL

Qtum：怎么调用合约

一句话：Qtum 在 UTXO 账本上加了一个兼容以太坊的合约虚拟机。调用合约，就是在交易里放一个特殊的输出，写明调哪个合约、传什么数据、给多少 gas。合约调用输出的脚本：OP_4 <gasLimit> <gasPrice> <调用数据> <合约地址> OP_CALL。

部分意思
OP_4虚拟机版本。节点要求版本字段里的 rootVM 是 1、其余为 0，OP_4 就是这个值；开源库 qtum-ethers-wrapper 也固定写 4
gasLimit最多用多少 gas。按脚本整数写：小端、最短、最多 8 字节、不能是负数。例如 250000 写成 3 字节 90d003
gasPrice每单位 gas 付多少，单位是聪（sat）。例如 40 写成 1 字节 28
调用数据和以太坊一样的 ABI 编码
合约地址20 字节
OP_CALL表示“调用已有合约”；部署新合约用 OP_CREATE，不带合约地址

几个下限（链上实际值由治理合约 DGP 决定，下面是默认值）：最低 gasPrice 40 聪；进内存池的 gasLimit 至少 22000；所有合约输出的 gasLimit × gasPrice 加起来不能超过手续费，否则节点报 bad-txns-fee-notenough已核实。

调用者是谁：Qtum 交易里没有“发送方”字段。没有用 OP_SENDER 时，合约看到的 msg.sender 是第一个输入所花那个输出的地址（20 字节 hash160）；那个输出必须是 P2PKH 或 P2PK，否则节点报 bad-txns-invalid-sender-script，不收进内存池已核实。

gas 怎么预付、怎么退：gasLimit × gasPrice 算在手续费里预付（手续费 ＝ 输入总额 − 输出总额）。执行成功时，用剩的 (gasLimit − 实际用量) × gasPrice 作为一个付给“第一个输入的地址”的输出，加进出块的那笔交易（权益证明区块是 coinstake）里；执行出异常的（主动 REVERT 除外），gas 全部扣光、不退。出块交易的输出要等成熟才能花：主网第 845000 块以后是 2000 个区块，按 32 秒一块约 17.8 小时（按目标间隔算，不是实测）；提前花报 bad-txns-premature-spend-of-coinbase已核实。

和托管桥的关系：所有输入都用运营地址的 UTXO，调用者和退回的 gas 就都落在运营地址。gasLimit 定得越贴近实际用量，被锁 17.8 小时的钱越少；算可用余额时，还没成熟的退款不能算进去。

EIP-712

审核员签名：EIP-712

一句话：EIP-712 是以太坊的“结构化数据签名”标准。钱包按字段把要签的内容显示出来（转账 ID、收款人、金额……），而不是一串看不懂的十六进制。签的是 keccak256(0x19 ‖ 0x01 ‖ domainSeparator ‖ hashStruct(消息))已核实。

domain：写明这个签名属于哪个应用、哪个版本、哪条链（name、version、chainId）。同样的内容拿到别的应用或别的链上，摘要就变了，签名作废。

一个容易踩的坑：MetaMask 要求 domain 里写了 chainId 的，必须等于钱包当前连接的链，否则直接报错、不让签已核实。审核员审 Qtum 铸币时不想来回切网络，做法是 domain 的 chainId 固定写以太坊主网 1，真正的目标链写进消息里的一个字段，例如 targetChainId。Qtum 在 EVM 里的链 ID：主网 81，测试网 8889，regtest 8890；测试网和 regtest 在 Shanghai 升级高度之前也返回 81已核实。

怎么验证：从签名和摘要恢复出签名者地址，和审核员名单比。消息里任何一个字段不同，摘要就不同，恢复出的是一个无关的地址，所以不用逐字段比，地址对不上就拒（见签名前的核对）。

常见误解：“硬件钱包一定会逐字段显示”。不一定：有的钱包和固件组合只显示 domain 和消息的两个哈希，审核员看不到金额和收款人，等于盲签。以 Ledger 为例：以太坊应用从 1.10.0 起支持完整的 EIP-712，在设备上算哈希、逐字段显示；老的 v0 模式只收 domain 和消息两个哈希，屏幕上只能看哈希已核实。钱包软件走哪种模式、要不要开盲签，各家不一样，所以上线前要用实际的硬件钱包加钱包软件签一次，看屏幕上是不是逐字段显示待验证。

AWS 和工程 ORG · SCP · IAM · LAMBDA · DYNAMODB · CLOUDTRAIL

后半章（核对、账本、权限、运维）用到的 AWS 服务和工程概念。和 AWS 有关的说法按官方文档核实，来源在文末。

Organizations · SCP

账号、组织、SCP

一句话：账号是 AWS 里资源和权限的边界，不同账号默认互相看不到。AWS Organizations 把多个账号归进一个组织，由管理账号统一管理；SCP（服务控制策略）是组织给成员账号设的权限上限。

SCP 只能拒绝，不能授予：它划定“这个账号里最多能做什么”。IAM 策略允许、SCP 拒绝的操作，照样做不了。作用范围：成员账号里的所有用户和角色，包括成员账号的 root；不作用于管理账号；不作用于服务关联角色（AWS 服务自己用的角色）已核实。条件里可以用 aws:PrincipalArn 区分调用者，一条 SCP 就能写成“除了某个角色，谁都不许做”。

组织级 CloudTrail：在管理账号里建，成员账号看得到，但改不了、删不掉已核实。签名账号的管理员想掩盖自己做过的事，删不掉这份日志。

常见误解：“账号管理员什么都能做”。被 SCP 拒绝的操作，成员账号的管理员和 root 都做不了。反过来，管理账号不受 SCP 约束，谁控制管理账号，谁就能改 SCP。所以管理账号不跑任何业务，root 绑硬件 MFA，日常不用（见权限）。

IAM · Key Policy · Grant

IAM：角色、策略、钥匙策略、grant

词意思
IAM 角色一种身份，程序“扮演”它来调用 AWS，用临时凭证，没有长期密码
策略一段 JSON 规则：允许或拒绝哪些操作（Action）、对哪些资源（Resource）、在什么条件下（Condition）
ARNAWS 资源的唯一名字，例如 arn:aws:kms:区域:账号:key/钥匙ID
信任策略挂在角色上，写明谁可以扮演这个角色
AssumeRole一个身份临时扮演另一个角色，常用于跨账号调用
钥匙策略挂在 KMS 钥匙本身上的策略，每把钥匙有且只有一份
grantKMS 的另一种授权方式：不改钥匙策略，也能把某些操作授权给别的身份

判定规则：默认拒绝；只要有一条明确的拒绝，任何允许都无效；SCP、IAM 策略、钥匙策略都允许才行。

KMS 特别之处 ①：钥匙策略说了算已核实。AWS 默认的钥匙策略里有一条“允许本账号 root 使用 kms:*”，它的作用是让 IAM 策略能给这把钥匙授权。钥匙策略里没有这一条，IAM 策略写的允许对这把钥匙无效（IAM 的拒绝仍然有效）。

② 防锁死检查已核实。CreateKey、PutKeyPolicy 会检查新策略是否还允许调用者以后再改策略，不允许就报错，除非显式设 BypassPolicyLockoutSafetyCheck（默认不设）。能管这把钥匙的唯一身份被删掉，就只能找 AWS Support。

③ grant 能绕开钥匙策略已核实。有 kms:CreateGrant 的人可以把 Sign 授给别人，自己都不需要有 Sign 权限。grant 不改钥匙策略，只看钥匙策略发现不了；生效有几秒到约 5 分钟的延迟。条件键 kms:GrantOperations 能限制授出哪些操作，最省事的是在 SCP 里直接禁止 CreateGrant。

条件键：kms:SigningAlgorithm、kms:MessageType 限定签名方式，只作用于 Sign 和 Verify；aws:sourceVpce 限定请求必须经过某个 VPC 端点，凭证被偷到 VPC 外面也签不了已核实。

Lambda · VPC

Lambda 和网络

一句话：Lambda 是 AWS 的托管运行环境：有请求来就运行一段代码，不用自己管服务器。本章的签名服务跑在 Lambda 上。

项内容
超时默认 3 秒，最长 900 秒已核实。签名服务要读两家 RPC、再调 KMS，默认值不够，必须改
预留并发既是上限也是下限：同时最多跑这么多个实例，也保证至少有这么多可用，不另收费已核实。设得小，被滥用时签名的速度也被限住
版本和别名发布出的版本代码不能再改；别名指向某个版本，调用方只调别名。回滚就是把别名指回上一个版本
VPC放进 VPC 才能访问私有子网里的节点。放进 VPC 的 Lambda 没有公网地址，放在公有子网里也上不了网，要经过 NAT 网关已核实
VPC 端点不经过公网访问 AWS 服务。接口型（KMS、Secrets Manager 等）按小时和流量收费；网关型（S3、DynamoDB）不收费已核实

常见误解：“Lambda 只会执行一次”。同步调用出错时 Lambda 自己不重试，由调用方决定；而调用方用的 AWS SDK 默认就会重试超时、限流、5xx 这类瞬时错误已核实。Lambda 的文档还提醒，出错的那一次，函数代码可能已经跑完、跑了一半或根本没跑。所以同一个签名请求可能到达两次，签名服务必须幂等（见幂等、账本）。重试几次看 SDK 的设置：AWS 的 SDK 参考文档写的是 standard 模式最多 3 次（1 次 ＋ 2 次重试，DynamoDB 客户端 4 次），但这一页描述的是 2026 年的新重试行为，要设 AWS_NEW_RETRIES_2026=true 才启用；不设时用旧行为，默认值不同，页面没有列出。具体次数以所用 SDK 版本的文档为准，结论都一样：请求会重复到达。

DynamoDB

DynamoDB：条件写入和事务

一句话：DynamoDB 是 AWS 的托管键值数据库，签名服务的账本放在这里。“只签一次”靠它的两样东西。

条件写入：写入时附带条件，例如“这条记录还不存在”“版本号还是 3”，条件不成立整次写入失败。两个并发请求抢同一条记录，只有一个能写成功，另一个收到失败，重新读取后再决定。

事务 TransactWriteItems：一次最多 100 个操作、总共不超过 4 MB，要么全成功，要么全失败；同一个事务里不能对同一条记录做两个操作。可以带 ClientRequestToken：第一次请求完成后 10 分钟内，用同一个 token 重复提交不会再执行；token 相同、参数不同报 IdempotentParameterMismatchException已核实。

限制和保护：单条记录最大 400 KB（属性名也算）；时间点恢复（PITR）能恢复到最近 1–35 天内的任意时刻，默认保留 35 天，恢复出来总是一张新表；新表默认不开 PITR，删除保护也默认关闭，都要手动打开；表可以挂资源策略，授权别的账号读已核实。

常见误解：“ContinuousBackupsStatus 是 ENABLED，就是开了时间点恢复”。不是。这个字段总显示 ENABLED，要看 PointInTimeRecoveryStatus，没开时是 DISABLED已核实。

CloudTrail · EventBridge · CDK

CloudTrail、EventBridge、Secrets Manager、CDK

CloudTrail 记录每一次 AWS API 调用。一条 Sign 记录里，请求参数只有 keyId、signingAlgorithm、messageType，返回内容为空；它是只读的管理事件（readOnly: true）已核实。被签的摘要不在日志里：文档没有专门这样写，但官方示例里没有，加密操作的返回内容按通则也不记。所以“签了什么”只能靠签名服务自己的账本，CloudTrail 用来核对次数和时间。

trail 可以整体排除 KMS 事件（只能全排，不能挑），排除期间的事件事后补不回来已核实。记签名账号的 trail 不能这样设。

EventBridge 按规则匹配事件、触发动作（例如告警）。要收到 CloudTrail 事件，账号里必须有开着的 trail。坑在这里：只读的管理事件（例如 Sign）只有规则状态设成 ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS 才匹配得到，默认的 ENABLED 永远不会触发已核实。“有别的身份在调 Sign”这条告警，状态写错了就是摆设。

Secrets Manager 存 RPC 凭证这类机密，程序运行时读取，不写进代码和配置。CDK 用 TypeScript 代码描述 AWS 资源，部署时生成 CloudFormation 模板，由 CloudFormation 去建；每个账号先做一次“引导”（bootstrap），建出部署要用的几个角色。

常见误解：“CDK 建 KMS 钥匙不写 policy 最省事”。不写时，CDK 生成的默认钥匙策略给本账号 root kms:*，等于允许 IAM 策略给这把钥匙授权，正是上面 ① 要避免的。写了 policy 就不再加默认语句，每一条都要自己写已核实 CDK 源码。还有一个从源码推出来的坑：自己写的策略里没有 root 那条时，key.grantSign(角色) 只把权限写进角色的 IAM 策略、不动钥匙策略，而 KMS 不认这份 IAM 授权，运行时 Sign 报 AccessDenied。所以钥匙权限全部在钥匙策略里显式写，不用 grant* 方法，部署前用 cdk synth 看一眼生成的策略待验证。

Idempotency

幂等、重试、乐观锁

幂等：同一个请求做一次和做多次，结果一样。网络超时、SDK 重试、执行器重启，都会让同一个请求到达不止一次。做法是每个请求带一个唯一的请求号（requestId），重试时不变；服务端先按它查，处理过就把上次的结果原样返回。

乐观锁：不加锁，每条记录带版本号，写入时附带条件“版本号还是我读到的那个”。两个请求同时改，先写的成功，后写的失败，重新读了再改。冲突少的场景比加锁简单，也不会因为持锁的程序崩了而卡住。

常见误解：“签名服务做到幂等，就不会重复付款”。托管桥里防重复付款的第一道是合约：网关按转账 ID 去重，同一个 ID 执行过就不能再执行，取消过就不能执行。签名服务的幂等是第二层，保证额度只算一次、nonce 不乱、重试拿到同一笔交易（见账本）。

KMS 提供什么

两个 API：GetPublicKey 取公钥，Sign 签 32 字节

先看懂：密码学和 KMS 那一组卡片。

“ECDSA_SHA_256 会不会再算一次 SHA256？”

不会。MessageType=DIGEST 时 KMS 跳过哈希，直接签你给的 32 字节。算法名里的 SHA_256 只决定摘要必须是 32 字节。所以以太坊的 keccak256 摘要（也是 32 字节）可以直接交给它签。AWS 官方以太坊示例就是这样做的。在测试账号上让 KMS 签一个 32 字节摘要，再用 openssl 按同一个摘要验证，通过：KMS 签的就是给它的 32 字节已实测。

“KMS 帮你签交易？”

不是。KMS 只签 32 字节，它不知道这 32 字节是哪笔交易的摘要，也不会检查交易发给谁、多少钱。能不能签，由签名服务判断。

“钥匙不用了，删掉最干净？”

区块链钥匙删了的后果比一般的加密钥匙重：钥匙一删，这个地址就再也签不出交易，余额和以后误打进来的钱都永远拿不回来。所以运营钥匙退役时只禁用、不删除，每把每月 1 美元留着；要防误删，就在 SCP 里禁止 ScheduleKeyDeletion（见权限）。应急时也用禁用：随即生效，查清楚了还能恢复。

代码里怎么调 KMS

签名逻辑只依赖一个很小的接口：取公钥（返回和 GetPublicKey 一样的 DER 格式 SPKI），对 32 字节摘要签名（返回 DER 签名，不保证 s 是低位）。生产环境用 KMS 实现，开发和测试用一把本地私钥实现，两边输出格式一样，上层的核对、转换代码一行不改。KMS 那一份要注意：

  • 钥匙写完整的 ARN，不写别名：别名能被改指到另一把钥匙。
  • 取公钥时顺便核对规格：GetPublicKey 的返回里有 KeySpec 和 KeyUsage已核实，不是 ECC_SECG_P256K1、SIGN_VERIFY 就当钥匙不对处理。公钥取一次缓存起来。
  • 签名的参数固定：MessageType 写 DIGEST、SigningAlgorithm 写 ECDSA_SHA_256；摘要不是 32 字节就不调。
  • 报错分两类：DisabledException、KMSInvalidStateException（钥匙被禁用或待删除）按严重处理、拒签；限流和内部错误让执行器稍后重试。
  • KMS 客户端放在模块顶层，冷启动时建一次，后面的调用复用。
  • 本地那一份故意用随机 k、不规范 s 签名，和 KMS 的输出一样“不友好”，测试才测得到高位 s 和短 r、s 的情况（见签名格式的统计）。

第一次让 KMS 签名

用日常身份登录，打开 Key Management Service，在右上角选一个区域（例如新加坡 ap-southeast-1）。钥匙建在哪个区域，就只能在那个区域用。点顶部工具栏上终端样子的图标（>_）打开 CloudShell：它在当前区域启动，自带 AWS CLI v2，直接用控制台的登录身份，本机不用放访问密钥已核实。然后分段运行：

# ① 建一把 secp256k1 签名钥匙，记下打印出来的 KeyId
KEY=$(aws kms create-key --key-spec ECC_SECG_P256K1 --key-usage SIGN_VERIFY \
  --description "kms test key" --query KeyMetadata.KeyId --output text)
echo $KEY

# ② 取公钥（返回的是 Base64，解码成 DER），看曲线
aws kms get-public-key --key-id $KEY --query PublicKey --output text | base64 -d > pub.der
openssl pkey -pubin -inform DER -in pub.der -noout -text | tail -1

# ③ 对同一个 32 字节摘要签两次（DIGEST：KMS 不再哈希）
printf 'abc' | openssl dgst -sha256 -binary > digest.bin
for i in 1 2; do
  aws kms sign --key-id $KEY --message fileb://digest.bin --message-type DIGEST \
    --signing-algorithm ECDSA_SHA_256 --query Signature --output text | base64 -d > sig$i.der
done
cmp -s sig1.der sig2.der && echo "两次签名相同" || echo "两次签名不同"

# ④ 不经过 KMS，用 openssl 和公钥自己验证
openssl pkeyutl -verify -pubin -inkey pub.der -keyform DER -in digest.bin -sigfile sig1.der

# ⑤ 看签名里的 r 和 s
openssl asn1parse -inform DER -in sig1.der

地址

GetPublicKey 返回的 SPKI 是 88 字节：前 23 字节是固定头（写明“椭圆曲线公钥、secp256k1”），后 65 字节是非压缩公钥 04 ‖ X(32) ‖ Y(32)。两条链都从这 65 字节出发。先认四个词：

Compressed Key

压缩公钥

公钥是曲线上的点 (X, Y)。同一个 X 只对应两个 Y，一个奇一个偶，所以记下 X 和 Y 的奇偶就够了：Y 是偶数写 02 ‖ X，奇数写 03 ‖ X，共 33 字节。非压缩公钥是 04 ‖ X ‖ Y，65 字节。

hash160

hash160

先 SHA256，再 RIPEMD160（另一种哈希，输出 20 字节）。比特币和 Qtum 用它把公钥缩成 20 字节。

Base58Check

Base58Check

把“版本字节 ‖ hash160”写成人能抄的字符串。末尾加 4 字节校验和（双 SHA256 的前 4 字节），抄错一个字符，校验就不通过，钱包会拒绝。所用的 58 个字符去掉了容易看错的 0、O、I、l。版本字节决定地址开头：Qtum 主网 58，开头是 Q；测试网 120，开头是 q已核实。

EIP-55

EIP-55

以太坊地址是十六进制，本来不分大小写。EIP-55 用 keccak256(小写地址) 决定每个字母大写还是小写，等于加了一层校验，抄错了钱包能发现。

关做法防的是什么
两人各自算从同一份 GetPublicKey 结果出发，一个人用自己的代码算，另一个人用不同的库独立算（例如以太坊用 ethers 的 computeAddress，Qtum 用 bitcoinjs-lib 的 payments.p2pkh，版本字节改成 58 或 120）。两份一致，才写进签名服务的配置、交给多签持有人登记到网关；多签持有人签名前再核对硬件钱包屏幕上的地址一个人的代码有错（例如用了非压缩公钥、用错哈希函数），没人发现
冷启动自检签名程序每次启动先调一次 GetPublicKey：检查 SPKI 的固定头是 secp256k1，再算出地址，和配置里的预期地址比，不一致就拒绝所有请求、发严重告警。配置里的钥匙写完整 ARN，不写别名配置里的钥匙 ARN 写错；别名被改指到另一把钥匙；钥匙被换过。不查的话，签出的交易发送方不是运营地址，网关全部拒绝

从建钥匙到登记到网关

  1. 建钥匙：用 CDK（或直接写 CloudFormation）建，规格 ECC_SECG_P256K1、用途 SIGN_VERIFY；钥匙策略显式写（见权限），不用 CDK 的默认策略，也不调 grant* 方法；给一个带日期的别名，方便以后换钥匙时区分；删栈也保留钥匙（RemovalPolicy.RETAIN）。部署前用 cdk synth 看一眼生成的钥匙策略，只有自己写的几条。
  2. 查规格、取公钥：aws kms describe-key 看 KeySpec、KeyUsage、KeyState、MultiRegion，期望是 ECC_SECG_P256K1、SIGN_VERIFY、Enabled、false；再按动手一节的第 ② 步取公钥、看曲线（取公钥和看曲线已实测，describe-key 还没跑过）。
  3. 算地址：按上面的两张表，从 SPKI 取出 65 字节公钥（固定头不是 secp256k1 就报错），以太坊地址 = keccak256(X ‖ Y) 后 20 字节、写成 EIP-55 大小写；Qtum 用压缩公钥的 hash160，展示和充值用 Base58Check 地址，和合约打交道用 hash160 的十六进制。两样都写进配置。
  4. 两人各自算、冷启动自检：见上面的表。
  5. 登记到网关：以太坊由冷钱包 Safe 调 EthGateway 换运营地址的函数，参数是以太坊地址；Qtum 由管理多签调 MintGateway 的同类函数，参数是 hash160。多签持有人签名前，自己核对硬件钱包屏幕上的地址。
  6. 充 gas，准备 Qtum 的输入：以太坊转够一两周用量的 ETH，低于约 3 天用量时告警补充。Qtum 要多张 UTXO，每一笔在途的交易占一张：分几次（例如 4 次）给运营地址转账，每次产生一张。每张要够好几笔铸币：一笔预付 gasLimit × gasPrice（例如 150000 × 40 聪 = 0.06 QTUM），加字节手续费（1 个输入约 332 字节，按 400 聪每字节约 0.0013 QTUM），再留余量，每张例如 0.5 QTUM，按实测用量调整。退回的 gas 约 17.8 小时后才能花，算余额时不算可用。
  7. 小额验证：测试网全部跑通后，主网先做一笔最小金额的存入和一笔提现，看到铸币和放款上链、合约记下的调用者是运营地址、签名账本和链上对得上，再放开额度。

签名格式

KMS 给的是 DER 编码的 (r, s)，s 可能是高位，没有 v。两条链都不能直接用，要按下面四步处理。先看懂：低位 s、DER 两张卡片。

DER → r, s

① 拆出 r、s

DER 里的 r、s 都是“大端、最短”编码的整数：前导 0 会去掉，最高位是 1 时要补一个 0，所以长度可能是 31、32 或 33 字节。拆出来后去掉补的那个 0，当作两个 256 位整数处理。

以太坊：r、s 作为整数写进 RLP，同样要按最短字节写、不带前导 00。自己拼字节时，r 或 s 不足 32 字节（本地实测 3000 次里 25 次，约 0.8%）要按实际长度写，硬补到 32 字节的话，go-ethereum 解码时报 rlp: non-canonical integer format，交易被拒已核实。Qtum：见第 ④ 步。

Low-s

② s 规范成低位

(r, s) 和 (r, n − s) 都是同一条消息的有效签名。为了防止别人把 s 换成 n − s、改出另一个交易哈希，两条链都只接受 s ≤ n/2：

以太坊：协议规则（EIP-2），高位 s 的交易无效，go-ethereum 报 invalid sender: invalid transaction v, r, s values已核实。Qtum：节点的标准策略包含 SCRIPT_VERIFY_LOW_S（继承自比特币），高位 s 的交易不进内存池已核实。

KMS 签出来的 s 大约一半是高位。s > n/2 时，用 n − s 替换。这一步不需要私钥。

v · yParity

③ 以太坊：算出 v

以太坊交易里不放公钥，节点要从签名恢复出公钥，再算出发送方地址。同一组 (r, s) 能恢复出两个候选公钥，v（EIP-1559 里叫 yParity，取 0 或 1）指明是哪一个。

KMS 不给 v，所以两个都试：用 v = 0 和 v = 1 分别恢复，恢复出的地址等于运营地址的那个就是对的。两个都对不上，说明签名或公钥有问题，必须拒绝。

顺序不能反：先把 s 规范成低位，再试 v。s 换成 n − s 后，对应的 v 也会翻转（下一节有真实数据）。

BIP66 · SIGHASH_ALL

④ Qtum：重新编成 DER，加上 0x01

Qtum 输入里放的签名格式是：严格 DER（BIP66）编码的 (r, 低位 s)，后面跟 1 字节 sighash 类型（SIGHASH_ALL = 0x01）。

KMS 给的已经是 DER，但 s 可能被签名服务换过，所以要用规范后的 r、s 重新编一次，不能直接拿 KMS 的原始 DER 用。sighash 是什么见 脚本卡片。

这几种情况有多常见：本地用 Node.js 22 自带的 crypto 对 3000 个随机摘要做 secp256k1 签名，KMS 的输出格式和它相同（DER、s 不规范）。统计如下（本地实测）：

Qtum

先看懂：UTXO、找零、手续费、脚本、P2PKH、sighash、合约调用输出。Qtum 没有账户和 nonce。运营地址的 QTUM 是一个个 UTXO，一笔交易花掉其中几个，再生成新的输出。

部分内容
输入运营地址的若干 UTXO。每个输入的 scriptSig = <DER 签名 ‖ 0x01> <压缩公钥>
输出 0：合约调用金额 0；脚本 = OP_4 <gasLimit> <gasPrice> <调用数据> <合约地址 20 字节> OP_CALL
输出 1：找零回到运营地址的标准脚本 OP_DUP OP_HASH160 <hash160> OP_EQUALVERIFY OP_CHECKSIG
手续费输入总额 − 输出总额。要覆盖 gasLimit × gasPrice（预付的 gas），加上按交易字节数算的手续费

状态：OP_CALL 是 0xc2已核实 Qtum 源码。合约调用脚本的写法和开源库 qtum-ethers-wrapper 一致已核实；该库默认 gasLimit 250000、gasPrice 40 sat（库的默认值，不是协议规定）。最低 gasPrice、gas 怎么退回见 OP_CALL 卡片。

每个输入怎么签（传统的 SIGHASH_ALL）做什么
1. 改写复制一份交易。正在签的输入，scriptSig 换成它所花 UTXO 的锁定脚本（运营地址的 P2PKH 脚本）；其他输入的 scriptSig 清空
2. 算摘要序列化，后面加 4 字节的 sighash 类型（1），做两次 SHA256，得到 32 字节摘要
3. 签名KMS 签名；规范 s、重新编 DER、加 0x01
4. 写回和压缩公钥一起写进这个输入的 scriptSig

一笔有 3 个输入的交易，要调 3 次 KMS。动画里的金额是示意值，只为说明“手续费 ＝ 输入 − 输出，要覆盖预付的 gas”。

合约里看到的调用者：是第一个输入所花那个输出的地址，源码已经核实（见 OP_CALL 卡片）。所有输入都用运营地址的 UTXO，调用者就是运营地址。上线前仍要在 regtest 上发一笔真实调用，看 MintGateway 记下的调用者待验证。

重发：没有 nonce，加价重发的做法是“花同一批输入、提高手续费、重新签”，新旧两笔互相冲突，只可能上链一笔。别人改不了这笔交易：替换要花同一批输入，只有运营钥匙能签。比特币的 BIP125 原本要求原交易用 nSequence 声明“可以被替换”；Qtum 现在的代码基于 Bitcoin Core 30.2，已经是 full RBF，不看这个声明，有冲突就按费用规则判断：新交易费率更高、总手续费更高且多出的至少是“字节数 × 10 聪”、最多替换 100 笔、不新增未确认的输入。没有针对合约调用的特殊规则，但替换交易同样要过 gas 和手续费的检查已核实源码。仍建议把 nSequence 设成 0xfffffffd（明确声明可替换），节点哪天改回只认声明也不受影响。实际替换效果要在测试网上试待验证。

核对

签名服务不信执行器给的任何数据，只信自己解析出的交易和自己读到的链

执行器送来的未签名交易、源链交易哈希、审核员签名，在签名服务眼里都只是“线索”：交易自己解析，源链自己读，审核员的消息自己生成。执行器被攻破，也只能送来过不了这一层的请求。先看懂：交易字段和调用数据、UTXO、EIP-712。

顺序核对什么不通过时

2请求格式；按 requestId 查账本，签过就原样返回（见账本）拒绝
3解析交易：只认网关的两个函数，逐个字段核对，手续费不超上限；解析出的操作和转账 ID 要和请求里写的一致拒绝

5审核员签名：人数够、在名单里、没过期拒绝

“拒绝”和“稍后重试”要分开：拒绝是请求本身有问题，等多久都不会好（交易被改过、签名人不在名单、钥匙对不上），一律告警，后端暂停自动放行，转人工。稍后重试是条件还不满足（源链还没 finalized、两家 RPC 不一致、KMS 限流），执行器用同一个 requestId 过一会儿再来，持续太久（例如 15 分钟）才告警。分不开的话，要么正常的延迟天天告警，要么真正的攻击被当成网络抖动。

先说清楚账本防什么：同一笔转账就算被签出两笔交易、两笔都上了链，网关按转账 ID 去重，第二笔会失败，不会重复付款。防重复付款的是合约。账本要保证的是另外四件事：

  1. 额度每笔转账只计一次，不能靠重复请求把自动上限用掉或绕过。
  2. 以太坊每个 nonce 只给一笔转账用，不跳号。跳号或撞号，后面的交易全部卡住。

两条链都一样：同一笔转账最多签几次（例如 5 次，含加价重发），超过就拒签、转人工。Qtum 不独占输入：Qtum 签名服务只核对以太坊上的存入，手上没有 Qtum 节点，看不到输入有没有被花掉；独占的话，一笔交易被内存池丢掉，它的输入就永远解不开。输入别被两笔交易抢用，靠执行器的 UTXO 锁和看门狗核对。

写入顺序

  1. 查 requestId：有记录、未签名交易的哈希也相同时，状态是 SIGNED 就原样返回签好的交易，是 PENDING 就跳到第 4 步、用同一笔交易重签；哈希不同就拒绝（同一个请求号换了交易内容）。
  2. 读转账记录（强一致读），按上面的表判断这次属于哪种情况，不合规则就拒签。
  3. 一个事务写入：新建签名尝试和 requestId 索引（条件“不存在”）；更新转账记录（条件“版本号还是读到的那个”，第一次签时是“不存在”）；以太坊第一次签时新建 nonce 归属（条件“不存在”）、“下一个 nonce”加一（条件“值等于本次 nonce”）；自动放行的第一次签再更新自动额度（条件“版本号不变”）。任何一个条件不成立，整个事务失败，执行器稍后重试。
  4. 写 KMS 调用记录，然后调 KMS、转换签名、自己验一遍。
  5. 把签名尝试改成 SIGNED，存签好的交易，条件“状态还是 PENDING”。条件不成立，说明另一个并发请求先签完了：丢掉自己这份，读出对方的返回。所以同一次签名尝试，签名服务只交出一笔签好的交易。
// 第 3 步，以太坊第一次签、不计额度（简写：省略了表名和属性类型）
TransactWriteItems({
  ClientRequestToken: requestId,   // 1–36 个字符；第一次请求完成后 10 分钟内重复提交不再执行
  TransactItems: [
    { Put: { Item: { pk: "转账#ID#放款", sk: "尝试#1", 状态: "PENDING", requestId, 摘要 },
             ConditionExpression: "attribute_not_exists(pk)" } },
    { Put: { Item: { pk: "请求#" + requestId, sk: "-", 指向: "转账#ID#放款 / 尝试#1" },
             ConditionExpression: "attribute_not_exists(pk)" } },
    { Put: { Item: { pk: "转账#ID#放款", sk: "概要", nonce: 7, 已签次数: 1, 版本: 1 },
             ConditionExpression: "attribute_not_exists(pk)" } },
    { Put: { Item: { pk: "nonce#运营地址#7", sk: "-", 归属: "转账#ID#放款" },
             ConditionExpression: "attribute_not_exists(pk)" } },
    { Update: { Key: { pk: "下一个nonce#运营地址", sk: "-" },
                UpdateExpression: "SET #n = #n + :one", ConditionExpression: "#n = :seven" } }
  ]
})

事务失败（并发冲突）什么都没变稍后重试正常
事务成功，调 KMS 之前崩溃尝试为 PENDING按 requestId 找到它，用同一笔交易重签正常
KMS 签完，第 5 步之前崩溃尝试为 PENDING，KMS 已签过一次但结果丢了同上KMS 多签了一次（调用记录里有），交出去的仍只有一笔
KMS 报错或限流尝试为 PENDING稍后重试正常
两个相同的请求同时到达一个事务成功，另一个失败失败的那个重试时直接拿到结果正常
两个请求都签完，同时改状态先写的成功后写的丢掉自己的签名，返回先写的那笔正常
  • 重签为什么可以接受：重签出来的交易哈希不同，但 nonce（或输入）相同，最多只有一笔能上链。看门狗核对时按 nonce 或“去掉签名后的交易”匹配，不按签好的交易哈希匹配。
  • KMS 调用记录为什么先写后调：中途崩溃，最多多出一条没有对应 CloudTrail 事件的记录。看门狗按“CloudTrail 里 Sign 的次数 ≤ 调用记录的条数”核对，CloudTrail 多出来的 Sign，就是账本之外有人签过，立即暂停网关。
  • 账本坏了：账本记的是签过什么，资金的最终依据是链上。账本丢失或被改：签名服务停签；用时间点恢复建一张新表，恢复到出问题之前；按链上运营地址的交易和 CloudTrail 的 Sign 记录补齐恢复点之后的部分，核对“下一个 nonce”和自动额度；发布新配置指向新表，再恢复签名。期间合约按转账 ID 去重，不会因为账本落后而重复执行。

执行器崩溃后怎么恢复

原则：先查链上，再决定；能广播已签的那笔，就不新签。

崩溃时点恢复时先做什么然后
请求签名之后、拿到结果之前用同一个 requestId 重新请求签名服务按 requestId 返回同一笔
拿到签好的交易、广播之前用只读查询从签名服务找回签好的交易查链上这个转账 ID 是否已执行；没执行就广播这一笔，不另签新的
广播之后、确认之前查链上：交易在不在、转账 ID 是否已执行还在途就继续等或加价重发；已执行就标记完成
确认之后、写数据库之前查链上转账 ID 的状态已执行就标记完成，以监听到的链上事件为准

只锁 kms:Sign 为什么不够：能调 kms:Sign 的身份只有一个，签名 Lambda 的执行角色（下面叫 signer-fn）。可签名账号的管理员能改这个 Lambda 的代码，或者新建一个 Lambda 挂上 signer-fn，照样想签什么签什么。所以要沿着“谁能改签名程序”一路锁上去：

让 CI 部署主网合并代码和发布都要另一个人批准GitHub 分支保护和环境审批（见下面的“发布”）

整份 SCP 里的语句防的是什么
只有 signer-fn 能 Sign管理员给自己或别的角色加 kms:Sign
谁都不许 CreateGrant、ScheduleKeyDeletion、ReplicateKey用 grant 绕开钥匙策略；删钥匙（删了地址就作废）；把钥匙复制到别的区域，另配一份宽松的钥匙策略
钥匙管理（改钥匙策略、启用钥匙、改别名）只能经 CloudFormation手动改钥匙策略；重新启用被禁用的钥匙；把别名指到另一把钥匙
签名 Lambda 的代码、配置、版本、别名、调用权限、并发只能经 CloudFormation 改手动换掉签名程序
保护几个关键角色：PassRole、改信任策略、挂策略都只能经 CloudFormation把 signer-fn 挂到别的函数或机器上；改调用角色和部署角色的信任关系
CDK 的部署角色只能由 CI 扮演人直接扮演部署角色，绕过 CI 和发布审批
账本记录只能由 signer-fn 写；账本表只能经 CloudFormation 改手动改账本记录、删表、关时间点恢复
不许退出组织，不许停掉或删除 trail账号退出组织以摆脱 SCP；关掉日志
  • 先引导，再挂 SCP：CDK 引导要建角色、改信任策略，SCP 挂上后就做不了。以后要改引导配置，由管理账号临时摘下 SCP，改完再挂回去，两个人在场。
  • 名字要对得上：SCP 按名字放行，CDK 代码里要显式写 roleName: "signer-fn"，函数名、账本表名也按约定起，否则 SCP 管不到。
  • 长度有上限：一份 SCP 最多 10,240 个字符，用 SDK 或 CLI 保存时空白也算已核实。写不下就拆成两份，挂在同一个组织单元上。
  • 整份 SCP 挂到测试账号后，按越权清单逐条试，该拒的都要拒、该能做的都能做（见还要验证的）。账本事务不用单独防：DynamoDB 文档写明，事务里的 Put、Update、Delete 按底层的 PutItem、UpdateItem、DeleteItem 授权，条件检查是 ConditionCheckItem已核实，所以按单个操作写的拒绝也管得住事务；挂上以后在测试账号上照样试一次。

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "AllowSignerToSign", "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::签名账号:role/signer-fn" },
      "Action": "kms:Sign", "Resource": "*",
      "Condition": { "StringEquals": {
        "kms:SigningAlgorithm": "ECDSA_SHA_256", "kms:MessageType": "DIGEST",
        "aws:sourceVpce": "vpce-KMS接口端点ID" } } },
    { "Sid": "AllowReadPublicKey", "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::签名账号:role/signer-fn" },
      "Action": ["kms:GetPublicKey", "kms:DescribeKey"], "Resource": "*" },
    { "Sid": "AllowCfnToManage", "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::签名账号:role/cdk-hnb659fds-cfn-exec-role-签名账号-区域" },
      "Action": ["kms:DescribeKey", "kms:GetKeyPolicy", "kms:PutKeyPolicy",
                 "kms:EnableKey", "kms:DisableKey", "kms:CreateAlias", "kms:UpdateAlias"],
      "Resource": "*" }
  ]
}
  • 故意没有“允许本账号 root 使用 kms:*”那一条（见 IAM 卡片 ①）。签名账号的 IAM 管理员改自己的 IAM 策略，拿不到 kms:Sign。
  • AllowSignerToSign 的三个条件：只许签摘要、只许 ECDSA_SHA_256、请求只许经过本账号的 KMS 接口端点。signer-fn 的临时凭证被偷到 VPC 外面，也签不了。文档提醒，aws:sourceVpce 会让“AWS 服务代你调 KMS”的请求失败；签名 Lambda 是自己直接调 Sign，不受影响已核实。
  • AllowCfnToManage 满足防锁死检查：建钥匙的 CloudFormation 执行角色以后还能改策略。这个角色被删掉的话，钥匙就没人能管，要找 AWS Support；它本身受 SCP 保护，运营钥匙也可以换（见运维），这个风险可以接受。
  • 另有一条给人工登录角色禁用钥匙：主体写本账号、条件限定登录角色，操作只有 kms:DisableKey 和 kms:DescribeKey。主体写账号时，还要那个角色的 IAM 策略也允许才生效，能授出的也只有这两个操作。

跨账号调用：执行器在业务账号里，先 AssumeRole 扮演签名账号里的调用角色，再调签名 Lambda。调用角色只能调签名 Lambda 的 live 别名（不能调 $LATEST 或别的版本），碰不到 KMS：SCP 和钥匙策略都不允许它。这样授权完全由签名账号决定，签名账号一改信任策略，业务账号就调不了；CloudTrail 里也留下每次 AssumeRole 的会话名。要配三处：

  • 调用角色的信任策略（签名账号里）：只允许业务账号里执行器的那个角色 sts:AssumeRole。
  • 调用角色的权限：只有一条 lambda:InvokeFunction，资源写签名 Lambda 的 live 别名的 ARN。
  • 执行器的角色（业务账号里）：另需一条允许 sts:AssumeRole 到这个调用角色。Qtum 一侧同样配一套。

换钥匙

非对称钥匙不能自动轮换（见 KMS 提供什么），换钥匙就是建新钥匙、换运营地址。按计划定期换（例如每季度）；人员变动、怀疑泄露时不等计划，立即换。

旧地址上剩下的钱：签名服务只签网关调用，旧地址上剩下的少量 ETH、QTUM，以及换钥匙前约 17.8 小时内退回、还没成熟的 gas，都转不出来。所以换钥匙前一两周就停止给旧地址补 gas，让余额自然用完。真要收回，可以给签名服务加一种“只能把余额转到固定地址、只对退役钥匙可用”的操作；这又是一个新的签名口子，要和别的规则一样核对。

出事怎么办

情况步骤
怀疑运营钥匙被滥用（签名程序被改、signer-fn 的凭证被偷、权限有漏洞）① 值班人员用守护者硬件钱包暂停两个网关：先暂停，再判断。② 登录角色禁用这把钥匙，之后任何人都签不了。③ 查 CloudTrail 里的 Sign、AssumeRole、Lambda 和 IAM 的变更，账本里的签名记录，链上运营地址发出的所有交易，确认哪些签名不是正常请求产生的、损失多少。④ 找到入口修好，走发布。⑤ 换钥匙，被禁用的旧钥匙不再启用。⑥ 多签恢复网关，先把上限调低运行一段时间
KMS 或整个区域不可用签名返回“稍后重试”，转账排队，执行器自动重试。时效允许就等它恢复；故障持续、快超过时效，就在另一个区域部署签名服务、建新钥匙、换运营地址，账本在新区域另建，起点按链上状态
账本丢失或损坏见账本最后一条

演练：上线前和此后定期，在测试网签名账号上演练禁用钥匙后恢复、执行器在各个时点崩溃、账本时间点恢复、完整换一次钥匙。每次都验证：没有重复铸币或放款，所有转账最后完成或进入退款。

单区域钥匙多区域钥匙
区域故障时签名停止，转账排队；故障久了就在别的区域建新钥匙、换地址在副本区域部署签名服务就能继续，地址不变
