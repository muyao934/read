CCTP 与 CCIP 深入

把两套协议拆到合约和字节层面：消息长什么样、目标链怎么验、Fast Transfer 的代价、CCIP 2.0 的验证与执行怎么分开、限速和费用怎么算。

一句话

CCTP 是 USDC 发行方自己的“销毁 → 证明 → 铸造”通道；CCIP 是 Chainlink 的通用跨链消息网络

两者经常被放在一起比，但出发点完全不同。CCTP 只解决一件事：让 USDC 在链之间移动时始终是原生 USDC。CCIP 解决的是“任意消息、任意代币怎么安全地跨链”，而它搬 USDC 时，底层又会用到 CCTP。

常见说法里，对的部分

  • CCTP 没有锁仓池，USDC 在源链真的被销毁，在目标链真的被铸造
  • CCIP 可以同时传代币和调用数据，到账后自动执行目标合约
  • 两者在支持的链上都不需要项目方自己运行验证者

需要纠正的部分

  • CCTP 不是 Chainlink 的，是 Circle 的；证明者是 Circle 自己的 attester，以太坊上目前 2 个里要 2 个签名（链上读取）
  • Fast Transfer 不是“确认得更快”，而是 Circle 在源链只到“已确认”、还没最终确定时就签名，自己承担重组风险，所以有额度上限、要收费
  • CCTP 的 Hooks 不会被 CCTP 自动执行。hookData 只是随消息带过去的数据，要由集成方的合约读出来执行
  • CCIP 不是只能搬代币，也可以只发消息。反过来，任意代币要走 CCIP 的标准代币池，必须由代币管理员自己注册
  • CCIP 2.0 里的 RMN 不再自动拦截，现在是一个手动的链上安全开关（curse）

消息长什么样

CCTP 消息是一段定长字段 + 可变长消息体拼起来的字节串。源码注释写明：除了消息体，其他字段都必须定长，以免出现哈希碰撞。签名签的就是整段字节的 keccak256。

CCTP · 验证

把它和第 03 章 Qtum 桥的验签放在一起看，同样是“几个签名者对一个哈希签名”，细节上有几处值得借鉴。

检查项CCTP V2（receiveMessage）Qtum 桥（withdrawERC20）
签的是什么整段消息字节的 keccak256，不加 EIP-191 前缀7 个字段的 keccak256，再加 EIP-191 前缀
签名数量attestation 长度必须正好等于 65 × 门槛至少达到门槛
去重签名者地址必须严格递增排列，重复或乱序直接拒绝按地址首字节做位图，首字节相同的不同签名者会被误判
签名者名单每个签名者都必须是已启用的 attester；以太坊上目前 2 个，门槛 2在签名人名单里，门槛 4/5
目标链消息里的 destinationDomain 必须等于本链哈希里有 chainId
来源合约sender 必须是登记过的“对方链 TokenMessenger”，否则 “Remote TokenMessenger unsupported”哈希里没有来源桥合约，也没有目标桥合约
谁能提交可选 destinationCaller：非零时只有它能提交任何人
防重放usedNonces[nonce]usedHashes[keccak(txHash, txNonce)]
过期expirationBlock 到期后 “Message expired and must be re-signed”没有

“严格递增”去重的写法来自 Christian Lundkvist 的 Simple Multisig，源码注释里注明了出处。它不需要额外存储，也不会误伤首字节相同的签名者。

CCTP · 新链

结合第 02 章和本章的源码，接入 CCTP 的每一步都需要 Circle 控制的角色来执行，项目方自己做不了。

CCIP · 组件

CCIP 2.0：发送、验证、索引、执行四步

Chainlink 原本以预言机网络（DON）出名，CCIP 默认的验证网络就建在同一套 DON 基础设施上。CCIP 2.0 把“谁来验证”和“谁来执行”拆开了：验证由 Cross-Chain Verifier（CCV）负责，执行谁都可以做。

组件在哪做什么
Router源链 / 目标链固定不变的入口地址，升级时 OnRamp / OffRamp 在它背后替换。检查目标链是否支持、有没有全局 curse，收费，把代币交给代币池
OnRamp源链出站把关：检查目标链没被 curse，确定这条消息需要哪些验证者和执行者，让代币池锁定或销毁代币，发出消息
Fee Quoter / Token Admin Registry / 代币池源链 / 目标链报价；登记每个代币由哪个池子处理；池子负责本链这一侧的锁定 / 销毁 / 释放 / 铸造
CCV（Committee Verifier）链下 + 目标链合约默认验证网络，16 个独立节点运营方各自签名，由 Aggregator 汇成法定人数证明；还可以叠加别的 CCV
Indexer链下（可选）按消息 ID 汇总各验证者的证明，方便执行者查询
Executor链下付目标链 gas、提交消息。默认是 Chainlink 的，但执行无需许可
OffRamp目标链无需许可的执行入口。不信任提交者给的验证者列表，自己根据接收合约、代币池和通道配置重新推出需要哪些 CCV，再逐个在链上核对证明
RMN（curse）各链手动的链上安全开关。某条链或通道被 curse 后，相关发送和执行全部回滚，直到解除

CCT

自助注册：代币管理员说了算

每条链有一个 Token Admin Registry，记录每个代币的管理员和当前使用的池子。注册流程：注册模块提议一个管理员 → 该地址接受 → 管理员设置池子。设置池子即启用，设成零地址即下架。能注册的前提是代币暴露 owner()、OpenZeppelin 的 DEFAULT_ADMIN_ROLE，或实现 CCIP 专用的 getCCIPAdmin()。

Rate limit

限速是一桶水

每个代币池在每条通道上都能设限速，官方原话 “It is highly recommended to set rate limits”。桶的容量是单笔能转的上限；补充速率是每秒加回多少；每次转账扣掉相应的量，桶满了就不再加。能不能转，看的是桶里现在还剩多少，不是桶有多大。

Simulator

试一试：限速桶

设好容量和补充速率，连续转几笔，看看第二笔大额为什么会被拒。你自己的桥也可以用同样的办法限速。

ccipReceive

接收合约必须自己检查三件事

官方最佳实践：在 ccipReceive 里校验源链（sourceChainSelector）、发送方（sender），以及调用者是不是 Router。不检查的话，任何链上的任何合约都能给你发消息。

extraArgs

每条消息的配置

新集成用 ExtraArgsV3：可以写验证者、执行者、确认程度、gas 上限等。旧的 GenericExtraArgsV2 只认 gasLimit，allowOutOfOrderExecution 在 2.0 里已弃用。

Manual execution

执行失败怎么办

证明已经齐了但自动执行失败，任何人都可以通过 OffRamp 手动执行。证明本身缺失时，手动执行也补不出来。

FTF

快于最终性（可选）

默认等源链完全最终确定。CCIP 2.0 的通道可以支持 Faster-Than-Finality，但要发送方（对所有消息）和代币发行方（对代币转账）都明确选择开启。
