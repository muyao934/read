Qtum 与 UTXO

比特币的记账方式上怎么跑以太坊的合约，以及“EVM 兼容”到底兼容到哪一层。

一句话

Qtum = 比特币的代码和记账方式 + 一台 EVM

Qtum 的代码分叉自 Bitcoin Core，底层用 UTXO 记账、用 PoS 出块；再通过一层叫 AAL 的“翻译层”，让以太坊虚拟机（EVM）能在上面运行 Solidity 合约。

常听到的说法里，对的部分

  • 能部署和运行 Solidity 合约，EVM 版本一直跟着以太坊升级，目前到 Pectra
  • 有自己的代币标准 QRC-20，接口和 ERC-20 一样
  • 每个 Qtum 地址背后都是 20 字节，可以写成 40 位 hex，看起来像以太坊地址

需要纠正的部分

  • Qtum 不是以太坊的分叉，是 Bitcoin Core 的分叉。最新 v30.2 同步的是 Bitcoin Core 30.2
  • 底层没有账户余额，也没有账户 nonce，链上只有 UTXO
  • 同一把私钥在 Qtum 和以太坊上算出来的地址不一样
  • 标准 MetaMask 不能直接给 Qtum 交易签名
  • 主网 chainId 81 在公共登记表里属于另一条链
档案内容
上线创世块 2017-09-06；主网 v1.0 发布于 2017-09-08
代码来源Bitcoin Core 分叉，持续跟进比特币上游版本

底层

要理解 Qtum，先得理解它和以太坊在“账本怎么记”上的根本区别。比特币和 Qtum 记的是一张张“钞票”，以太坊记的是每个账户的余额。

UTXO 模型（Bitcoin、Qtum）账户模型（Ethereum、Base、BSC）
链上存什么一张张“未花费的输出”，每张写着金额和谁能花每个地址一行：余额、nonce、合约代码和存储
余额怎么来钱包把属于你的所有 UTXO 加起来直接读那一行的数字
转账花掉整张输入，生成新输出（含找零）一行减、一行加
防重放输出花掉就没了每个账户的递增 nonce
手续费输入总额 − 输出总额gasUsed × gas 价格
写合约Bitcoin Script 能力有限，写不了通用合约EVM 图灵完备，合约直接读写账户状态

Qtum 想要的是两边的好处：底层沿用比特币久经考验的 UTXO，上层又能跑以太坊生态的合约。代价就是中间要有一层翻译，也就是下一节的 AAL。

核心机制

AAL：把 UTXO 交易翻译给 EVM

EVM 只认“账户”：谁调用、带了多少钱、余额多少。Qtum 链上只有 UTXO。AAL（Account Abstraction Layer）夹在中间，把 UTXO 交易里的合约指令取出来，翻译成 EVM 能执行的调用，再把执行结果翻译回 UTXO。

别和以太坊的“账户抽象”搞混。以太坊的 ERC-4337、EIP-7702 也叫 account abstraction，讲的是让用户账户可编程，和 Qtum 的 AAL 毫无关系，只是名字撞了。

四个 Qtum 特有的脚本操作码

操作码出现在哪作用
OP_CREATE (0xc1)交易输出部署合约。输出脚本里带 gas 上限、gas 价格和合约字节码
OP_CALL (0xc2)交易输出调用合约。带合约地址、调用数据、gas 上限和价格；这个输出的金额就是 msg.value
OP_SPEND (0xc3)节点生成的交易输入花掉合约名下的 UTXO。只出现在节点自动生成的“condensing transaction”里
OP_SENDER (0xc4)交易输出显式指定调用者是谁（2019 年 QIP-5 加入）。离线质押的委托就用到它

一次合约调用的旅程

谁是 msg.sender

规则

从交易的第一个输入推出来

交易里有 OP_SENDER，就用它指定的地址；否则用第一个输入所花的那个 UTXO 的地址。这个 UTXO 必须是 P2PKH 或 P2PK 类型，否则交易无效。gas 找零永远退回第一个输入的地址，不跟随 OP_SENDER。

限制

多签地址不能直接调合约

Qtum README 原文：合约“不能从 pay-to-pubkeyhash（Q 开头）以外的任何地址类型收币或向其发币”。比特币式的 P2SH 多签地址、segwit 地址都不能当 msg.sender。OP_SENDER 也没有放宽这一点。另外，创建合约时不能附带 QTUM。

地址

Qtum 沿用比特币的算法：对压缩公钥做 SHA-256 再做 RIPEMD-160，得到 20 字节（hash160）。以太坊则对未压缩公钥做 Keccak-256，取最后 20 字节。算法不同，所以同一把私钥导入两边，得到的地址完全不同。

这 20 字节在 Qtum 上有两种写法：给人看的 base58 地址（主网 Q 开头），和给 EVM 用的 40 位 hex。两者是同一个东西，只是编码不同。

Tool

Q 地址 ↔ hex 互转

输入 Q / q 开头的地址，或 40 位 hex。全部在浏览器里计算，不联网。

示例取自 Janus README 和 Qtum RPC 文档。base58check 末尾 4 字节是校验和，抄错一位就能被发现。

Types

Qtum 的地址类型

类型开头能调合约吗
P2PKH 主网Q能
P2PKH 测试网q能
P2SH（多签）主网 / 测试网M / m不能
segwit（bech32）qc1 / tq1不能
合约地址40 位 hex—

合约地址怎么来：以太坊用“部署者地址 + nonce”算；Qtum 没有账户 nonce，用的是 RIPEMD160(SHA256(创建交易的 txid ‖ 输出序号))。用 Qtum 主网上 USDC.e 的创建交易验证过：txid 4b01f6e6…85e6、输出 0，算出来正好是它的地址 0xecfc68f4…019a。按以太坊规则预先计算合约地址的工具，在 Qtum 上会算错。

共识与治理

PoS

谁来出块

持有已成熟 QTUM 的人都能参与“质押”出块，内核算法源自 Blackcoin，目标间隔 32 秒。UTXO 要有 2000 个确认（约 18 小时）才能用于质押；新挖出的币和 gas 找零也要等 2000 块才能花。

Offline Staking

离线质押（2020 年起）

不想一直开着钱包的人，可以通过委托合约把质押权委托给一个 Super Staker，约定分成比例。官方原文：离线质押是非托管的，币不会被锁定，私钥一直在自己手里。默认最少 100 QTUM。

DGP

链上治理协议

一组系统合约，可以不分叉就调整网络参数：gas 价目表、区块大小、最低 gas 价格、区块 gas 上限。当前最低 gas 价格 40 sat/gas，区块 gas 上限 4000 万。

Finality

没有“最终确定”这个状态

以太坊有明确的 finalized 区块。Qtum 没有，它用同步检查点拒绝过深的重组：早于币成熟期（当前 2000 块）的分叉会被拒绝。比这浅的重组理论上都可能发生，桥要自己选等多少个确认。

关键结论

Qtum 的 EVM 兼容是真的，但只在“合约执行”这一层。往外每多走一层，差异就多一些。

层面和以太坊一样吗具体差异与后果
合约执行（opcode、存储、事件）基本一样EVM 版本到 Pectra；底层引擎是 evmone
Solidity 编译一样编译目标要选节点支持的 EVM 版本。Qtum Core 把 EVM 版本最高映射到 EVMC_PRAGUE：blob 相关操作码能执行，但 Qtum 没有 blob 交易，节点给 EVM 的区块上下文里 blob 哈希、blob 基础费、基础费都没填，BLOBHASH / BLOBBASEFEE / BASEFEE 都返回 0；v29.1 发布说明列出的 Pectra 内容只有 EIP-2537、EIP-2935，没有 EIP-7702（UTXO 交易里也没有 7702 的交易类型）
代币标准接口一样QRC-20 与 ERC-20 方法和事件相同
金额单位不同msg.value 以 satoshi 计（8 位小数），不是 wei（18 位）
地址与私钥不同同一私钥两边地址不同；签名消息前缀是 QTUM Signed Message
交易构造不同要挑 UTXO、写 OP_CALL 脚本；没有账户 nonce。ethers.js 直接生成的交易不能广播到 Qtum
合约地址不同由 txid + 输出序号算出，不是部署者 + nonce
调用者有限制只能是 P2PKH / P2PK；合约钱包（合约调合约）可以
节点 RPC不同Qtum 节点讲比特币式 RPC，以太坊工具需要 Janus 或专用库翻译
钱包不同标准 MetaMask 不能签 Qtum 交易，要用 Qtum Snap 或专用钱包
chainId有冲突81 在 ethereum-lists 登记的是 Japan Open Chain（标记 reusedChainId），Qtum 没有登记
出块与确认不同32 秒一块，没有 finalized 状态，深度重组上限约 2000 块

工具链

MetaMask、ethers.js、Hardhat 只会说 eth_* 这套 RPC。Qtum 节点（qtumd）说的是比特币式的 RPC。Janus 是官方做的翻译代理：前面接 eth_* 请求，后面转成 Qtum 节点能执行的调用。

Limits

README 里写明的限制

  • 公共实例只适合“不需要 eth_sendTransaction 或 eth_accounts”的场景；要发交易得自建 Janus + qtumd，由节点钱包保管私钥
  • 把以太坊格式签名的 eth_sendRawTransaction 透明转换成 Qtum 交易，写在“未来工作”里
  • eth_subscribe 只支持 logs
Status

现状（2026-10-27 查询）

GitHub 上的 qtumproject/janus 仓库于 2026-09-17 被 GitHub 封禁访问，API 返回原因 “tos”。官方没有声明继任项目。仍在维护的替代方案是在客户端签名、自己选 UTXO 的 qtum-ethers-wrapper，以及 Qtum 的 MetaMask Snap。
