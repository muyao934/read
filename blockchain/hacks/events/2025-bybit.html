区块链被盗事件编年史

总览　/　2025 年　/　十亿美元级失守与信任链

Bybit 冷钱包被盗 14.6 亿美元

2025 年 2 月 21 日，Bybit 的签名人在网页上确认了一笔看似普通的冷钱包转账，实际签下的却是一笔把冷钱包合约逻辑换成攻击者版本的交易，约 40 万枚 ETH 和 11 万多枚质押类 ETH 随即被转走。攻击者没有攻破 Bybit 自己的系统，攻破的是它用来发起多签交易的工具 Safe{Wallet}。在 2026 年 10 月币安事件之前，这是金额最大的已确认盗币案。

概要

Bybit 的以太坊冷钱包是一个 Safe 多签合约，6 个签名人中凑够 3 个签名才能转出资产。签名人通过 Safe 团队运营的网页 Safe{Wallet} 发起交易，再用 Ledger 硬件钱包签名。2 月 19 日，攻击者替换了 Safe{Wallet} 存放在 AWS S3 上的前端 JavaScript。恶意代码只在 Bybit 冷钱包发起交易时生效：网页显示的是正常转账，送去签名的却是一笔对攻击者合约的 delegatecall。

三个签名凑齐后，这笔交易在链上执行，把冷钱包代理合约里保存“实现合约地址”的存储槽改成了攻击者的后门合约。冷钱包的地址没变，里面运行的代码已经换了。攻击者随后不再需要任何签名，转走 401,346 枚 ETH 和约 11.3 万枚 stETH、cmETH、mETH，按当时价格约 14.6 亿美元[4]。约两分钟后，Safe{Wallet} 服务器上的恶意文件被换回干净版本[3]。

源头是 2 月 4 日一名 Safe{Wallet} 开发者在 Mac 上运行了一个伪装成股票模拟器的 Docker 项目，攻击者借此劫持了他的 AWS 会话[7]。FBI 在 2 月 26 日认定这是朝鲜 TraderTraitor 所为[2]。Bybit 没有暂停提现，三天内靠借款、大额存入和购币补足了 ETH 缺口[15]。赃款在十天左右基本被洗成比特币，主要通道是 THORChain；截至 2025 年 4 月，只有约 3.84% 被冻结，约 27.6% 已无法追踪[19]。

背景

Bybit 是一家中心化加密货币交易所。事发当天，它在公告中称自己管理的资产超过 200 亿美元，足以覆盖这次损失[1]。交易所通常把大部分资产放在冷钱包里，只在热钱包留够日常提现用的部分，需要时从冷钱包往热钱包调拨。2 月 21 日出事的，正是一次例行的“冷转热”。

Bybit 的以太坊冷钱包不是一个普通地址，而是部署在链上的 Safe 多签合约：合约里登记了 6 个签名人地址，任何转出都要其中 3 人签名[11]。签名人的私钥保存在 Ledger 硬件钱包里，不接触联网电脑。Safe（原 Gnosis Safe）是以太坊上常用的多签合约，这次事件的取证没有发现它的合约代码有漏洞[6]。

合约只负责核对签名和执行交易，签名人具体签什么，是由另一个软件算出来再交给他们看的。对 Bybit 来说，这个软件就是 Safe 团队运营的网页应用 Safe{Wallet}（app.safe.global）：它把签名人想做的操作编码成待签数据，送到硬件钱包签名，再收集签名、提交上链。

这种“网页发起、硬件签名”的流程在 2024 年已经出过两次事。7 月，印度交易所 WazirX 的多签钱包被盗约 2.3 亿美元，它和提供签名界面的托管商 Liminal 事后互相指责[10]。10 月，Radiant Capital 三名开发者的电脑被植入恶意软件，Safe{Wallet} 界面显示正常交易，后台签下的是恶意交易，损失约 5,000 万美元，Mandiant 将其归因于朝鲜相关组织 UNC4736[28]。Sygnia 在 Bybit 事件的报告中把这三起放在一起比较：都是界面显示一笔交易，实际签下另一笔[3]。

攻击 Bybit 的 TraderTraitor（又名 Jade Sleet、UNC4899）是朝鲜专门针对加密行业的黑客组织，惯用假招聘、假编程测试和恶意 Docker 项目接近开发者，再从开发者电脑进入云环境[9]。2024 年 5 月 DMM Bitcoin 被盗 4,502.9 枚 BTC，也是它先用假编程测试攻破了钱包服务商 Ginco 的一名员工[9]。

攻击原理

这次攻击没有利用智能合约漏洞。Safe 合约忠实地执行了它收到的交易，问题出在签名人以为自己签的和实际签下的不是同一笔交易。要看清这一点，需要先看 Safe 钱包的结构。

冷钱包里运行的代码从哪来

每个 Safe 钱包在链上是一个很小的代理合约（proxy）。它保存签名人名单、门槛、nonce 和资产，自己几乎没有逻辑；收到的每一次调用都用 delegatecall 转交给一个共用的实现合约（Safe 称为 masterCopy，v1.3.0 起改名 singleton）去执行。delegatecall 的含义是“运行对方的代码，但读写我自己的存储”。至于转交给谁，取决于代理合约第一个存储槽（slot 0）里存的地址。公开报告没有写明 Bybit 冷钱包的 Safe 版本，下面引用的是 v1.1.1 的源码，v1.3.0 的结构相同[32][33]：

// Proxy.sol（Safe v1.1.1），英文注释是原有的，中文注释是本站加的
contract Proxy {

    // masterCopy always needs to be first declared variable, to ensure that it is at
    // the same location in the contracts to which calls are delegated.
    address internal masterCopy;     // 第一个变量，位于 slot 0
    ……
    function ()
        external
        payable
    {
        assembly {
            // 每次调用都先读出 slot 0，把它当作实现合约地址
            let masterCopy := and(sload(0), 0xffffffffffffffffffffffffffffffffffffffff)
            // ……（省略：查询 masterCopy 地址的特殊分支）……
            calldatacopy(0, 0, calldatasize())
            let success := delegatecall(gas, masterCopy, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())
            if eq(success, 0) { revert(0, returndatasize()) }
            return(0, returndatasize())
        }
    }
}

来源：safe-global/safe-contracts 仓库 v1.1.1 标签，contracts/proxies/Proxy.sol 第 12–46 行。略去构造函数、部分注释和第 35–39 行，第 14 行的长注释折成两行。

谁能改写 slot 0，谁就能决定这个钱包运行什么代码。正常情况下，slot 0 只能通过 Safe 自己的 changeMasterCopy 修改，这个函数带有 authorized 修饰符，要求调用来自钱包自身，也就是一笔凑够签名的 Safe 交易[32]。所以攻击者仍然需要 3 个签名，难点在于让这笔交易在界面和签名设备上看起来不像“升级”。

operation 字段

Safe 交易里有一个 operation 字段。它为 0 时，钱包对目标地址发起普通 call；为 1 时，钱包对目标地址发起 delegatecall，用钱包自己的存储运行目标地址的代码：

// Enum.sol（Safe v1.1.1）
enum Operation {
    Call,           // 0：普通调用，转账用的就是它
    DelegateCall    // 1：在钱包自己的存储上运行目标合约的代码
}

// Executor.sol（Safe v1.1.1）
function execute(address to, uint256 value, bytes memory data,
                 Enum.Operation operation, uint256 txGas)
    internal
    returns (bool success)
{
    if (operation == Enum.Operation.Call)
        success = executeCall(to, value, data, txGas);
    // 目标合约的代码可以改写钱包的任何存储槽，包括 slot 0
    else if (operation == Enum.Operation.DelegateCall)
        success = executeDelegateCall(to, data, txGas);
    else
        success = false;
}

来源：同上仓库 v1.1.1 标签，contracts/common/Enum.sol 第 7–10 行，contracts/base/Executor.sol 第 9–19 行（函数签名折成两行）。

delegatecall 是 Safe 的正常功能，官方的批量交易合约 MultiSend 就要求必须用 delegatecall 调用[32]。但对一个只做“冷转热”的冷钱包来说，一笔 operation = 1、目标是陌生合约的交易本身就是最强的危险信号。

签名人签的是什么

execTransaction 把 to、value、data、operation 等字段连同 nonce 按 EIP-712 规则编码，算出一个哈希，再核对签名人对这个哈希的签名。operation 在被签名的数据里：

// GnosisSafe.sol（Safe v1.1.1）
//keccak256(
//    "SafeTx(address to,uint256 value,bytes data,uint8 operation,uint256 safeTxGas,
//     uint256 baseGas,uint256 gasPrice,address gasToken,address refundReceiver,uint256 nonce)"
//);
……
bytes memory txHashData = encodeTransactionData(
    to, value, data, operation, // Transaction info   // operation 也在签名范围内
    safeTxGas, baseGas, gasPrice, gasToken, refundReceiver, // Payment info
    nonce
);
// Increase nonce and execute transaction.
nonce++;
txHash = keccak256(txHashData);
checkSignatures(txHash, txHashData, signatures, true);   // 凑够门槛就放行
……
success = execute(to, value, data, operation,
                  safeTxGas == 0 && gasPrice == 0 ? gasleft() : safeTxGas);

来源：同上仓库 v1.1.1 标签，contracts/GnosisSafe.sol 第 28–30 行、第 132–147 行。类型字符串和最后一行为排版折行，中间省略了 gas 检查和退款逻辑。

所以链上这一侧没有问题：签名人确实签了 operation = 1，合约也只执行了被签名的内容。问题出在签名之前。CertiK 指出，送到 Ledger 的确实是被篡改后的数据，签名人判断交易内容时看的却是 Safe{Wallet} 网页上的显示[4]。CertiK 还引述 Ben Zhou 的话：他签名前没有在 Ledger 屏幕上核对交易数据。Hex Trust 的分析也说，签名人依赖 Safe 界面，没有在设备上核对解码后的交易[11]。

这就是“盲签”（blind signing）：硬件钱包上显示的往往只是哈希或难以人工核对的原始字段，签名人实际上只能信任电脑屏幕。2026 年以太坊基金会发布 Clear Signing 标准时，称盲签是“造成数十亿美元用户损失的结构性缺陷”，并点名了 Bybit[30]。

恶意代码做了什么

Sygnia 和 Verichains 各自取证后得出同一结论：被改动的是 Safe{Wallet} 网页从 AWS S3 加载的 JavaScript 文件，而不是 Safe 的源码仓库或合约[3][6]。Sygnia 在 Bybit 签名人电脑的 Chrome 缓存和公开网页存档里都找到了这份恶意文件，证明它确实是从 Safe{Wallet} 的服务器下发的。按 Sygnia 的报告，这段代码有三个特点：

  • 只对两个合约地址生效：Bybit 的冷钱包，以及另一个可能属于攻击者的地址。其他用户打开同一个网页，一切照常。这解释了为什么它在线上放了两天没人发现。
  • 在签名之前替换交易：把签名人要发起的交易换成一笔 operation = 1、目标是攻击者预先部署的合约的交易，网页上仍显示签名人原本想做的转账。
  • 篡改网页自己的校验函数，让替换后的交易和签名能够通过检查、顺利提交。

Verichains 根据证据推断，Safe{Wallet} 的 AWS S3 或 CloudFront 账户或 API 密钥可能已经泄露[6]。Mandiant 后来查清了完整链条：攻击者从开发者电脑上偷走了 AWS 会话令牌，借此绕过了多因素认证[7]。

签名人签下的这笔 delegatecall 在冷钱包的上下文里运行攻击者的代码，把一个后门合约的地址写进了 slot 0。从这一刻起，代理合约收到的任何调用都会转交给后门合约。CertiK 记录，后门合约带有 sweepETH 和 sweepERC20 两个转出资产的函数，调用它们不需要任何多签批准[4]。

3/6 多签为什么没有起作用

多签的前提是签名人彼此独立：攻击者要同时骗过或控制多个人。Bybit 的签名人用的是同一个网页，看到的是同一个被篡改的界面，硬件钱包又没有给出他们能独立核对的信息。显示层一旦被攻破，3 个签名就退化成了 1 次判断。Huntress 的总结是：“没有独立核验，多签就不够”[35]。

攻击过程

下面的步骤综合了 Safe 公布的 Mandiant 调查、Sygnia 与 Verichains 的取证和 CertiK 的链上分析[3][4][7][8]。攻击者事后删除了恶意软件、清空了 Bash 历史，部分环节只能由日志和残留证据推断。

  1. 攻破一名开发者的电脑（2 月 4 日）攻击者冒充可信的开源贡献者接近一名 Safe{Wallet} 开发者，让他在 macOS 上以较高权限运行一个伪装成股票投资模拟器的 Docker 项目。这个项目连接的域名两天前才注册。
  2. 进入 AWS，绕过多因素认证这名开发者在 AWS 里有较高权限。攻击者没有去破解他的密码，而是偷走他已登录的会话令牌，直接以他的身份操作，还试图注册一个虚拟 MFA 设备长期驻留。登录来自 ExpressVPN 的 IP，User-Agent 带有 Kali Linux 特征；活动时间与开发者的作息对齐，以免引起注意。攻击者在系统里待了近 20 天。
  3. 预先部署合约（2 月 18 日）在以太坊上部署两个合约：一个在被 delegatecall 时改写存储槽，一个是带转出函数的后门“实现合约”。
  4. 替换前端文件（2 月 19 日）替换 Safe{Wallet} 存放在 AWS S3 上的 JavaScript。恶意代码先判断当前钱包地址，只有遇到 Bybit 冷钱包等两个地址才动手。
  5. 等待例行转账（2 月 21 日）Bybit 按计划从冷钱包往热钱包调拨 ETH。签名人在网页上看到的是这笔转账，硬件钱包收到的是被替换的交易。3 个签名凑齐后，交易上链执行。
  6. 接管并转空delegatecall 把冷钱包的 slot 0 改成后门合约地址，攻击者随即调用转出函数，把 401,346 枚 ETH 和 stETH、cmETH、mETH 转到自己的地址。
  7. 清理痕迹约两分钟后，S3 上的文件被换回正常版本；开发者电脑上的恶意软件和 Bash 历史也被清除。

这条链上没有一步需要破解密码学。每一步利用的都是一种信任：开发者信任“开源项目”，AWS 信任已登录的会话，签名人信任官方网页，合约信任有效签名。每一层都把上一层的结果当作真的，没有再核对一次。

被盗资产的美元估值有几种说法：Bybit 的首份公告写“超过 15 亿美元”，后来的版本改为“超过 14 亿美元”[1]；FBI 写约 15 亿美元[2]；CertiK 和 Elliptic 按事发时价格算出约 14.6 亿美元[4][12]。本页采用 14.6 亿美元。按代币计，CertiK 的统计如下：

洗钱路径

  1. 换币、拆分stETH、cmETH 等在 DEX 上换成 ETH，避免被发行方冻结；两小时内分散到约 50 个钱包
  2. 跨链换成 BTC主要经 THORChain，也用了 eXch 和 OKX 的 DEX 聚合器
  3. 再拆散、混币BTC 分散到数万个钱包，部分进入 Wasabi、CryptoMixer
  4. 出金经场外交易（OTC）和 P2P 渠道换成法币或稳定币

这次洗钱最突出的是速度。TRM 统计，事发 48 小时内至少 1.6 亿美元进入洗钱渠道，到 2 月 26 日超过 4 亿美元[13]。Elliptic 记录，最初的约 50 个钱包在 9 天里被逐个清空，最后一个在 3 月 3 日清空；eXch 拒绝了封堵请求，从中赚了数十万美元手续费[12]。3 月 4 日，Ben Zhou 称约 83% 的 ETH 已换成比特币，分散在 6,954 个钱包里[18]。到 4 月 21 日，84.45%（432,748 ETH）已经过 THORChain 换成比特币，仍可追踪的部分变成 10,003 枚 BTC，分散在 35,772 个钱包里，平均每个 0.28 枚[19]。

冻结与追回

能冻结的主要是两类资产：发行方能控制的代币，和流进合规交易所的资金。

  • mETH Protocol 追回 15,000 枚 cmETH（约 4,300 万美元）。协议对提款设有 8 小时延迟，团队在 Polygon CISO Mudit Gupta 和 SEAL 的协助下，在延迟期内暂停合约并把这批 cmETH 转到恢复地址[25]。
  • 事发首日，多家交易所和链上项目按 Bybit 公布的黑名单冻结了约 4,289 万美元[25]。
  • Tether 先冻结 181,000 枚 USDT[25]；2026 年 10 月，又在 ZachXBT 追踪到的一组 Bybit 赃款里冻结 442,000 枚 USDT[24]。
  • 2026 年 8 月，美国法院对部分匿名被告持有的赃款下达初步禁令，报道没有披露金额[26]。

按 Bybit 自己的口径，冻结比例在 3 月 4 日约为 3%[18]，4 月 21 日为 3.84%[19]。crypto.news 转述的 3 月下旬数字是可追踪 88.87%、无法追踪 7.59%、冻结 3.54%，和前后两组数字衔接不上，可能是统计口径不同[27]。截至 2026 年 10 月，本页没有查到大额追回的公开报道；按已公布的冻结比例，九成五以上的被盗资产没有追回。

影响

挤兑与偿付

Bybit 没有暂停提现。首份公告发出时，70% 的待处理提现已经完成[1]。按 Cointelegraph 的报道，2 月 22 日用户提走了超过 50 亿美元，Hacken 的审计显示储备仍然高于负债[16]。交易所被盗后常见的做法是冻结提现、按比例分摊损失，七个月前的 WazirX 就是这样。Bybit 在三天内补上了约 44.7 万枚 ETH 的缺口，提现没有中断，用户没有承担损失[15]。

朝鲜的年度纪录

Elliptic 统计，朝鲜相关黑客在 2025 年前九个月盗取了超过 20 亿美元，是有记录以来最高的年度金额，接近 2024 年全年的三倍；此前的纪录是 2022 年的 13.5 亿美元，主要来自 Ronin 和 Harmony 两座跨链桥[14]。Bybit 一案的 14.6 亿美元占了其中大半。Elliptic 的判断是，朝鲜的手法正从技术漏洞转向社会工程，“加密安全的薄弱环节越来越多是人，而不是技术”。

谁该负责

Bybit 的说法

两家取证机构都没有发现 Bybit 基础设施被入侵。是 Safe 一名开发者的凭证被盗，攻击者借此进入 Safe{Wallet} 的基础设施，“彻底骗过了签名人”[5]。

Safe 的说法

攻击来自一台被攻破的 Safe{Wallet} 开发者电脑，影响的是 Bybit 运营的一个账户。外部研究者的审查“没有发现 Safe 智能合约或前端与服务源码中的漏洞”[10]。

CoinDesk 援引一位知情人士的话说，如果 Bybit 没有“盲签”，攻击就不可能成功[10]。两种说法都有事实依据：恶意代码确实是从 Safe{Wallet} 的服务器下发的，Bybit 的签名流程也确实没有独立核对交易内容的环节。CoinDesk 指出，这和 2024 年 WazirX 与 Liminal 的互相指责如出一辙。

“中立”基础设施的争论

THORChain 成了这次洗钱的主通道。CoinDesk 援引研究者的数据，约 12 亿美元、85% 的被盗资金经过了 THORChain；3 月 1 日一天的兑换量就超过 10 亿美元，比它平常一个月的量还多[20]。验证者 TCB 说：“当你的大部分流量都是朝鲜偷来的钱，这就成了国家安全问题，不再是游戏。”THORChain 创始人 John-Paul Thorbjornsen 则称自己已不参与 THORChain，并认为“指望这些区块链去审查交易不现实”[21]。一位前美国财政部官员提醒，明知资金来自 Lazarus 还收手续费，可能有违反 OFAC 制裁的风险[20]。

同一种手法的三起事件

事件时间损失被篡改的显示层
WazirX2024-07约 2.3 亿美元托管商 Liminal 提供的签名界面，事后双方互相指责[10]
Radiant Capital2024-10约 5,000 万美元3 名开发者自己的电脑被植入恶意软件[28]
Bybit2025-02约 14.6 亿美元Safe{Wallet} 官方网页，所有用户共用的前端[3]

Sygnia 指出，Safe 开发者电脑被入侵的最早证据晚于前两起事件，所以 WazirX 和 Radiant 看来不是从 Safe{Wallet} 的基础设施开始的[3]。三起事件的共同点是：签名人信任的显示层可以被攻击者控制。区别在于被篡改的是哪一层：Radiant 是开发者自己的电脑，WazirX 是托管商的界面，Bybit 是所有 Safe 用户共用的官方网页。最后一种的影响面最大，攻击者改一个文件，就同时控制了所有用户看到的界面，再让它只对一个目标生效。

后续处置

72 小时补足储备

事发当天，Bybit 称管理的资产超过 200 亿美元，必要时会借过桥贷款[1]。CNBC 报道，到 2 月 24 日，Bybit 通过紧急借款和大额存入获得了近 44.7 万枚 ETH，资金来自 Galaxy Digital、FalconX、Wintermute 等机构；Hacken 的审计确认 BTC、ETH、SOL、USDT、USDC 的储备率都超过 100%[15]。CoinDesk 的数字是：超过 4 亿美元通过 OTC 买入，另有约 3 亿美元从其他交易所调入[18]。同行也伸了手：Bitget 无息、无抵押借给 Bybit 4 万枚 ETH，三天后收回。Bitget CEO Gracy Chen 说：“这只是在帮助一个有困难的同行。”[16]

赏金计划

Bybit 拿出追回金额的 10% 作为赏金，总额上限约 1.4 亿美元：5% 给提供线索的人，5% 给执行冻结的机构，并建立 LazarusBounty 网站公开追踪进展。到 2 月 26 日已向 5 名赏金猎人支付 423 万美元[17]。按 The Block 的报道，协助 mETH 追回资金的 Mudit Gupta 与 SEAL 可得约 430 万美元[25]。两个月里，Bybit 收到 5,443 份线索，其中 70 份被认定有效[19]。

调查与归因

Bybit 请 Sygnia 和 Verichains 取证，两家的初步结论都是 Bybit 基础设施没有被入侵[5]。Safe 请 Mandiant 调查，确认开发者电脑被攻破、AWS 会话被劫持，攻击者是 TraderTraitor，即 Mandiant 追踪的 UNC4899，也叫 Jade Sleet、PUKCHONG[7]。FBI 在事发五天后发布公告，正式认定朝鲜对此负责，并呼吁 RPC 节点运营者、交易所、跨链桥和链上分析公司封堵攻击者正在使用的地址[2]。这是执法机构的认定，不是安全公司根据链上特征做的推测。

Safe 的整改

Safe 称已“完全重建、重新配置了所有基础设施，并轮换了所有凭证”[6]。SecurityWeek 列出的措施包括：轮换所有密钥和凭证、重置集群、更换开发者电脑、重新构建并部署容器镜像、限制外部访问交易服务（Transaction Service），以及为对外服务增加防火墙规则[8]。之后的两项产品改动直接针对签名环节：

  • 2025 年 11 月，Safe{Wallet} 集成 Hypernative 的风险引擎，每笔交易执行前评分，低风险直接放行，可疑的要求额外确认，高风险的直接拦截[29]。
  • 2026 年 10 月，Safe Labs 推出 Policy Engine，通过 Safe 的 Transaction Guard 挂载链上策略合约：收款地址白名单、限额、合约调用白名单，以及对增删签名人、改门槛、启用模块的延时或联签。Safe 的原话是：“不符合策略的交易不能执行，不管有多少签名人批准。”[31]

Transaction Guard 是 Safe v1.3.0 起才有的接口：execTransaction 在核对签名之后、执行之前，调用 Guard 合约的 checkTransaction，Guard 可以拒绝 operation = 1 或白名单之外的目标[33]。v1.1.1 的 execTransaction 里没有这一步[32]。

行业标准

2026 年 5 月 12 日，以太坊基金会发布 Clear Signing 标准，所用的描述格式是 Ledger 发起的 ERC-7730：应用方用统一格式描述“这笔交易会做什么”，钱包据此显示人类可读的确认信息，安全专家再对描述的正确性做审核与背书。Fireblocks、Trezor、MetaMask、WalletConnect 等参与了这项工作[30]。另一类工具在客户端本地重算 Safe 交易哈希，供签名人和 Ledger 屏幕上的值逐位比对，例如 pcaversaccio 维护的 safe-tx-hashes-util[34]。

诉讼与 Bybit 自身

2026 年 8 月，Bybit 在美国哥伦比亚特区联邦地区法院起诉朝鲜、侦察总局和 Lazarus Group，取得一项初步禁令，冻结部分匿名被告持有的被盗资产，案件尚未判决[26]。Ben Zhou 说，Lazarus 的攻击“不只是对 Bybit 的攻击，也是对整个行业信任的攻击”。事发后不久，Bybit 表示正在评估其他托管钱包方案[5]。按 Bybit 2026 年上半年的风控报告，它对冷、温、热钱包和上架代币合约的链上活动做到全覆盖监控，半年里拦截了 3 万多笔可疑提现申请[27]。

教训与防御

按攻击链的顺序，每一环都有事后报告指出的检查可以加上[4][9][11]。这些检查都不新，这次缺的是把它们放在同一条链上。

环节这次发生了什么本可以拦住的检查
开发者电脑高权限员工在工作电脑上运行了陌生人给的 Docker 项目开发与生产权限分离；陌生代码只在隔离环境里跑
云账户偷来的会话令牌绕过了多因素认证短时效凭证；会话绑定设备；对 IAM 枚举、新 MFA 设备注册告警
前端发布S3 上的生产文件被直接替换，两天没人发现只允许 CI 发布；线上文件与构建产物持续比对，不一致立即告警
签名3 名签名人都只看网页，Ledger 上的内容没有核对用另一套工具独立解码交易并模拟执行；硬件钱包上清晰签名
合约一笔 delegatecall 就换掉了整个钱包的逻辑用 Guard 禁止 operation = 1 和白名单外的目标；权限类操作加延时
资金集中一个钱包里放着约 15 亿美元分散存放；限制单笔、单日转出额度；大额转出加时间锁
给交易所和托管方
  • 多签的安全来自签名人彼此独立。至少一名签名人要用不同的工具链核对交易，例如命令行工具或自建解码服务，而不是和其他人用同一个网页。
  • 冷钱包的日常操作应该只有“固定目标的普通转账”。任何 operation = 1、任何白名单外的目标，都按安全事件处理，不签。
  • 不要把全部储备放在一个钱包里。mETH Protocol 靠 8 小时提款延迟追回了 4,300 万美元，时间锁对托管钱包同样有用。
  • 第三方工具是你的攻击面。这次 Bybit 的系统没有被攻破，损失仍然由 Bybit 承担。
给钱包和前端开发者
  • 前端是签名流程的一部分。生产环境的发布权限、构建链和静态资源，要像合约一样审计和监控。
  • 对 delegatecall、改实现合约、改签名人和门槛这类操作，界面和硬件钱包上都要有醒目的警告。
  • 支持 Clear Signing（ERC-7730）这样的标准，让硬件钱包直接显示交易的含义，而不只是一串哈希。
给签名人
  • 硬件钱包屏幕上的内容才是你签的东西，网页只是一个可能被篡改的显示层。看不懂设备上的内容，就不要签。
  • 用独立工具在本地重算 Safe 交易哈希，和硬件钱包上显示的值逐位比对[34]。
  • 在专用、干净的设备上签名。CertiK 建议用加固的专用或隔离设备、每次使用全新的系统环境[4]；safe-tx-hashes-util 的说明建议核对、签名后立即关机[34]。
