Parity 多签钱包两次事故

2017 年，Parity 多签钱包在四个月里出了两次事故，原因都是初始化函数谁都能调用。7 月 19 日，攻击者把三个 ICO 项目的钱包改成自己名下，转走 153,037 枚 ETH；11 月 6 日，所有钱包共用的库合约被人初始化后自毁，587 个钱包里的 513,774 枚 ETH 从此无法动用。2018 年的恢复提案没有通过，这些 ETH 至今仍锁在原地，同类的“未初始化合约被接管”问题此后在可升级合约里反复出现。

概要

Parity 多签钱包分成两层：每个用户部署一个很小的钱包合约，只保存所有者名单、确认数和余额；转账、确认、换所有者这些逻辑都放在一个全网共用的库合约 WalletLibrary 里，钱包用 delegatecall 借用库合约的代码。这样部署一个钱包便宜得多，代价是库合约里的每个公开函数，任何人都能通过任何一个钱包调用，其中包括本该只在创建时执行一次的初始化函数 initWallet。

2017 年 7 月 19 日，有人对三个钱包调用 initWallet，把所有者改成自己，随后转走了 æternity、Swarm City 和 Edgeless 三个 ICO 项目共 153,037 枚 ETH[11][13]。Parity 统计当时共有 596 个钱包存在这个漏洞，其余钱包被自称 White Hat Group（WHG）的白帽团队用同样的方法抢先转空，约 37.7 万枚 ETH 和大量代币随后归还原主[2][13][31]。攻击者的身份至今没有公开。

当晚的修复给 initWallet 加了“已经初始化就拒绝”的检查，但这个检查读的是当前执行环境的存储。7 月 20 日重新部署的库合约本身从没被初始化过。11 月 6 日，GitHub 用户 devops199 直接对库合约调用 initWallet，成了库合约的所有者，接着调用 kill 让它自毁[3][5]。所有钱包的逻辑都在这份代码里，代码没了，587 个钱包里的 513,774.16 枚 ETH 就再也转不出来，其中约 30.6 万枚属于 Web3 Foundation 为 Polkadot 募集的资金[4][29]。devops199 自称是无意触发。

要让这些 ETH 重新可用，只能硬分叉改写链上状态。2018 年提出的 EIP-999 主张把修补过的库合约代码放回原地址，但在代币投票中以 55% 对 39.4% 落败，核心开发者会议也没有推进，2020 年被作者撤回[24][27]。截至 2025 年 7 月的统计，Web3 Foundation 的约 30.6 万枚 ETH 仍锁在 Parity 多签合约里[32]。

背景

Parity Technologies 由以太坊前 CTO Gavin Wood 创立[17][29]，开发的 Parity 客户端自带一个钱包界面，可以一键部署多签合约。多签合约的规则是：转账要有足够多的所有者确认才能执行；低于每日限额的小额转账，单个所有者就能直接发出[8]。2017 年的 ICO 项目普遍把募来的 ETH 放在这类钱包里[11][30]。那一年的 ICO 热潮见大事记的ICO 狂潮（2017–2018）。

这份多签合约并不是 Parity 从零写的。它改编自以太坊基金会 DEV 团队、Parity 和社区共同编写并审计过的“Foundation”多签钱包[2]。原版每建一个钱包都要把全部代码部署一遍。2016 年 12 月合并的 PR #3773 把它拆成两部分：一个只负责转发的小合约（下文称桩合约），加上一个全网只部署一次的 WalletLibrary。按 PR 说明，部署一个钱包的 gas 从约 180–200 万降到约 50 万[9]。这个版本随 2017 年 1 月 19 日发布的 Parity 1.5 上线[15][18]。

漏洞在拆分时就已经存在。Hacking, Distributed 的作者查看提交历史后指出，合约第一次加入仓库时就带着问题代码，3 月 7 日大改过一次，之后直到被攻击都没再动过[13]。Parity 的事后报告解释了它为什么没被发现：库合约的改造夹在一次约 4,000 行、几乎全是 JavaScript、CSS 和 HTML 的钱包界面改动里，被误标成纯界面修改，只经过一人审查就合并了；后来一位 Solidity 专家做的审计也没有发现问题[2]。

两次事故的受害者主要是 ICO 项目方。7 月被盗的三个项目都把募资放在这种钱包里；11 月被冻结的资金中，最大的一笔属于 Web3 Foundation，它在 2017 年 10 月为 Gavin Wood 主导的 Polkadot 募集了约 1.44 亿美元[38]。ETH 价格在 7 月事发时约 200 至 235 美元，11 月约 300 美元[17][20][22]。

漏洞原理

两层结构：存储在钱包，代码在库

每个 Parity 多签钱包是一个很小的合约，只存所有者名单、所需确认数、每日限额和余额。它的构造函数用 delegatecall 让库合约完成初始化；此后钱包不认识的调用，都由 fallback 原样转给库合约。下面引用的是修复前的 v1.6.9 版本[8]，英文注释是原有的，中文注释是本站加的：

// enhanced-wallet.sol（v1.6.9），Wallet 桩合约的 fallback，第 423–430 行
// gets called when no other function matches
function() payable {
  // just being sent some cash?
  if (msg.value > 0)
    Deposit(msg.sender, msg.value);
  else if (msg.data.length > 0)
    _walletLibrary.delegatecall(msg.data);  // 不认识的调用，一律原样转给库合约
}

// 第 448 行：编译期占位地址，部署时换成库合约的真实地址，写死在每个钱包的字节码里
address constant _walletLibrary = 0xcafecafecafecafecafecafecafecafecafecafe;

来源：openethereum/parity-ethereum 仓库 v1.6.9 标签，js/src/contracts/snippets/enhanced-wallet.sol（去掉了一层缩进）。占位地址的替换方式见 PR #3773 的说明。

delegatecall 执行的是库合约的代码，读写的却是钱包自己的存储，msg.sender 也还是最初的调用者，效果相当于把库合约的代码临时贴进钱包里运行[12][13]。这是省 gas 的关键，也意味着库合约里任何一个外部可见的函数，任何人都能通过任何一个钱包调用。

7 月：初始化函数没有看守

库合约里有三个初始化函数：initWallet、initMultiowned、initDaylimit。它们都没写可见性，也没有任何修饰符。在当时的 Solidity 里，不写可见性就默认是 public[13][2]。

// enhanced-wallet.sol（v1.6.9），WalletLibrary 的初始化函数
// 第 107–117 行：没有可见性，也没有修饰符，默认 public
function initMultiowned(address[] _owners, uint _required) {
  m_numOwners = _owners.length + 1;
  m_owners[1] = uint(msg.sender);          // 调用者自己成为 1 号所有者
  m_ownerIndex[uint(msg.sender)] = 1;
  for (uint i = 0; i < _owners.length; ++i)
  {
    m_owners[2 + i] = uint(_owners[i]);
    m_ownerIndex[uint(_owners[i])] = 2 + i;
  }
  m_required = _required;                  // 需要几个确认，由调用者决定
}

// 第 201–204 行：每日限额，同样由调用者决定
function initDaylimit(uint _limit) {
  m_dailyLimit = _limit;
  m_lastDay = today();
}

// 第 216–219 行：本该只在钱包创建时执行一次
function initWallet(address[] _owners, uint _required, uint _daylimit) {
  initDaylimit(_daylimit);
  initMultiowned(_owners, _required);
}

来源：同上，v1.6.9 标签（去掉了一层缩进）。

钱包合约自己没有叫 initWallet 的函数。有人对一个已经在用的钱包调用它，调用就落进 fallback，经 delegatecall 进入库合约执行，改写的正是这个钱包自己的所有者名单。只要 initWallet 检查一下“是否已经初始化过”，这条路就走不通；两个辅助函数则本该标成 internal[13][11]。

拿到所有权之后，转钱只差一步。execute 只要求调用者是所有者之一；如果是不带数据的普通转账且金额在当天限额以内，或者钱包只要求一个确认，就立即执行，不用等其他所有者：

// enhanced-wallet.sol（v1.6.9），第 230–233 行
function execute(address _to, uint _value, bytes _data)
    external onlyowner returns (bytes32 o_hash) {
  // first, take the opportunity to check that we're under the daily limit.
  if ((_data.length == 0 && underLimit(_value)) || m_required == 1) {
    // yes - just execute the call.

来源：同上，函数头折成两行显示。onlyowner 只检查调用者在不在所有者名单里。

OpenZeppelin 当天解码了攻击者对其中一个钱包发出的两笔调用[11]。initWallet 的所有者名单里只有攻击者的地址，_required 是 0，_daylimit 是十六进制的 0x116779808c03e4140000 wei；紧接着的 execute 向攻击者转出同样的数额，数据为空。这个数换算过来是 82,189 ETH，和 æternity 公布的约 8.2 万枚被盗 ETH 相符[17]。也就是说，攻击者把“每日限额”设成了钱包的全部余额，整笔提款就成了一笔“限额以内”的普通转账。每个钱包只需要两笔交易。

当晚的修复

PR #6102 加了一个修饰符：所有者数量大于 0 就拒绝初始化；PR #6103 随后让两个辅助函数也使用它[9]。修复后的版本：

// enhanced-wallet.sol（v1.7.0，修复后），第 214–222 行
// throw unless the contract is not yet initialized.
modifier only_uninitialized { if (m_numOwners > 0) throw; _; }

// constructor - just pass on the owner array to the multiowned and
// the limit to daylimit
function initWallet(address[] _owners, uint _required, uint _daylimit) only_uninitialized {
  initDaylimit(_daylimit);
  initMultiowned(_owners, _required);
}
// initMultiowned（第 107 行）和 initDaylimit（第 201 行）也加上了 only_uninitialized

来源：openethereum/parity-ethereum 仓库 v1.7.0 标签，同一文件。

Parity 同时在链上注册表里注销了旧库合约，新建的钱包不会再用到它[2]。已经部署的钱包没法这样修：库合约的地址写死在它们的字节码里，只能由 WHG 先把资金转出，再逐个部署替换合约[14]。

11 月：库合约自己从未初始化

only_uninitialized 检查的是 m_numOwners，而这个变量从哪份存储里读，取决于代码在哪个合约的上下文里执行。经由钱包调用时，delegatecall 读的是钱包自己的存储，已初始化的钱包会被拒绝，7 月的修复针对的就是这种情况。

库合约本身也是一份独立部署的合约，有自己的存储。7 月 20 日部署之后，从来没有人直接对它调用过 initWallet，所以它自己的 m_numOwners 一直是 0。任何人直接调用库合约的 initWallet，都能通过检查[12][3]。Parity 的事后报告解释，为了尽量贴近经过审计的原版合约，库合约保留了普通钱包的全部功能，所以它需要初始化，也保留了用来“退役”钱包的自毁函数 kill[5]。

kill 需要多签确认，但需要几个确认，是初始化时由调用者自己填的。issue #6995 下的分析指出，devops199 初始化库合约时，把所需签名数填成了 0[10]。确认逻辑把“剩余所需确认数不超过 1”当作已经满足，于是第一次调用 kill 就直接执行了：

// enhanced-wallet.sol（v1.7.0，即 7 月修复后的版本）
// 第 225–227 行：库合约保留了原版钱包的自毁函数
function kill(address _to) onlymanyowners(sha3(msg.data)) external {
  suicide(_to);                      // 直接对库合约调用时，删除的是库合约自己的代码
}

// 第 91–94 行：多签修饰符，先调用 confirmAndCheck
modifier onlymanyowners(bytes32 _operation) {
  if (confirmAndCheck(_operation))
    _;
}

// confirmAndCheck 第 297 行：新操作的“剩余所需确认数”取自 m_required
pending.yetNeeded = m_required;      // devops199 初始化时 m_required 填的是 0
// 第 308–309 行
// ok - check if count is enough to go ahead.
if (pending.yetNeeded <= 1) {        // 0 ≤ 1，第一次确认就放行

来源：openethereum/parity-ethereum 仓库 v1.7.0 标签，js/src/contracts/snippets/enhanced-wallet.sol（节选，去掉了缩进）。这几行在 7 月的修复中没有改动。

自毁之后，库合约地址上不再有代码，而 587 个钱包的 fallback 仍然把调用转给这个地址。对没有代码的地址做 delegatecall，什么也不会执行[12]。Parity 的警报写道，这些钱包现在实际上只剩一个记录收款事件的 fallback[3]：转账、确认、换所有者都做不了。钱包自己的 kill 同样写在库合约里，所以连“销毁钱包、把余额退给所有者”这条路也断了。issue 里有用户试过让三个所有者一起调用 kill，没有任何效果[10]。

两次事故的异同

7 月 19 日：被盗

对象是已经在用的钱包，调用经 fallback 转给库合约。用到的函数是 initWallet 加 execute。3 个钱包被转空，共 153,037 枚 ETH；其余钱包里的资金被白帽抢先转出，后来归还[2][31]。

11 月 6 日：冻结

对象是库合约本身，直接调用。用到的函数是 initWallet 加 kill。库合约的代码被删除，587 个钱包里共 513,774.16 枚 ETH 转不出来，没有人从中获利[4]。

哪一步本可以拦住

两次事故是同一个问题：初始化函数谁都能调用。7 月的补丁默认“未初始化”只会发生在刚创建的钱包上，没有想到库合约自己也处在这个状态。按时间顺序，至少有四处可以拦住：

  1. 拆分合约时，让 initWallet 检查自己是否已经初始化过，或者不让它被外部调用。Hacking, Distributed 指出，做到其中任何一项，7 月的攻击都不会发生[13]。当晚的 PR #6102 采用了前一种，同时把两个辅助函数改成 internal[9]。
  2. 7 月部署新库合约后，立刻对它自己调用一次 initWallet，或者去掉库合约里的 kill。Parity 的事后报告承认，这两件事做到任何一件，11 月的事故都能避免[5]。
  3. 8 月那条“部署时就初始化”的建议，本该当作安全修复尽快单独部署，而不是等下一次例行更新[5]。
  4. 让库合约的每个改状态函数先检查当前地址是不是库合约自己，只允许经由 delegatecall 调用。这是 OpenZeppelin 在 11 月提出的办法[12]。

攻击过程

7 月 19 日：两笔交易接管一个钱包

  1. 选定目标攻击者挑了三个余额很大的多签钱包，分别属于刚完成 ICO 的 æternity、Swarm City 和 Edgeless[13]。
  2. 改写所有者对每个钱包调用 initWallet，把所有者换成自己。OpenZeppelin 解码的那一笔里，所有者只填了攻击者，确认数填 0，每日限额填成钱包的全部余额[11]。
  3. 转走余额调用 execute，把余额全部转到攻击者地址 0xb3764761e297d6f121e79c32a65829cd1ddb4d32。三个钱包合计被转走 153,037 枚 ETH[11][15]。
  4. 被发现Swarm City 的团队发现钱包被清空，通知了以太坊基金会和多个开发团队，很快确定问题出在 Parity 多签代码上[15]。
  5. 白帽抢先漏洞利用非常简单，攻击者随时可能继续。WHG 决定用同样的两步把能找到的易受攻击钱包全部抢先转空，资金进入地址 0x1dba1131000664b884a1ba238464159892252d3a，所需 gas 打算用当年 The DAO 救援收到的捐款支付[14]。另有一名不属于 WHG 的白帽独立转出了将近 150 万美元的资产[14]。

11 月 6 日：两笔调用，库合约消失

  1. 成为库合约的所有者devops199 直接对库合约 0x863df6bfa4469f3ead0be8f9f2aae51c91a907b4 调用 initWallet。库合约自己的所有者数量是 0，检查通过；所需签名数填的是 0[5][10]。
  2. 自毁调用 kill。确认数为 0，第一次调用就执行了 suicide，库合约的代码被删除[5]。
  3. 公开UTC 15:54，GitHub 上出现 issue #6995，写道“I accidentally killed it.”。Parity 的事后报告说，发帖的 devops199 据称就是触发者[10][5]。
  4. 补充说明第二天，devops199 在同一个 issue 里说：自己本来不是库合约的所有者，因为它没有初始化，才能把自己设成所有者；并贴出了依赖这个库合约的钱包清单[10]。
意外还是故意，说法不一

devops199 自称是意外。Parity 的安全警报也写“据目前了解是意外触发”；一周后的事后报告开头却写这名用户“决定利用这个漏洞”，后文又说 devops199“选择”初始化库合约、“选择”把它杀死[3][5]。《卫报》采信了意外的说法，说此人删掉代码是想挽回局面[21]。这个 GitHub 账户后来已经注销，现在显示为 ghost[10]。本页查到的公开资料里，没有执法机构立案或认定其身份的报道。

影响

受害的是 ICO 项目的金库

两次事故打在同一类钱包上，也就打在同一类人身上。Swarm City 钱包里的 44,055 枚 ETH 全部被盗[15]。Edgeless 联合创始人 Tomas Draksas 2021 年说，被盗发生在项目刚上线时，此后一直限制着项目的规模[30]。11 月的冻结锁住了 Web3 Foundation 为 Polkadot 募集的资金中相当大的一部分[38]，较小的项目如 Cappasity 也有 3,264 枚 ETH 被锁[23]。

Parity 的调整

11 月事故后，Parity 停止在钱包界面里部署多签钱包，转而默认使用 WHG 的合约，并委托外部机构审计密钥生成、密码管理、签名和自动更新等敏感代码[5][10]。事后报告还建议，像航空和医疗行业那样，每次部署合约都按检查清单走，并持续比对链上合约和仓库里最近一次审查过的版本[5]。2018 年 4 月，Parity 宣布多签钱包已经“退役”，写合约时改用更严格的测试、部署流程和第三方审计要求，审计合作方是 Trail of Bits[7]。

Solidity 的默认可见性

两份事后分析都把一部分责任归到 Solidity 的设计上：函数不写可见性就默认 public。Parity 建议改成默认 private，或者干脆禁止既没有访问修饰符也没有看守修饰符的函数；Hacking, Distributed 提出了同样的建议[2][13]。Solidity 0.4.17（2017 年 9 月）开始对没写可见性的函数发出警告，0.5.0（2018 年 11 月）起必须显式写明[34]。

“未初始化的合约被接管”反复出现

Parity 的“桩合约加库合约”，就是后来“代理加实现合约”模式的早期形态：代理保存状态，实现合约提供逻辑，构造函数换成一个可以从外部调用的初始化函数。实现合约自己没被初始化、可以被别人接管，这个问题后来多次重演。OpenZeppelin 的合约库文档专门警告：未初始化的合约可能被攻击者接管，这既适用于代理，也适用于它背后的实现合约，并可能波及代理[35]。

事件时间问题结果
OpenZeppelin UUPSUpgradeable2021-09未初始化的实现合约可被他人初始化，成为升级管理员后让实现合约自毁，所有依赖它的代理随之失效披露前 OpenZeppelin 抢先初始化了 150 多个这类合约，4.3.2 版修复[36]
Wormhole 以太坊核心合约2022-02实现合约未初始化，存在被自毁、锁住用户资金的风险白帽报告，当天修复，支付 1,000 万美元赏金，无资金损失[37]
Nomad 跨链桥2022-08一次升级把“可信根”初始化成 0x00，未经证明的消息被当作有效桥在几小时内被搬空

Wormhole 这次是 2 月 24 日报告的未初始化问题，和同月早些时候 Wormhole 被盗是两个不同的漏洞。Nomad 的方向与 Parity 相反：不是没有初始化，而是初始化写进了一个错误的值。

SELFDESTRUCT 被削弱

2024 年 3 月的 Dencun 升级包含 EIP-6780：除非在创建合约的同一笔交易里调用，SELFDESTRUCT 只转走余额，不再删除代码和存储[33]。按新规则，一个早已部署的库合约已经不可能被删掉。这项改动主要是为 Verkle 树做准备[33]，并不是针对 Parity 的补丁，也不会让 2017 年被删除的代码回来。

后续处置

从 EIP-156 到 EIP-999

11 月 13 日，Parity 说团队在找一个能被广泛接受的解冻方案，并提到 Vitalik Buterin 早先提出的 EIP-156[4]。12 月的文章承认，EIP-156 只能让私钥持有者取回几类卡住的 ETH，覆盖不了这次的情况：被冻结的钱包合约自己还有代码，没了的只是库合约，而且它取不回 ETH 以外的代币。Parity 另外列了两条路：针对具体地址的 ETH 和代币恢复；修改协议，允许已自毁的合约复活[6]。后一类改动 EVM 语义的提案，后来被认为副作用太大[24]。

2018 年 4 月，Afri Schoedon 提交 EIP-999。它不改 EVM 的规则，只在某个硬分叉区块做一次性的状态变更：把库合约地址上的代码换成一个修补过的版本，新版本既不能被认领，也不能被杀死；ETH 总量不变，也不转移任何资产[24][25]。

为什么没有通过

支持的理由

资金归属没有争议：ETH 一直在受害者自己的钱包里，恢复只是把被删掉的代码放回原处，不动任何人的余额。Vitalik 在核心开发者会议上也说，技术上这个提案风险低，能达到目的[24][28]。

反对的理由

道德风险和先例：为一家公司的一个合约改写链上状态，等于默许“大到不能倒”，以后每次事故都会有人来要同样的待遇。也有人认为，合约有多不可变，取决于它自己的设计，Parity 的钱包本来就写死了一个后来被删除的库地址。还有分裂的风险：有争议的硬分叉可能像 2016 年那样再分出一条链[26][28]。

etherchain 的代币投票里，按投票地址的 ETH 余额加权，反对 55.0%，赞成 39.4%[27]。EIP-999 的作者在讨论帖里说自己不认可这次投票[26]。投票的公平性也受到质疑。CCN 转述社交媒体上的批评：合约的创建者可以替合约里的资金投票，Polkadot 因此能用被冻结的 30.6 万枚 ETH 投赞成票[29]；Vitalik 在会上指出，这种签名投票让合约钱包和硬件钱包的持有者很难参与，一次代币投票本身不能算社区共识[28]。

4 月 20 日的核心开发者会议上，Vitalik 认为这更多是社会层面的取舍，应当交给社区讨论；除非有很高的把握最终会被采纳，比如 75% 以上，否则不值得投入开发。Nick Johnson 说，如果导致分裂，代价会远超好处。Péter Szilágyi 认为 Parity 团队自己就握有大量 ETH，会左右投票结果。会议没有结论[28]。4 月 26 日，Parity 发表声明，向至今无法取用 ETH 的用户道歉，并表示无意分裂以太坊链[7]。此后 EIP-999 没有进入任何一次硬分叉。2019 年 12 月，作者提交撤回请求，理由只有一句：不再有意恢复这个地址上的代码[25]。

和 The DAO 有什么不同

The DAO 的硬分叉，是在锁定期内把钱从攻击者手里拿回来。这一次没有获利的一方，钱一直在受害者自己的钱包里，“恢复”实际上是为一个项目改写一份特定合约。核心开发者会议上，Piper Merriam 认为不该拿 The DAO 类比，理由是 The DAO 是网络的安全问题；Vitalik 不同意这个定性[28]。Alex Van de Sande 在同一次会议上说，The DAO 分叉当时的共识比这次清楚，仍然留下了一条至今还在运行的链，所以这次分裂几乎无法避免[28]。

7 月的攻击者

7 月的攻击者至今没有被公开认定。Hacking, Distributed 在事发三天后就判断，这笔钱大概率追不回：The DAO 的资金有锁定期，社区有时间讨论分叉；这一次攻击者立刻拿到了 ETH，只要找到肯收的交易所，或者换成 ZEC，就能保住所得。文章发出时，攻击者已经通过 Changelly 换出约 50 枚 ETH[13]。

此后资金大多没有动，直到 2021 年 6 月，受害方发现攻击者开始把部分 ETH 转入交易所[30]。同年 10 月，三个项目联合发文，点名 8 家收到赃款的交易所，要求冻结并归还；同时向攻击者提出，归还 135,000 枚 ETH 就不再追究，剩下的约一成按当时价格约值 5,800 万美元[31][30]。The Defiant 报道，有交易所已经初步同意归还，正在做法律和身份核查[30]。本页没有查到攻击者接受条件、交易所实际归还或执法机构立案的后续公开报道。

冻结资金的现状

EIP-999 撤回后，再没有获得广泛支持的恢复方案。2025 年 7 月，Coinbase 产品负责人 Conor Grogan 统计约 91.2 万枚 ETH 已被证实永久无法取用，报道列出的几笔大额损失中，排在第一位的就是 Web3 Foundation 用过的 Parity 多签合约里的约 30.6 万枚[32]。本页没有找到这笔钱此后发生变化的报道。

教训与防御

给合约开发者
  • 初始化函数必须只能执行一次，并且和部署放在同一笔交易里完成。部署和初始化之间留出的空档，就是 11 月的事故窗口，前后有三个半月。
  • 库合约、代理背后的实现合约也有自己的存储，部署时就要锁住：在构造函数里调用 OpenZeppelin 的 _disableInitializers()[35]，或者让每个改状态的函数检查自己是不是经由 delegatecall 被调用。
  • fallback 不要把任意调用原样转给库合约，只转发明确列出的函数[11]。
  • 不要在被大量合约依赖的代码里留自毁这类全局开关。EIP-6780 之后 SELFDESTRUCT 仍会转走余额，而且已被标为弃用，新合约不该再用[33]。
  • 每个函数都写明可见性。今天的编译器会强制要求写，但 internal、external、public 选错了一样危险。
// 示意：用今天的写法，一份给代理共用的逻辑合约至少要做到这几点
contract WalletLogic is Initializable {
    address private immutable self = address(this); // 部署时记下自己的地址

    constructor() { _disableInitializers(); }  // 实现合约自己永远不能被初始化

    modifier onlyDelegateCall() {
        // 直接调用实现合约时，address(this) 就是 self，拒绝
        require(address(this) != self, "direct call");
        _;
    }

    function initialize(address[] calldata owners, uint256 required)
        external initializer onlyDelegateCall   // 只能经由代理调用，且只能一次
    { /* …… */ }

    // 不提供任何自毁函数
}

示意代码，不是 Parity 的修复。Initializable 和 _disableInitializers() 来自 OpenZeppelin Contracts；onlyDelegateCall 对应 OpenZeppelin 2017 年 11 月提出的“检查当前地址是不是库合约自己”，以及它在 2021 年 UUPS 修复中加的 onlyProxy[12][36]。

给开发团队
  • 审查强度按改动内容定，不按 PR 标题定。任何改动 .sol 文件的提交都要由合约专家审查；Parity 的库合约改造夹在界面改动里，只审了一次[2]。
  • 涉及已部署合约安全的建议，要当作修复处理，不能当作便利性改进。8 月那条“部署时就初始化”的建议被归为后者，三个月后出了事[5]。
  • 部署要有检查清单，部署后要持续核对：链上的代码和关键状态（所有者、是否已初始化）是否和审查过的版本一致。
  • 修一个漏洞时，把通往同一个函数的所有调用路径都过一遍。7 月的修复堵住了“经由钱包调用”，没有堵住“直接调用库合约”。
给用多签保管资金的项目方
  • 多签只保证“谁能批准转账”，不保证钱包依赖的外部代码没有问题。使用前要弄清钱包会 delegatecall 到哪份合约、那份合约由谁控制、能不能被销毁或升级。
  • 不要把大额资金全部放在依赖同一份实现合约的钱包里。11 月的 587 个钱包，是因为共用一个库合约而一起失效的。
  • 不要指望出事后靠协议层面救援。EIP-999 的结局说明，为个别项目改写链上状态，很难再得到社区的支持。
