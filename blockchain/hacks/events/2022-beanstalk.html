Beanstalk 闪电贷治理攻击

2022 年 4 月 17 日，攻击者用闪电贷借来约 10 亿美元，存进 Beanstalk 换成投票权，在同一笔交易里投票并执行了自己前一天提交的提案，把协议金库转给了自己。攻击者带走约 7,600 万美元，协议的损失按不同口径在 7,700 万到 1.82 亿美元之间。这起事件说明，只按当前余额计票的链上治理，投票权本身就可以借来。

概要

Beanstalk 是以太坊上的算法稳定币协议，由持有 Stalk 的存款人对改进提案（BIP）投票。普通提案要投 7 天；另有一条紧急通道 emergencyCommit：提案提交满 1 天、赞成票达到当前全部投票权的三分之二，任何人都可以立即执行它[7]。投票权按投票那一刻的存款计算，没有快照，也没有锁定期[8]。

攻击者在 4 月 16 日用少量存款提交了两个提案：BIP-18 把协议资产转给攻击者合约，BIP-19 向乌克兰捐款地址转钱[10][11]。一天后，攻击者从 Aave、Uniswap V2 和 SushiSwap 闪电借出约 10 亿美元的资产，换成可以存进 Beanstalk 的 Curve LP 代币存入，瞬间拿到约 79% 的投票权，随即调用 emergencyCommit 执行 BIP-18[10][11]。协议的资产被转走，闪电贷还清，剩下的约 24,830 枚 ETH 进了 Tornado Cash[12]。

Beanstalk 暂停了约四个月，用名为 Barn Raise 的公开募资重新筹集被盗的约 7,700 万美元非 Bean 资产，2022 年 8 月 6 日重启，链上治理改为社区多签[2][5]。到重启时，Barn Raise 只募到约 1,700 万美元[6]。攻击者身份至今没有公开认定。

背景

Beanstalk 由化名 Publius 的匿名开发者在 2021 年 8 月 6 日部署到以太坊主网[3]，Publius 在攻击后公开表示自己是一个三人团队[12]。它的稳定币 BEAN 不靠抵押品，而是靠“借款给协议换取 Pods”“存款换取 Stalk 和利息”这一套激励把价格维持在 1 美元附近。按 Beanstalk Farms 的说法，攻击前约八个月里 BEAN 市值涨到约 1 亿美元，吸引了约 1.44 亿美元的长期激励流动性；攻击前两周还向债权人偿还了约 2,500 万美元[2]。

协议从第一天起就由 Beanstalk DAO 通过链上治理拥有[2]。用户把 BEAN 或白名单里的 LP 代币存进名为 Silo 的模块，就得到 Stalk，Stalk 就是投票权。合约内部用 roots 记录每个账户的投票权，计票时拿提案获得的 roots 除以当前的 roots 总量[8]。可以存进 Silo 的资产包括 BEAN 与 3CRV、BEAN 与 LUSD 组成的两个 Curve 池的 LP 代币。CertiK 认为，正是这些能用闪电贷大量制造的 LP 代币，让投票权变得可以借来[10]。

Beanstalk 的合约由 Omniscia 审计过。事发后各方对审计范围的说法不一：CoinDesk 转述 Omniscia 称，审计完成于闪电贷漏洞被引入之前[13]；rekt.news 称 Omniscia 表示这次攻击不在审计范围内，但审计报告里有对治理合约的评论[12]；Halborn 的说法是被利用的治理功能在上线前没有经过审计[11]。本站查了代码历史：emergencyCommit 和“1 天、三分之二”这两个参数在 2021 年 8 月的首个版本里就已存在[9]，2022 年 4 月 1 日的“Omniscia 审计更新”提交只是把它的执行逻辑重构成了一个内部函数[7]。来源没有说明“被引入的漏洞”具体指哪一次改动。

漏洞原理

Beanstalk 的治理合约里有两条执行路径。commit 是普通路径：投票期（168 个 Season，约 7 天）结束后，赞成票过半即可执行。emergencyCommit 是紧急路径，下面是攻击前最后一个版本的代码[7]：

// GovernanceFacet.sol（提交 ee4720c，2022-04-01），紧急执行
function emergencyCommit(uint32 bip) external {
    require(isNominated(bip), "Governance: Not nominated.");
    require(
        block.timestamp >= timestamp(bip).add(C.getGovernanceEmergencyPeriod()),
        "Governance: Too early.");   // 只要求提案提交满 1 天
    require(isActive(bip), "Governance: Ended.");
    require(
        bipVotePercent(bip).greaterThanOrEqualTo(C.getGovernanceEmergencyThreshold()),
        "Governance: Must have super majority."
    );   // 当前投票权的三分之二
    _execute(msg.sender, bip, false, true);   // 立即执行提案里的任意代码
}

// C.sol（同一提交），相关常量
uint32 private constant GOVERNANCE_PERIOD = 168; // 168 seasons = 7 days
uint32 private constant GOVERNANCE_EMERGENCY_PERIOD = 86400; // 1 day
uint256 private constant GOVERNANCE_PASS_THRESHOLD = 5e17; // 1/2
uint256 private constant GOVERNANCE_EMERGENCY_THRESHOLD_NUMERATOR = 2; // 2/3
uint256 private constant GOVERNANCE_EMERGENCY_THRESHOLD_DEMONINATOR = 3; // 2/3

来源：BeanstalkFarms/Beanstalk 仓库提交 ee4720c，protocol/contracts/farm/facets/GovernanceFacet/GovernanceFacet.sol 第 180–191 行、protocol/contracts/C.sol 第 43–47 行，去掉了一层缩进，把行尾注释移到了单独位置[7]。

1 天的等待从提案提交时算起，而不是从投票结束时算起。攻击者提前一天提交提案，这个条件到攻击时已经满足。剩下的唯一门槛是三分之二的票，问题就在票怎么算：

// VotingBooth.sol（同一提交），投票时把账户当前的 roots 加到提案上
function recordVote(address account, uint32 bipId) internal {
    s.g.voted[bipId][account] = true;
    s.g.bips[bipId].roots = s.g.bips[bipId].roots.add(balanceOfRoots(account));
}

// Bip.sol（同一提交），赞成比例 = 提案获得的 roots ÷ 此刻的 roots 总量
function bipVotePercent(uint32 bipId) internal view returns (Decimal.D256 memory) {
    return Decimal.ratio(rootsFor(bipId), totalRoots());
}

function balanceOfRoots(address account) internal view returns (uint256) {
    return s.a[account].roots;   // 账户当前的存款份额，没有快照
}

来源：同一提交的 VotingBooth.sol 第 32–35 行、Bip.sol 第 151–153 行与第 188–190 行[8]。

这几行合在一起，意味着投票权就是投票那一刻的存款份额。没有“提案创建时的余额快照”，也没有“存入后多久才能投票”的锁定期。只要在同一笔交易里先存入、再投票、再执行，借来的钱和自己的钱没有区别。据 CoinDesk 转述，Beanstalk 的项目负责人事后在 Discord 中写道：“Beanstalk 没有用抗闪电贷的方式计算 Stalk 的占比……这就是让攻击者得手的缺陷。”（本站译文）[13]

1 天的等待为什么没起作用

紧急通道要求提案提交满 1 天，本意是给社区留出发现恶意提案的时间。Halborn 指出，这个恶意提案在这一天里没有被注意到[11]。rekt.news 还发现，攻击者把向乌克兰捐款的那个提案也命名为“Bip18”，两个提案看起来很像[12]。更根本的问题是等待期从提交时算起：攻击者提前一天提交，等待期在投票开始之前就已经过完了，投票、计票、执行之间没有任何间隔。

哪一步本可以拦住

// 示意：两处改动，任何一处都能让闪电贷借来的票失效（不是 Beanstalk 的代码）
function vote(uint32 bipId) external {
    Bip storage b = bips[bipId];
    // 一：按提案创建那个区块的余额计票，之后才存入的资产不算
    uint256 weight = rootsAt(msg.sender, b.snapshotBlock);
    b.roots += weight;
}

function emergencyCommit(uint32 bipId) external {
    Bip storage b = bips[bipId];
    // 二：投票结束后再等一段时间才能执行，投票和执行不能在同一笔交易里
    require(block.timestamp >= b.votingEndedAt + EXECUTION_DELAY, "too early");
    require(b.roots * 3 >= totalRootsAt(b.snapshotBlock) * 2, "no supermajority");
    _execute(bipId);
}

示意代码。rekt.news 的评论是，给链上治理提案的执行加上延迟，是防止这类攻击的一种办法[12]。

攻击过程

下面按 CertiK、rekt.news 和 Halborn 发表的分析转述攻击的结构[10][11][12]，只写到结论层面。

  1. 提前一天提交提案攻击者的资金经 Synapse 跨链桥转入，rekt.news 称最初来自 Tornado Cash[12]。攻击者存入少量 BEAN，取得提案资格（提案门槛是全部 Stalk 的 0.1%[7]），提交了 BIP-18 和 BIP-19。
  2. 闪电贷借入约 10 亿美元第二天，攻击者在一笔交易里从 Aave 借出约 3.5 亿 DAI、5 亿 USDC 和 1.5 亿 USDT，从 Uniswap V2 借出约 3,200 万 BEAN，从 SushiSwap 借出约 1,160 万 LUSD[12]。
  3. 换成投票权这些资产被加进 BEAN 的两个 Curve 池，得到的 LP 代币存进 Silo，攻击者因此拿到约 79% 的投票权[11]。
  4. 投票并立即执行攻击者为 BIP-18 投票，赞成票超过三分之二，随即调用 emergencyCommit。BIP-18 附带的初始化合约把 Silo 中的 BEAN 和各种 LP 代币转给了攻击者合约[10]。BIP-19 也被执行，25 万 USDC 转到了乌克兰的加密货币捐款地址[10][13]。
  5. 还贷离场攻击者撤出流动性、还清闪电贷，把剩下的资产换成 ETH。约三小时后，约 24,849 枚 ETH 被转入 Tornado Cash[10]。
乌克兰捐款是 BEAN 还是 USDC

CertiK 和 CoinDesk 转述的 PeckShield 都说捐出的是 25 万美元的稳定币，CertiK 写明为 250,000 USDC[10][13]；rekt.news 引述的早期分析则说 BIP-19 转出的是“价值 25 万美元的 BEAN”[12]。本页采用前者。

影响

对 Beanstalk

BEAN 当天较 1 美元的锚定价跌去约 86%[13]，协议暂停了近四个月，链上治理被整体移除[2]。DefiLlama 记录的 Beanstalk 锁仓量从攻击前一天的约 3,200 万美元变为 0[14]，这个数字和 Beanstalk 自己说的 1.44 亿美元激励流动性统计口径不同，只能看出变化的方向。

对链上治理

闪电贷在此之前主要被用来操纵价格，比如 2020 年的 bZx。Beanstalk 证明它也能用来买下一次投票：只要投票权按当前余额计算、投票和执行之间没有间隔，治理代币就可以在一笔交易里借来、用完、还掉。DefiLlama 把这起事件单独归为“Flashloan Governance Attack”[14]。同年 10 月的 Mango Markets 事件里，攻击者则用治理提案和 DAO 谈判归还金额，治理被以另一种方式卷了进来。

Halborn 在复盘里指出，攻击同样暴露了运维问题：1 天的等待本来是留给人发现恶意提案的，但没有人在看[11]。rekt.news 的评论是，这次事件也许会促使代币持有人更仔细地盯治理提案，而普通用户往往以为被大力宣传的项目自然有更有经验的人在盯着[12]。

后续处置

当天的应对

Beanstalk Farms 收到警报后关闭了链上治理并暂停协议，随后销毁了攻击者合约里剩余的 BEAN[1]。为避免被怀疑监守自盗，化名 Publius 的创始人在 Discord 中公开了身份，表示是一个三人团队[12]。

Barn Raise：用借款重启

2022 年 5 月 25 日，Beanstalk Farms 公布重启方案[2]。核心是 Barn Raise：协议向出资人借入约 7,700 万美元，用来补回 Silo 里被盗的非 Bean 资产。出资人按每枚 1 USDC 购买名为 Fertilizer 的代币，年化利率（Humidity）从 500% 起，重启几周后降到 20%；重启后新铸出的 BEAN 有三分之一用来偿还 Fertilizer[2][4]。攻击前的 BEAN 和 LP 变成 Unripe 资产，按 Fertilizer 的售出比例和已偿还比例逐步解锁，提前兑换要承担折扣[4]。DAO 通过的方案名为 BFP-72《The Path Forward, No Haircuts》，即不对攻击前的资产直接打折[6]。

Barn Raise 从 6 月 6 日开始[4]。到 8 月 4 日 BIP-21 获得绝对多数时，共募到约 1,700 万美元，不到目标的四分之一[6]。8 月 5 日执行 Replant，合约所有权从 Publius 转给 Beanstalk Community Multisig，Humidity 降到 250%；8 月 6 日，即部署一周年当天，协议恢复运行[5][14]。攻击前持有人的损失并没有当场补回，而是取决于此后 Fertilizer 的销售和偿还进度。

治理和安全的改动

重启后，Beanstalk 由一个九人的社区多签管理，提案改在 Snapshot 上投票，作为开发出安全的去中心化治理之前的临时措施。重启前，Halborn 和 Trail of Bits 分别做了全面审计，项目还在 Immunefi 上设立了漏洞赏金[2][15]。

此后

DefiLlama 记录 Beanstalk 在 2024 年 10 月迁移到 Arbitrum[14]，截至 2026 年 9 月，它的 GitHub 仓库仍有维护提交[7]。截至 2026 年 10 月，本站没有查到攻击者被公开认定或起诉的信息，也没有查到被盗 ETH 被追回的记录。

教训与防御

给治理合约的设计者
  • 投票权按提案创建时的快照计算，不要用投票那一刻的余额。快照之后才存入的资产，无论来自哪里，都不该有投票权。
  • 执行延迟从投票结束起算，而且不能被“紧急”通道绕过。投票和执行至少不能发生在同一笔交易里。
  • 紧急通道只用来做防御性的动作，比如暂停。emergencyCommit 能执行任意代码、转走全部资产，等于给“临时凑够三分之二的人”留了一把万能钥匙。
  • 给新的存款资产授予投票权时，要重新评估治理的安全假设。能用闪电贷大量制造的 LP 代币，不该直接换算成投票权[10]。
给社区和监控
  • 等待期只有在有人盯着的时候才有用。新提案的初始化代码应当被自动解析，异常的资产转移要触发告警。
  • 提案的名称和内容要能对上。这次两个提案用了几乎相同的名称[12]。
  • 审计报告要写清楚覆盖了哪个版本、哪些模块。这次各方对审计范围的说法互相矛盾[11][12][13]，用户无从判断。
