区块链被盗事件编年史

总览　/　2026 年　/　十亿美元级失守与信任链

Coldcard 随机数缺陷

2026 年 7 月 30 日（UTC）起，用 Coldcard 硬件钱包生成的数千个比特币地址被分几波扫空，到 8 月下旬统计约 1,790 枚 BTC，事发时价值约 1.15 亿美元。设备从来没有被入侵：2021 年 3 月的一次固件改动让种子生成用上了一个只靠芯片编号和计时器初始化的软件伪随机数生成器，攻击者在离线状态下就能把种子算出来。编译、链接和代码审查都没有发现这个问题，它在开源代码里存在了五年多。

概要

Coldcard 的设计是只用主控芯片 STM32 的硬件真随机数发生器（TRNG）生成种子。2021 年 3 月，固件把加密运算迁移到新库 libNgU，种子生成随之改走 libNgU 的随机数接口；由于一个构建配置错误，这个接口实际链接到的是 MicroPython 自带的软件回退生成器 Yasmarang，而它的初始状态只来自芯片编号和时钟寄存器[2][7]。编译和链接都没有报错。

Coinkite 估计，Mk2、Mk3 上受影响固件生成的种子，有效搜索空间约 40 位；Mk4、Q、Mk5 额外混入了一点安全芯片的随机数，约 72 位，而设计目标是 128 位[1][2]。2026 年 7 月 30 日 01:10 至 01:51（UTC），第一波攻击在 41 分钟里从 1,196 个地址扫走 1,082.65 枚 BTC[10]。Coinkite 当天发布安全通告和技术说明[1][2]，次日发布修复固件[12]；但固件更新改变不了已经生成的种子，此后又有多波次、多个攻击者继续清扫[13][14]。

Galaxy Research 8 月下旬的统计是：8,865 个地址被盗 1,789.28 枚 BTC，事发时价值约 1.147 亿美元，其中 87% 没有移动过[15]。被盗的全是单签钱包，没有一笔来自多签[14]。截至 2026 年 10 月，Coinkite 的正式事后分析仍在准备中[6]；它在 8 月 20 日称执法机构仍在调查这些盗窃[12]。

背景

Coldcard 是 Coinkite 公司生产的只支持比特币的硬件钱包，型号有 Mk2、Mk3、Mk4、Q 和 Mk5，固件在 GitHub 上开源。Mk4 及以后的型号在主控之外还有两颗安全芯片 SE1 和 SE2[2]。按 Block 对固件历史的梳理，Mk2、Mk3 在 3.2.2 及以前的固件里直接调用 STM32 的硬件随机数，不受这个问题影响[7]。

2021 年 3 月 17 日发布的 4.0.0 是一次大改：椭圆曲线运算改用 Bitcoin Core 的 libsecp256k1，“所有加密和 BIP39 相关代码都被替换”，新库 libNgU 由开发者 switck 提供[17]。Coinkite 事后说，选择 libsecp256k1 本身没有问题，“问题在集成”[2]。

Coldcard 允许用户在生成种子时加入掷骰子的结果。受影响的固件会把设备生成的种子与每一次骰子结果一起做哈希；独立、保密地掷了 50 次以上的用户，骰子本身就贡献了至少 128 位熵，不受这次缺陷影响。使用了强 BIP-39 密码短语的钱包，也多了一道独立的屏障[1]。

漏洞原理

Coldcard 生成新钱包时，先取 32 字节随机数，再做一次 SHA-256，作为 24 词助记词的熵。按设计，这 32 字节应该来自 STM32 的硬件 TRNG。问题在于从固件代码到硬件之间的那条调用链：它经过两个子模块（libNgU 和 MicroPython），最后接到了错误的实现上[2][4]。

先看固件这一端。4.0.1 的种子生成代码本身很简单，random.bytes 就是 libNgU 的 ngu.random.bytes：

# Coldcard/firmware，shared/seed.py（v4.0.1）
async def make_new_wallet():
    # Pick a new random seed.
    await ux_dramatic_pause('Generating...', 4)
    # always full 24-word (256 bit) entropy
    seed = random.bytes(32)
    # 只能发现输出“卡死”的情况；一个确定性的伪随机序列能轻松通过
    assert len(set(seed)) > 4       # TRNG failure
    # hash to mitigate possible bias in TRNG
    # 哈希能消除偏差，但不能增加熵
    seed = ngu.hash.sha256s(seed)

# shared/random.py（v4.0.1）：注释写着“使用密码学级别的随机数”
bytes = ngu.random.bytes

来源：Coldcard/firmware 仓库标签 2021-03-29T1927-v4.0.1，shared/seed.py 第 348–359 行，shared/random.py 第 3、11 行[8]。省略了空行。

libNgU 这一端，取随机字节时调用 rng_get() 作为“芯片 TRNG”，并设了一道构建检查，防止在没有硬件 RNG 的情况下编译：

// Coldcard/firmware，stm32/COLDCARD/mpconfigboard.h（v4.0.1）
// We have our own version of this code.
#define MICROPY_HW_ENABLE_RNG       (0)   // 本意是“不用 MicroPython 的版本”

// switck/libngu，ngu/random.c
#ifdef MICROPY_PY_STM
// ports/stm32/rng.c
extern uint32_t rng_get(void);
# define CHIP_TRNG_SETUP()
# define CHIP_TRNG_32()         rng_get()
// 只检查宏有没有定义，不检查它的值；定义成 0 也能通过
# ifndef MICROPY_HW_ENABLE_RNG
# error "get a HW TRNG plz"
# endif
#endif

void my_random_bytes(uint8_t *dest, uint32_t count)
{
    uint32_t last = 0;
    while(count) {
        // 这里拿到的其实是 MicroPython 的 Yasmarang 软件回退
        uint32_t chip = CHIP_TRNG_32();
        if(chip == last) {
            // maybe TRNG is not clocked? Fail hard
            mp_raise_OSError(MP_EFAULT);
        }
        last = chip;
        // 再与 libNgU 自己的 Yasmarang 异或，它从固定常数 0x0a8ce26f 起步
        chip ^= my_yasmarang();
        int here = MIN(4, count);
        memcpy(dest, &chip, here);
        dest += here;
        count -= here;
    }
}

来源：Coldcard/firmware 标签 2021-03-29T1927-v4.0.1，mpconfigboard.h 第 76–77 行；switck/libngu 提交 0cf3196 的 ngu/random.c 第 22–31 行、第 55 行和第 68–89 行[8][9]。省略了空行。

MICROPY_HW_ENABLE_RNG 为 0 时，MicroPython 并不是“什么都不提供”，而是编译出一个同名的 rng_get()，用软件生成器代替硬件：

// micropython/micropython，ports/stm32/rng.c（v1.14），MICROPY_HW_ENABLE_RNG 为 0 时的分支
STATIC uint32_t pyb_rng_yasmarang(void) {
    static bool seeded = false;
    static uint32_t pad = 0, n = 0, d = 0;
    static uint8_t dat = 0;
    if (!seeded) {
        seeded = true;
        rtc_init_finalise();
        // 全部初始状态：芯片唯一 ID 异或 SysTick 计数，再加两个 RTC 寄存器
        pad = *(uint32_t *)MP_HAL_UNIQUE_ID_ADDRESS ^ SysTick->VAL;
        n = RTC->TR;
        d = RTC->SSR;
    }
    // ……此后每次调用只做确定性的状态更新，不再收集任何新的熵……
}

uint32_t rng_get(void) {
    return pyb_rng_yasmarang();
}

// switck/libngu，ngu/random.c（2022-03-11 加入）：Mk4 开机时调用
STATIC mp_obj_t random_reseed(mp_obj_t arg)
{
    // 只替换一个 32 位状态字，不接收完整摘要，也不重置其他状态
    yasmarang_pad = mp_obj_get_int_truncated(arg);
    return mp_const_none;
}

来源：MicroPython v1.14，ports/stm32/rng.c 第 74–98 行（中间的状态更新部分从略）[20]；Block 的分析引用了 Coldcard 所用版本中相同的初始化语句[7]。libNgU 提交 61ffc74，ngu/random.c 第 157–162 行[9]。

据 Block 的分析，Mk4、Q、Mk5 开机时会从 SE1 取 32 字节、从 SE2 取 8 字节，做双重 SHA-256，但只把摘要的前 4 个字节传给 reseed()；MicroPython 那一侧的回退生成器也没有被重新播种[7]。于是安全芯片最多只贡献了 32 位熵。

为什么每一道检查都没拦住

  • 构建检查：#ifndef 只问“这个宏定义过没有”，Coldcard 把它定义成了 0，#error 就不会触发[2]。
  • 链接：两个 rng_get() 的函数签名完全相同，链接器选了 MicroPython 那一个，不会报任何错[2]。
  • 运行时检查：chip == last 和 len(set(seed)) > 4 只能发现输出卡死或几乎全是同一个值。一个确定性的伪随机序列，输出看上去和真随机一样。
  • 哈希：SHA-256 能抹平硬件随机数的统计偏差，但输入只有 40 位的不确定性，输出也只有 40 位。
  • 代码审查：既有的审查确认了正确的 TRNG 代码在固件二进制里，却没有核实种子生成路径最终调用的是哪一个 rng_get()[2]。

The bulk of randomness on the COLDCARD was coming from a PRNG that I didn't know was actually in the source code base (it is from a submodule, Micropython).

AI 审查没有发现它

Coinkite 写道，事发前几周它用“最好的 AI 模型之一”审查过代码，没有发现这个缺陷；它推测有人用 AI 审查旧版固件时偶然发现了这个问题，“同样的 AI 工具，攻击者和防守者都有，今天它没有帮到我们，只帮了坏人”[2]。事后它又用 Kimi K3、Claude Fable、Codex 5.6 等前沿模型测试，也都没有发现，因此建议依赖 AI 审查安全代码的团队，专门针对构建和子模块的边界做测试[4]。

攻击过程

Coinkite 说得很明确：设备没有被入侵、远程访问或接管，攻击者是在离线状态下重新算出了弱种子对应的私钥[1]。Galaxy 的描述是，只要大致知道设备标识和种子生成的时间，就可以离线生成候选种子，再与公开的区块链比对，不需要接触钱包[25]。下面依据 Galaxy、TRM、Cointelegraph 等已发表的分析整理。

  1. 第一波：41 分钟7 月 30 日 01:10 至 01:51（UTC），1,196 个地址的 1,082.65 枚 BTC 被转走，交易都用 30 sat/vB 的手续费、没有找零输出。Galaxy 提醒，之后的攻击不一定还有这个特征[10]。其中约 562 枚随即被归集到另一个地址[23]。Arkham 公布的盗贼地址 bc1qq85v2c926eg6pgxhwp6q7lf6cnsz80qs3fcu9r 后来成了一块公开留言板，不少人用 OP_RETURN 往里写话，从哀求到恶搞都有[26]。
  2. 更多波次、更多攻击者8 月 4 日，Galaxy 识别出至少 15 个不同的攻击者；一名受害者报告自己被盗不到 1 BTC，研究者顺着它找到了另一起从 126 个地址盗走 12 BTC 的攻击[13]。到 8 月 14 日，Galaxy 的结论改为“高度确信有多个攻击者”，但无法判断各个波次是否出自同一人；所有高置信度的波次都发生在 8 月 6 日或以前[14]。
  3. 程序化清扫Galaxy 的 Alex Thorn 称这些清扫“看起来是有计划、程序化的”，被盗的币平均已经放了 3.18 年没动[16]。一名把 Coldcard 放在银行保险箱里、从未联网的用户，7 分钟内丢了 18.25 BTC，他说：“最难受的是，我每一步都做对了。”[25]
  4. 白帽也在抢9 月，Galaxy 指出第二波中约四成其实是白帽在抢先转移、保护受害者的资金，其中 52.37 枚 BTC 被归集到为受害者设立的 Crypto Recovery Trust 地址[19]。
与交易所被盗的根本区别

交易所被盗，攻击者要先拿到某一个热钱包的密钥。这次每个受害者的种子都各自很弱，任何理解了缺陷的人都能独立地重算、扫描、清扫，没有迁移的地址会一直暴露。Galaxy 因此判断“每一台有漏洞的设备最终都会被清空”[16]，这也解释了为什么会出现多个攻击者、多个波次，以及白帽与攻击者赛跑。

  2. 多个波次扫走约 1,790 BTC
  3. 攻击者地址8 月 25 日时 87.3% 仍未移动

本页采用 Galaxy 8 月 25 日按被盗时价格计算的 1,789.28 BTC、约 1.147 亿美元。Galaxy 说明，其中约 44% 的金额有受害者直接报案佐证，221 份报告的损失中位数约 1.04 BTC[15]。9 月 22 日，Thorn 按波次核对：第一波 1,082.57 BTC 未动，第三波 116.98 BTC 未动、97.09 BTC 已洗出，信托地址 52.37 BTC，合计约占被盗总额的 76%；第二波另外六成的去向仍不清楚，是否也是白帽所为无法确定[19]。

影响

自托管的风险换了地方

TRM 称这是 2026 年最大的硬件钱包漏洞事件[11]。受害者大多是严格按照“不信任交易所、自己保管私钥”的原则行事的比特币持有者，有人把设备放在银行保险箱里从不联网，资金照样被转走。Galaxy 的总结是：去掉第三方托管人并不能消除托管风险，只是把风险转移到了硬件、软件和密钥生成过程上；“私钥的安全程度，取决于生成它的流程和基础设施”[25]。Galaxy 的 Thorn 还直言，这件事除了 Coinkite 不能怪任何人[14]。

多签挡住了全部损失

Galaxy 核对的被盗交易里，没有一笔来自多签钱包[14]。多签要求多把密钥同时签名，即使其中一把是在有缺陷的 Coldcard 上生成的，攻击者算出它也不够。Block 的分析也指出，需要一组足够数量的安全设备，才能防住这类问题[7]。

开源与 AI

Coldcard 的代码一直公开，缺陷在公开代码里待了五年多，却在 2026 年突然被多人利用。Coinkite 推测攻击者借助了 AI 审查代码[2]，这一点没有被证实。可以确定的是，缺陷位于两个子模块的交界处，而大多数内部和第三方审查关注的是加密和比特币相关逻辑本身[4]。竞争对手 Ledger 的 CTO 事后撰文强调，其设备的种子来自安全芯片内置的真随机数发生器，并经过 AIS-31 PTG.2 认证[24]。

弱随机数的老问题

这是本站收录的第三起因密钥生成熵不足造成的大额损失。2020 年的 LuBian 和 2022 年的 Wintermute，问题都出在用 32 位种子初始化的软件生成器上。这一次的软件生成器同样不是为密码学设计的，只是藏得更深：它不在 Coldcard 自己的代码里，而在一个依赖库的回退分支里。

后续处置

升级固件为什么不够

修复固件只保证今后新生成的种子是安全的，不能修复已经用旧固件生成的种子。Coinkite 要求受影响的用户：先升级固件，再生成全新的种子，记录并核对备份、钱包指纹和收款地址，先发一笔小额测试交易，确认无误后再转移全部资金，旧备份留到迁移完成为止；它同时提醒，仓促迁移可能比这个缺陷本身带来更直接的风险[1]。只有一台 Mk2 或 Mk3 的用户，可以在升级到 4.2.0 后在同一台设备上交替恢复新旧种子完成迁移，也可以选择用至少 99 次骰子单独生成种子，完全不经过设备的随机数生成器[1]。

修复与加固

  • 7 月 31 日的紧急修复：构建时明确排除 MicroPython 的回退生成器，并加入符号检查，除非板级代码定义了全局的 rng_get() 且上游回退代码没有定义任何符号，否则构建失败[2]。
  • libNgU：8 月 1 日起，Yasmarang 被换成 SHA-256 Hash_DRBG，并加强了熵输入的检查[9]。
  • 5.6.1 / 1.5.1Q（8 月 20 日）：每个新种子都必须加入一种用户自己提供的熵，至少 65 次时机不可预测的按键、50 次骰子或 128 次抛硬币；再与 STM32 TRNG、SE1、SE2 的新随机数混合[12]。
  • 5.6.2 / 1.5.2Q（9 月 4 日）：新增“View TRNG Words”，把设备提供的 256 位熵显示成 24 个词，并附上独立的校验脚本 verify_seed_mix.py，用户可以自己重算最终种子[22]。

公司与社区

Coinkite 销毁了用受影响固件生产的剩余库存，确认漏洞时就已停止发货，并请受影响的用户不要丢弃设备，称如果资金被追回，设备可能成为关键证据；其法律团队会视情况与多个司法辖区的执法机构配合[3]。8 月 7 日，它因法律上的证据保全义务，暂停了“交付 120 天后自动清除客户资料”的做法[5]。它还建立了一个页面，汇总所有与 Coldcard 有关的公开安全研究、披露和审查记录[4]。9 月初，Coinkite 称 Coldcard 已恢复供货，需求有所增加[22]。

社区方面，Rob Hamilton、Calle、James O'Beirne 和另外约 25 人组成的“比特币红队”开始审计相关代码库；Galaxy 持续统计损失并与执法机构共享攻击者地址[14][15]。截至 2026 年 10 月，官方状态页没有提到任何赔偿安排，详细的技术事后分析仍在准备中[6]；本站也没有查到与此案有关的逮捕报道。

教训与防御

给固件和钱包开发者
  • 对安全关键的符号做构建期检查：确认 rng_get() 这类函数最终链接到的是哪个目标文件，不是预期的就让构建失败。Coinkite 的修复正是这么做的。
  • 条件编译的保护要检查值，而不只是检查“有没有定义”。用 #if !MICROPY_HW_ENABLE_RNG 加 #error，宏被定义为 0 时同样会报错。
  • 密钥生成路径要“失败即停”，不允许任何软件回退。硬件随机源不可用时，宁可无法生成种子。
  • 审查熵来源时，从种子生成的调用一路追到硬件寄存器。源码里有正确的实现，不等于运行时调用的就是它。
  • 输出看起来随机、通过了重复值检查，都证明不了熵来源是对的。伪随机序列的输出同样“看起来随机”。
给持有人和机构
  • 不要把种子的全部熵交给一家厂商的随机数生成器。生成时加入至少 50 次独立、保密的骰子，或使用强而唯一的 BIP-39 密码短语，都能让这次的缺陷失效。
  • 大额资金用多签，并让各把密钥来自不同厂商的设备。这次没有一笔多签被盗。
  • 厂商发布随机数相关的通告后，尽快迁移到新种子。升级固件不会改变旧种子，拖得越久，被扫走的可能越大。
  • 迁移要按步骤来：先验证新种子和地址，再小额测试，最后转移全部资金。
