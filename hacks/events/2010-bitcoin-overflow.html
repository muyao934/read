比特币价值溢出漏洞

2010 年 8 月 15 日，比特币区块 74638 里出现了一笔交易，两个输出各约 922 亿枚 BTC，合计约为 2,100 万总量上限的 8,800 倍。原因是客户端在把输出金额相加时没有检查整数溢出。中本聪当天发布补丁，升级后的节点另起一条链，第二天反超了包含这笔交易的旧链，这些凭空产生的币随之作废。

概要

比特币节点在接受一笔交易前要检查两件事：每个输出不能是负数，输出总额不能超过输入总额。当时的代码对单个输出做了非负检查，但把所有输出加起来时用的是有符号 64 位整数，没有检查溢出。两个都接近上限的正数相加后回绕成了一个负数，“输出总额小于输入”这一检查因此被绕过。

这笔交易只花掉了 0.5 BTC 的输入，却在两个地址上记入了各约 922 亿枚 BTC，矿工还多拿到 0.01 BTC 的“手续费”[1][2]。从区块产生到论坛上有人发现异常，大约过了一小时；从发现到中本聪把修复提交到代码库，大约三个半小时[2][5]。

修复版本 0.3.10 收紧了交易规则，属于软分叉：新规则下有效的区块，旧节点同样认为有效。升级的节点从区块 74637 重新出块，新链在第二天反超旧链，没有升级的节点也按“最长链”规则自动切换过去[1][4]。这笔交易的编号后来定为 CVE-2010-5139[8]。造出这笔交易的人至今身份不明，也没有人公开认领。

背景

2010 年 8 月，比特币主网运行了一年半。客户端由中本聪维护，代码放在 SourceForge 的 SVN 仓库里，Gavin Andresen、Jeff Garzik 等少数开发者参与修改。讨论几乎都集中在 bitcointalk 论坛，挖矿就是运行客户端自带的“生成”功能，用普通电脑的 CPU 或显卡出块。当时没有正式的安全公告渠道，也没有内置的警报机制。按 Decrypt 的回顾，补丁发布那天一枚比特币约值 0.07 美元[11]。同年 5 月 22 日，Laszlo Hanyecz 在 BitcoinTalk 论坛报告，他用 1 万枚比特币换到了两个披萨[13]，见大事记的比特币披萨日。

比特币的总量约束靠两条规则维持：新币只能由每个区块的 coinbase 交易按固定数额发行，当时是每块 50 BTC；其他交易的输出总额不能超过输入总额，差额作为手续费归矿工。只要这两条成立，2,100 万的上限就自然成立。但在 0.3.10 之前，代码里并没有“任何金额不得超过 2,100 万 BTC”这样的显式检查，常量 MAX_MONEY 是这次补丁才加上的[5]。

客户端里另有一种叫“检查点锁定”的机制：代码中写死了若干历史区块的哈希，例如区块 74000，与之冲突的链会被直接拒绝[6]。这原本是防止有人重写早期历史的手段，在这次事件中成了修复方案的一部分。

漏洞原理

比特币的金额以“聪”（satoshi，1 BTC = 108 聪）为单位，存在有符号 64 位整数 int64 里，最大值约为 922.3 亿 BTC。正常交易的金额远小于这个数，开发者也就没有考虑相加会不会越界。修复前，和金额有关的检查分在三个地方，每一处单独看都没有错：

// main.h（修复前），CTransaction::CheckTransaction：交易的基本检查
// Check for negative values
foreach(const CTxOut& txout, vout)
    if (txout.nValue < 0)          // 只检查每个输出不是负数
        return error("CTransaction::CheckTransaction() : txout.nValue negative");

// main.h（修复前），CTransaction::GetValueOut：计算输出总额
int64 nValueOut = 0;
foreach(const CTxOut& txout, vout)
{
    if (txout.nValue < 0)
        throw runtime_error("CTransaction::GetValueOut() : negative value");
    nValueOut += txout.nValue;     // 有符号 64 位相加，越界后回绕成负数
}
return nValueOut;

// main.cpp（修复前），CTransaction::ConnectInputs：输入减输出就是手续费
// Tally transaction fees
int64 nTxFee = nValueIn - GetValueOut();
if (nTxFee < 0)                    // 输出总额是负数时，手续费反而是正数
    return error("ConnectInputs() : %s nTxFee < 0", ...);

来源：bitcoin/bitcoin 仓库提交 4bd188c（SVN r131，修复前的最后一个版本）中 main.h 第 474–477、520–527 行与 main.cpp 第 1011–1014 行，去掉了一层缩进，最后一行的参数从略。英文注释是原有的，中文注释是本站加的。

区块 74638 里的那笔交易恰好落在这三处检查的缝隙里。论坛上的分析者当天就把数字算清楚了[2][3]：

  1. 两个输出各约 922 亿 BTC输入只有 0.5 BTC；每个输出单看都是正数，通过非负检查
  2. 求和越界两者之和超过 int64 上限，回绕为 −0.01 BTC
  3. 手续费 0.51 BTC0.5 −（−0.01）≥ 0，检查通过
  4. 写入区块 74638矿工的 coinbase 记为 50.51 BTC

每个输出只比 int64 的上限小约 0.005 BTC。原帖的第二条回复就指出，922 亿这个数正是 263/108，也就是有符号 64 位整数的上限[2]。两者相加后超出上限，结果按补码回绕成一个很小的负数。在节点看来，这只是一笔多付了 0.01 BTC 手续费的普通交易。矿工按规则把 50 BTC 补贴和 0.51 BTC 手续费都记进 coinbase，其中 0.01 BTC 在任何地方都没有来源。

逐个检查为什么不够

“每个输出都不是负数”是对单个元素的约束，“输出总额不超过输入”是对总和的约束。前者成立并不能推出后者成立，因为总和是在固定宽度的整数里算出来的，可能越界。要守住总和的约束，必须在求和过程中每一步都检查，或者用不会静默回绕的运算。

补丁改了什么

中本聪在 SVN 修订 132 中做了三处改动：新增常量 MAX_MONEY，即 2,100 万 BTC；CheckTransaction 对每个输出和累计值都检查上限；ConnectInputs 对输入一侧做同样的检查[5]。

// main.h（修复后，SVN r132）
static const int64 MAX_MONEY = 21000000 * COIN;

// CTransaction::CheckTransaction
// Check for negative or overflow output values
int64 nValueOut = 0;
foreach(const CTxOut& txout, vout)
{
    if (txout.nValue < 0)
        return error("CTransaction::CheckTransaction() : txout.nValue negative");
    if (txout.nValue > MAX_MONEY)
        return error("CTransaction::CheckTransaction() : txout.nValue too high");
    nValueOut += txout.nValue;
    if (nValueOut > MAX_MONEY)     // 每加一次就检查累计值
        return error("CTransaction::CheckTransaction() : txout total too high");
}

来源：bitcoin/bitcoin 仓库提交 d4c6b90《fix for block 74638 overflow output transaction》，2010-08-15 21:35:24 UTC。同一提交还在 main.cpp 的 ConnectInputs 里对输入金额和输入总额加了相同的上限检查，并把版本号从 309 改为 310。

这个写法能杜绝溢出，是因为每个加数不超过 MAX_MONEY，加之前的累计值也不超过 MAX_MONEY，两者之和最多约 4,200 万 BTC，离 int64 的上限差四个数量级，加法本身不可能越界。今天 Bitcoin Core 的 src/consensus/tx_check.cpp 里仍是这三个检查，注释直接写着“see CVE-2010-5139”，只是累计值的判断换成了 MoneyRange()[12]。

攻击过程

造出这笔交易的人没有留下任何公开说明，下面只按论坛讨论、Bitcoin Wiki 和中本聪当时的帖子，概括已知的经过。

  1. 准备一笔小额输入交易花掉的是 0.5 BTC。Bitcoin Wiki 记载，这 0.5 BTC 看起来来自一个水龙头（当时向新用户免费发放少量比特币的网站），此后一直没有再动过[1]。
  2. 构造官方客户端不会生成的交易官方钱包不会造出金额接近 int64 上限的输出。论坛上有人推测，构造者用的是自行修改过的客户端[2]。
  3. 交易被打包当时所有节点都会认为这笔交易有效，它在区块 74638 里得到确认。出块的矿工因此多拿了 0.01 BTC。没有公开证据表明这个矿工和交易的构造者是同一个人。
  4. 旧节点反复把它放回新块补丁发布后，没有升级的节点仍把这笔交易留在内存池里，每出一个新块都试图把它重新打包，因而不断制造出新节点会拒绝的区块。重启节点可以清空内存池，但交易会被其他旧节点再次广播过来[3]。
  5. 随旧链一起消失新链反超后，这笔交易不在最长链上，两个地址上的“余额”也就不存在了[1]。现有公开资料没有显示这些币在旧链存续的不到一天里被转移或兑换过。

与这本编年史中的大多数事件不同，这次没有任何人的币被偷走。被破坏的是整个系统最基本的承诺：总量不超过 2,100 万。如果这条链没有被放弃，这 1,844 亿枚 BTC 会和其他币一样可以流通，比特币的稀缺性也就不复存在。

这笔交易随旧链一起被放弃后，Bitcoin Wiki 记载那 0.5 BTC 的输入在最长链上仍是未花费状态[1]。这次真正蒙受损失的，是在旧链上出块的矿工：从区块 74638 开始，他们在旧链上挖到的每一块都不在最长链上，每块 50 BTC 的补贴一并作废。旧链上的普通交易不受影响。中本聪在回答一位用户时说，这些交易“会被重新纳入修复后的链”，两边都能看到，只是确认数会跳回 0 重新计算[3]。

影响

总量上限第一次写进代码

在这之前，2,100 万的上限只是发行规则推出来的结果，代码里没有任何地方直接检查它；这条发行规则是 2009 年 1 月 v0.1 定下的[16]，见大事记的比特币白皮书与创世区块。补丁之后，“任何金额和金额之和都必须落在 0 到 2,100 万 BTC 之间”成了一条显式的共识规则，并一直保留到今天[12]。中本聪在事后几天又给客户端加了警报系统。事发当晚有用户提出，大多数人不看论坛，客户端里应该有能显示紧急警告的地方，中本聪回复说自己早就想做，只是没时间[3][7]。

同一类漏洞后来又出现过

2018 年，比特币又出现了一个可以增发的共识漏洞 CVE-2018-17144。两次的处理方式差别很大，可以看出八年间应急流程的变化：

2010：CVE-2010-51392018：CVE-2018-17144
根因输出金额求和时整数溢出同一交易内重复花费同一输入，一次性能优化去掉了检查[10]
怎么发现的漏洞被利用后，论坛用户发现异常区块匿名研究者先按拒绝服务漏洞报告，开发者约 3 小时后确认它也能用来增发
是否被利用是，区块 74638披露时未发现利用
修复速度发现后约 3.5 小时提交代码，约 5.5 小时提供二进制下载报告后约 7 小时公开补丁，约 30 小时发布正式版本
处置方式软分叉，并放弃已经包含溢出交易的那段链补丁发布时只公开拒绝服务问题，私下联络矿工升级；三天后有人在论坛泄露真实影响，开发者随即全面披露，当时估计过半算力已升级

整数溢出也在智能合约里反复出现。2018 年的 BeautyChain（BEC）是同一类错误：乘积越界后变成 0，绕过了余额检查。智能合约领域直到 Solidity 0.8 把溢出检查内置进编译器，才把这类问题大体堵住。

靠升级丢弃已确认区块的先例

这次事件开了一个先例：发现链上历史违反了协议的根本承诺时，社区可以通过发布新客户端、让新链超过旧链的方式，把已经确认的区块整段作废。六年后 The DAO 事件里关于“要不要改写历史”的争论，在这里还没有出现。这次作废的是明显违反规则的增发，而不是合约按规则执行出的结果，当时论坛上讨论的是怎样尽快修复，而不是该不该修复[3]。

后续处置

三层修复

  1. 收紧规则SVN 修订 132 加入 MAX_MONEY 与求和检查，任何包含超额输出的交易都无效[5]。
  2. 拒绝那一段链修订 133 在 AcceptBlock 中加入回扫：沿着新区块往回检查到区块 74000，如果路径上出现区块 74638 的那个哈希，就拒绝这个区块[6]。这样即使有人在旧链上继续出块，升级的节点也不会接到它后面。
  3. 自动清理本地数据最初的升级步骤要求用户手动删除区块文件，再从一个较早的快照重新同步。8 月 16 日的提交让客户端启动时自动找出坏块、退回分叉点并删除坏链，还在连接每个区块时再做一次完整检查，注释写着“以防旧版本放进了坏块”[7]。中本聪说，前一天他知道自己没法既快又稳地写好这段代码，所以先用了手动方案[3]。

为什么当时能丢弃已确认的区块

一是这次修复属于软分叉。新规则只是比旧规则更严，新链上的每个区块，旧节点也认为有效。所以只要升级节点的算力超过一半，新链迟早会更长，没升级的节点会自己切换过去，不需要所有人同时动作。中本聪当晚的说法是：一旦过半算力升级、好链反超坏链，0.3.10 节点会让坏交易很难再得到确认[3]。2017 年 8 月在比特币上生效的 SegWit 也是软分叉[14][15]，经过见大事记的比特币区块大小之争（BCH 分叉与 SegWit 激活）。

二是网络很小，协调集中在一处。几乎所有用户都在同一个论坛上，运行同一个客户端，中本聪一句“请暂停挖矿”就能让相当一部分算力停下来。有用户提供了旧的区块快照，帮大家更快重新同步[3]。

三是作废的东西很少。坏链只延续了约 50 个区块，不到一天。旧链上的普通交易会被重新打包进新链，真正消失的只有溢出交易本身和旧链上的出块奖励。

这三个条件今天都不成立。节点和矿池分布在全世界，交易所和托管机构按确认数自动入账，作废一天的区块意味着撤销大量真实的付款。2018 年的 CVE-2018-17144 说明了现在的做法：在被利用之前修复，先联络矿工和大型服务商升级，再公开细节[10]。

两处记载不一致

反超高度：中本聪在 8 月 16 日 12:59 的帖子里说“大约在 74689 附近”，Bitcoin Wiki 记载为 74691[1][3]。修复版本：中本聪当时发布的补丁版本是 0.3.10，而 NVD 的描述写的是“0.3.11 之前的版本受影响”，Bitcoin Wiki 的漏洞表也把修复版本记为 0.3.11[8][9]。本页按当时的发布帖叙述。

教训与防御

给写金额处理代码的开发者
  • 对单个值的检查保证不了总和。凡是有“总额不超过某值”的约束，就要在累加的每一步检查，或者用发生越界就报错的加法，而不是事后检查结果。
  • 系统的根本不变量要写成代码里的显式断言。“总量不超过 2,100 万”在 2010 年之前只存在于设计里，代码里没有任何一处直接检查它。
  • 只把金额限制在一个远小于整数类型上限的范围内，加法本身就不可能越界。MAX_MONEY 比 int64 的上限小四个数量级，累计值每次都和它比较，这样的写法比单纯换更宽的整数类型可靠。
给协议维护者
  • 要有能触达所有节点的紧急渠道。2010 年只能靠论坛和邮件列表，警报系统是事后才补上的。
  • 修复要考虑已经被坏数据污染的节点。最初的补丁只能拦住新的坏块，本地已有的坏链要靠用户手动删除；第二天的提交才让客户端自动识别并清理。
  • 能在被利用前发现的漏洞，处理代价小得多。2018 年的增发漏洞没有造成任何链重组，靠的就是在被利用之前完成修复。
给交易所和其他接收方
  • 入账逻辑可以加一层与协议无关的合理性检查，例如单笔金额超过总供应量时直接暂停入账。
  • 确认数只在链不被大规模重组时有意义。共识层出现问题时，最先要做的是暂停充值和提现，而不是等待更多确认。
