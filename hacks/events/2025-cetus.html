区块链被盗事件编年史

Cetus 溢出检查错误

2025 年 5 月 22 日，攻击者利用 Cetus 所依赖的数学库里一个写错的溢出判断，只存入 1 个最小单位的代币，就给自己记上了天量流动性，在 15 分钟内从 Cetus 的池子里取走约 2.23 亿美元。其中约 1.62 亿美元还没离开 Sui 就被验证者拦下，一周后又经链上投票和协议升级从攻击者地址转了回来。资金大部分追回了，Sui 能冻结并转走一个地址的资产这件事，也让它的去中心化程度成了争论焦点。

概要

Cetus 是 Sui 上的集中流动性 DEX。用户添加流动性时，合约用 get_delta_a 算出应存入多少 token A，其中一步要把一个 256 位整数左移 64 位。负责判断这一步会不会溢出的，是开源数学库 integer-mate 里的 checked_shlw。它本该在数值达到 2¹⁹² 时报溢出，却把门槛写成了 2²⁵⁶ − 2¹⁹²，夹在两者之间的数被当成“没溢出”，左移时高位被直接截掉。

攻击者选了一个只有 200 个 tick 宽的价格区间，填入约 1.04×10³⁴ 的流动性，让乘积刚好落进这个漏判区间。截断后，合约算出他只需存入 1 个最小单位的 token A，却照单给他的头寸记上了全部流动性。随后他按正常规则分批撤出这些流动性，拿走的是池子里其他用户存入的真实资产[1][12][13]。每一轮都在一笔闪电兑换里完成，攻击地址在 10:30 到 10:45（UTC）之间发出了 287 笔这样的交易[31]。

Cetus 估算损失约 2.23 亿美元。约 6,000 万美元被攻击者跨链到以太坊换成 ETH，其余约 1.62 亿美元留在 Sui 上，被超过三分之一质押量的验证者拒绝处理，等于被冻结[1]。5 月 29 日，代表 90.9% 质押的验证者投票通过一次协议升级，允许一个指定地址替攻击者签署两笔事先公开的交易，把冻结资产转入托管多签[6][10]。Cetus 用取回的资产、自有现金和 Sui 基金会 3,000 万 USDC 的贷款补回池子，缺口用 CETUS 代币补偿，6 月 8 日重新上线[2]。截至 2026 年 10 月，攻击者身份仍未公开，转到以太坊的 ETH 大部分还在攻击者地址里[30]。

背景

Cetus 在 Sui 和 Aptos 上都有部署，在 Sui 主网上线当天就已运行，自称 Sui 上领先的 DEX 和流动性基础设施[4][17]。这次只有 Sui 上的池子出事，Aptos 一侧未受影响[21]。它的核心是集中流动性做市（CLMM），设计思路和 Uniswap V3 类似：流动性提供者（LP）只在自己选定的价格区间里提供流动性，交易发生在哪个区间，就用哪个区间的流动性报价。很多 Sui 代币的链上交易都要经过 Cetus 的池子，所以池子被抽干后，这些代币在 DEX 上的价格随之暴跌[17]。

CLMM 的记账方式

CLMM 用价格的平方根 √P 记账。Cetus 把 √P 存成 Q64.64 定点数（真实值乘以 2⁶⁴ 后取整，类型为 u128），流动性 L 也是 u128。当池子当前价格低于某个头寸的区间时，这个头寸全部由 token A 组成，数量为：

// 示意：价格低于区间时，头寸需要的 token A（√P 为 Q64.64 定点数，L 为 u128）
Δa = L × (√P_upper − √P_lower) × 2⁶⁴ ÷ (√P_lower × √P_upper)

示意公式。√P 的 2⁶⁴ 缩放在分母里出现两次、分子里只有一次，所以分子要再乘一次 2⁶⁴，也就是左移 64 位。

L 和 Δ√P 都是 128 位，乘积用 256 位存放。再左移 64 位时，只要乘积的最高 64 位里有任何一位是 1，结果就放不进 256 位。换句话说，乘积必须小于 2¹⁹²，左移才安全。checked_shlw 守的就是这条边界。

integer-mate 与审计

integer-mate 是 Cetus 维护的开源 Move 库，提供有符号整数和若干整数运算函数，采用 MIT 许可，最初同时有 Aptos 和 Sui 两个版本[7]。在仓库 2023 年 2 月 23 日的提交里，checked_shlw 就已经是出事时的写法，之后直到 2025 年 5 月 22 日都没有改过[7]。

Cetus 的 Sui 版 CLMM 经过多轮审计：2023 年春有 MoveBit 和 OtterSec，2024 年 11 月有 OtterSec，2025 年 3 月至 4 月有 Zellic[9]。Zellic 这一轮的范围是 cetus_clmm 和 integrate 两个包的源码，不含 integer-mate，报告只有 3 条信息级发现[9][26]。Dedaub 事后指出，OtterSec 2023 年初审计 Aptos 版代码时曾发现分子在调用 u256::shlw 前没有校验，建议改用 checked_shlw。问题在于 Sui 版用上的 checked_shlw 本身就写错了，此后几轮审计都没有发现[12]。

漏洞原理

从 add_liquidity 到 checked_shlw

用户按“指定流动性”的方式添加流动性时，pool::add_liquidity_internal 会调用 clmm_math::get_amount_by_liquidity，按头寸的 tick 区间和池子当前价格算出应存入多少 token A 和 token B，取整方向是向上[8]。如果当前价格低于区间下沿，只走 get_delta_a 一个分支：

// clmm_math.move，get_amount_by_liquidity（节选）
let (amount_a, amount_b) = if (i32::lt(current_tick_index, tick_lower)) {
    // 当前价格低于区间：头寸全是 token A，只算 Δa
    (get_delta_a(lower_price, upper_price, liquidity, round_up), 0)
} else if (i32::lt(current_tick_index, tick_upper)) {
    (
        get_delta_a(current_sqrt_price, upper_price, liquidity, round_up),
        get_delta_b(lower_price, current_sqrt_price, liquidity, round_up),
    )
} else {
    (0, get_delta_b(lower_price, upper_price, liquidity, round_up))
};

来源：CetusProtocol/cetus-contracts，提交 a477627，packages/cetus_clmm/sources/math/clmm_math.move 第 400–409 行。

// clmm_math.move，get_delta_a
public fun get_delta_a(
    sqrt_price_0: u128,
    sqrt_price_1: u128,
    liquidity: u128,
    round_up: bool,
): u64 {
    let sqrt_price_diff = if (sqrt_price_0 > sqrt_price_1) {
        sqrt_price_0 - sqrt_price_1
    } else {
        sqrt_price_1 - sqrt_price_0
    };
    if (sqrt_price_diff == 0 || liquidity == 0) {
        return 0
    };
    // 分子 = L × Δ√P，再由 checked_shlw 左移 64 位
    let (numberator, overflowing) = math_u256::checked_shlw(
        full_math_u128::full_mul(liquidity, sqrt_price_diff),
    );
    if (overflowing) {
        abort EMULTIPLICATION_OVERFLOW
    };
    let denominator = full_math_u128::full_mul(sqrt_price_0, sqrt_price_1);
    let quotient = math_u256::div_round(numberator, denominator, round_up);
    assert!(quotient <= std::u64::max_value!() as u256, EAMOUNT_CAST_TO_U64_OVERFLOW);
    (quotient as u64)
}

来源：同上，第 88–113 行（numberator 的拼写是原文）。事发时 CLMM 源码没有公开，这是 2025 年 9 月开源的版本；Dedaub 在 5 月 23 日引用的 get_delta_a 结构与此相同[12]。

这段代码的安全性完全押在 checked_shlw 上。只要它如实报告溢出，分子过大的请求就会在 abort EMULTIPLICATION_OVERFLOW 处失败；即使分子没溢出，算出的 token A 超过 u64 上限，最后一行的 assert! 也会拒绝。

Move 的左移不检查溢出

Move 的加、减、乘都是受检运算，溢出会直接 abort。移位不一样：只有移位的位数大于或等于类型位宽时才会 abort[29]，被移出去的高位直接丢掉，交易照常执行。Dedaub 在分析中专门指出，左移是 Move 里唯一不会因溢出而 abort 的运算[12]。所以 checked_shlw 必须自己判断 n 的最高 64 位是否全为 0。下面是修复前的源码：

// integer-mate，sui/sources/math_u256.move（修复前，Move.toml 版本 1.1.0）
public fun checked_shlw(n: u256): (u256, bool) {
    let mask = 0xffffffffffffffff << 192;   // 等于 2²⁵⁶ − 2¹⁹²
    if (n > mask) {                         // 只有 n 比它还大才报溢出
        (0, true)
    } else {
        ((n << 64), false)                  // n ≥ 2¹⁹² 时，高位在这里被悄悄截掉
    }
}

来源：CetusProtocol/integer-mate，提交 4d09c8b，sui/sources/math_u256.move 第 18–25 行。中文注释为本站所加。

Cetus 的事故报告给出了两种正确写法：一种是用这个掩码做按位与，检查最高 64 位是否全为 0（mask & n != 0 即溢出）；另一种是直接和第一个会溢出的数比较（n >= 1 << 192 即溢出）。出错的代码用了第一种的掩码，却套上了第二种的比较方式，报告称之为“两种正确方法的错误组合”[1]。结果是，只有 n 大于 2²⁵⁶ − 2¹⁹² 时才报溢出。从 2¹⁹² 到 2²⁵⁶ − 2¹⁹² 这一整段，几乎覆盖了所有本该报溢出的数，全部被判成“没溢出”。

用攻击参数复算

Dedaub 公布了第一笔攻击交易（摘要 DVMG3B2kocLEnVMDuQzTYRgjwuuFSfciawPvXXheB3x）的关键参数：头寸区间为 tick 300000 到 300200，流动性 L 约 1.04×10³⁴[12]。Halborn 和 rekt.news 给出的区间与此相同[15][26]。本站用这些参数复算：

# 示意：用 Dedaub 公布的攻击参数复算（Python 整数运算，可直接运行）
L  = 10365647984364446732462244378333008     # 攻击者填入的流动性，约 2^113
p0 = 60257519765924248467716150              # tick 300000 的 √P（Q64.64）
p1 = 60863087478126617965993239              # tick 300200 的 √P（Q64.64）
n  = L * (p1 - p0)                           # full_mul(liquidity, sqrt_price_diff)
print(n > 2**256 - 2**192)                   # False：旧检查放行
print(n >= 2**192)                           # True：正确的检查会报溢出
num = (n << 64) % 2**256                     # 模拟 u256 左移，高位被截掉
print(-(-num // (p0 * p1)))                  # 1：向上取整后的应付 token A
print((n << 64) // (p0 * p1))                # 约 3.16×10^25：不截断时的值

示意代码，本站据 Dedaub 公布的参数编写并运行，结果与 Dedaub、Verichains 的结论一致。

Δ√P约 6.06×10²³tick 300000 到 300200，约 2⁷⁹

攻击者没有猜。L 和区间宽度是配好的：区间越窄，Δ√P 越小，L 就要越大才能让乘积越过 2¹⁹²，而头寸记上的正是这个 L。乘积只要稍稍越过 2¹⁹²，截断后剩下的分子就很小，应付金额被压到 1。

修复：两次提交

5 月 22 日，integer-mate 先后合入两次修复[7]：

// 提交 ffb2292（14:19 UTC）：阈值改对了，比较符没改
let mask = 1 << 192;
if (n > mask) {           // n 恰好等于 2¹⁹² 时仍会放行，左移后变成 0

// 提交 970667a（15:51 UTC）：比较符改为 >=
let mask = 1 << 192;
if (n >= mask) {          // 最高 64 位只要有一位是 1，就报溢出

来源：CetusProtocol/integer-mate 提交 ffb2292 与 970667a 的 diff，sui/sources/math_u256.move。

第一次修复把阈值改成了 2¹⁹²，比较符却还是 >。n 恰好等于 2¹⁹² 时仍会被放行，而 2¹⁹² 左移 64 位等于 2²⁵⁶，截断后是 0。约 92 分钟后的第二次提交才改成 >=。修复期间 Move.toml 的版本号从 1.1.0 升到 1.1.1、1.1.2，每次都发布了新的包地址[7]。

为什么测试和审计都没拦住

正常添加流动性时，L × Δ√P 远小于 2¹⁹²，左移不会溢出，旧检查和正确检查的结果完全一样，功能测试看不出差别。要进入漏判区间，需要同时满足 L 极大和区间极窄，只有刻意构造的输入才做得到。修复前的 math_u256 模块只有两个测试，一个调用 div_round，一个做 u256 加法，没有一个碰到 checked_shlw[7]。

审计范围也有空档。Zellic 2025 年的审计只覆盖 CLMM 和 integrate 两个包[9]。rekt.news 评论说，审计查了每一扇窗，却没看“所有人都在用的那个共享数学库”[26]。事后 Asymptotic 用 Sui Prover 对 integer-mate 做了形式化验证，证明所覆盖函数的数值结果和 abort 条件[9]。

和 MAX_U64 那条审计发现无关

攻击发生后，社交媒体上有人把漏洞归到此前审计报告里一条关于 MAX_U64 检查的发现上。Cetus 在事故报告中否认了这种说法：那条发现只是信息级的优化建议，极端情况下最多导致交易回滚，而且早已在之前的版本中修复[1][17]。

攻击过程

以下步骤综合了 Cetus 事故报告、Verichains 和 Cyfrin 对单笔攻击交易的还原，以及本站对攻击地址链上记录的核对[1][13][16][31]。攻击者对不同池子用的是同一套流程，具体数量和撤出轮数因池子而异。

  1. 准备据 SlowMist 分析，攻击者提前两天给钱包充好 gas，还试过一个失败的早期版本[21]。5 月 22 日 07:26，攻击地址有一笔失败交易；正式攻击从 10:30:50 开始[31]。
  2. 闪电兑换，把价格压到底攻击者调用池子的 flash_swap，先从池子借出一种代币，暂时欠着另一种。Verichains 还原的那笔交易里，价格上限参数是 4,295,048,016，正是 Cetus 允许的最低价格 MIN_SQRT_PRICE_X64[13][8]。价格被压到底以后，攻击者接下来要开的头寸就整个处在当前价格之上。
  3. 开一个极窄的高价头寸攻击者在 tick 300000 到 300200 开仓。这个区间远在当前价格之上，计算存入数量时只走 get_delta_a 一个分支，头寸被视为全部由 token A 组成[12]。
  4. 用 1 个单位记上天量流动性攻击者调用 add_liquidity，填入约 1.04×10³⁴ 的流动性。乘积越过 2¹⁹² 而没被拦下，合约算出只需存入 1 个最小单位的 token A，却给头寸记上了全部流动性[12][13]。
  5. 分批撤出攻击者用 get_liquidity_from_a 反算出“取回闪电兑换所欠数量的 token A 需要多少流动性”，再调用 remove_liquidity 撤出这一份[13][16]。这一份远小于 2¹⁹² 的门槛，运算不会溢出，拿到的是货真价实的代币。remove_liquidity 直接从池子的共享余额 pool.coin_a、pool.coin_b 里拆出代币[8]，这些余额属于所有 LP，不只属于攻击者这个头寸。Cetus 的报告称，攻击者会计算池子里还剩多少可撤的流动性，再重复撤出[1]。
  6. 还款，留下利润用撤出的代币还清闪电兑换，借出的那一侧就成了净利润。第一笔交易结束时，攻击地址在 haSUI/SUI 池净得约 1,002 万枚 haSUI 和 577 万枚 SUI[31]，与 Dedaub 估算的约 570 万枚 SUI 利润相符[12]。
  7. 脚本化重复同样的流程在 15 分钟里执行了 287 次，约每 3 秒一笔，其中 22 笔失败[31]。Cetus 事后公布的受影响池子共 265 个[3]。

“经 Wormhole 转出”的说法不准确

rekt.news 等报道称攻击者经 Wormhole 把资金转到以太坊[26]。链上记录显示，主要通道是 Circle 的 CCTP，要么直接走，要么经 Mayan：攻击者地址收到的约 4,089 万 USDC 中，约 3,400 万来自 Mayan 的 CCTP 合约，约 689 万由 USDC 合约直接铸给它，随后全部换成 ETH。经 Wormhole 和 Sui Bridge 到账的只是少量 ETH、WSOL 和 USDT[30]。本站只核对了以太坊收款地址，Sui 一侧各通道的金额没有逐笔汇总。

17 个月后才被领取的跨链转账

2026 年 10 月 16 日，以太坊地址 0x7f2e…6671 用 Multicall3 批量处理了一批跨链领取和提款，同一批里还有其他用户的 Sui Bridge 转账以及 Lido、Optimism、Scroll 的提款。其中 6 笔 Sui Bridge 转账的发送方是攻击地址 0xe28b…ff06，收款方是 0x8901…919b，合计 86 ETH、9.3 万 USDT 和 0.9 WBTC[30]。领取交易由谁发起、和攻击者有没有关系，链上看不出来。这几笔的桥序号（7021 至 7031）都小于 5 月 22 日 11:12 已被领取的那一笔（7034），而攻击地址在 5 月 22 日 12:38 之后再没发出过交易[31]。由此看，这些转账是冻结前发起、在以太坊一侧搁置了约 17 个月才被领取的。为什么当时没有被领取，公开资料里没有解释。

影响

Sui 代币连锁下跌

Cetus 的池子被抽干后，LOFI、HIPPO 等代币在 DEX 上一小时内跌去一半以上，有的跌幅超过 90%。CETUS 在 DEX 上跌了约 50%，整体跌了约 30%[17]。事发当天，部分 Sui 社区成员坚称 Cetus 没有被黑，问题出在预言机，直到事故报告公布根因才平息[17][19]。6 月 8 日重新上线时，CETUS 仍比 5 月 21 日低约 44%[21]。

同一段代码被别人复制

integer-mate 是开源的，别的项目也在用。Verichains 用 Move 反编译工具扫描了 Sui 上已部署的包，5 月 23 日公布：Kriya（锁仓约 1,000 万美元）和 FlowX（约 460 万美元）用了同一个有缺陷的 checked_shlw，已经修补并升级；Turbos（约 1,030 万美元）的合约里仍有这个函数，只是没有被调用。Verichains 的结论是“dead code is not safe code”[14]。Cyfrin 列出的同类项目是 Kriya、Momentum 和 Bluefin[16]，和 Verichains 的名单不完全一致，两家都没有说明差别从何而来。

“去中心化”之争

批评

Cyber Capital 创始人 Justin Bons 写道，Sui 的验证者正在合谋审查黑客的交易，这说明 Sui 是中心化的，“创始人”持有大部分供应量，而验证者只有 114 个[18]。Bitcoin.com 转述他的看法：冻结本身也许没错，问题在于这种协调冻结竟然做得到[25]。Gabriel Shapiro 的说法更直接：“除了以太坊，每条智能合约链都只是企业链。”[25]

辩护

Sui 基金会称 Sui 是通过委托权益证明治理的去中心化系统，验证者代表自己、SUI 持有人和质押者投票，基金会自己的质押不计入[6]。Cetus 表示“没有人能单方面做这个决定”，会尊重社区的结果[19]。Cointelegraph 提到，也有业内观察者认为快速响应有助于遏制攻击[23]。

rekt.news 的评论是：“代码即法律”从此带了一个星号，除非我们真的需要把钱拿回来[26]。

这次其实是两件事。冻结只需要足够多的验证者在自己的节点上拒绝处理某些地址的交易，不改协议，攻击开始约 2 小时 20 分钟后就做到了。取回则要求全网升级到同一个协议版本，在共识规则里写进一个“允许替攻击者签名”的例外，从投票到编码再到升级用了一周[1][6][10]。前者是验证者集体拒绝服务，后者是协议层面改写了谁能动这笔资产，后者引发的争议更大。截至 2026 年 10 月，Sui 主干代码里出现了一套经共识同步拒绝规则的机制（PeerDenySyncConfig），提议达到一定质押门槛后生效；代码注释没有提到它和 Cetus 事件的关系[11]。

后续处置

当天：停池、冻结、修补

Cetus 的监控在攻击开始约 9 分钟后发现异常，27 分钟后关停核心池子，50 分钟后关停全部相关合约[1]。链上记录显示，最后一笔攻击交易在 10:45，早于核心池子关停的时间[31]，也就是说，关停时损失已经造成。当天下午 integer-mate 合入两次修复，18:15 合约完成升级，但池子没有立刻重启[1][7]。

冻结是怎么做到的

Sui 的交易要得到投票权合计超过 2/3 的验证者认可才能生效[28]。反过来，只要投票权超过 1/3 的验证者拒绝处理，一笔交易就永远凑不够。在 mainnet-v1.48.2 版本里，每个验证者节点的配置中都有这样一张名单[11]：

// crates/sui-config/src/transaction_deny_config.rs（mainnet-v1.48.2）
/// A list of sui addresses that are not allowed to be used as the sender or sponsor.
#[serde(default, skip_serializing_if = "Vec::is_empty")]
address_deny_list: Vec<SuiAddress>,

来源：MystenLabs/sui 仓库 mainnet-v1.48.2 标签，transaction_deny_config.rs 第 36–38 行。

这是节点本地的配置，不需要改协议。5 月 22 日 12:50 起，验证者陆续把攻击者的两个地址加进去，投票权超过 33% 后，这两个地址就无法再发出有效交易[1]。Sui 官方当时的说法是：“大量验证者识别出了持有被盗资金的地址，在另行通知前忽略这些地址的交易。”[17]

和解提议与悬赏

5 月 22 日 18:04，Cetus 和数据分析公司 Inca Digital 在链上给攻击者留言：归还 20,920 ETH 和 Sui 上的全部冻结资金，就可以留下 2,324 ETH（约 600 万美元）作为赏金，此后不再采取法律、情报或公开行动；如果资产被转去出金或混币，就启动法律程序[1][18]。攻击者没有回应。Cetus 随后悬赏 500 万美元，征集能导致攻击者被识别和逮捕的线索，是否发放由 Sui 基金会决定[19]。

链上投票与协议升级

5 月 27 日，Sui 基金会公布投票规则：验证者按质押权重投票；赞成票加反对票要超过总质押的一半（弃权不计），且赞成多于反对，才算通过；基金会自己的质押不计入，以保持中立。投票从太平洋时间 5 月 27 日下午 1 点开始，最长 7 天，满 2 天后结果已定即可提前结束。投票的对象是一次协议升级：在不需要攻击者签名的情况下，把两个冻结地址里的资金转入一个 4/6 多签，Cetus、Sui 基金会和 OtterSec 各持 2 把钥匙。Cetus 按恢复方案提出交易，OtterSec 核对交易与公开方案一致后才签，基金会只在其他签名方无法签署时才签[6]。代表 90.9% 质押的验证者投了赞成票，投票提前结束[6][23]。

同一天，Mysten Labs 提交了实现代码（PR #22237）。PR 说明写道：协议配置可以指定地址别名，让地址 B 的签名充当发送方 A，但只限于一组指定的交易摘要，这些交易也会绕过地址拒绝名单[10]。核心改动在签名校验里：

// crates/sui-types/src/signature_verification.rs（PR #22237 新增部分）
// Replace signers with their aliased addresses if they exist.
let mut signers: NonEmpty<_> = txn.intent_message().value.signers();
if let Some(aliased_addresses) = aliased_addresses {
    for signer in signers.iter_mut() {
        if let Some((aliased, allowed_digests)) = aliased_addresses.get(signer) {
            let digest = intent_message.value.digest();
            // 只有交易摘要在白名单里，才用别名地址的签名代替原地址
            if allowed_digests.contains(&digest) {
                *signer = *aliased;
            }
        }
    }
}

来源：MystenLabs/sui PR #22237 的 diff。

主网的配置写在协议版本 83 里：两个冻结地址各配一笔允许的交易，签名方是同一个新地址。为了把这次升级作为 1.48 版的补丁尽快发出，原定在版本 83 开启的其他几项功能被推迟到版本 84[10]。

5 月 30 日 18:42 和 20:46，两笔恢复交易先后执行。两笔都先调用投票合约 0x4eb9c090…::governance_voting::assert_can_be_executed 确认投票已经通过，这个包地址与基金会公布的投票包一致[6][31]。第一笔从 0xcd89…9562 转出约 2,402 万枚 SUI 和少量其他代币，第二笔从 0xe28b…ff06 转出数十种代币，都转入 0xa165cf7f150f34375b3943ccc66edd52de8561191ec7d663ec32fb836f078544。这个地址此后的交易都用 MultiSig 签名，其中几笔正是 Cetus 公布的资产换仓交易[3][31]。

安全整改

教训与防御

给写数学库的人
  • 移位不是受检运算。Move 的加减乘溢出会 abort，左移不会[29]。左移 k 位之前，先确认 n < 2^(256−k)；或者改用乘以 2^k，让语言自带的溢出检查兜底。
  • 溢出检查要用边界值测试。给 checked_shlw 测 2¹⁹² − 1、2¹⁹²、2¹⁹² + 1 和 2²⁵⁶ − 2¹⁹² 这四个数，原版本和第一次修复的错误都会暴露。
  • 规格明确的数学函数适合做形式化验证。integer-mate 在事后就是这样补上的[9]。
给协议方和审计方
  • 依赖库也是攻击面。Zellic 那一轮审计覆盖了业务合约，没有覆盖 CLMM 每一步计算都要用的数学库[9]。审计范围要写清楚依赖有没有被审。
  • 审计建议落地后要复核。2023 年的审计建议改用 checked_shlw，而 checked_shlw 本身就是错的[12]。
  • 开源代码出事，要做全链排查。Verichains 一天之内就在另外三个项目里找到了同一个函数，其中一个是没被调用的死代码[14]。
  • 给资金流出设上限。这次攻击 15 分钟就打完了，核心池子在第 27 分钟才关停[1][31]。按池子限制流出速度，比事后暂停更能控制损失，Cetus 事后也加上了资产流速限制[1]。
给公链和验证者
  • 冻结和转走一旦用过，就成了先例。这次 Sui 把例外写得很窄，只放行两笔事先公开的交易，并在交易里校验投票结果[10][31]。但冻结所需的质押门槛和取回所需的投票规则，都是出事之后才定下来的。
  • 如果要保留这种手段，门槛、投票规则和适用范围最好事先写成公开的规则，让用户在存钱之前就知道，什么情况下自己的资产可能被冻结或转走。
