区块链被盗事件编年史

总览　/　2021 年　/　DeFi 之夏与闪电贷

BadgerDAO 前端注入

2021 年 12 月 2 日凌晨（UTC），BadgerDAO 用户约 1.2 亿美元的资产被转走，其中一个地址就损失了约 900 枚 BTC 等值的代币。攻击者借 Cloudflare 注册流程的缺陷拿到 Badger 账户的 API 密钥，在官网前端注入脚本，让用户在正常操作时多签了一笔把代币授权给攻击者的交易。整个过程中 Badger 的合约都按设计运行，出问题的是合约审计覆盖不到的两处：用户实际加载的网页，和托管网页的云服务账户。

概要

BadgerDAO 是一个把比特币带进 DeFi 的协议，用户通过官网 app.badger.com 把 BTC 相关代币存进 Sett 金库，官网流量经过 Cloudflare 代理。Cloudflare 当时的注册流程允许账户在邮箱验证完成前就创建和查看 API 密钥。攻击者在 2021 年 8 月底到 9 月初抢先为三个 Badger 账户生成了密钥；9 月中旬，Badger 在不知情的情况下完成了其中一个账户的注册，那把密钥随之生效[1]。

从 11 月 10 日起，攻击者用这把密钥通过 Cloudflare Workers 向官网页面注入脚本。用户在官网上发起交易时，钱包会多弹出一笔把代币授权给攻击者地址的请求。11 月 20 日出现第一笔这样的授权；12 月 2 日，攻击者集中调用 transferFrom，把已获授权的代币和金库份额转走[1]。PeckShield 估计损失约 1.203 亿美元[19]；CoinDesk 报道 Badger 事后报告时写的是 约 1.3 亿美元，其中约 900 万美元的金库份额因合约被暂停而没能取出[22]。

社区报警后 30 分钟内，Badger 暂停了大部分金库。卡住的约 900 万美元份额随后经治理投票追回并原样退还，被盗的 BADGER 由国库补回，其余损失由国库出资，以 wBTC 和分两年发放的 BADGER 补偿[10]。损失最大的地址属于借贷平台 Celsius[12]。Celsius 破产后，其诉讼管理人在 2024 年起诉 Cloudflare 和 BadgerDAO 创始人之一 Christopher Spadafora，两名被告的驳回动议都被法院驳回，案件截至 2026 年 10 月仍在审理[14][17]。攻击者身份至今没有公开。

背景

BadgerDAO 以“让比特币在 DeFi 里可用”为目标，产品包括 Sett 金库、ibBTC、DIGG 和连接比特币与以太坊的 Badger Bridge，治理代币是 BADGER[1][13]。用户把 BTC 相关的流动性代币（如 Curve 的 renBTC/WBTC 池代币）或 BADGER、CVX 等存进 Sett 金库，换到一种可转让的 ERC-20 份额代币（bToken，如 bcrvRenWBTC），金库再把资产投入收益策略[4]。

协议的紧急刹车由 guardian 合约掌握。登记在 guardian 上的地址可以暂停合约，暂停后金库的存入、取出和转账，策略的提款，以及 ibBTC 的铸造和赎回都会被拦下；解除暂停只能由开发多签执行，并且要经过治理批准[1]。

普通用户通过 app.badger.com 与这些合约交互。网站流量经过 Cloudflare 代理，Badger 团队用 Cloudflare 账户管理它。Cloudflare Workers 是 Cloudflare 的边缘脚本功能，可以在流量经过代理时运行脚本、修改网页内容。账户的 API 密钥是用程序管理这些功能的凭证，开发者登录账户后可以查看[1][12]。

使用官网的不只是散户。按 Celsius 诉讼管理人的起诉书，Celsius 陆续把数百枚比特币通过一个 MetaMask 钱包存进 Sett 金库赚取收益[12]。

攻击原理

Badger 的合约始终按设计运行。失守的地方都在合约之外，依次是托管官网的 Cloudflare 账户、用户实际加载的网页，以及用户在钱包里签下的授权。

注册流程漏出了 API 密钥

2021 年 9 月，Cloudflare 社区论坛上有用户报告：新账户在邮箱验证完成之前，就能创建和查看 API 密钥。攻击者可以用别人的邮箱注册，生成密钥，然后等邮箱主人点击验证链接；账户一旦激活，预先生成的密钥就有了 API 权限。论坛上的建议是，收到不是自己发起的注册验证邮件并点了链接的人，要立即重置密码、更换 API 密钥[11]。

Badger 的事后报告补充了两点。一是这个缺陷涉及的是 Global API Key，报告称这类密钥不能删除或停用。二是 Badger 在 9 月中旬完成注册时，界面没有明显提示这个账户早已建好、密钥早已生成[1]。

修好注册流程，不等于收回了已经发出去的密钥

Cloudflare 在 9 月 29 日前后改了注册流程，此后新账户在邮箱验证前看不到 API 密钥[1]。攻击者在 8 月和 9 月初生成的密钥不受影响。Badger 激活的那个账户上的密钥一直有效，攻击者在 11 月 10 日照样用它部署了脚本。Celsius 的起诉书称 Cloudflare 没有主动提醒用户账户可能已被抢注[12]；Cloudflare 在诉讼中则称，问题在论坛公开讨论后两天内就修好了，并主张它对 Celsius 不负注意义务[14]。本站没有找到 Cloudflare 就此事发布的公开事故报告。

Workers 让持钥人改写用户看到的页面

Cloudflare Workers 让账户持有人在流量经过 Cloudflare 代理时运行脚本，修改返回给用户的网页[1]。能部署 Worker 的人，不需要碰源站服务器或代码仓库，就能改变用户实际收到的页面。只审查代码仓库和构建产物，发现不了这种改动。

按 Badger 的报告，攻击者从 11 月 10 日起用 API 权限，通过 Workers 向 app.badger.com 的 HTML 注入脚本。脚本在用户发起 web3 交易时介入，提示用户允许一个外部地址动用钱包里的 ERC-20 代币[1]。用户访问的仍然是官方域名，地址栏和证书都没有异常。

授权比转账更难察觉

ERC-20 代币有两种转移方式。一是持有人自己调用 transfer；二是持有人先用 approve（或 OpenZeppelin 等库提供的 increaseAllowance）给另一个地址一笔额度，对方以后可以随时调用 transferFrom 代为转账，不需要持有人再签名。用户被诱导签下的正是这类授权，被授权方是攻击者控制的外部账户[1]。

// 示意：按 EIP-20 接口语义简化，并非 Badger 或任何代币的真实源码
// 第 1 步：用户在被篡改的页面上签名，只是写下一笔额度，代币没有动
token.approve(attacker, amount);

// 第 2 步：之后任何时候，被授权方都可以自己发起转账
function transferFrom(address from, address to, uint256 value) external returns (bool) {
    require(allowance[from][msg.sender] >= value);   // 只检查额度，不需要 from 再签名
    allowance[from][msg.sender] -= value;
    balanceOf[from] -= value;
    balanceOf[to] += value;
    return true;
}

// 撤销：把额度改回 0，之后攻击者的 transferFrom 会失败
token.approve(attacker, 0);

示意代码，按 EIP-20 标准的 approve/transferFrom 语义简化，省略了事件和其他检查。

授权本身不转移资产，所以第一笔授权在 11 月 20 日上链，到 12 月 2 日攻击者集中调用 transferFrom，中间隔了 12 天，受害者的余额在这段时间里看不出变化[1]。金库份额 bToken 也是 ERC-20，同样可以被授权转走，但它的转账和取出都受 Badger 的暂停开关控制。WBTC、BADGER、CVX 这类普通代币不受 Badger 的暂停约束，这也是暂停之后攻击者仍能卖掉一部分资产的原因[1]。

攻击过程

下面的经过按 Badger 与 Mandiant 合作完成的事后报告整理[1]。

  1. 抢注账户，预生成密钥2021 年 8 月底到 9 月初，攻击者利用 Cloudflare 注册流程的缺陷，抢先为三个 Badger 账户创建账户并生成 API 密钥。
  2. 等 Badger 自己激活9 月中旬，Badger 完成了其中一个账户的注册，并开始用它做正常的 Cloudflare 管理。攻击者的密钥由此获得这个账户的 API 权限。
  3. 注入前端脚本11 月 10 日起，攻击者通过 Workers 向 app.badger.com 注入脚本。用户在官网上发起交易时，会被提示额外批准一笔以攻击者地址为被授权方的代币授权。
  4. 积攒授权11 月 20 日起，这些授权陆续上链。授权不改变余额，用户钱包里的资产照旧。
  5. 集中兑现一个资金账户向攻击者主地址转入 8 ETH 作 gas，攻击者随后对已获授权的代币和金库份额批量调用 transferFrom，把资产转到其他账户变现，再经 Badger Bridge 换成 BTC 离开以太坊。
  6. 被暂停截住一部分12 月 2 日社区报警后，Badger 暂停金库，攻击者对金库份额的 transferFrom 开始失败，已经转到攻击者手里但还没取出的份额也被卡住。WBTC、BADGER、CVX、cvxCRV 等普通代币不受暂停影响，暂停之后仍被卖出。
转账发生在几点

事后报告称大部分合约在 12 月 2 日 03:30（UTC）前已暂停，未暂停金库的最后一笔恶意取出发生在 04:57[1]；Badger 12 月 4 日的用户须知却写着“许多未经授权的交易从 12 月 2 日 05:00（UTC）开始”[2]。两份官方文件对不上，本页统一写作“12 月 2 日凌晨（UTC）”，准确时间以链上记录为准。

按后来的一份治理提案，资金被转走之前，就有用户在 Discord 上对多出来的授权请求提出过疑问。提案据此提议向这名用户支付 10 万美元白帽赏金，本站没有查到赏金最终是否发放[8]。

资金去向

Badger 公布的攻击者主地址是 0x1fcdb04d0c5364fbd92c73ca8af9baa72c269107，用户签下的授权都指向它[1]。被转走的资产此后分成了两种结局。

已经变现的部分

  1. 凭授权转走对用户的代币和金库份额调用 transferFrom
  2. 取出、变现从还没暂停的金库取出底层资产，卖掉普通代币
  3. 换成 BTC 离场经 Badger 自己的跨链桥换成比特币，离开以太坊
  4. 下落不明没有查到这部分资金的公开追回或执法进展

被暂停卡住的部分

  1. 暂停金库已转给攻击者、尚未取出的份额无法再转出或赎回
  2. BIP 76 升级合约加入全局暂停、黑名单和一次性救援函数 patchBalances
  3. BIP 77 救回份额把份额从攻击者地址转进多签 recovered.badgerdao.eth
  4. BIP 78 原样退还按被盗前的持有人逐一退回，约 900 万美元

BIP 76 把 11 个攻击者地址列入黑名单[3]。BIP 78 能做到“原样退还”，是因为每个钱包被盗的 bToken 要么全部被取出，要么完全没动，没有部分取出的情况，追回的份额可以准确对应到原持有人；论坛投票以 50 比 6 通过[4]。约 900 万美元这个数字来自 CoinDesk 对事后报告的报道，起诉书写作 920 万美元[12][22]。12 月 5 日，Badger 通过链上消息联系攻击者，表示愿意为其“发现系统漏洞”给予补偿[2]，本站没有查到攻击者回应或归还资金的公开记录。

影响

损失集中在少数大户

Badger 的公开材料没有给出受害地址总数。已知的是损失高度集中：The Record 和 The Block 都报道一名用户损失约 900 枚 BTC 等值的代币，价值约 5,050 万至 5,080 万美元，The Block 称这些代币是在一笔交易里被转走的[18][19]。Cointelegraph 报道链上分析者认为这个地址属于 Celsius[21]。2024 年的起诉书写明，Celsius 在这次事件中损失约 900 枚比特币，价值超过 5,000 万美元，占全部损失的 40% 以上[12]。

起诉书还给出了补偿的覆盖面：约 37% 的受害者通过追回的金库份额按原代币得到退还，约 17% 通过补发 BADGER 恢复了被盗代币；金额上的大头约 1.21 亿美元无法追回，只能靠后来的补偿方案[12]。

保险没有覆盖前端

FX Empire 报道，Badger 合作的保险方 Nexus Mutual 以保单不覆盖前端攻击为由，拒绝向 Badger 和 Celsius 的用户赔付[23]。本站没有找到 Nexus Mutual 的原始声明。如果报道属实，只覆盖合约代码的保险就管不到前端和云账户这一层。

攻击面从合约移到网页

这次合约没有出错，被攻破的是用户对官网的信任。同类问题此前此后都出现过：2018 年 MyEtherWallet 的域名解析被劫持，用户被引到钓鱼站；2025 年 Bybit 的签名人在被篡改的 Safe{Wallet} 前端上签下了和界面显示不符的交易。这几起都是真网站被攻破；骗子自建假网站骗人签授权的，见诈骗站的 Inferno Drainer。合约审计之外，用户实际加载的网页、托管网页的云账户和 DNS，都成了需要单独设防的环节。

法律上的新问题

Celsius 诉 Cloudflare 案把一个问题带上了法庭：为网站提供安全服务的云服务商，对网站的用户负不负责。2025 年 5 月，法官驳回 Cloudflare 的驳回起诉动议，认为起诉书合理地主张了注意义务、违反义务和因果关系[14]。这只是诉答阶段的裁定，法院按起诉书的说法假定事实成立，没有认定 Cloudflare 有过错。

另一个争点是 BadgerDAO 算不算合伙。Cloudflare 起初在驳回起诉动议中称 Celsius 没有主张合伙的基本要件，后来又以“Celsius 自称是 BadgerDAO 的治理成员、即普通合伙人”为前提，主张 Celsius 受 Cloudflare 订阅协议约束。诉讼管理人在 2026 年 2 月改称 BadgerDAO 并非合伙，BadgerDAO 附议，并主张如果它不是合伙或其他法律实体，可能根本不具备被诉资格[16]。BadgerDAO 还在信中指出，Cloudflare 援引的 Samuels v. Lido DAO 和 Sarcuni v. bZx DAO 两案，法院只是认为原告的主张足以撑过驳回起诉动议，并没有在实体上认定 DAO 是普通合伙[16]。

后续处置

暂停与调查

报警后约 30 分钟，大部分金库被暂停，多数合约在 03:30（UTC）前完成暂停。几个旧金库的合约本身没有暂停功能，只能暂停它们的策略来阻止取出；其中三个策略的 guardian 账户当时无法使用，后来发现参与设计这些合约的策略师账户也有暂停权限，才用它把策略停下，这时已是约 15 小时后[1]。暂停期间用户无法存取和领取奖励，直到 BIP 77 通过后合约重新启用[2][3]。

Badger 请 Chainalysis 做链上调查，Mandiant 做 Web2 部分的调查，并向美国和加拿大的执法部门报案[2]。Cloudflare 账户改了密码、换了 MFA，能处理的 API 密钥都删除或更新了，Badger 也确认 Cloudflare 已修补注册缺陷[1]。按起诉书引用的一封 12 月 15 日的邮件，Spadafora 告诉 Celsius，Mandiant 审查了前端的改动，Halborn 已开始做全面审计和重构，所有合约已升级以拉黑攻击者地址[12]。

事后报告还列了几项准备做的改进：把各合约的紧急暂停统一成“一键全停”，目标是把暂停所需时间从 15 分钟压到 2 至 3 分钟（报告没有说明这里的 15 分钟和前文的“30 分钟内”是否同一口径）；重新上线前对全部 Web2 和 Web3 基础设施做第三方审计；提供部署在 IPFS 上、可以从公开源码构建的前端；开发监控工具，持续比对 app.badger.com 各路由返回的页面和本地构建的版本，以发现代码注入[1]。这些是计划，本站没有找到逐项落实情况的公开说明。

Celsius 的 remBADGER

按起诉书，Celsius 在 2022 年 1 月 13 日收到 89.89 枚 BTC 的补偿，3 月 17 日分到约 901 枚 remBADGER，起诉书称其价值约 210 万美元。3 月 18 日，Celsius 一名员工误把这些 remBADGER 取出换成 BADGER，按规则失去了后续分配；起诉书称 Celsius 通知 Badger 团队后，社区拒绝让它重新存入[12]。4 月的 BIP 91 提议让“一名误操作的受害者”重新存入 901.35 枚 remBADGER，没有点名，但数字与起诉书一致，论坛投票以 9 比 24 未通过[9]。起诉书称，即使没有这次误操作，按 remBADGER 的条款 Celsius 在最好的情况下也会损失惨重[12]。

Celsius 诉 Cloudflare 与 Spadafora

2024 年 7 月 12 日，Celsius 的诉讼管理人 Mohsin Meghji 在纽约南区破产法院提起对抗程序（Adv. Pro. 24-03981）。对 Cloudflare 的诉由是过失和重大过失：在账户验证完成前就发放 API 密钥，发现漏洞后又没有通知用户。对 BadgerDAO 创始人之一、住在多伦多的 Christopher Spadafora，诉由是违反信义义务：起诉书称他明知 BadgerDAO 的安全措施达不到行业标准，仍向 Celsius 招揽了数百万美元的投资[12]。BadgerDAO 本身不在被告之列，BadgerDAO 后来在法庭文件中称 Celsius 考虑过、但决定不起诉它[15]。

2025 年 4 月 28 日，法院认定对 Spadafora 有特定属人管辖权，驳回他的驳回起诉动议，并指出事实虽有争议，但不应在这个阶段解决[13]。5 月 6 日，法院驳回 Cloudflare 的动议。Cloudflare 的理由是：它和 Celsius 没有直接关系，不负注意义务；BadgerDAO 自身缺乏基本安全措施、依赖免费服务，这些介入因素切断了因果关系；问题在论坛公开讨论后两天内就修好，谈不上轻率漠视。法院认为，提供网络安全相关服务、又处在能防止可预见损害位置上的一方，在纽约法下可能负有注意义务；可以预见的介入行为也不切断因果链[14]。Cloudflare 就此申请上诉许可，2026 年 3 月 31 日被联邦地区法院法官 Lewis A. Kaplan 驳回[17]。

此后 Cloudflare 提出反诉和交叉请求，并在 2025 年 8 月依据其自助订阅协议中的赔偿条款，把 BadgerDAO 列为第三方被告，要求赔偿或分担责任。BadgerDAO 以缺乏管辖权为由申请驳回，2026 年 7 月又申请强制仲裁并中止对它的程序[15][17]。截至 2026 年 10 月，案件仍处于证据开示等审前阶段，公开案卷里没有看到对这几项驳回动议的裁定，也没有任何一方被认定承担责任[17]。

教训与防御

给协议的前端与运维团队
  • 把托管前端的云账户、DNS 和 CDN 配置当成和合约同等级的资产管理：开启 MFA，用限定范围、可撤销的 API Token，不用账户级的全局密钥。
  • 定期核对账户成员、密钥清单和审计日志。收到不是自己发起的注册或验证邮件，先查清再点；攻击者的密钥正是在 Badger 一次看似正常的“完成注册”中生效的。
  • 持续比对线上页面和构建产物。边缘脚本、代理层改写这类改动不会出现在代码仓库里，只看仓库发现不了。
给钱包开发者和用户
  • 钱包要醒目显示被授权地址、额度和代币；被授权方是外部账户而不是合约时，应额外提醒。领取奖励这类操作，本不需要给陌生地址授权。
  • 只授权当次所需的额度，定期检查并撤销闲置授权。授权不会立刻转走资产，因此最容易被忽视。
  • 签名请求和预期操作不符时，先拒绝，再去官方渠道核实。这次有用户产生过疑问，但疑问没有变成警报。
给协议设计者和基础设施服务商
  • 紧急暂停要覆盖全部合约，并定期演练。Badger 大部分金库在 30 分钟内暂停，几份 guardian 无法操作的旧合约却拖了约 15 小时。
  • 暂停只保护协议自己的合约。用户已经授出的普通代币，暂停后照样能被转走，所以社区渠道里的异常报告需要有人值守、有处理流程。
  • 买保险前确认保单范围。只覆盖合约代码的保险，管不到前端和云账户被攻破的情况。
  • 服务商的注册流程在验证完成前不应发放任何凭证。修复这类缺陷时，要清点缺陷期间已经生成的凭证，主动通知或吊销；只改流程，旧凭证依然有效。
