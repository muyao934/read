区块链被盗事件编年史

总览　/　2026 年　/　十亿美元级失守与信任链

Liquid Network 凭空铸造 L-BTC

2026 年 9 月 6 日，攻击者在 Liquid 侧链上凭空铸出约 4,000 枚没有比特币支撑的 L-BTC，随后通过正常的赎回通道，在 36 分钟内从联盟储备换走约 3,996 枚真实比特币，储备从约 4,205 枚降到 197 枚。漏洞在 Elements 的范围证明缓存里，是 8 月修补上一个缓存漏洞时新引入的；整个过程没有私钥被盗，每一个签名都按设计执行。侧链上的假币可以回滚，已经付到比特币主链上的真币不能。

概要

Liquid 用保密交易（Confidential Transactions）隐藏金额，每个保密输出都附带一个范围证明（rangeproof），证明金额不是负数。验证范围证明很耗时，Elements 就把验证通过的结果按一个哈希键缓存起来。2026 年 8 月，开发者为了修补上一个缓存键漏洞，把资产承诺和输出脚本加进了键里，但四个字段是不带长度前缀直接拼接的。攻击者构造出一笔交易，它拼接出的字节与一条已缓存的合法记录逐字节相同，伪造的范围证明因此从未被真正验证。

这笔交易凭空造出约 4,000 枚 L-BTC。攻击者 12 分钟后把它们存进联盟成员 SideSwap 的赎回服务，联盟 15 个功能节点中的 11 个签名，放出 3,996.02 枚比特币，SideSwap 在同一个比特币区块里自动转给了攻击者[1][6]。比特币离开储备约四小时后，Blockstream 才让桥节点下线、暂停网络，次日凌晨部署紧急补丁。

攻击者在链上自称“白帽”，补丁上线后归还 3,400 枚，留下约 600 枚并索要 10% 的赏金。Blockstream 拒绝付款，称这是盗窃[14]。Liquid 通过侧链回滚清除了无效的 L-BTC，9 月 9 日恢复出块；截至 10 月 28 日，联盟储备仍比流通的 L-BTC 少约 550 枚，联盟的直接赎回还没有恢复[20]。攻击者身份至今不明，也没有公开的执法行动。

背景

Liquid 是 Blockstream 在 2018 年推出的比特币侧链，主要供交易所和交易商更快地结算比特币[11]。它运行 Elements Core，这是 Blockstream 开发的、从 Bitcoin Core 派生出来的开源区块链软件，Liquid 用自己的链参数和共识配置运行它。网络由分布在各地的 15 个功能节点（functionary）运营，一个区块至少要有其中 11 个的签名才会被接受[1]。按 Blockstream 的说法，联盟成员有 80 多家交易所、基础设施公司和资产管理机构[11]。

比特币和 L-BTC 之间是双向锚定。挂入（peg-in）时，用户把 BTC 锁进联盟控制的多签钱包，等 102 个比特币确认后，在 Liquid 上得到等量的 L-BTC[6]。赎回（peg-out）时，L-BTC 在 Liquid 上被销毁，联盟从储备里放出等量的 BTC。Blockstream 的事故评估写得很直白：1:1 储备完全依赖共识正确地验证“没有凭空产生的 L-BTC”，赎回时没有独立的链下储备核对，赎回机制信任侧链自己验证过的状态[1]。

能直接发起赎回的只有持有赎回授权密钥（Peg-out Authorization Key，PAK）的联盟成员。每个 PAK 条目有两把密钥。离线密钥是从成员冷钱包派生的扩展公钥，功能节点的 HSM 用它确认赎回目的地址属于已登记的条目，放出的 BTC 只能付到由它派生的地址。在线密钥放在运行中的 Elements 节点上，用来签署赎回请求。联盟章程要求成员让比特币收款钱包保持离线。Blockstream 解释，这是为上游故障准备的安全网：即使共识错误地接受了坏的 L-BTC，放出的 BTC 也还在冷钱包里，要有人手动取出才能动，这段时间可以让联盟发现问题[1]。

普通用户一般不直接赎回，而是通过 SideSwap 这样的服务。SideSwap 是 Liquid 上的非托管钱包和交易平台，也是持有 PAK 的联盟成员。它称自 2021 年以来处理了超过 11.1 万次挂入和 20.5 万次赎回，占 Liquid 全部挂入交易的 95%。为了让用户少等，它先垫付挂入，赎回则用一个预先充值的钱包自动付款[6]。事发前，联盟储备约有 4,205 枚 BTC[1]。

漏洞原理

范围证明防的是什么

保密交易用 Pedersen 承诺把金额藏起来，验证者看不到具体数字，只检查输入承诺之和是否等于输出承诺之和。问题在于这些运算发生在一个有限的循环群里，足够大的数会“溢出”，表现得像负数。Elements 的技术文档举过一个例子：(1 + 1) − (−5 + 7) == 0，也就是花掉 2 个币，得到一个“−5”的输出和一个 7 的输出，账照样配平，却凭空多出 5 个币[22]。

范围证明就是为了堵住这一点：它在不暴露金额的前提下，证明承诺里的值落在合法区间内。Elements 还把范围证明和这个输出的资产生成元、输出脚本绑定在一起，同一个证明只对那个位置的那个输出有意义[1]。9 月 6 日的攻击交易创建了一个金额没有输入支撑的保密输出，这正是范围证明要防止的情况[1]。评估没有公开它在金额上的具体构造。

缓存为什么危险

验证范围证明很耗时，同一个证明在交易进内存池和打包进区块时各要验一次。Elements 因此把验证结果缓存起来，第二次直接查表[1]。下面是事发时最新正式版 23.3.3 中的这段代码[5]：

// src/script/sigcache.cpp（Elements 23.3.3），中间的承诺解析从略
bool CachingRangeProofChecker::VerifyRangeProof(
        const std::vector<unsigned char>& vchRangeProof,
        const std::vector<unsigned char>& vchValueCommitment,
        const std::vector<unsigned char>& vchAssetCommitment,
        const CScript& scriptPubKey,
        const secp256k1_context* secp256k1_ctx_verify_amounts) const
{
    uint256 entry;
    // 缓存键只用了证明和金额承诺两项（漏洞 A）
    rangeProofCache.ComputeEntryRangeProof(entry, vchRangeProof, vchValueCommitment);

    if (rangeProofCache.Get(entry, !store)) {
        return true;    // 查到就直接返回“有效”，下面的验证一行都不执行
    }
    // ……（解析金额承诺 commit 和资产生成元 tag）……

    // 真正的验证同时用到证明、金额承诺、输出脚本和资产生成元
    if (!secp256k1_rangeproof_verify(secp256k1_ctx_verify_amounts, &min_value, &max_value,
            &commit, vchRangeProof.data(), vchRangeProof.size(),
            scriptPubKey.size() ? &scriptPubKey.front() : NULL, scriptPubKey.size(),
            &tag)) {
        return false;
    }
    // ……（可花费的输出不允许最小值为 0）……

    if (store) {
        rangeProofCache.Set(entry);    // 真正验证通过，才把键记入缓存
    }
    return true;
}

来源：ElementsProject/elements 仓库 elements-23.3.3 标签（2026-04-13 发布），src/script/sigcache.cpp 第 176–216 行，节选；函数签名和过长的行做了折行。

这段代码的逻辑是：先用几个字段算出一个键去查表，查到就当作有效；查不到才真正验证，验证通过后把键记进表里。它要成立，前提是键必须覆盖验证用到的全部输入。真正的验证用了证明、金额承诺、输出脚本和资产生成元四样东西，键里却只有前两样，这就是漏洞 A。一个节点只要缓存过某个“证明 + 金额承诺”的组合，就可能在资产承诺或输出脚本不同的场合把它当成已验证。缓存是每个节点自己的，有缓存的节点会接受一笔冷缓存节点拒绝的交易，网络因此可能分叉或停止出块。Blockstream 把它定为严重的共识漏洞[1]。2018 年“简化”之前，键里本来包含资产承诺和输出脚本[5]。

修漏洞 A 时引入的漏洞 B

8 月 3 日的修复把缺的两个字段补进了键里。下面是合入 23.x 生产分支的版本[3]：

// src/script/sigcache.cpp（23.x 生产分支，2026-08-03 修复漏洞 A 之后）
void ComputeEntryRangeProof(uint256& entry,
        const std::vector<unsigned char>& proof,
        const std::vector<unsigned char>& commitment,
        const std::vector<unsigned char>& asset_commitment,   // 新增
        const CScript& scriptPubKey) {                         // 新增
    CSHA256 hasher = m_salted_hasher_range_proof;   // 已预先写入随机 nonce 和填充
    // 四段原始字节首尾相接，没有长度前缀，也没有分隔符（漏洞 B）
    hasher.Write(proof.data(), proof.size())                         // 变长
          .Write(commitment.data(), commitment.size())               // 固定 33 字节
          .Write(asset_commitment.data(), asset_commitment.size())   // 固定 33 字节
          .Write(scriptPubKey.data(), scriptPubKey.size())           // 变长
          .Finalize(entry.begin());
}

来源：ElementsProject/elements 提交 212c43f（2026-08-03，cherry-pick 自 6253d7e），src/script/sigcache.cpp；同一修复在 master 分支是提交 c26d719。原代码的函数签名和链式调用各在一行，这里做了折行。

人工审查和 AI 辅助审查都确认补上的字段是对的[1]。问题出在四个字段怎么拼。金额承诺和资产承诺固定 33 字节，范围证明和输出脚本是变长的。范围证明自带一个编码长度的头部，可这个头部只在 secp256k1_rangeproof_verify 里才被检查，而缓存的用途恰恰是跳过这一步。从缓存的角度看，范围证明只是一段没有边界的字节[1]。攻击者可以把证明加长、把脚本缩短同样的长度，拼出来的字节串不变，键也就不变。道理和 "ab" + "c" 等于 "a" + "bc" 一样。

每个节点启动时会随机生成一个 nonce，作为所有缓存键的前缀[5]。它能防止外人预先算出某个节点的缓存键，却挡不住这种碰撞：在同一个节点上，同样的前缀加同样的字节串，SHA256 必然相同。Bitcoin Core 的签名缓存同样把变长的公钥和签名直接拼接，却没有这个问题，因为这两种对象内嵌的长度前缀在查缓存之前就已经检查过了[1]。

评估描述的实际做法是：攻击者沿用一条已经验证并缓存的合法交易所用的资产承诺，以及它目标脚本的最后一个字节，把问题化成让范围证明与键的其余部分对上。最终拼出的字节流与原记录逐字节相同，尽管证明和承诺的内容都不一样。缓存命中就跳过验证，所以伪造的范围证明根本不需要能通过验证，只需要拼出对得上的字节[1]。

被借用的“合法记录”从哪里来

评估没有给出攻击交易的字节级构造。按上图的长度关系推算，攻击交易沿用的资产承诺 A，必须原样出现在那条合法记录的输出脚本 S1 里；改过的金额承诺 C2 也必须和 S1 中相应位置的字节完全一致。普通转账的输出脚本装不下这样一段数据，所以那条“合法记录”很可能是专门构造、先让节点验证并缓存下来的。这与 SideSwap 观察到的情况相符：攻击前有 70 笔形态几乎相同、能配平的交易，每笔都在一个不可花费的输出上带着隐藏的金额[6]。这一段是本站根据公开描述做的推断，不是 Blockstream 的说法。

为什么有的节点接受，有的拒绝

缓存只有在节点手里已经有一条匹配的、真实验证过的记录时，才会给出错误的“有效”。事发时 15 个功能节点运行的都是同一个修复版本，差别只在各自缓存里碰巧存了什么。缓存里有那条记录的节点接受了区块；缓存是冷的节点，以及仍带着漏洞 A 的节点，都执行了真正的验证，验证失败，于是拒绝了区块[1]。带漏洞 A 的节点只用两个字段算键，与四字段算出的记录对不上，反而被迫做了真检查。SideSwap 说，它运行安全版本的节点接受了这笔交易，而标准的 Liquid 节点，包括它自己的一个独立节点，都以金额不平衡为由拒绝[6]。

造币交易所在的区块凑够签名、进入链上状态以后，这约 4,000 枚 L-BTC 在其他节点看来就和真的 L-BTC 没有区别。保密交易隐藏的是金额和资产类型，不是地址和交易图，所以事后可以追查；但在事发当时，单看链上数据发现不了异常[1]。

早期分析与官方结论不一致

Halborn 在 9 月 9 日的分析中认为，问题在于漏洞的补丁已经进了代码库、但还没进正式发布版本，运行旧版本的节点因此暴露[10]。两周后 Blockstream 的评估给出的情况正好相反：被利用的是补丁本身引入的漏洞 B，所有功能节点当时都已运行修复版本，带漏洞 A 的旧版本节点反而拒绝了攻击交易[1]。本页以官方评估为准。

修复

9 月 8 日合入、随 Elements v23.3.4 发布的修复，把范围证明和满射证明（surjection proof）两个缓存的哈希方式，从直接拼接原始字节改为用 CHashWriter 序列化。序列化会在每个字段前写入长度，不同的参数组合不再可能拼出同样的字节流。四个字段都加了长度前缀，包括目前长度固定的两个，这样即使以后字段长度改变，代码仍然正确[1]。同一提交还把满射证明缓存原本完全没有放进键里的 vTags 补了进去[4]。新版本另外加了 -norangeproofcache 启动选项，运营者可以整个关掉这个缓存[1]。

为什么几轮审查都没发现

按 Blockstream 的说法，从修复写成到被利用，有三道检查看过相关代码，每道都有工程师人工复核。第一道是内部 QA 中的 AI 辅助代码审查，确认缓存键里加对了字段。第二道是测试网功能测试，确认修复挡住了针对漏洞 A 的缓存投毒交易。第三道是用当时较新的开放权重模型 Kimi-K3（通过 PremAI 使用）对 Elements 29.x 分支做的补充 AI 扫描，那个分支已经含有同样的无前缀拼接[1]。三道检查问的都是“漏洞 A 修好了没有”，没有一道在问新的拼接方式本身有没有歧义。

最先报告漏洞 A 的 stutxo 当天提交的第二个修复，用的正是带长度前缀的序列化，但它针对的是一个非生产分支。Blockstream 当时判断这个更大的改动超出了所报问题的范围，生产分支选了改动更小的直接拼接[1]。评估同时强调，包括 stutxo 自己的分析在内，事发前没有任何审查者发现漏洞 B。

攻击过程

攻击者没有公开过自己的代码。下面的经过来自 SideSwap 根据自己的服务记录和链上数据整理的时间线，以及 Blockstream 的评估[6][1]。

  1. 补丁公开9 月 1 日漏洞 A 的修复合入公开仓库，含漏洞 B 的代码从此人人可读。随后几天，有少数钱包通过 SideSwap 反复做小额挂入、卖出 L-BTC、再小额赎回。其中一个钱包 2025 年 4 月经受监管的交易所注资，闲置 17 个月后在 9 月 1 日第一次动用。SideSwap 说无法在链上证明这些钱包属于攻击者，已把细节交给 Blockstream。
  2. 准备启动资金9 月 5 日 20:55，攻击者向 SideSwap 挂入 0.001 BTC。这笔钱经一个跨链桥追溯到以太坊上 Tornado Cash 的一笔提款，是攻击钱包得到过的唯一一笔资金。
  3. 预演攻击者把换到的 L-BTC 拆成 20 个输出，从 22:01 起发送一长串几乎相同的交易，每笔都在一个不可花费的输出上带着隐藏的金额，再合并、再拆开。这 70 笔交易全部配平、没有造币，所以标准节点都接受了。最后一笔在 9 月 6 日 13:52，比真正的造币早一分钟。SideSwap 扫描了 9 月 1 日到网络暂停之间的全部区块，这种交易形态正好出现 71 次：70 次预演，1 次造币。
  4. 造币13:53，区块 4,050,336 中的一笔交易创建了一个金额没有输入支撑的保密输出，约 4,000 L-BTC。缓存里存有匹配记录的节点把伪造的范围证明当成了已验证。
  5. 试探出口14:00，攻击者先赎回 2.5 L-BTC，SideSwap 约一分钟后从自有库存付出 2.49749857 BTC。这 2.5 枚和随后的 4,000 枚都来自同一笔造币交易。
  6. 大额赎回14:05，攻击者把 4,000 L-BTC 存入赎回服务，14:06 被销毁。订单超出 SideSwap 自己赎回钱包的余额，付款两次因余额不足失败；14:28，联盟签名者放出 3,996.02 BTC，SideSwap 在同一区块把 3,995.99999857 BTC 转到攻击者的地址。从造币到比特币离开储备，大约 36 分钟。

联盟的赎回流程为什么放行

Blockstream 把损失归结为两个独立的问题：Elements 的共识漏洞，以及一个成员的 PAK 签名流程在配置上的缺口[1]。把赎回拆开看，资金先后经过四道关口：

  1. 共识验证缓存命中，伪造的范围证明被当成已验证，约 4,000 L-BTC 进入链上状态
  2. PAK 授权SideSwap 的在线密钥签名，目的地是已登记的地址，授权本身合法
  3. 联盟 11/15 签名只核对侧链状态，没有链下储备核对，也不看订单规模
  4. “离线”收款钱包实际在线，同一区块自动转出，没有延迟和人工复核

第一道关口失守以后，后面每一道都只核对了自己那一项。Liquid 在事故报告中说，功能节点没有被黑，私钥没有泄露，按白名单地址授权提款的赎回机制“按设计运行”[13]。评估的说法是，PAK 机制核验的是一个真实的签名请求，背后的 L-BTC 在请求被评估之前就已经被共识错误地当成了真的[1]。

本可以把损失挡在可追回范围内的是第四道。章程要求成员让比特币收款钱包保持离线，这样即使共识出错，放出的 BTC 也还在成员手里。SideSwap 事后承认了两点：它的赎回授权密钥放在线上服务器，每笔联盟付款都在同一个比特币区块里自动转给客户，这一设计把 Liquid 上一个可以逆转的事件变成了比特币上不可逆转的付款；它的赎回流水线没有规模上限、速度控制、相对 L-BTC 总量的上限，也不检查存款钱包的年龄和历史，一个只存在了几个小时的钱包下了约 4,000 L-BTC 的订单，没有经过任何人工复核[6]。Blockstream 在评估中转述了这两点，并写明联盟章程要求这把密钥离线保管[1]。

资金去向

  1. 凭空铸出约 4,000 L-BTC，Liquid 区块 4,050,336
  2. SideSwap 赎回销毁约 4,000 L-BTC，另有 2.5 L-BTC 的试探
  3. 联盟放款，转给攻击者3,996.02 BTC（区块 965,783）；连同试探，攻击者共收到约 3,998.5 BTC
  4. 部分归还9 月 7 日 3,400 BTC 回到联盟锚定钱包（区块 965,950），约 598.5 BTC 未还

数字来自 Blockstream 的评估和 SideSwap 的时间线[1][6]。未归还的数额有两种口径。TRM Labs、Decrypt 和 Bitcoin.com News 报的是攻击者地址里剩下的 598.5 BTC[9][14][15]，与 SideSwap 公布的两笔付款之和减去 3,400 BTC 大致相符。Blockstream 的评估写的是“约 602 BTC 仍待追回”，口径是储备中可归因于未授权交易的部分[1]。

事发当天的早期报道写的是“从储备转出 4,019.4 BTC”“剩下 207 BTC 多一点”[12]，与官方后来公布的 3,996.02 BTC 放款和 197 BTC 余额不同。储备从约 4,205 BTC 降到 197 BTC，差额里还包括网络暂停前已在处理的正常赎回[1]。本页统一使用官方数字。

影响

L-BTC 持有人

网络暂停期间，Liquid 上的一切都停了。USDt、DePix 等由各自发行方背书的资产没有受漏洞影响，但同样用不了[1]。受影响最大的是 L-BTC 持有人。交易所暂停了 L-BTC 的充提，部分交易所到 10 月下旬仍未恢复[8]。9 月 10 日交易恢复后，储备只覆盖流通量的约 86%，联盟的直接赎回一直关闭[9][17]。有用户在 X 上说，他经 SideSwap 和 SideShift.ai 绕道换回比特币，前后花了几周，价差和手续费合计约 5%[17]。直到 10 月 20 日兑换商通道恢复，持有人才重新有了按 1:1（扣 0.1% 手续费）换回比特币的路径[7]；联盟自己的直接赎回到 10 月底还没开。

规模

按事发时的价格，被取走的比特币价值约 3.19 亿至 3.2 亿美元[9][11]。TRM Labs 称这是有记录以来针对比特币侧链的最大一次攻击，也是截至 9 月 8 日 2026 年最大的一起加密货币盗窃，排在 4 月的 KelpDAO 和 Drift 之前[9]。这个“年度之最”没有保持多久：本站收录的 9 月 24 日 Bitget 事件，以及 10 月 29 日的币安事件，规模都更大。

联盟模式的信任边界

Liquid 的锚定钱包由 15 个身份公开的成员控制[12]，安全依赖的是一组已知的功能节点，而不是去中心化的验证者集合。这次事故说明，签名门槛设得再高，联盟能核实的也只有侧链告诉它的东西。TRM Labs 把它和以往的跨链事件做了对比：Ronin 是验证者私钥被盗，Poly Network 是跨链合约有缺陷，Wormhole 是签名被伪造，Liquid 则是验证软件的漏洞让攻击者直接伪造了资产本身[9]。保密交易隐藏金额的特性，又让这种伪造在当时更难从外部看出来[1]。

AI 审查的两面

漏洞 A 在五天内被外部研究者、Blockstream 的内部审查和一个外部团队分别确认，评估认为 AI 辅助工具正在改变审查旧代码库的方式[1]。可同样有 AI 参与的审查和补充扫描，都看过含漏洞 B 的代码，都没有发现问题。Adam Back 在 X 上说，漏洞 B 是“对一个 AI 发现的、本身也不严重的漏洞做了错误修复”引入的[16]；而 Blockstream 的正式评估把漏洞 A 定为严重的共识漏洞[1]，两种说法对漏洞 A 严重程度的判断并不一致。

后续处置

止损

9 月 6 日 18:26，Blockstream 协调让 Liquid 的桥节点下线。用户的交易几乎都先经过桥节点再到出块节点，桥节点一停，新交易和赎回就都停了。Blockstream 同时通知交易所暂停 L-BTC 充提。9 月 7 日 01:09，紧急补丁先于正式版本部署到桥节点[1]。

链上谈判与 3,400 BTC 的归还

攻击者用 OP_RETURN 留言自称白帽之后，双方通过链上的加密消息沟通。攻击者承诺，等所有节点修补了漏洞就归还资金；补丁上线后，资金开始回流[9]。9 月 7 日 16:09，3,400 BTC 回到联盟锚定钱包[1]。

剩下的约 600 BTC 成了争议。9 月 9 日，攻击者在一笔比特币交易里写道，Blockstream 只拿出“150 万美元（甚至可能是 0）来保护 50 亿美元的资产”，是“明目张胆的安全疏忽”，要求 Blockstream“用自己的钱”付 10% 作为漏洞赏金，否则“你们会因为自己的不负责任和吝啬，让所有持有人承担 15% 的损失”[14][15][21]。另一条留言称 Blockstream“妄想、贪婪、傲慢”，并威胁公开双方全部的加密通信，除非对方付这 10%[21]。

Blockstream 拒绝付款

未经授权拿走资产并扣着不还，是犯罪，不是负责任的披露。这不是白帽行为，这是盗窃。

Blockstream 在 X 上的声明，2026-09-11，据 Decrypt 与 Bitcoin.com News 转引[14][15]

Blockstream 说，它参与谈判“不应被误解为接受对方的行为或条件”；它不会成为一个先例的一方，让为比特币社区开发开源软件的人去付一笔远超自身经济参与的赎金。它也不打算让用户承担：“比特币是硬通货，不能无成本地铸造。比特币不会为了付赎金而让用户打折。”如果资金不归还，它将与执法机构、交易所和取证专家一起走“一切合法途径”[14][15]。

Ledger CTO Charles Guillemet 此前就说，如果这是在链上用加密合约谈下来的报酬，“看起来更像勒索，而不是白帽黑客”[13]。社交媒体上也有人站在攻击者一边，指责 Blockstream 代码写得差，出了事又去找执法机构[15]。截至本文写作时，本站没有查到公开的执法行动或起诉。Blockstream 在评估的结尾向攻击者喊话：如果动机是暴露弱点而不是造成持久的伤害，就归还剩下的比特币。它同时宣布为 Elements 等关键开源基础设施设立正式的漏洞赏金计划，明确范围并提供安全港[1]。

回滚侧链

因为问题出在缓存，Blockstream 可以关掉范围证明缓存、重放受影响的那段链：没有缓存，Elements 就会正确拒绝依赖漏洞 A 或 B 的交易。团队再用独立实现 rust-elements 交叉核对，确认了两个无效的原始输出和由它们派生的四笔交易[1]。9 月 9 日 21:05，修正后的链在攻击前最后一个区块 4,050,335 之后接上替换的 4,050,336 号区块，下一个区块重放了 329 笔经核实有效的交易。Blockstream 称，当前的 Liquid 链上已没有漏洞 A 或 B 造成的增发[1]。

回滚只对侧链有效。已经付到比特币主链上的 3,996 BTC 不受影响。一周前 Cronos 为 Tectonic 回滚链状态时，损失还留在同一条链上，大部分追了回来；Liquid 的损失已经过桥，回滚只能清掉假币。

分阶段恢复

恢复计划分三步：恢复出块并暂停锚定操作，重放经独立核实的有效交易，网络状态完全恢复后再重开锚定[1]。前两步从 9 月 9 日开始，9 月 10 日用户交易恢复。9 月 29 日，Liquid 宣布对 Elements v23.3.4 做独立的外部安全审计，并更新 PAK 名单，替换现有条目，确保所有赎回密钥都放在冷存储里[17]。

10 月 20 日，联盟说管理储备的联盟软件已经更新，能适应事故后的账目状态；BTC 与 L-BTC 的半自动兑换开始恢复，协议不设额度。最后一步是恢复完整的 1:1 储备，再为 PAK 持有人有控制地重开联盟赎回，并通过区块浏览器公开监测储备，没有给出日期[2]。SideSwap 当天重开赎回，付款全部来自它自己的比特币钱包，次日称已处理约 600 笔、付出 60 多 BTC[7][8]。10 月 27 日的联盟更新说，独立安全审计接近完成[20]；Crypto Briefing 则报道外部审计在 10 月 20 日前已经完成[18]，两者说法不一。

填补缺口的比特币从 10 月 27 日开始转入。当天一笔 2.53048101 BTC 的交易进了 Samson Mow 公布的联盟钱包，Mow 称这是测试，“剩下的 600 BTC 会在几天内转入”[19]。Crypto Briefing 报道，Blockstream 承诺自己补上缺口、不让用户承担，称这是“何时”而不是“是否”的问题[18]。10 月 28 日又转入 50 BTC，缺口降到约 550 BTC[20]。公开报道没有说明这些比特币由谁转出。

责任之争

SideSwap 承认的

赎回授权密钥在线运行，联盟付款在同一区块自动转给客户；赎回订单没有规模、速度和来源检查。它把这笔订单约 4 BTC 的 0.1% 手续费全额退给了联盟，并说会采用联盟安全审查后制定的规则，而不是自行零散修改[6]。

SideSwap 同时指出的

联盟多年来知道它的密钥在线运行；发现漏洞后，没有人告诉它细节，也没有人要它改变做法或暂停赎回；它应要求部署的安全版本没能阻止攻击；联盟自己的 11/15 签名也没有检查订单规模。“单个成员不能为整个网络的完整性负责。”[6]

披露过程也有争议。Bitcoin Red Team 联合负责人 Calle 回应 Adam Back 时说：“原来无视红队的一封邮件只要 600 BTC。”他称 Blockstream 对补丁历史的说法有选择性且不准确。前 Blockstream 高管 Samson Mow 否认有邮件被无视。Calle 说，会等 Blockstream 发布事后报告再公布自己的完整记录[16]。Blockstream 的评估则称，它在首次报告后 24 小时内完成了漏洞 A 的分级和修复，一周内又从两个渠道独立确认，“没有漏掉报告，没有无视警告”[1]。截至 10 月底，本站没有找到 Bitcoin Red Team 公布的完整记录。

教训与防御

给写验证缓存的人
  • 缓存键必须覆盖验证函数的全部输入。Elements 后来把这条写成了注释：除了无状态的上下文，每个携带数据的参数都必须进键。
  • 多字段做哈希，用带长度前缀的序列化或其他无歧义的编码，不要直接拼接原始字节。只要有一个变长字段没有边界，就可能拼出同样的字节串。
  • 对象内部带长度头的，在查缓存之前先检查它。Bitcoin Core 的签名缓存同样是拼接，因为先检查了长度前缀才没有出事。
  • 给缓存留一个关闭开关，并定期不走缓存重新验证全链。这次正是靠关掉缓存重放，确定了哪些交易无效。Blockstream 表示会把事故中写的零缓存复验工具和缓存碰撞搜索工具保留为常设工具[1]。
  • 用差分测试比较“走缓存”和“不走缓存”的验证结果，两者不一致就是漏洞。
给修漏洞的人
  • 修复本身也是新代码，要按漏洞的类别测试，而不是只重放报告里的那一个概念验证。漏洞 B 漏过的三道检查，问的都是“漏洞 A 修好了没有”。
  • 有多种修复方案时，默认选结构上最安全的那个。Blockstream 事后把这定为共识关键问题的默认规则，偏离要有理由并经批准[1]。
  • 修复合入公开仓库就等于公开了漏洞。先确认生产节点都已部署，提交标题也不要直接描述可利用的问题。这次的修复是以描述漏洞的标题合入的，当时还没有任何正式版本包含它[6]。
  • 修复期间，把操作风险告诉最可能放大损失的成员。SideSwap 说它没有拿到漏洞细节，也没有被要求暂停赎回[6]。
给跨链桥和侧链运营者
  • 放行赎回要有不依赖共识状态的检查：单笔上限、速度上限、相对流通总量的比例上限、大额订单人工审核。共识是第一道防线，不能是唯一一道。
  • 收款钱包真正离线，付款延迟、人工转出。PAK 离线密钥原本就是为“共识出错”准备的安全网，自动转发让它失效了。
  • 把共识异常和赎回暂停联动起来。这次内部监控在 14:10 报出块停滞，比比特币离开储备早 18 分钟，网络在四个多小时后才暂停。
  • 持续公开核对储备与流通量，偏差超过阈值就自动暂停赎回。
