Poly Network 跨链攻击

2021 年 8 月 10 日，攻击者借 Poly Network 跨链管理合约之手调用了一个特权函数，把负责签名放行跨链提款的 keeper 换成了自己的地址，随后从以太坊、BSC 和 Polygon 的资产池转走约 6.11 亿美元，这是当时金额最大的 DeFi 盗窃案。攻击者此后在链上留言与项目方周旋，两周内交还了除被冻结的 USDT 之外的全部资产。一个能执行任意跨链消息、同时又握有特权的合约，从此成为跨链桥安全的反面教材。

概要

Poly Network 是一个跨链协议：用户在一条链上把资产锁进 LockProxy 合约，另一条链上的 LockProxy 根据 keeper 签过名的跨链消息放出对应资产。keeper 的公钥存放在 EthCrossChainData（下文简称 ECCD）合约里，而 ECCD 的 owner 是负责验证并执行跨链消息的 EthCrossChainManager（简称 ECCM）。ECCM 执行跨链消息时只检查目标地址是不是合约，不限制调用哪个合约、哪个函数。

攻击者构造了一个方法名，让它和固定参数类型拼接后算出的 4 字节函数选择器，恰好等于 ECCD 中修改 keeper 公钥的函数 putCurEpochConPubKeyBytes 的选择器。这条跨链消息带着真实有效的签名和证明进入 ECCM，ECCM 以 owner 身份调用 ECCD，把 keeper 换成了攻击者的地址。此后攻击者可以自己给任意提款消息签名，在三条链上依次转走了资产池里的主要资产[12][15][22]。Poly Network 转发的 SlowMist 分析明确指出，这不是 keeper 私钥泄露[2]。

当天 13:40（UTC），Tether 冻结了攻击者以太坊地址上约 3,343 万枚 USDT[8]。第二天攻击者开始归还资产，并在链上自问自答，称攻击是“为了好玩”，想赶在内部人员之前暴露漏洞[27][30]。Poly Network 改称其为“白帽先生”（Mr. White Hat），提出 50 万美元赏金和“首席安全顾问”的邀请[5][29]。8 月 23 日攻击者交出共管多签钱包的最后一把私钥，8 月 25 日 Tether 把冻结的 USDT 重新发行给项目方，受影响资产全部收回[9][10]。攻击者的身份至今没有公开。2023 年 7 月，Poly Network 再次失守，这一次是 4 个 keeper 中有 3 个对伪造的跨链证明签了名[34]。

背景

Poly Network 于 2020 年 8 月 18 日上线，由 Neo、Ontology、Switcheo 等项目联合发起，目标是在比特币、以太坊、Neo、Ontology、Cosmos 这类架构不同的“异构链”之间转移资产和任意数据[11]。到 2021 年 8 月，它已接入比特币、以太坊、Neo、Ontology、BSC、Heco、OKExChain、Polygon、Elrond、Zilliqa 和 Cosmos-SDK 这 11 条链[26]。PeckShield 称它“按锁仓量和流动性算，可以说是最大的跨链协议之一”[18]。跨链兑换应用 O3 Swap 的跨链交易池也依赖 Poly Network，事后要等 Poly Network 清点完资产才能恢复[7]。

一次从源链到以太坊的跨链转账，大致经过以下几步[13][22]：

  1. 源链发起用户在源链把资产锁进 LockProxy，源链的跨链管理合约把目标链、目标合约、方法名和参数打包成一条跨链消息。
  2. 中继到 Poly 链源链的 relayer 监听到这条消息，提交给 Poly 链。Poly 链是一条由共识节点维护的中继链，区块头里的 crossStatesRoot 是本区块所有跨链消息的默克尔根。
  3. 共识节点签名Poly 链的共识节点对区块头签名。在以太坊这一侧，这些节点的公钥称为 keeper，存放在 ECCD 合约里。
  4. 提交到目标链以太坊的 relayer 调用 ECCM 的 verifyHeaderAndExecuteTx，提交 Poly 链区块头、签名和默克尔证明。
  5. 验证并执行ECCM 检查签名数是否达到门限、消息是否在默克尔树里、是否执行过，然后按消息里的目标合约和方法名发起调用。正常情况下调用的是 LockProxy 的 unlock，把资产放给收款人。

以太坊一侧的三个合约各管一件事：ECCM 负责验证和执行，ECCD 存储 keeper 公钥和已执行消息的记录，LockProxy 托管资产。LockProxy 的 unlock 只接受 ECCM 的调用；ECCD 的写操作只接受 owner 的调用，而 ECCD 的 owner 就是 ECCM[12][13]。这样安排的本意，是让 ECCM 在 Poly 链共识节点正常换届时，通过 changeBookKeeper 更新 ECCD 里的 keeper 公钥。

被攻击时，Poly Network 在以太坊上的合约没有在 Etherscan 上公开验证源码，安全研究者只能拿 GitHub 上发布的代码对照链上行为[16]。按仓库的提交记录，修复前的 EthCrossChainManager.sol 最后一次修改是在 2020 年 8 月 27 日，提交说明为“update based on audit review”，此后到事发再没有改动[12]。

漏洞原理

这次攻击没有破解任何密码学，也没有用到被盗的 keeper 私钥。问题出在两处设计的叠加：ECCM 执行跨链消息时不限制目标，而 ECCD 把修改 keeper 的权力交给了 ECCM[13][19]。下面的代码均摘自 polynetwork/eth-contracts 仓库修复前的版本[12]。

ECCM：签名对了就执行，执行什么由消息决定

verifyHeaderAndExecuteTx 是公开函数，任何人都可以调用。它用 ECCD 里存的 keeper 公钥验证 Poly 链区块头的签名，用默克尔证明从区块头里取出跨链消息，然后把消息里的目标合约、方法名和参数交给内部函数 _executeCrossChainTx：

// EthCrossChainManager.sol（修复前），verifyHeaderAndExecuteTx 节选
// 从 ECCD 读出当前的 keeper 列表
address[] memory polyChainBKs = ECCUtils.deserializeKeepers(eccd.getCurEpochConPubKeyBytes());
uint256 curEpochStartHeight = eccd.getCurEpochStartHeight();

uint n = polyChainBKs.length;
if (header.height >= curEpochStartHeight) {
    // It's enough to verify rawHeader signature
    // 门限 n - (n - 1) / 3：4 个 keeper 需要 3 个签名，只剩 1 个 keeper 时只需 1 个
    require(ECCUtils.verifySig(rawHeader, headerSig, polyChainBKs, n - ( n - 1) / 3),
        "Verify poly chain header signature failed!");
} else {
    // ……（用当前纪元的区块头和 headerProof 验证较早的 rawHeader）……
}

// ……（用 proof 取出跨链消息 toMerkleValue，并检查是否执行过）……

require(toMerkleValue.makeTxParam.toChainId == uint64(2),
    "This Tx is not aiming at Ethereum network!");
address toContract = Utils.bytesToAddress(toMerkleValue.makeTxParam.toContract);
// 目标合约、方法名、参数都直接取自跨链消息，执行前没有任何限制
require(_executeCrossChainTx(toContract, toMerkleValue.makeTxParam.method,
    toMerkleValue.makeTxParam.args, toMerkleValue.makeTxParam.fromContract,
    toMerkleValue.fromChainID), "Execute CrossChain Tx failed!");

来源：polynetwork/eth-contracts 仓库 commit d16252b（PR #12 的基线），contracts/core/cross_chain_manager/logic/EthCrossChainManager.sol 第 133–166 行节选。去掉了一层缩进，长行按参数折行；英文注释是原有的，中文注释是本站加的。

_executeCrossChainTx 只检查目标地址是不是合约，然后用方法名拼出函数选择器，直接发起调用：

// EthCrossChainManager.sol（修复前）
function _executeCrossChainTx(address _toContract, bytes memory _method, bytes memory _args,
    bytes memory _fromContractAddr, uint64 _fromChainId) internal returns (bool){
    // 唯一的目标检查：是合约就行
    require(Utils.isContract(_toContract), "The passed in address is not a contract!");
    bytes memory returnData;
    bool success;

    // The returnData will be bytes32, the last byte must be 01;
    // 选择器 = keccak256(方法名 + "(bytes,bytes,uint64)") 的前 4 字节，方法名来自跨链消息
    (success, returnData) = _toContract.call(abi.encodePacked(
        bytes4(keccak256(abi.encodePacked(_method, "(bytes,bytes,uint64)"))),
        abi.encode(_args, _fromContractAddr, _fromChainId)));

    // Ensure the executation is successful
    require(success == true, "EthCrossChain call business contract failed");

    // Ensure the returned value is true
    require(returnData.length != 0, "No return value from business contract!");
    (bool res,) = ZeroCopySource.NextBool(returnData, 31);
    require(res == true, "EthCrossChain call business contract return is not true");

    return true;
}

来源：同上，第 183–201 行。函数签名和 call 一行按参数折行；第一条英文注释过长，换成了中文注释，其余未改动。

按设计，跨链消息要调用的是 LockProxy 的 unlock(bytes,bytes,uint64) 这类专门接收跨链调用的函数，参数类型是固定的。代码似乎默认“参数类型固定，就只能调到这类函数”。Kraken Security Labs 在事后分析中指出，这个隐含假设并不成立[22]。

ECCD：只认 owner，而 owner 正是 ECCM

ECCD 中写入 keeper 公钥的函数是这样的：

// EthCrossChainData.sol（修复前）
// Store Consensus book Keepers Public Key Bytes
function putCurEpochConPubKeyBytes(bytes memory curEpochPkBytes)
    public whenNotPaused onlyOwner returns (bool) {
    ConKeepersPkBytes = curEpochPkBytes;   // 整个 keeper 列表被传入的字节覆盖
    return true;
}

// Ownable.sol（修复前），onlyOwner 只比较调用者地址
modifier onlyOwner() {
    require(isOwner(), "Ownable: caller is not the owner");
    _;
}
function isOwner() public view returns (bool) {
    return _msgSender() == _owner;
}

来源：同一 commit，contracts/core/cross_chain_manager/data/EthCrossChainData.sol 第 44–48 行；contracts/libs/ownership/Ownable.sol 第 37–47 行节选。

ECCD 的 owner 是 ECCM，这是为了让 keeper 正常换届时，ECCM 的 changeBookKeeper 能调用 ECCD 写入新公钥。可是 ECCM 在执行任何一条跨链消息时，调用者也是它自己。从 ECCD 的角度看，“ECCM 在做 keeper 换届”和“ECCM 在转发一条跨链消息”是同一个 msg.sender，无从区分[13][22]。

正规换届：changeBookKeeper

要求区块头高度高于当前纪元起点，nextBookkeeper 字段非空；区块头要有当前 keeper 达到门限的签名；传入的新公钥列表算出的地址，必须等于区块头里承诺的 nextBookkeeper。全部通过后才写入 ECCD。

被利用的路径：一条普通跨链消息

只要求 Poly 链区块头签名有效、默克尔证明正确。消息里的参数原样传给 putCurEpochConPubKeyBytes，不和任何承诺比对，任意字节都能成为新的 keeper 列表。

4 字节选择器碰撞

Solidity 用“函数名(参数类型)”这个字符串的 keccak256 哈希的前 4 字节作为函数选择器。ECCD 写入函数的选择器来自 putCurEpochConPubKeyBytes(bytes)，而 ECCM 拼出的字符串总是“消息里的方法名”加上 (bytes,bytes,uint64)。表面上两者不可能相同。但方法名完全由消息发送者决定，攻击者只要不断换方法名，直到哈希的前 4 字节恰好等于目标选择器。4 字节只有约 43 亿种取值，普通计算机就能搜出来[13][22][28]。攻击者用的方法名是 f1121318093[15][20]：

// 示意：两个不同的签名字符串，keccak256 后前 4 字节相同（数值引自 Kraken 与 rekt.news 的分析）
bytes4(keccak256("putCurEpochConPubKeyBytes(bytes)"))     // = 0x41973cd9，ECCD 的写入函数
bytes4(keccak256("f1121318093(bytes,bytes,uint64)"))      // = 0x41973cd9，攻击者的“方法名”

示意代码，选择器数值来源：Kraken Security Labs[22]、rekt.news（引用 Kelvin Fichter 的分析）[28]。

选择器对上以后，参数类型不同也不碍事。从代码看，ECCM 发出的调用数据是 abi.encode(args, fromContract, fromChainId)，ECCD 的函数只声明了一个 bytes 参数，按 ABI 规则只会读出第一个参数，也就是攻击者放进去的新 keeper 公钥，后面两个参数被忽略。函数返回 true，又恰好满足 _executeCrossChainTx 对返回值的检查。

换掉 keeper 之后

攻击者把 ECCD 里的公钥列表换成只含一个自己控制的地址 0xA87fB85A93Ca072Cd4e5F0D4f178Bc831Df8a00B[13][15]。签名门限按 n - (n - 1) / 3 计算，4 个 keeper 时是 3，只剩 1 个 keeper 时变成 1。BlockSec 回放交易时也看到了这一点：替换 keeper 的那笔交易里还是 4 个合法 keeper，随后的提款交易里 keeper 只剩 1 个[16]。

此后攻击者可以自己构造一个 Poly 链区块头，在 crossStatesRoot 里放进任意解锁消息，用自己的私钥签名后提交。LockProxy 的 unlock 只检查调用者是不是 ECCM、消息声称的来源合约是不是登记过的 LockProxy[12]，伪造的消息两条都能满足。

哪一环本可以拦住

环节当时的检查能否作为安全边界
源链跨链合约按用户传入的参数生成跨链消息，不限制目标合约和方法[13]可以设防，但每条接入链都要做到
Ontology relayer只检查 RPC 是否成功、参数是否为空，不检查目标合约和方法名是否合理[15]不可靠，链下程序可被绕过或配置出错
Poly 链对源链提交的跨链请求照单打包，恶意消息成了 Poly 链上一笔有效交易[15]BlockSec 认为在中继链上做策略检查“可能是更好的位置”[17]
以太坊 relayer只转发目标为 LockProxy 的消息，这次确实拒绝了[15]不能：verifyHeaderAndExecuteTx 谁都能调用
ECCM只检查目标地址是合约能，补丁就加在这里
ECCD只检查调用者是 owner，owner 是通用执行器 ECCM能：keeper 只应由 changeBookKeeper 写入

修复

Poly Network 在事发当天提交补丁，8 月 16 日合并。补丁的核心是三张白名单：只有登记过的合约才能发起跨链；跨链消息只能调用登记过的目标合约和方法[12][18]。

// EthCrossChainManager.sol（PR #12 合并后）
mapping(address => bool) public whiteListFromContract;
mapping(address => bool) public whiteListToContract;
mapping(bytes => bool) public whiteListMethod;

// crossChain()：只有白名单里的合约能发起跨链
require(whiteListFromContract[msg.sender],"Invalid from contract");

// verifyHeaderAndExecuteTx()：执行前检查目标合约和方法
// only invoke PreWhiteListed Contract and method For Now
require(whiteListToContract[toContract],"Invalid to contract");
require(whiteListMethod[toMerkleValue.makeTxParam.method],"Invalid method");

来源：polynetwork/eth-contracts 仓库 commit 2b1cbe0（PR #12 的合并提交），EthCrossChainManager.sol 第 15–17、123、198–200 行。

补丁还加了 recoverEpochPk：部署时登记一份正确的 keeper 公钥，合约暂停期间可以把它写回 ECCD，每份登记只能用一次。从代码看，这是为了把被攻击者改掉的 keeper 公钥改回来。发起方白名单是 PeckShield 审查时提出、团队采纳的建议。PeckShield 和 BlockSec 都认为白名单能修复这次被利用的漏洞，也都声明审查是非正式的，不保证系统没有其他问题[17][18]。2021 年 12 月，ECCM 按审计报告再次修改，把合约白名单和方法白名单合成一张表，按目标合约分别登记允许的方法，白名单里的方法只能在登记它的合约上调用[12]。

攻击过程

下面的步骤主要依据 BlockSec 对以太坊这一侧的还原[15]，BSC 和 Polygon 上的过程相同。第 4 步各家说法不一，见后文。

  1. 准备资金据 SlowMist 的追踪，攻击者最初的资金来自门罗币（XMR），在交易所换成 BNB、ETH、MATIC 后提到 3 个地址[13]。Chainalysis 发现，攻击前一天攻击者从 Hoo 交易所提出 0.47 ETH 支付 gas[23]。
  2. 在源链发出恶意消息攻击者在 Ontology 链上发起一笔跨链交易，目标链是以太坊，目标合约是 ECCD，方法名是 f1121318093，参数是攻击者自己的公钥[15][22]。Beosin 认为，攻击者先在 Ontology 链上试验确认有效，才发出这笔批量修改多条链 keeper 的消息[21]。
  3. 被打包进 Poly 链Ontology relayer 没有检查目标和方法名，把这笔交易提交给 Poly 链，它成了 Poly 链上一笔由共识节点正常签名的有效交易[15]。
  4. 绕过以太坊 relayer，替换 keeper以太坊 relayer 发现目标合约不是 LockProxy，没有转发。攻击者自己调用 ECCM 的 verifyHeaderAndExecuteTx，提交 Poly 链上真实的区块头、签名和默克尔证明，校验全部通过。ECCM 随即调用 ECCD，把原来的 4 个 keeper 换成攻击者控制的 1 个地址[15]。
  5. 伪造提款攻击者用自己的私钥给自制的区块头签名，再次调用 verifyHeaderAndExecuteTx，让 ECCM 调用 LockProxy 的 unlock，把资产转到自己的地址。在以太坊、BSC、Polygon 上分多笔交易执行[20]。
  6. 其他链与正常用户PeckShield 指出，同样的手法在 Heco 上没有成功，因为那里的 relayer 行为与其他链不同[18]。keeper 被换掉之后，其他正常的跨链交易随之回滚[2]，直到修复上线后才陆续补发[6]。
第 4 步的三种说法

BlockSec 认为以太坊 relayer 拒绝了这条消息，替换 keeper 的交易是攻击者自己提交的[15]。SlowMist 的描述是“在目标链使用官方 relayer 正常提交数据，替换 keeper”[13]。Beosin 则说 BSC 上是 relayer 先处理了这条跨链交易，攻击者再把 BSC 上用过的有效签名重放到以太坊和 Polygon[21]。三种说法在关键一点上一致：恶意消息来自 Ontology，经 Poly 链拿到了真实有效的签名。verifyHeaderAndExecuteTx 是谁都能调用的公开函数，所以不论哪种说法成立，relayer 一侧的检查都拦不住这次攻击。

转移路径

在以太坊上，攻击者把 96,389,444 USDC 和 673,227 DAI 存进 Curve，换成 95,269,796 枚 3CRV，不到一小时后又赎回成 96,942,061 枚 DAI。Chainalysis 认为，这是为了把可以被发行方冻结的中心化稳定币换成去中心化的 DAI[23]。在 BSC 上，攻击者把约 3,210 万 BUSD 和 8,760 万 USDC 作为流动性存进 Curve 的分叉项目 Ellipsis Finance[13]。以太坊上的约 3,343 万 USDT 没来得及转走，被 Tether 整笔冻结[8]。

攻击者很快开始给自己发带附言的交易，公开喊话，其中一条写着“Wonder why Tornado? Will miners stop me? Teach me please”[28]。用户 hanashiro.eth 用交易附言提醒攻击者 USDT 已被冻结，攻击者回赠了 13.37 ETH[23][28]。

8 月 11 日，攻击者宣布“准备归还”，Poly Network 给出三条链上各一个收款地址，BSC 和 Polygon 上的资产最先退回[24][27]。攻击者还要求 Poly Network 建一个多签钱包，用来接收剩余资产[23]。最后一批资产转进了这个需要双方密钥共同操作的以太坊多签钱包，Poly Network 称之为“3/4 多签钱包”[3]，公开资料没有说明各方各持几把密钥。攻击者表示会在“所有人都准备好”时交出最后一把密钥[24]。8 月 19 日，96,942,063 枚 DAI 被放行；8 月 23 日，攻击者公开了私钥，Poly Network 取回剩余的 28,953 枚 ETH 和 1,032 枚 WBTC[6][9]。

被冻结的 USDT 由 Tether 按正式流程重新发行给 Poly Network：双方从 8 月 12 日开始商讨，8 月 19 日 Tether 请 Poly Network 确认收款的多签地址，8 月 25 日把 33,431,200 枚 USDT 发到这个地址[8][10]。退回的 96,942,063 枚 DAI 和 BSC 上的 87,557,051 枚 BUSD 都不是被盗时的原币种，Poly Network 在 8 月 23 日把它们换回 USDC，用于恢复用户的 USDC 余额，滑点和手续费由团队自己的资金补足[8]。

影响

当时最大的 DeFi 盗窃案

按事发时的价格，这次转走的金额超过了 2018 年 Coincheck 被盗的约 5.35 亿美元和 2014 年 Mt.Gox 丢失的约 4.5 亿美元比特币[31]，Chainalysis 称之为“史上最大的 DeFi 盗窃案”[23]。这个纪录保持了约 7 个月，2022 年 3 月被 Ronin 跨链桥的约 6.24 亿美元超过[32]。

跨链桥接连失守

Poly Network 之后，跨链桥接连出事。CertiK 统计，2022 年因跨链桥安全事件损失约 13 亿美元，全部来自 5 起事件，约占当年全部损失的 35%[33]。这些事件的手法各不相同，失守的都是“谁有权放行一笔提款”这一环：

“白帽”之争

Poly Network 在给攻击者的留言中写道“我们认为你的行为是白帽行为”，并承诺“你不会为这次事件承担责任”[27]。安全界有不少人反对这种说法。曼彻斯特城市大学讲师、白帽黑客 Katie Paxton-Fear 对 BBC 说，白帽测试要有授权范围、与团队配合、写专业报告、证明风险后就停手，把这次攻击称作白帽“非常令人失望”。前美国司法部和 FBI 官员 Charlie Steele 则指出，私人公司无权承诺免于刑事追诉[27]。

冻结与链上透明

公开资料中，这次被发行方冻结的只有 USDT。Tether 在接到通知约 70 分钟后冻结了攻击者的地址[8]。rekt.news 的评论是“他们的币，他们说了算”，提醒持有 USDT 的人记住这一点[28]。Chainalysis 推测，攻击者把以太坊上的 USDC 换成 DAI，就是为了避开这种风险[23]。

Elliptic 和 Chainalysis 都认为，这件事说明从加密资产盗窃中获利越来越难：攻击者的地址几分钟内就被公开，交易所、稳定币发行方、分析公司和社区实时盯着每一笔转账[23][24]。攻击者自称从一开始就打算归还；媒体和分析人士则推测，他可能发现这么大的金额根本无法洗白[29][31]。两种说法都无法证实。

后续处置

修复与分阶段恢复

Poly Network 把恢复分成五个阶段：修复漏洞、主网升级、按项目恢复跨链、恢复资产、恢复服务[3]。补丁先交给 PeckShield、BlockSec 和 Beosin 审查，8 月 16 日随主网升级上线[1][4]。BlockSec 说明，它审查的只是以太坊和 BSC 的补丁，而且补丁没有在 Poly 链本身加安全策略[17]。升级后 Poly Bridge 下架了全部资产，项目方要重新申请、测试通过后才恢复跨链，到 8 月 26 日恢复了 59 种资产[10]。攻击期间卡住的正常跨链交易在之后几天陆续补发[6][7]。依赖 Poly Network 资产池的 O3 Swap，要等 WBTC 和 ETH 归还、USDC 恢复、USDT 解冻之后才能恢复[7]。

赏金与“首席安全顾问”

Poly Network 起初提出 50 万美元漏洞赏金，攻击者公开表示不要，说考虑把它交给为区块链安全做过贡献的技术社区[5][24]。8 月 17 日，Poly Network 邀请攻击者担任“首席安全顾问”，同时表示仍会把赏金转到攻击者认可的地址[5]。8 月 19 日，在“没有得到白帽先生积极回应”的情况下，Poly Network 向攻击者公开的捐款地址转入 160 ETH[6]。连同公众的捐款，这个地址共收到约 52.5 万美元的 ETH[24]。攻击者交出私钥时，把这个地址里的钱连同赏金全部转回 Poly Network，要求分给受影响的用户[24]。本页查阅的公开资料里，没有对方接受这个职位的记录：Poly Network 在 9 月的回顾文章里只写了“曾邀请”[1]。

攻击者是谁

没有定论。据 Chainalysis 8 月 12 日的报道，SlowMist 称已掌握攻击者的邮箱、IP 地址和设备指纹，Chainalysis 表示无法证实[23]。SlowMist 追踪到攻击者的初始资金来自门罗币[13]，Chainalysis 发现支付 gas 的 ETH 提自 Hoo 交易所[23]，rekt.news 提到一笔交易的发送地址与 FTX、币安、OKEx 的账户有关联，质疑攻击者是否用错了地址[28]。这些线索都没有公开的后续。Poly Network 多次表示不追究攻击者的法律责任[5][27]。截至 2026 年 10 月，公开资料中没有与本案相关的起诉或执法记录。

我相当确信他们有意愿、也有能力恢复并保护这个项目……我唯一的担心是，作为整个网络核心的 Poly 链不是很去中心化，而这一点我帮不上忙。也许是我错了。

攻击者在链上的留言（中文为本站翻译），收录于 Poly Network 的事后回顾[1]

2023 年的第二次失守

CertiK 记录的攻击开始时间是 2023 年 7 月 1 日 18:47（UTC），Dedaub 记的是 7 月 2 日 18:47，相差整一天，本页无法核实哪个正确[33][34]。攻击者在一条链上锁定少量代币，再在另一条链上用伪造的证明提出数量大得多的同种代币，对 57 种资产重复这个过程[32][33]。Poly Network 称受影响的是 10 条链，CertiK 写的是 11 条[32][33]。

攻击者地址上的账面价值高达数百亿美元，CertiK 写约 420 亿，Halborn 写约 430 亿[33][35]。但目标链上大多没有足够的流动性：Metis 上的 Poly 映射 BNB 和 BUSD 根本卖不出去，OpenOcean、StackOS、Revomon、NEST 等项目在事发后还撤走了流动性[33]。实际变现的金额，rekt.news 估计约 440 万美元，CertiK 和 Halborn 估计约 1,000 万美元[32][33][35]。

据 Dedaub 的还原，这次没有利用任何合约逻辑漏洞：伪造的区块头上确实有 4 个 keeper 中 3 个的有效签名，满足门限，而这份 keeper 名单两年来没有变过。Dedaub 认为最可能是这 3 个 keeper 的私钥被盗或被滥用，但也不排除内部作恶，或者运行 keeper 的链下系统被攻破，三种情况的效果一样。Dedaub 还发现默克尔验证器接受路径为空的证明，只要叶子节点的哈希等于签过名的状态根即可。从攻击开始到 Poly Network 暂停多条链上的 ECCM 合约，用了约 7 个小时[34]。本页没有找到 Poly Network 发布的根因报告。

2021 年攻击者在留言里唯一的担心，是 Poly 链“不是很去中心化”。两年后失守的，正是放行跨链提款的签名权，据 Dedaub，它两年来一直握在同样 4 个外部账户手里。

教训与防御

给跨链桥和合约开发者
  • 通用的消息执行器不能同时握有特权。ECCM 既执行任意跨链消息，又是 ECCD 的 owner，一条消息就等于拿到了 owner 权限。修改签名者这类操作，应放在跨链消息到达不了的合约里，或者只留一个专用入口。
  • 在目标链合约里限制跨链消息能调用的合约和方法，最好按合约逐一登记方法。不要依赖 relayer 过滤，任何人都能绕过 relayer 直接调用合约。
  • 不要把“参数类型固定”当成访问控制。函数选择器只有 4 字节，方法名一旦来自外部输入，就能对上任意函数。
  • 更换签名者集合是桥上最危险的操作，只应有一条路径，要求与旧签名者集合的承诺严格匹配，最好再加时间锁。
  • 托管大额资产的合约要在区块浏览器上公开验证源码。Poly Network 被攻击时没有做到[16]。
给协议运营方和应急响应者
  • 桥的安全上限就是签名者集合。2023 年的事件中，4 个外部账户里的 3 个就能放出任意资产。签名者应分散在不同运营方，私钥放在 HSM 或 MPC 中，并定期轮换。
  • 为 keeper 变更和大额解锁设置实时告警和暂停开关。2021 年 keeper 被换后，正常的跨链交易随即开始回滚，这本身就是可以捕捉的信号；2023 年从攻击开始到暂停合约用了约 7 个小时。
  • 按资产设置提款限额和单位时间流出上限，让一次失守的损失有上限。2023 年铸出的资产名义价值数百亿美元，实际损失不大，主要是因为目标链上流动性不足。
  • 事先和稳定币发行方、交易所建立联络渠道。2021 年 Tether 在接到通知约 70 分钟后完成冻结，但它只能冻结自己的币。
  • 分析事故时先查关键状态有没有被改过。BlockSec 起初在提款交易里只看到 1 个 keeper，判断可能是私钥泄露或签名服务出错，没有去查 keeper 本身是否已被替换[16]。
  • 和攻击者谈判可能换回资金，但私人公司无权承诺免于追诉，“白帽”的称呼也会被认为是在替犯罪行为洗白[27]。
