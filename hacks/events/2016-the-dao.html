区块链被盗事件编年史

总览　/　2016 年　/　智能合约登场

The DAO 重入攻击

2016 年 6 月 17 日，攻击者利用 The DAO 合约“先转账、后记账”的顺序错误，在几个小时里转走约 364 万枚 ETH，约占 The DAO 全部资金的三分之一。为了追回这笔钱，以太坊社区在一个月后硬分叉，链从此分成 ETH 和 ETC 两条。

概要

The DAO 是一个用智能合约管理的投资基金，代币持有人投票决定资金投向。合约提供了“分拆”功能，让反对多数决议的人带着自己那份 ETH 离开。分拆函数 splitDAO 在转出 ETH 和发放奖励之后，才把调用者的代币余额清零；而发放奖励时会调用调用者的地址，把执行权交给对方。

攻击者在这次回调里再次调用 splitDAO。由于余额还没清零，同一份余额可以一次又一次地兑换成 ETH，全部转进攻击者控制的“子 DAO”。子 DAO 的规则规定资金要锁定约 27 天才能动用，这段时间成了社区应对的窗口[1]。

社区先提出软分叉冻结资金，后因该方案会给矿工带来拒绝服务风险而放弃。最终以太坊在 2016 年 7 月 20 日于区块 1,920,000 硬分叉，把 The DAO 及其子 DAO 的资金转入只能退款的 WithdrawDAO 合约，每 100 个 DAO 代币可取回 1 ETH[2][3]。不接受分叉的人继续运行原链，即今天的 Ethereum Classic，攻击者在那条链上保住了全部所得。攻击者的身份至今没有经过司法认定。

背景

The DAO 建在 2015 年 7 月 30 日上线的以太坊上[15]，以太坊的上线经过见大事记的以太坊主网上线（Frontier）。The DAO 由德国创业公司 Slock.it 的团队发起，核心合约主要由 Christoph Jentzsch 编写。它的设想是一个“没有管理人的风险投资基金”：任何人都可以用 ETH 换取 DAO 代币，代币持有人对投资提案投票，资金只按投票结果流出。

为了防止多数人投票把钱转给自己，合约设计了两道保护。一是“策展人”（Curator），负责审核可以收款的地址白名单。二是分拆：如果少数人不同意多数人的决定，可以发起分拆，带着自己按比例应得的 ETH 进入一个新的“子 DAO”，并为它指定自己的策展人。后来被攻击的，正是这第二道保护。

众筹从 2016 年 4 月 30 日开始，持续 28 天，共募集约 1,150 万枚 ETH，按当时价格超过 1.5 亿美元，参与者超过 1.1 万人，约占当时 ETH 总量的 14%[6][8]。在当时，这是规模最大的众筹项目之一。

上线后不久就有人提出质疑。5 月下旬，Dino Mark、Vlad Zamfir 和 Emin Gün Sirer 发文指出投票机制存在博弈漏洞，呼吁暂停 The DAO。6 月 12 日，Slock.it 的 Stephan Tual 公开表示团队发现了一个“递归调用”漏洞，但称 The DAO 的资金没有风险[5]。五天后，攻击就发生了。

漏洞原理

分拆提案投票通过后，投了赞成票的人可以调用 splitDAO。这个函数依次做五件事：第一次调用时创建子 DAO，并把当前的资金总额和代币总量存成快照；按调用者的代币余额算出应得的 ETH，转给子 DAO；转移奖励权益；给调用者发放奖励；最后把调用者的代币销毁，也就是余额清零。

问题出在第四步和第五步的顺序上。下面是 The DAO v1.0 源码中 splitDAO 的后半段[4]，英文注释是原有的，中文注释是本站加的：

// DAO.sol（v1.0），splitDAO 函数后半段，中间奖励代币的记账部分从略
// Move ether and assign new Tokens
// 按余额占比算出应转走的 ETH；splitBalance 和 totalSupply 是第一次调用时存下的快照
uint fundsToBeMoved =
    (balances[msg.sender] * p.splitData[0].splitBalance) /
    p.splitData[0].totalSupply;
if (p.splitData[0].newDAO.createTokenProxy.value(fundsToBeMoved)(msg.sender) == false)
    throw;                        // ETH 转进子 DAO
// ……（奖励代币 rewardToken 的转移记账）……

// Burn DAO Tokens
Transfer(msg.sender, 0, balances[msg.sender]);
withdrawRewardFor(msg.sender); // be nice, and get his rewards   // 外部调用在清零之前
totalSupply -= balances[msg.sender];
balances[msg.sender] = 0;      // 余额到这里才清零
paidOut[msg.sender] = 0;
return true;

来源：blockchainsllc/DAO 仓库 v1.0 标签，DAO.sol 第 639–671 行（去掉了一层缩进）。

withdrawRewardFor 会算出调用者应得的奖励，再让奖励账户 rewardAccount 把钱付给他：

// DAO.sol（v1.0）
function withdrawRewardFor(address _account) noEther internal returns (bool _success) {
    if ((balanceOf(_account) * rewardAccount.accumulatedInput()) / totalSupply < paidOut[_account])
        throw;

    uint reward =
        (balanceOf(_account) * rewardAccount.accumulatedInput()) / totalSupply - paidOut[_account];
    if (!rewardAccount.payOut(_account, reward))   // 调用奖励账户付款
        throw;
    paidOut[_account] += reward;
    return true;
}

// ManagedAccount.sol（v1.0），奖励账户的付款函数
function payOut(address _recipient, uint _amount) returns (bool) {
    if (msg.sender != owner || msg.value > 0 || (payOwnerOnly && _recipient != owner))
        throw;
    if (_recipient.call.value(_amount)()) {   // 交出全部剩余 gas，收款方的代码被执行
        PayOut(_recipient, _amount);
        return true;
    } else {
        return false;
    }
}

来源：同上，DAO.sol 第 716–726 行，ManagedAccount.sol 第 57–66 行。

_recipient.call.value(_amount)() 是当时 Solidity 里最常见的转账写法。它会把剩余的全部 gas 转给收款地址；如果收款地址是一个合约，它的 fallback 函数就会被执行，即使转账金额是 0 也一样。也就是说，splitDAO 还没执行到清零那一行，执行权就已经交到了调用者手里。

攻击者让一个合约来持有 DAO 代币并调用 splitDAO。这个合约的 fallback 函数里写的是“再调用一次 splitDAO”。第二次进入时，函数开头的各项检查照样通过，因为第一次调用卡在 withdrawRewardFor 里，余额还没清零；fundsToBeMoved 用的又是第一次调用时存下的快照，所以每一层算出来的金额都一样。同一份余额就这样被一层层重复兑现，直到攻击者主动停下或 gas 不够用，然后调用栈才逐层返回，清零只执行了一次。

什么是重入

一个函数还没执行完，就因为它发出的外部调用被再次调用，这就叫重入（reentrancy）。重入本身不一定是漏洞；只有当函数在外部调用之后才更新状态时，重入进来的那次调用看到的才是过期的状态。今天的合约开发规范把这条原则总结为“检查-生效-交互”（Checks-Effects-Interactions）：先检查条件，再改自己的状态，最后才和外部合约交互。splitDAO 恰好把后两步颠倒了。

按这个原则改写，只需要在任何外部调用之前，先记下要转的金额并把余额清零。下面是示意写法，并非 The DAO 当时的补丁：

// 示意：按“检查-生效-交互”调整顺序后的分拆逻辑
uint fundsToBeMoved =
    (balances[msg.sender] * p.splitData[0].splitBalance) / p.splitData[0].totalSupply;
uint reward =
    (balances[msg.sender] * rewardAccount.accumulatedInput()) / totalSupply - paidOut[msg.sender];

totalSupply -= balances[msg.sender];   // 生效：先改自己的状态
balances[msg.sender] = 0;
paidOut[msg.sender] = 0;

// 交互：最后才调用外部合约。此时再重入，余额已经是 0，算出来的金额也是 0
if (!p.splitData[0].newDAO.createTokenProxy.value(fundsToBeMoved)(msg.sender)) throw;
if (!rewardAccount.payOut(msg.sender, reward)) throw;

示意代码，省略了奖励代币的记账和部分检查。

为什么漏洞早有人提过却没修

The DAO 合约部署后不能修改代码。要修复，只能通过 newContract 提案把资金迁到新合约，而普通提案的辩论期至少两周。另外，即使奖励账户里一分钱都没有，payOut 照样会调用收款方并触发 fallback，所以“奖励为零”并不能让这个漏洞变得无害。

攻击过程

根据合约代码和事后公开的分析，攻击大致分以下几步。攻击者没有公开过自己的代码，下面的部分细节来自事后对链上交易的还原。

  1. 准备代币和攻击合约攻击者买入 DAO 代币，部署一个 fallback 函数会再次调用 splitDAO 的合约，由这个合约持有代币。
  2. 发起分拆提案提出一个“更换策展人”的分拆提案，把新策展人设为自己控制的地址，并用持有代币的地址投赞成票。分拆提案的最短辩论期是 1 周；投票截止后，有 27 天可以执行分拆。
  3. 触发递归6 月 17 日，攻击合约调用 splitDAO。The DAO 把 ETH 转进新建的子 DAO，在发放奖励时回调攻击合约，攻击合约的 fallback 再次调用 splitDAO，同一份余额被反复兑换。
  4. 保住代币，重复执行余额最终会被清零。The DAO 的 transfer 只阻止“已投票且提案未到期”的地址转账，投票截止后就不再受限。事后的分析普遍认为，攻击者在递归结束前把代币转到另一个地址，让最后的清零落了空，然后把代币转回来，用同一批代币发起下一笔攻击交易。
  5. 停手数小时内累计转走约 364 万枚 ETH 后，攻击在 The DAO 还有大量余额时停了下来，原因不明。剩下的资金随后被白帽团队用同样的方法转走保护起来。
// 示意：攻击合约的核心结构（不是真实的攻击代码）
contract Attacker {
    DAO dao;
    uint proposalId;
    address curator;
    uint depth;

    function attack() {
        dao.splitDAO(proposalId, curator);   // 第一次进入
    }

    function () {                            // 收到 payOut 时被执行的 fallback
        if (depth < 20) {                    // 控制递归层数，避免 gas 耗尽导致整笔交易回滚
            depth++;
            dao.splitDAO(proposalId, curator); // 余额尚未清零，再兑现一次
        }
    }
}

示意代码。真实攻击每笔交易的递归层数和代币转移细节以链上记录为准。

资金去向

攻击者转走的 ETH 进了一个和 The DAO 结构相同的子 DAO，地址是 0x304a554a310c7e546dfe434669c62820b7d83490，通常被称为 Dark DAO[1]。按子 DAO 的规则，这笔钱至少约 27 天内无法取出。硬分叉后，同一笔资金在两条链上的命运完全不同。

在分叉后的以太坊（ETH）上

  1. Dark DAO约 364 万枚 ETH，处于锁定期
  2. 硬分叉改写状态区块 1,920,000，The DAO 及子 DAO 的余额被直接转走
  3. WithdrawDAO 合约只有一个功能：按 100 DAO 换 1 ETH 退款
  4. 代币持有人基金会公告时，已有约 450 万枚 ETH 被领回

在原链（ETC）上

  1. Dark DAO没有分叉，资金原样留在攻击者的子 DAO 里
  2. 锁定期结束攻击者取得约 364 万枚 ETC 的控制权
  3. 陆续转出变现数月后这部分 ETC 价值约 850 万美元[8]
  4. 身份仍是谜2022 年的调查通过链上追踪指向一名嫌疑人，未经司法认定

影响

以太坊分裂

这是以太坊第一次面对一个根本问题：当代码的执行结果和社区的是非判断冲突时，以哪个为准。支持分叉的一方认为，被盗资金规模大、仍在锁定期内，追回它是维护用户信任的必要之举。反对的一方坚持“代码即法律”（code is law）：合约允许的就是有效的，回滚资金会破坏区块链不可篡改这一最根本的承诺[7]。分叉之后，后者聚集在 Ethereum Classic 周围，两条链从此并存。

合约安全的起点

重入成了智能合约安全的第一课。“检查-生效-交互”被写进开发规范，Solidity 文档加入了相应警告，重入锁（如 OpenZeppelin 的 ReentrancyGuard）成了常用工具，上线前做独立审计也逐渐成为惯例。一度流行的“用 transfer() 只给 2300 gas 防重入”的做法，在 2019 年 EIP-1884 调整 gas 价格后也被认为不再可靠。

监管

2017 年 7 月，美国 SEC 发布针对 The DAO 的调查报告，认定 DAO 代币属于证券，相关发行可能违反美国证券法[9]。此后 SEC 又以未登记发售证券处理了 Munchee、Block.one 等 ICO[13][14]，见大事记的ICO 狂潮（2017–2018）。

后续处置

白帽“抢先转移”

攻击者停手时，The DAO 里还有大量 ETH，而漏洞对所有人都开着。Griff Green 等人组成的白帽团队于是用同样的手法，把剩余的大部分资金转进他们控制的子 DAO[6]。这是区块链史上第一次大规模的“为了保护资金而抢先攻击”。

软分叉为什么放弃

软分叉方案要求矿工拒绝任何会减少 The DAO 及其子 DAO 余额的交易[1]。问题在于，要判断一笔交易会不会碰到这些合约，矿工必须先执行它；而被拒绝的交易不会被打包，也就不用付 gas。攻击者因此可以免费制造大量需要执行、最终又被拒绝的交易，拖垮矿工[12]。

硬分叉

硬分叉直接在状态里改写余额，不存在上面的问题。Carbonvote 投票中，3,964,516 枚 ETH 投了赞成，577,899 枚投了反对；但参与投票的 ETH 只占总量的约 5.5%，赞成票中约四分之一来自同一个地址，这一点至今被反对者引用[7]。7 月 20 日 13:20:40（UTC），区块 1,920,000 执行分叉，约 85% 的算力跟随[2][3]。

退款与无人认领的余款

WithdrawDAO 合约只有一个提款功能，持有人按每 100 个 DAO 代币取回 1 ETH[3]。众筹后期参与的人当时付出的价格高于这个比例，多付的部分进了 ExtraBalance，由单独的合约处理。多年后，ExtraBalance 等合约里仍有约 7.05 万枚 ETH 无人认领。2026 年 1 月，Griff Green 等人宣布用这笔钱设立 TheDAO Security Fund，以质押收益资助以太坊安全工作，由以太坊基金会的资助管理团队做资格审核[11]。

攻击者是谁

攻击者从未被正式认定。2022 年，记者 Laura Shin 在为新书做调查时借助 Chainalysis 追踪 ETC 链上的资金流向，指向奥地利程序员、TenX 联合创始人 Toby Hoenisch[10]。Hoenisch 否认了这一说法，此事也没有进入任何司法程序。

教训与防御

给合约开发者
  • 先改状态，再调外部。任何会把执行权交出去的调用（转账、调用其他合约、代币回调）都放在状态更新之后。
  • 给涉及资金的函数加重入锁，但不要只依赖锁。2023 年 Curve 的事件说明，锁本身也可能因为编译器问题失效。
  • 优先用“拉取”代替“推送”：让用户自己来领钱，而不是在复杂逻辑中途给用户打钱。
  • 不要指望 gas 限额挡住重入。gas 价格会随协议升级改变。
给协议设计者
  • 托管大额资金的合约要有出事时的手段：限额、暂停、可控的升级路径。The DAO 一样都没有，最后只能动用整条链的分叉。
  • 漏洞被公开讨论时，应当假设攻击者也在读。从 Slock.it 承认存在递归调用问题到攻击发生只隔了五天。
  • 链级干预是代价极高的最后手段，它换回了资金，也永久地分裂了社区。
