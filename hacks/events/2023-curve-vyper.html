Curve / Vyper 编译器重入锁失效

2023 年 7 月 30 日的九个小时里，四个与原生 ETH 配对的 Curve 池子先后被掏空，各家统计的损失在 6,200 万到 7,350 万美元之间。池子的源码给每个函数都加了同一把重入锁，但 Vyper 0.2.15 到 0.3.0 把它编译成了五把互不相干的锁。这个编译器缺陷 2021 年就被顺手修掉，却没有人意识到已部署的合约还带着它。

概要

Curve 的 ETH 池子在 remove_liquidity 里先用 raw_call 把 ETH 发给用户，再更新 LP 总量。这段时间里执行权在收款方手里，池子靠 @nonreentrant('lock') 挡住回调：五个改动资金的函数写的是同一个 key，本应共用一个锁槽，任何一个在执行，其余四个都进不来。Vyper 0.2.15、0.2.16 和 0.3.0 的存储分配代码忽略了 key，给每个带装饰器的函数各分配一个新槽，锁只能防止函数重入自己[1][3]。

攻击者用闪电贷借来 ETH，在 ETH 回调里调用同一池子的 add_liquidity 或 exchange，让池子按一组互相矛盾的中间状态记账：稳定池的 LP 总量被旧值覆盖，CRV/ETH 池的账面余额多于实际余额。当天 13:10 到 22:00（UTC），pETH/ETH、msETH/ETH、alETH/ETH、CRV/ETH 四个池子依次被抽干[2]。不少攻击交易在公开内存池里被 MEV 机器人照抄抢跑，最早出手的几个攻击者反而没拿到钱[8][10]。

到 8 月 5 日，alETH 池和 pETH 池的资金经链上谈判退回，msETH 池和 CRV/ETH 池第二笔的资金由白帽机器人 c0ffeebabe.eth 退回。CRV/ETH 池第一笔的攻击者一直没有回应，他拿走的 7,193,401.77 枚 CRV 和 7,680.49 枚 WETH 没有追回[2][18]。CRV 价格在 8 月 1 日最低跌到约 0.48 美元。Curve 创始人 Michael Egorov 用 CRV 作抵押在多个借贷协议借了大量稳定币，有被清算的风险，他以每枚约 0.40 美元场外出售了约 1.06 亿枚 CRV 来还债[15][19]。

背景

Curve 是以太坊上专做稳定币和锚定资产兑换的 AMM。除了官方池子，它还有 Factory：任何人都可以按官方模板部署新池，新池子是指向同一个实现合约的 EIP-1167 最小代理。被攻击的 pETH/ETH、msETH/ETH、alETH/ETH 都是这样的 factory 池，三者指向同一个实现合约 0x6326DEbBAa15bCFE603d831e7D75f4fc10d9B43E。它在链上的已验证源码第一行是 # @version 0.2.15，正文与 curve-factory 仓库 2021 年 7 月 26 日版本的 Plain2ETH.vy 完全相同[6][7]。CRV/ETH 是 Curve 自己的 v2 加密资产池，用 Vyper 0.3.0 编译[7]。

三个 factory 池分别承载三个协议发行的锚定 ETH 资产：JPEG'd 的 pETH、Metronome 的 msETH、Alchemix 的 alETH。项目方自己也在池子里提供流动性，例如 Alchemix 的 AMO（算法做市合约），池子的深度关系到这些代币能否维持与 ETH 的锚定。事发时 pETH/ETH 池约有 2,100 万美元，msETH/ETH 约 410 万美元，alETH/ETH 约 4,600 万美元，CRV/ETH 约 4,700 万美元[2]。

为什么 ETH 池需要锁

EVM 上发送原生 ETH 只能用 CALL，它会把执行权交给收款地址；如果收款方是合约，它的 fallback 就会被执行[1]。Curve 的 ETH 池在退出流动性和兑换时用 raw_call(_receiver, b"", value=...) 付 ETH，付完之后还有状态要更新，没有严格遵守“检查-生效-交互”的顺序。挡住回调的只有 @nonreentrant('lock')。

与 WETH 配对的池子付的是 ERC-20 代币，没有回调，因此不受影响。ERC-777 代币带回调，相关池子同样有风险，但那些池子当时基本已经停用[2]。

应急时只能撤资

Curve 的紧急 DAO（eDAO）不能暂停池子，也不能动用户的资金，只能停掉某个池子的 CRV 奖励（kill gauge）[2]。一旦池子本身的代码有问题，LP 和项目方能做的只有抢在攻击者之前把流动性撤出来。

就在九天前的 7 月 21 日，Conic Finance 因 Curve ETH 池付款时的回调被攻击，损失约 335 万美元。那是一次只读重入：Conic 以为 Curve v2 的 ETH 池用零地址表示 ETH，实际上这些池子持有 WETH，判断函数 _isETH 返回 false，本该启用的重入检查被跳过[17]。两次事件的入口都是 ETH 回调，但 Conic 的错在它自己的代码里，和 Vyper 无关。

漏洞原理

锁是怎么生成的

Vyper 的 @nonreentrant(key) 不是库代码，而是编译器在函数入口和出口插入的几条存储读写。0.3.0 生成这段代码的函数只有几行[4]：

# vyper/old_codegen/function_definitions/utils.py（v0.3.0）
def get_nonreentrant_lock(func_type):
    if not func_type.nonreentrant:
        return ["pass"], ["pass"]

    nkey = func_type.reentrancy_key_position.position   # 锁槽位置，由前端分配
    # 入口：断言 sload(nkey) == 0，然后写入 1；出口：写回 0
    nonreentrant_pre = [["seq", ["assert", ["iszero", ["sload", nkey]]], ["sstore", nkey, 1]]]
    nonreentrant_post = [["sstore", nkey, 0]]
    return nonreentrant_pre, nonreentrant_post

来源：vyperlang/vyper 仓库 v0.3.0 标签，vyper/old_codegen/function_definitions/utils.py 第 1–8 行。中文注释为本站所加，下同。

锁槽 nkey 记在函数的类型信息上，由前端在计算存储布局时写进去。按设计，同一个 key 的函数应该拿到同一个 nkey。Curve 池子里五个改动资金的函数都写 @nonreentrant('lock')，用意就是让任何一个在执行时，其余四个都进不来。问题出在 0.2.15 的存储分配函数里[4]：

# vyper/semantics/validation/data_positions.py（v0.2.15）
def set_storage_slots(vyper_module: vy_ast.Module) -> None:
    """
    Parse module-level Vyper AST to calculate the layout of storage variables.
    """
    # Allocate storage slots from 0
    # note storage is word-addressable, not byte-addressable
    storage_slot = 0

    for node in vyper_module.get_children(vy_ast.FunctionDef):
        type_ = node._metadata["type"]
        if type_.nonreentrant is not None:
            type_.set_reentrancy_key_position(StorageSlot(storage_slot))
            # TODO use one byte - or bit - per reentrancy key
            # requires either an extra SLOAD or caching the value of the
            # location in memory at entrance
            storage_slot += 1   # 不看 key 的值，每个带锁的函数都换一个新槽

    for node in vyper_module.get_children(vy_ast.AnnAssign):
        type_ = node.target._metadata["type"]
        type_.set_position(StorageSlot(storage_slot))   # 普通状态变量接在锁后面
        # ……（一段关于 HashMap 占槽的注释从略）……
        storage_slot += math.ceil(type_.size_in_bytes / 32)

来源：vyperlang/vyper 仓库 v0.2.15 标签，vyper/semantics/validation/data_positions.py 第 20–44 行。

循环只看函数有没有 nonreentrant，从不看它的值。于是一个合约里有几个带锁的函数，就有几个锁槽，每个函数的锁只能挡住它自己被重入。0.2.16 和 0.3.0 的这段循环逻辑没变，只多了一个 ret 字典，用来输出 -f layout 存储布局。五个函数的 key 相同，ret["nonreentrant.lock"] 被覆盖了五次，布局里只显示最后一个槽，前四个看上去像是“分配了却没用的空洞”[1]。

0.3.1 的修复是在分配前查一下这个 key 是否出现过：

# vyper/semantics/validation/data_positions.py（v0.3.1）
    for node in vyper_module.get_children(vy_ast.FunctionDef):
        type_ = node._metadata["type"]
        if type_.nonreentrant is None:
            continue

        variable_name = f"nonreentrant.{type_.nonreentrant}"

        # a nonreentrant key can appear many times in a module but it
        # only takes one slot. after the first time we see it, do not
        # increment the storage slot.
        if variable_name in ret:
            _slot = ret[variable_name]["slot"]
            type_.set_reentrancy_key_position(StorageSlot(_slot))   # 复用第一次分配的槽
            continue

        type_.set_reentrancy_key_position(StorageSlot(storage_slot))
        # ……（写入 ret 布局记录、TODO 注释从略）……
        storage_slot += 1

来源：vyperlang/vyper 仓库 v0.3.1 标签，同一文件第 35–63 行。

漏洞是怎么被带进来的

这个错误不是一次手误，而是一连串修补的副产品。当时 Vyper 正在把单遍编译器拆成前端（类型检查、语义分析）和后端（代码生成）两层，存储槽的分配在两层之间搬来搬去[1][5]：

版本发布与锁槽有关的改动结果
0.2.92021-02-17PR #2308：锁从固定偏移 0xFFFFFF 挪到普通变量之后的第一个空闲槽只要变量都只占一个槽就没问题
0.2.132021-07-06PR #2361：普通变量改由前端分配，锁仍在代码生成阶段按旧算法算，两套分配器并存锁的偏移算错，版本撤回
0.2.142021-07-20PR #2379：按变量实际大小重算锁的偏移，但旧分配器不给 HashMap 留槽，新分配器留槽锁与普通变量重叠，版本撤回
0.2.152021-07-24PR #2391：锁挪到普通变量之前，一起在前端分配；按 key 去重的逻辑被删掉每个函数一把锁，漏洞引入
0.2.16、0.3.02021-08-28、10-05分配逻辑不变，新增 -f layout 布局输出漏洞仍在
0.3.12021-12-01PR #2439、#2514：同 key 共用一个槽，补上跨函数重入测试修复，没有安全公告

旧代码里“一个 key 只分配一个槽”靠的是 get_nonrentrant_counter 函数开头的一个判断：key 已经在字典里，就直接返回原来的槽。PR #2391 把分配挪到前端时，这个字典和判断一起被删掉了，新的循环里没有对应的检查[1]。

修复它的 PR #2439 也没有把问题当成安全漏洞。它的描述是[1]：

this is not a semantic bug but an optimization bug since we allocate more slots than we actually need, leading to "holes" in the slot allocator -- slots which are allocated but unused.

Vyper PR #2439 的描述，转引自 Vyper 团队的技术复盘

也就是说，开发者看到布局输出里锁槽之间有空洞，以为只是浪费了几个槽。这个 PR 本身只做到了去重，没有把复用的槽写回后面的函数，结果编译器直接报错；第二天的 PR #2514 补上了这一步，并加入了第一个“两个函数共用 key、互相调用应当回滚”的测试[1][5]。

为什么两年没人发现

Vyper 自己的测试在 0.3.1 之前只验证“函数不能重入自己”，没有跨函数的用例[1]。审计看的是源码，源码里每个函数都写着 @nonreentrant('lock')，挑不出毛病；布局输出又只显示一个锁槽。修复版本发布时没有人回头评估已部署的合约，用 0.2.15 到 0.3.0 部署的协议没有收到任何通知[1]。

Vyper 的安全公告列出了获利的三个前提：合约用 0.2.15、0.2.16 或 0.3.0 编译；某个带 key 的 @nonreentrant 函数在更新存储之前调用了不可信的外部地址；另一个用同一 key 的函数会受这个中间状态影响[3]。Curve 的 ETH 池三条全中。

稳定池：回调里重入 add_liquidity

三个 factory 池的实现合约里，remove_liquidity 是这样写的。ETH 是 0 号币，循环先处理它[6]：

# Plain2ETH.vy（# @version 0.2.15），即链上实现合约 0x6326…B43E 的源码
@external
@nonreentrant('lock')
def remove_liquidity(
    _burn_amount: uint256,
    _min_amounts: uint256[N_COINS],
    _receiver: address = msg.sender
) -> uint256[N_COINS]:
    total_supply: uint256 = self.totalSupply      # 进入时读一次，存在局部变量里
    amounts: uint256[N_COINS] = empty(uint256[N_COINS])

    for i in range(N_COINS):
        old_balance: uint256 = self.balances[i]
        value: uint256 = old_balance * _burn_amount / total_supply
        assert value >= _min_amounts[i], "Withdrawal resulted in fewer coins than expected"
        self.balances[i] = old_balance - value
        amounts[i] = value

        if i == 0:
            raw_call(_receiver, b"", value=value)   # 付 ETH，执行权交给收款方
        else:
            # ……（1 号币用 ERC-20 transfer 付出，从略）……

    total_supply -= _burn_amount
    self.balanceOf[msg.sender] -= _burn_amount
    self.totalSupply = total_supply   # 用进入时的旧值回写，回调期间的变化被覆盖

来源：curvefi/curve-factory 仓库提交 f389123，contracts/implementations/plain-2/Plain2ETH.vy 第 613–655 行，省略了文档字符串和日志；与 Blockscout 上 0x6326…B43E 的已验证源码一致。

付 ETH 的那一刻，池子处在一个不一致的状态：ETH 余额已经扣了，pETH 余额还没扣；LP 还没烧，totalSupply 还是旧值。正常情况下锁让这个状态不可能被别的函数看到。锁失效后，攻击者在回调里调用 add_liquidity，后者用 self.balances 算出存款前的不变量 D0，再按 mint_amount = total_supply * (D2 - D0) / D0 铸 LP[6]。D0 因为少了一大块 ETH 而偏小，total_supply 却还包括马上要烧掉的 LP，同样存入 40,000 ETH，第一次只换到 32,431 LP，在回调里换到了 82,182 LP[2]。

回调结束后，外层的 remove_liquidity 接着付出 pETH，然后用进入函数时读到的 total_supply 减去这次烧掉的 LP，写回 self.totalSupply。回调里新铸的 LP 因此从账面总量中消失，却还留在攻击者的余额上。LlamaRisk 的概括是：由于重入，新铸 LP 是按烧毁前的余额计算的，攻击者几乎可以无限制地铸 LP[2]。

这时攻击者持有的 LP 远多于合约记录的总量。第二次取款他只烧了 10,273 LP，就取走了池里剩下的 47,507 ETH 和 1,185 pETH[2]。

CRV/ETH 池：用内存里的旧余额回写

CRV/ETH 池的 LP 是独立的代币合约，remove_liquidity 一开始就把 LP 烧掉，所以上面“总量被旧值覆盖”的路径不存在。但它同样在循环中途付 ETH，而且开头把余额读进内存，循环里用这份副本回写存储[7]：

# CRV/ETH 池 0x8301…C511 的已验证源码（# @version 0.3.0）
# coins[0] 是 WETH，coins[1] 是 CRV；ETH_INDEX = 0
@external
@nonreentrant('lock')
def remove_liquidity(_amount: uint256, min_amounts: uint256[N_COINS], use_eth: bool = False):
    """
    This withdrawal method is very safe, does no complex math
    """
    _coins: address[N_COINS] = coins
    total_supply: uint256 = CurveToken(token).totalSupply()
    CurveToken(token).burnFrom(msg.sender, _amount)        # LP 先烧掉
    balances: uint256[N_COINS] = self.balances              # 余额读进内存
    amount: uint256 = _amount - 1  # Make rounding errors favoring other LPs a tiny bit

    for i in range(N_COINS):
        d_balance: uint256 = balances[i] * amount / total_supply
        assert d_balance >= min_amounts[i]
        self.balances[i] = balances[i] - d_balance   # 用内存里的旧余额回写存储
        balances[i] = d_balance  # now it's the amounts going out
        if use_eth and i == ETH_INDEX:
            raw_call(msg.sender, b"", value=d_balance)   # 先付 ETH，CRV 余额和 D 还没更新
        else:
            if i == ETH_INDEX:
                WETH(_coins[i]).deposit(value=d_balance)
            assert ERC20(_coins[i]).transfer(msg.sender, d_balance)

    D: uint256 = self.D
    self.D = D - D * amount / total_supply

来源：Blockscout 上 0x8301AE4fc9c624d1D396cbDAa1ed877821D7C511 的已验证源码（编译器 0.3.0+commit.8a23feb）第 960–985 行。docstring 里那句 “very safe” 是原文。

付 ETH 发生在循环中途。锁失效后，攻击合约可以在回调里调用 add_liquidity 和 exchange，两个函数各有各的锁槽。控制权回到外层后，循环处理 CRV 时用回调之前读进内存的余额计算并写回 self.balances[1]，exchange 刚刚卖出的 CRV 又被记回账上，池子账面上的 CRV 从此多于它实际持有的数量。LlamaRisk 的描述是“池子以为自己还有 CRV，实际上 CRV 已经在第一次攻击中被抽干”[2]。

攻击者随后把 CRV 卖回池子换 ETH，同样的过程重复多轮，直到池里真实的 CRV 所剩无几[2]。

第二阶段利用的正是这笔假账。任何人都能调用的 claim_admin_fees 会先把账面余额同步成合约实际持有的数量，再重算 D[7]：

# 同一合约，_claim_admin_fees 中的一段（由带锁的外部函数 claim_admin_fees 调用）
    # Gulp here
    _coins: address[N_COINS] = coins
    for i in range(N_COINS):
        if i == ETH_INDEX:
            self.balances[i] = self.balance
        else:
            self.balances[i] = ERC20(_coins[i]).balanceOf(self)   # 账面余额改成真实余额

来源：同上，第 558–564 行。

c0ffeebabe.eth 在第二笔交易里往池子转入少量 CRV，调用这个函数把账面同步成真实余额，再用 CRV 换走池里剩下的大部分 ETH，最后留下 2,879.65 ETH[2]。The Block 报道称，它是抢在另一笔针对 CRV/ETH 池的恶意交易之前完成的[12]。

攻击过程

LlamaRisk 拆解了四个池子的攻击交易[2]。做法相同：借 WETH 闪电贷，换成 ETH 存进池子，取款时在池子用 raw_call 付 ETH 的回调里重入同一个池子，最后还掉闪电贷。下面只列结果，不复述交易的具体步骤。

攻击者、抢跑者与白帽

Metronome 的复盘写道，原攻击者大多没有获利，他们的交易被对抗性的 MEV 机器人发现并抢跑，随后黑帽和白帽开始比赛寻找还没被打的合约[8]。alETH 池的攻击者事后分多笔退回了全部资金[9]。Chainalysis 记录到，这几天的抢跑竞争产生了以太坊历史上最大的 MEV 区块奖励[11]。

CertiK 在 7 月 31 日统计：被取走约 6,930 万美元，已退回 1,670 万美元，净损失约 5,200 万美元[10]。Chainalysis 给出的是约 7,000 万美元[11]。CoinDesk 在 8 月 7 日报道：被盗约 7,350 万美元，约 73% 已追回，仍有约 1,970 万美元未归还[18]。差异来自统计时点的币价，以及是否计入抢跑者和套利机器人的所得。本站以 6,930 万美元作为事发时的损失。

影响

CRV 价格与创始人的借贷仓位

按 Binance 的日线数据，CRV 在 7 月 30 日开盘约 0.738 美元，8 月 1 日最低跌到 0.482 美元[19]。市场更担心的是 Michael Egorov 本人的仓位：他用大量 CRV 作抵押，在 Aave、Abracadabra 等多个借贷协议借出稳定币。如果 CRV 继续下跌触发清算，抵押品在流动性已经变差的市场里很难卖出，坏账会落到这些借贷协议身上。The Block 统计，截至 8 月 4 日他在各 DeFi 平台仍欠约 6,530 万美元[15]。

Egorov 的办法是场外折价卖币。他以每枚约 0.40 美元的价格，把约 1.06 亿枚 CRV 卖给 Wintermute、Justin Sun、DCFGod、Jun Du 等买家，换得约 4,200 万美元，先还了 Abracadabra 和 Aave 的部分借款[15]。9 月 27 日，他把 6,800 万枚 CRV 存进 Silo，还清了 Aave 上的全部借款，剩余约 4,270 万美元的债务分布在 Silo、Fraxlend、Inverse 和 Cream[16]。这一轮他靠卖币和还款避开了清算。这段插曲说明，一个协议出事，风险可以经由创始人的个人仓位传到别的协议。

编译器成了攻击面

这次的漏洞出在编译器里。池子的源码写法没有问题，@nonreentrant('lock') 的语义在文档里写得很清楚，只看源码的审计发现不了它，问题在编译器生成的字节码里。Vyper 团队承认，0.3.1 修复这个缺陷时没有意识到它对已部署合约的影响，也没有通知仍在使用旧版本的协议[1]。此后“审计只看源码是否足够”“编译器旧版本由谁负责”成了行业讨论的话题。

抢跑与白帽

攻击交易一进入公开内存池就被 MEV 机器人照抄抢跑，Chainalysis 称这几天产生了以太坊历史上最大的 MEV 区块奖励[11]。Metronome 把这描述为黑帽和白帽之间的一场竞赛，双方都在找还没被打的合约[8]。结果是大部分资金落在了愿意归还的抢跑者手里。白帽抢先转走剩余资金的做法，可以对照 2016 年 The DAO 事件里的白帽团队。

后续处置

Curve 能做的很少

Curve 的池子不可升级，也没有暂停开关。LlamaRisk 指出，Curve 的紧急 DAO 无法暂停池子或动用用户资金，唯一能做的是停发受影响池子的 CRV 激励[2]。Curve 同时提醒 Arbitrum 上 Tricrypto 池的 LP 撤出，尽管审计方和 Vyper 开发者没有找到可获利的攻击路径[2]。Alchemix 一类的受害协议也只能撤资，而撤资本身需要时间[9]。

追讨与悬赏

Curve、Alchemix、JPEG'd 和 Metronome 联合向攻击者喊话：归还九成，可以留下一成作为赏金，期限为 8 月 6 日 08:00（UTC）[14][18]。pETH 池的抢跑者和 alETH 池的攻击者在期限前退回了资金。CRV/ETH 第一笔的攻击者没有回应。期限过后，Curve 公开悬赏剩余被盗资金的 10%，约 185 万美元，给能指认攻击者并促成法院定罪的人，同时表示如果对方全额归还，就不再追究[14]。

补偿与重建

Metronome 用退回的资金新建了 msETH/WETH 池[8]。Alchemix 表示正与 Curve 一起分析攻击前的 LP 持仓、制定补偿方案，内容包括退还追回的资金，以及 Curve 可能以锁仓 CRV 的形式给予补偿；Curve 此后部署的 ETH 池都改用 Vyper 0.3.1 及以上版本[9]。

编译器一侧

8 月 5 日，Vyper 发布安全公告 GHSA-5824-cm3x-3c38，严重等级 critical，同时发布技术复盘[1][3]。复盘列出的后续措施包括：针对最新版本的竞赛审计，覆盖所有历史版本的漏洞赏金，由多个协议联合出资的 Vyper Security Alliance，以及请 ChainSecurity、OtterSec、Statemind、Certora 等审计方回头检查仍在保护大额资金的旧版本[1]。语言层面，0.4.0 删除了具名重入锁，所有 @nonreentrant 共用一把全局锁；0.4.2 加入 #pragma nonreentrancy on，可以让一个文件里的外部函数默认上锁[20]。

教训与防御

给合约开发者
  • 重入锁是第二道防线，不是第一道。如果 remove_liquidity 按“检查-生效-交互”的顺序，先更新 totalSupply 和余额、最后才付 ETH，锁失效也不会出事。
  • 给锁写测试：在一个上锁函数的回调里调用共用同一个 key 的另一个函数，确认交易回滚。Vyper 的复盘建议同时做源码级和字节码级的测试[1]。
  • 付原生 ETH 等于把执行权交给对方。能用 WETH 的地方优先用 WETH，否则把付款放在所有状态更新之后。
给协议、审计方和编译器维护者
  • 审计范围要包括编译器版本。部署时记录编译器版本和提交号，编译器发布安全公告时，能立刻查出自己有哪些合约受影响。
  • 编译器修复要配套安全公告。0.3.1 在 2021 年 12 月就修好了这个问题，但没有公告，用旧版本部署的项目方一直不知情[1]。
  • 不可升级、不可暂停的池子，应急手段只剩撤资，事先要准备好撤资路径。Alchemix 的平衡撤资函数受时间锁限制，紧急时只能单边撤，没能撤完[9]。
  • 大户以单一代币抵押的集中仓位是借贷协议的系统性风险。CRV 下跌时，压力同时落在了多个协议上。
