Nomad 跨链桥“众筹式”抢劫

2022 年 8 月 1 日 21:32（UTC）起，Nomad 跨链桥在以太坊上的合约开始放行从未被证明过的跨链消息。第一批攻击交易公开后，数百个地址照抄交易数据、只换上自己的收款地址，几个小时内把桥里约 1.86 亿美元的资产搬空。起因是部署时写入的一个零值可信根和两个月后的一次升级相互作用，参与者不需要私钥，复制一笔交易就够了。

概要

Nomad 在以太坊上的 Replica 合约负责验证从其他链发来的消息：消息先要用默克尔证明（Merkle proof）证明自己属于某个已签名的树根，合约记下这个根；process() 放款前再检查这个根已经过了挑战窗口。2022 年 4 月部署 Replica 代理合约时，起始可信根传入的是 0x00，合约因此写下 confirmAt[0x00] = 1。6 月 21 日的升级把消息记录从状态枚举改成“证明时用的根”，而从没证明过的消息，记录的默认值恰好也是 0x00。两件事叠在一起，任何没见过的消息都会被当作“在一个早已确认的根下证明过”[1][15]。

攻击者只要伪造一条“从 Moonbeam 的 BridgeRouter 发来的转账消息”，直接调用 process()，以太坊上的 BridgeRouter 就会从托管资金里把代币转给消息里写的地址。第一批交易在公开内存池里出现后，模仿者只需替换收款地址重新广播。从 8 月 1 日 21:32 到 8 月 2 日 05:49（UTC），数百个地址按币种把 WBTC、WETH、USDC 等资产逐个抽干[15]。各家统计的损失在 1.56 亿到 1.9 亿美元之间，本页采用 Nomad 和 FTC 使用的约 1.86 亿美元。

Nomad 随后公布回收地址，并承诺归还至少 90% 的人可以留下 10% 作为赏金、不被追究[2]。最终追回的资产按事发时价值约 3,750 万美元，2022 年 12 月桥重启后按比例返还给用户；按 FTC 的说法，用户净损失超过 1 亿美元[10]。2025 年 12 月，FTC 对运营公司 Illusory Systems 提起行政控诉[9]。2026 年 10 月 29 日，被指控拿走约 280 万美元的以色列-俄罗斯双重国籍男子被以色列引渡到美国受审，他目前只是被起诉，没有被定罪[13][14]。

背景

乐观验证怎么工作

Nomad 是 Illusory Systems 公司以 Nomad 名义运营的跨链消息协议[10]，采用“乐观验证”（optimistic verification）。每条接入的链上有一个 Home 合约，把发往其他链的消息依次写进一棵默克尔树；链下的 Updater 对每个新树根签名；Relayer 把签了名的根搬到目标链的 Replica 合约上。新根到达后要先等一段挑战窗口，Nomad 文档举的例子是 30 分钟，其间 Watcher 如果发现 Updater 签了假根，可以签名把这个 Replica 移出信任列表[7]。窗口过后，任何人都可以提交某条消息在这个根下的默克尔证明，Replica 记下“已证明”，再把消息投递给目标合约。Nomad 的宣传口径是：只要有一个诚实的 Watcher，系统就是安全的[6]。

真金白银集中在一个合约里

Nomad 的旗舰应用是 Token Bridge。以太坊原生的 WBTC、WETH、USDC 等代币跨出时，锁在以太坊的 BridgeRouter 合约里，其他链上铸出对应的 madWBTC、madUSDC 等“mad 资产”。跨回以太坊时，用户在源链销毁 mad 资产，消息通过 Replica 的验证后，以太坊上的 BridgeRouter 从托管中放出原生代币[8]。所以各条链上 mad 资产的价值，全都系于以太坊这一个合约里的托管资金。

BridgeRouter 自己只核对两件事：调用者是不是已登记的 Replica，消息里声明的发送方是不是对方链的 BridgeRouter。后一项只是消息自带的一个字段，可信与否完全取决于 Replica 有没有真的验证过这条消息[8]。

“security-first”

Nomad 对外以“security-first”为卖点。它在 2022 年 4 月宣布了 Polychain 领投、约 2,200 万美元的种子轮，7 月 28 日（被盗前四天）又公开了 Coinbase Ventures、Crypto.com Capital、Polygon、OpenSea、Wintermute、Gnosis 等战略投资方[6]。这些宣传后来被 FTC 逐条列进了控诉书[10]。

Watcher 机制有一个盲区：它只盯 Updater 有没有签假根，不检查合约代码本身出的问题。Nomad 的根因分析承认，这次被利用的消息根本不需要伪造 Updater 签名，所以没有任何 Watcher 采取行动[1]。FTC 控诉书还提到，被盗前一名工程师发现 36 个 Watcher 钱包余额不足、需要手工调整，他向管理层报告说这个流程本该自动化[10]。

漏洞原理

Nomad 的根因分析用一句话概括了问题：Replica 合约没能正确验证消息，只要一条消息还没被处理过，就可以被伪造（“any message to be forged as long as it had not already been processed”）[1]。下面按调用顺序拆开看。代码引自根因分析所链接的 monorepo 提交 7510d54，英文注释是原有的，中文注释是本站加的。

process() 怎么判断“已证明”

// Replica.sol：两张映射表
// Mapping of roots to allowable confirmation times
mapping(bytes32 => uint256) public confirmAt;   // 根 → 可用时刻
// Mapping of message leaves to MessageStatus
mapping(bytes32 => bytes32) public messages;    // 消息哈希 → 证明时用的根

function process(bytes memory _message) public returns (bool _success) {
    // ensure message was meant for this domain
    bytes29 _m = _message.ref(0);
    require(_m.destination() == localDomain, "!destination");
    // ensure message has been proven
    bytes32 _messageHash = _m.keccak();
    // 从没证明过的消息，messages[_messageHash] 读出来是默认值 0x00
    require(acceptableRoot(messages[_messageHash]), "!proven");
    // ……标记为已处理，再调用接收合约的 handle()……
}

function acceptableRoot(bytes32 _root) public view returns (bool) {
    // this is backwards-compatibility for messages proven/processed
    // under previous versions
    if (_root == LEGACY_STATUS_PROVEN) return true;     // 旧版“已证明”= 1
    if (_root == LEGACY_STATUS_PROCESSED) return false;  // 只排除了 2，没排除 0

    uint256 _time = confirmAt[_root];   // _root 为 0x00 时读到 1
    if (_time == 0) {
        return false;
    }
    return block.timestamp >= _time;    // 任何区块时间都 ≥ 1，返回 true
}

来源：nomad-xyz/monorepo 提交 7510d54，packages/contracts-core/contracts/Replica.sol 第 41–44、186–192、262–273 行（去掉了一层缩进，中间有省略）。

正常流程里，prove() 用提交的默克尔证明算出根 R，只有 acceptableRoot(R) 为真时才写入 messages[h] = R[8]。之后 process() 读到的是 R，再查 confirmAt[R]，也就是这个根挑战窗口结束的时刻。设计者默认 messages[h] 只会是 R 或旧版的状态值 1、2。同一份合约里其实定义了 LEGACY_STATUS_NONE = bytes32(0)，代表“从没见过”，但 acceptableRoot() 没有拒绝它，于是 0x00 被当成了一个普通的根去查 confirmAt。

第一个条件：4 月写下的 confirmAt[0x00] = 1

// Replica.sol：代理合约部署时调用一次
function initialize(
    uint32 _remoteDomain,
    address _updater,
    bytes32 _committedRoot,      // 2022 年 4 月部署时传入 0x00
    uint256 _optimisticSeconds
) public initializer {
    __NomadBase_initialize(_updater);
    // set storage variables
    entered = 1;
    remoteDomain = _remoteDomain;
    committedRoot = _committedRoot;
    // pre-approve the committed root.
    confirmAt[_committedRoot] = 1;   // 于是 confirmAt[0x00] = 1
    _setOptimisticTimeout(_optimisticSeconds);
}

来源：同上，第 103–117 行。

_committedRoot 是 Replica 开始接收的那个可信根，让新部署的 Replica 不必重放源链的全部历史。Nomad 的根因分析解释，如果 Replica 和对应的 Home 同时部署，源链的消息树还是空的，而 Nomad 实现里空树的根是 bytes32(0)，于是起始根就是 0x00[1]。Coinbase 查到，以太坊上的 Replica 代理合约在 2022 年 4 月 21 日部署时，这个参数正是 0，confirmAt[0x00] = 1 从那时起一直留在存储里[15]。

第二个条件：6 月的升级改了 0x00 的含义

升级之前，这条记录不会造成任何影响，因为 process() 只认状态枚举，根本不读 confirmAt：

// PR #289 之前：MessageStatus 枚举，0 = None，1 = Proven，2 = Processed
// 未证明的消息是 None，会被拒绝（这一行在当时是安全的）
    require(messages[_messageHash] == MessageStatus.Proven, "!proven");

// PR #289 之后（6 月 21 日上线）：messages 改存根，交给 acceptableRoot 判断
    require(acceptableRoot(messages[_messageHash]), "!proven");

来源：nomad-xyz/monorepo 提交 46d1457（PR #289）中 Replica.sol 的改动。

这次改动有它的道理。按旧规则，一条合法消息如果附带了无效的认证（attestation），就会永远卡住；新设计允许消息在另一个根下重新证明，防止恶意 Updater 用无效的认证阻止合法消息投递[1]。代价是 messages 里的同一个 0x00，含义从“没证明过”变成了“在根 0x00 下证明过”。FTC 控诉书的表述是，漏洞来自智能合约初始化表中一条既有记录与 2022 年 6 月 21 日代码更新之间的相互作用[10]。

messages[h] 的值升级前6 月 21 日升级后

根 R

旧版下证明过的消息		放行放行，向后兼容

四行里只有第一行的结果变了，而第一行覆盖的正好是桥从没收到过的所有消息。

伪造的消息怎么拿到钱

Replica 放行之后，把消息标记为已处理，调用消息里 recipient 字段指定的合约，也就是以太坊上的 BridgeRouter：

return remotes[_domain] == _router && _router != bytes32(0);

来源：nomad-xyz/monorepo 提交 7510d54，packages/contracts-bridge/contracts/BridgeRouter.sol 第 113–118、416–421 行，packages/contracts-router/contracts/Router.sol 第 61 行（有省略）。

onlyReplica 检查调用者是不是已登记的 Replica，这次调用确实来自 Replica。onlyRemoteRouter 检查的 _sender 是攻击者自己填的，填上 Moonbeam 那边 BridgeRouter 的地址就能通过。BridgeRouter 的设计默认 Replica 已经验证过消息，所以它没有任何办法分辨真假。消息正文指定 WBTC 这类以太坊原生代币时，代码走的是从托管里转账的分支，转出的是真实资产。

为什么能被复制几百次

process() 处理完一条消息，会把它的哈希标记为已处理，同一条消息不能再处理第二次。但哈希覆盖整条消息，只要改一个字节，比如把收款地址换成自己的，就是一条全新的消息，它的 messages[h] 同样是 0x00，同样能通过。复制别人成功的交易、替换地址、重新提交，这就是全部门槛。samczsun 当时的描述是：

“这就是这次攻击如此混乱的原因。你不需要懂 Solidity，不需要懂默克尔树，什么都不用懂。只要找到一笔有效的交易，把里面别人的地址换成你的，再重新广播出去。”

samczsun，2022-08-01（UTC），转引自 The Verge[21]

修复

Nomad 在 2022 年 9 月 4 日合并了修复 PR #441，标题是“zero root is not acceptableRoot”，改了两行[8]：

// Replica.sol，initialize()：不再为零根预先批准
-   confirmAt[_committedRoot] = 1;
+   if (_committedRoot != bytes32(0)) confirmAt[_committedRoot] = 1;

// Replica.sol，acceptableRoot()：显式拒绝“从没见过”的 0x00
-   if (_root == LEGACY_STATUS_PROCESSED) return false;
+   if (_root == LEGACY_STATUS_PROCESSED || _root == LEGACY_STATUS_NONE)
+       return false;

来源：nomad-xyz/monorepo 提交 0e02cc1（PR #441）中 Replica.sol 的 diff，第 115、266–267 行。

两处都需要。initialize 只能执行一次，以太坊上那个 Replica 代理存储里的 confirmAt[0x00] = 1 不会因为改了初始化代码就消失，只有在 acceptableRoot() 里拒绝 0x00 才能让这条旧记录失效；改 initialize 是防止以后的新部署再写进同样的记录。2022 年 10 月合并的审计改动（PR #486）又给管理员用的 setConfirmation() 加了限制，不允许为零根设置确认时间[8]。

一条反向测试就能发现

FTC 控诉书引述 Nomad 事后的内部分析：原有测试主要覆盖“happy path”，也就是给合法输入、看它是否被当作合法处理，没有测试非法输入会不会被当作合法处理[10]。“没证明过的消息必须被拒绝”就是这样一条测试：

// 示意：Foundry 风格的反向测试（不是 Nomad 的真实测试代码）
function test_unprovenMessageIsRejected() public {
    // 按 2022 年 4 月的部署参数初始化：起始可信根为 0x00
    replica.initialize(remoteDomain, updater, bytes32(0), 1800);

    // 构造一条从没调用过 prove() 的消息，目的链填本链
    bytes memory forged =
        buildMessage(remoteDomain, remoteRouter, localDomain, attacker);

    vm.expectRevert("!proven");
    replica.process(forged);   // 6 月的版本在这里不会回滚，测试失败
}

示意代码，省略了部署代理合约和拼装消息的辅助函数。

审计里出现过同类问题

Quantstamp 2022 年 6 月的报告里有一条 QSP-19“Proving With An Empty Leaf”，评级低风险，状态标为“Acknowledged”（已知悉）。报告指出，Nomad 用的稀疏默克尔树里没用到的叶子默认是空的 bytes32，有人可以把空值当作叶子、配上人为构造的证明和指定的位置通过包含检查，把这个“空叶子”标记为已证明。Nomad 回复说找到空叶子的原像在实际上不可能；Quantstamp 在报告里写道，Nomad 团队误解了问题，问题与原像无关，而在于空值本来就可以被证明“存在”于树中[20]。

QSP-19 说的是 prove()，被利用的是 process()，两者不是同一个漏洞，但出自同一个错误假设：零值不会被当成真实存在的数据。根因分析还提到，5 月 26 日的改动本身就是审计相关整理的一部分，被包含在提交复审的版本里；6 月 9 日上线的 Immunefi 赏金在攻击前也没有收到这个问题的报告[1]。

攻击过程

以下按 Coinbase、Halborn 等机构事后对链上数据的分析整理。各家用的是公开交易记录，本页只转述他们的结论。

  1. 试探Coinbase 发现，2022 年 7 月 31 日有一个地址多次直接调用 process()，用小额 WBTC 等代币测试，消息的来源链写的是 Avalanche。这些消息事先不在 messages 映射里，调用都成功了。攻击前约一小时，同一地址还通过正常流程往 Moonbeam 跨了 0.01 WBTC；首批四笔攻击交易中的第四笔也是它发出的[15]。美方引渡请求另外指控 Gurevich 在攻击前测试过这个漏洞六次，测试时往 Nomad 钱包里存钱以免被察觉[14]。本页查阅的来源没有说明这两组测试是否指同一件事。
  2. 第一批交易8 月 1 日 21:32（UTC），区块 15,259,101 里的四笔交易各提走 100 WBTC，合计 400 枚。前两笔经 Flashbots 私下提交，通过辅助合约在 Uniswap 换成 WETH；后两笔直接调用有漏洞的合约，在公开内存池里广播。Coinbase 称前三个地址都由 Tornado Cash 注资、彼此有交易往来，像是同一个团伙。同一区块里，还有地址用辅助合约不顺利，改为直接调用，攻击数据就此公开[15][19]。
  3. 每次只拿 100 WBTC四笔交易的 payload 除了收款地址完全相同。Coinbase 推测，攻击者重放了一条真实的跨链消息、只改了收款人，所以每笔金额固定在 100 WBTC，没有一次搬空[15]。rekt 也指出，更老练的攻击者完全可以写一个合约独自抽干整座桥[20]。
  4. 跟风之后几个小时，越来越多的地址加入，输入数据几乎一样，只改代币、金额和收款地址。按 Coinbase 的统计，88% 以上的参与地址直接调用了与原始攻击相同的 process(bytes) 函数，其余通过中间合约批量调用；跟风者合计拿走约 8,800 万美元。资金按币种逐个被抽干：第一个小时只有 WBTC 和 WETH，之后是 USDC、CQT 等[15]。rekt 描述，跟风者在 Etherscan 上复制调用参数、换上自己的地址即可，MEV 机器人和自称白帽的人也都参与了进来[20]。Halborn 统计共 960 笔交易、1,175 次提款[19]。
  5. 止血太晚Nomad 把 Replica 从 Bridge 和治理合约中移除后，BridgeRouter 的 onlyReplica 检查开始拒绝一切消息[1]。FTC 控诉书称，公司最先是从一名社交媒体用户那里得知异常交易，几名主要工程师起初还在争论截图是不是伪造的；公司只能靠一名正在飞机上的工程师，在聊天里和值班的事故负责人来回传代码片段，桥直到资产被搬空之后才被关停[10]。Coinbase 记录的最后一笔盗取交易在 8 月 2 日 05:49（UTC）[15]。

资金去向

几百个地址各拿各的，资金去向也就分成了很多条线。Coinbase 在 8 月 9 日给出过一个快照：被盗资产中约 17% 已经归还（含部分归还），约 34% 原地未动，约 49% 已被继续转移。归还的主要是 USDC、USDT、WBTC、DAI、CQT 和 WETH，和被盗的币种构成差别很大，因为最早动手的几个地址拿的主要是 WBTC 和 WETH，并且没有归还的意思[15]。

归还的部分

  1. 官方回收钱包8 月 3 日公布；赏金规则下可自留最多 10%
  2. 按来源分类原样归还的直接对应原交易；换过币的交给做市商换回原币种
  3. 多签暂存钱包2/4 Gnosis Safe，补发事后申请的赏金后装入升级后的桥

没有归还的部分

Mandiant 在 2022 年 11 月的分析中，把单个地址拿走超过 200 万美元的 14 个地址分成四组[16]。A 组三个地址都向回收地址还过钱，但只有一个还了大部分（77.6%），另外两个只还了 1.7% 和 3.4%。B 组约 401 万美元，通过 1inch 换币后进入 Tornado Cash，其中一个地址也与 2022 年 4 月 Rari Capital 被盗有关。C 组约 520 万美元，经 Uniswap 换币后进入 Tornado Cash。D 组按分析时的价值约 5,450 万美元，经 OrionPool、Uniswap、Curve 换币，一部分进入 Tornado Cash，约 5,000 万美元停在两个充值地址里。Coinbase 也发现一个资金混在一起、累计流水超过 6,200 万美元的地址群，其中包括第一个实施攻击的地址；它同时注明，Tornado Cash 自 2022 年 8 月 8 日起已是美国制裁对象[15]。

还有一部分价值直接蒸发了。Nomad 在 8 月 17 日的更新里写道，很多参与者拿到代币后马上通过 DEX 的流动性池换成其他代币，高滑点让一部分资金无法再追回；另一些白帽归还的币种与拿走的不同，增加了记账难度[3]。被起诉的 Gurevich，按引渡请求的说法，把约 280 万美元分散到多个地址并换成其他币种[14]；TRM Labs 称他用过 Tornado Cash，并把 ETH 换成 Monero、Dash 等隐私币[17]。

影响

依赖 Nomad 的链

以太坊上的托管被搬空后，Moonbeam、Evmos、Milkomeda 等链上的 madWBTC、madUSDC 等资产一夜之间失去了 1:1 的支撑。rekt 在 8 月 2 日给出的锁仓量（TVL）变化如下[20]：

链攻击前 TVL8 月 2 日 TVL
Moonbeam约 3 亿美元约 1.35 亿美元
Milkomeda约 3,100 万美元约 2,000 万美元
Evmos约 700 万美元约 300 万美元

TVL 同时受币价和资金撤出影响，不等于 mad 资产的损失。Nomad 后来在重启说明里明确，被攻击的只有以太坊一侧；如果用户跨的是其他链的原生资产，比如 Moonbeam 的 GLMR、Evmos 的 EVMOS，完成 KYC 后可以照常跨回[5]。

人人都能参与的抢劫

Nomad 回顾此前的几起跨链桥事件时写道，那些攻击据报道都只有一个攻击者[3]。这一次，漏洞随着攻击交易出现在公开内存池里，会复制粘贴的人都能参与，结果有两个。一是处置窗口被压缩：几百个地址并行提款，桥的资产在几小时内被分光，任何一个提款者停手都不会让损失变小。二是“攻击者”“白帽”“围观者”之间的界线变得模糊：有人声称是为了保护资金才提走，有人全额归还，有人部分归还，有人一分不还。Coinbase 在分析中按归还情况把参与者分成白帽、灰帽、黑帽三类，同时特别注明，即使是“白帽”，最初的提取也未经授权，Coinbase 不认可这种做法[15]。

此后几年，司法和监管机构的态度一致：漏洞容易被利用，不会让提款变得合法。以色列最高法院在引渡案中写明，利用智能合约的漏洞与利用其他任何程序的漏洞没有区别[14]；FTC 则把矛头对准了项目方自身的安全做法[10]。

后续处置

止血：移除 Replica

Nomad 的应急手段是把 Replica 从 Bridge 和治理合约里移除。BridgeRouter 的 handle() 先检查 onlyReplica，Replica 被注销后，任何消息都投递不进来，漏洞随之关闭，正常的跨链消息也一起停了。根因分析写明，新的跨链转账仍可发起，但不会被处理，前端界面也已下线[1]。这一步来得太晚，桥已经基本空了。

合约设计本身也有局限。Watcher 可以签名注销 Replica，但这个功能是为“Updater 作恶”准备的[7]；这次的漏洞不涉及 Updater 的签名，Watcher 根本不会被触发[1]。

赏金与回收地址

8 月 3 日，Nomad 在推特和链上公布官方回收地址[15]。8 月 4 日（美国时间）又宣布赏金：归还至少 90% 的人被视为白帽，最多可以留下 10%，Nomad 不追究法律责任，会向第三方说明其白帽身份，并向执法机构建议不提起刑事指控[2]。Mandiant 记录，归还者还会收到一枚“Whitehat”NFT 作为感谢[16]。由于赏金是在回收地址之后才宣布的，一些早先已全额归还的人事后申请 10%，Nomad 同意兑现，到 11 月这部分约 61 万美元[3][4]。

骗子也跟了上来。有人注册冒充 Nomad 的 ENS 域名，在链上给归还者发消息，让他们把钱打到与官方回收地址开头相同的靓号地址，有的消息还许诺“10% 赏金”[15]。Nomad 的赏金公告专门提醒要警惕冒充者[2]。

重启：按比例分配，不搞先到先得

如果直接重开桥，最先跨回的人能按 1:1 换走剩下的原生代币，后来的人什么也拿不到。Nomad 因此重新设计了桥，2022 年 12 月 20 日上线[5]：

  1. KYC用户通过 CoinList 完成身份验证，并绑定钱包地址。
  2. 跨回并领取 NFT把 mad 资产跨回以太坊，得到一枚不可转让的 NFT，记录可领取的资产种类和数量。
  3. 按比例领取NFT 按每种代币的追回比例兑付。例如被盗的 ETH 追回了 10%，代表 20 ETH 的 NFT 可以领 2 ETH。领取后 NFT 仍归用户所有，以后再追回的资金可以接着领。

重启后的桥在任何链上都不再接收新的原生资产。12 月 20 日的更新显示，暂存钱包里还有约 120 万美元，其中约 60.5 万美元在等待换回原币种，约 58.8 万美元留作待付的赏金[5]。

FTC 的行政控诉

2025 年 12 月 16 日，FTC 对 Nomad 的运营公司 Illusory Systems 提起行政控诉，指控它宣传“security-first”，实际却没有采取合理的安全措施。控诉包括“不公平的安全做法”和“对安全做法的虚假陈述”两项，称用户损失超过 1 亿美元[9][10]。控诉书列出的具体问题包括：

  • 测试主要覆盖“happy path”，没有测试非法输入会不会被当作合法处理。
  • 没有接收和处理漏洞报告的明确流程，没有书面的信息安全计划和足够的事故响应流程，应对攻击时出现混乱和拖延。
  • 没有自动检测异常交易的系统，第一个预警来自社交媒体用户。
  • 没有部署熔断机制（circuit breaker）或“kill switch”。Nomad 自己的营销页面写过“让 1 亿美元在一笔交易里流出、没有任何熔断机制是荒谬的”，一名高级工程师也曾建议建立熔断机制。
  • 一家潜在合作方曾提醒“升级本身就有风险，可能导致资金无法找回”，Nomad 没有理会，照样把后来被利用的代码推上了生产环境。

同时公布的和解令草案要求[11]：

  • 不得就安全做法作虚假陈述；建立全面的信息安全计划，包括安全的开发与测试流程、每年至少一次的安全培训，以及监控所有与用户资产安全有关的服务、识别异常活动的技术手段。
  • 对于资金转出不可撤销的系统，要有在出现异常时快速暂停或限制其功能的手段；如果技术上做不到，负责的高管要在 90 天内向 FTC 提交书面声明，以伪证罪为担保说明原因。
  • 每年评估和测试一次安全措施；十年内由独立第三方每两年评估一次。
  • 把事发后追回、按事发时名义价值约 3,750 万美元的资产中尚未返还的部分，通过原有的赏金流程和“恢复桥”流程返还给用户。

委员会以 2:0 表决接受控诉和和解令草案并征求公众意见。按和解协议，Illusory Systems 对控诉中的指控既不承认也不否认；和解令一旦生效，期限为十年[9][11]。截至 2026 年 10 月，FTC 的案件页面状态仍为“Pending”，没有发布最终决定。

刑事案件

被告人原名 Alexander Gurevich，以色列和俄罗斯双重国籍，2025 年 4 月改姓 Block[12][13]。按以色列媒体援引的起诉和引渡文件，他在攻击前测试过漏洞，2022 年 8 月 1 日前后分四次提走价值 280 多万美元的代币，再分散到多个地址、换成其他币种；几天后以假身份在 Telegram 上联系 Nomad 的 CTO，自称是“业余地”探查漏洞并道歉，说已经往回收钱包打了约 16.2 万美元，同时索要 50 万美元的“漏洞奖励”。Nomad 只同意按赏金规则给 10%，他说要咨询律师，此后断了联系，Nomad 随后把此事交给了美国当局[12][14]。

2023 年 8 月 16 日，加州北区联邦法院对他提起八项罪名的起诉。Unchained 援引以色列最高法院的判决，列出的是三项洗钱、四项计算机欺诈和一项运输被盗财产[14]；TRM Labs 的文章写的是电信欺诈、共谋和洗钱[17]，两者不一致，本页以法院文件的说法为准。美国在 2024 年 12 月 10 日提出引渡请求。2025 年 5 月 1 日，他在本-古里安机场准备登机飞往俄罗斯时被捕，距他改名只有两天[12]。

耶路撒冷地区法院在 2025 年 7 月裁定他可以被引渡。2026 年 3 月 8 日，以色列最高法院合议庭维持原判，判决由 Ofer Grosskopf 法官撰写。辩方主张他只是按合约原样使用，没有被指控修改代码；法院不接受，认为利用智能合约的缺陷与利用任何其他程序的缺陷没有区别，就像一台有制造缺陷、塞进一张白纸就吐钱的 ATM，取走这笔钱并不因此就不算犯罪。法院也驳回了“区块链记录公开所以不构成洗钱”的说法，指出链上记录只显示钱包，不显示谁控制钱包。最高法院院长 Isaac Amit 随后拒绝了他再次审理的申请[14]。2026 年 10 月 29 日，以色列把他移交美国[13][14]。

以上都是指控和引渡程序中的认定，不是有罪判决，他在美国受审前应被推定无罪。在本页查阅的公开报道里，几百个参与者中只有他一人被提起刑事指控。

谁是“第一个”，来源说法不一

Coinbase 的分析显示，最早的两笔攻击交易经 Flashbots 私下提交、通过辅助合约执行，攻击数据是随后直接调用合约的交易公开出去的[15]。以色列媒体援引的引渡文件则称，Gurevich 的几笔提款让其他人看到了方法[14]。TRM Labs 称他与他人合谋实施攻击，并在洗钱环节扮演核心角色[17]。这几种说法并不完全吻合，本页查阅的来源也没有公开说明哪些链上地址对应哪个人，所以无法判断他与首批四笔交易的关系。另外，TRM 的文章最初写错了嫌疑人的名字，后来更正；它的标题在 2025 年 5 月就写“已引渡”，而实际移交发生在 2026 年 10 月[17]。

教训与防御

从 4 月部署到 8 月被盗，下面每个环节都有机会拦住这次攻击：

环节与当时发生了什么本可以怎样拦住
2022-04 部署
起始可信根传入 0x00，confirmAt[0x00] = 1 写进存储		在 initialize 里拒绝零根，“没设置”用单独的标志表示
2022-05 改代码
messages 的含义变了，acceptableRoot() 没有拒绝 0x00		改数据含义时，把每个可能的取值（0x00、1、2、R）逐一过一遍；补反向测试
2022-06 审计
QSP-19 指出“零值被当成存在的数据”，回复没有对上问题		把它当作一类问题，排查所有读取默认值为零的地方
2022-06-21 升级
新代码遇上旧存储		在带真实存储的主网分叉上跑升级，再提交伪造消息做测试
2022-07-31 试探
小额消息不带证明直接 process()		监控每次 process() 是否有对应的证明记录，没有就报警
2022-08-01 首批交易
四笔各提走 100 WBTC		按币种、按时间窗口限制流出总量，超限自动暂停
跟风阶段
几百个地址照抄，数小时搬空		预先确定谁能一键暂停，并演练过；值班覆盖所有时区
给合约开发者
  • 不要让“默认值”有含义。Solidity 的 mapping 对没写过的键返回 0；如果 0 恰好也是一个合法状态（零根、空叶子、零地址），“从没写过”就等于“已授权”。凡是从 mapping 读出来再拿去做判断的值，都要确认 0 被显式拒绝，或者用单独的标志区分。
  • 升级要连同链上已有的状态一起测。4 月的那条记录在旧逻辑下无害，是 6 月的代码改变了它的意义。只审 diff 看不出来，要在带真实存储的分叉上跑新代码。
  • 除了 happy path，更要写“应该失败”的测试。把“process 成功意味着消息此前被证明过”写成不变量，做 fuzz 或形式化验证，一条这样的测试就能发现这个漏洞。
  • 审计意见被驳回时，要确认驳回的理由针对的是审计师描述的那个问题。QSP-19 的回复答非所问，审计师在报告里写明了这一点，这正是该停下来重看的时候。
给跨链桥和协议运营方
  • 设限额和熔断，让验证层即使完全失效，也不能让全部余额在几小时内流出。按币种、按时间窗口限制流出，超限自动暂停。FTC 和解令也要求具备快速暂停或限制的手段。
  • 监控要盯协议行为，不能只盯签名者。Nomad 的 Watcher 只检查 Updater 有没有签假根；“每笔 process 是否都有对应的证明”这条规则简单得多，也能更早报警。
  • 暂停权限和流程要事先定好：谁能暂停、需要几个签名、是否覆盖所有时区。工程师在飞机上用聊天传代码，是任何演练都不该接受的情况。
  • 攻击交易一旦出现在公开内存池里，按分钟计算。容易复制的漏洞会被迅速复制，响应是几分钟还是几小时，基本决定了损失多少。
给用户和集成方
  • 跨链包装资产的价值完全取决于另一条链上的托管。Moonbeam 上的 madUSDC 值钱，只是因为以太坊的 BridgeRouter 里锁着 USDC；桥出事时，所有链上的包装资产同时失去支撑。持有包装资产的风险，等于这座桥最弱一环的风险。
  • 自称白帽不会让行为变得合法。Nomad 的赏金换回了约 20% 的资金，但法院和监管机构都把“复制交易取走别人的资产”定性为未经授权的取得，以色列最高法院明确驳回了“只是按合约原样使用”的辩护。
  • 同类问题没有消失。2026 年的 KelpDAO 事件中，攻击者同样伪造了跨链消息，在目标链上放出了没有对应锁仓的资产。跨链设计里最该审视的，仍然是消息验证这一环的信任模型。
