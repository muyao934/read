区块链被盗事件编年史

总览　/　2020 年　/　DeFi 之夏与闪电贷

bZx 闪电贷攻击

2020 年 2 月，攻击者两次用闪电贷在一笔交易里借来 7,500 至 10,000 枚 ETH，攻击借贷协议 bZx。第一次利用 bZx 保证金交易中一处被跳过的检查，把 Uniswap 上的 WBTC 价格推高约 3 倍；第二次操纵 bZx 赖以定价的 Kyber sUSD 报价，用被高估的抵押品多借出 ETH。这是最早被广泛报道的闪电贷攻击之一，它说明协议一旦依赖可以被瞬间推动的价格，攻击者连本金都不需要。

概要

bZx 是以太坊上的保证金交易与借贷协议。用户在它的 Fulcrum 产品里开杠杆仓位时，协议从 iETH 借贷池借出 ETH，经 Kyber 换成目标资产，最后检查仓位的抵押是否仍然充足。2020 年 2 月 15 日的第一次攻击中，这道最终检查被一个为“无兑换贷款”设计的捷径条件跳过了，保证金交易恰好也满足这个条件，于是一笔滑点约 200% 的兑换照样成交[2][4]。

攻击者先从 dYdX 闪电贷借来 1 万枚 ETH，借 bZx 的仓位把 Uniswap 池里的 WBTC 价格推高约 3 倍，再把事先从 Compound 借到的 WBTC 高价卖回这个池子[1]。约三天后的 2 月 18 日，第二次攻击不依赖代码漏洞：bZx 用 Kyber 的实时报价给抵押品定价，而 sUSD 在 Kyber 上的报价只来自两个 AMM 型储备。攻击者用 900 ETH 把 sUSD 的价格推高约 2.5 倍，再以约 110 万枚 sUSD 作抵押从 bZx 借出 6,796 枚 ETH[3][5]。

两次的闪电贷都在同一笔交易里还清，损失落在 bZx 的 iETH 借贷池，留下两笔抵押严重不足的贷款。bZx 两次都靠下架“预言机白名单”上的代币来暂停协议，这个白名单不受时间锁约束。事后公司和协议利益相关方承担了损失，并改用 Chainlink 作为参考价格[5][6]。攻击者身份至今不明，两次攻击是否出自同一人也没有公开结论。

背景

bZx 由 Tom Bean 和 Kyle Kistner 创办，运营公司是 bZeroX, LLC。协议 2018 年上线以太坊主网，2019 年 6 月推出借贷与代币化保证金交易产品 Fulcrum[5][16]。在 Fulcrum 上，出借人把资产存进借贷池，换得生息的 iToken，ETH 池对应的就是 iETH；交易者买入 pToken 开杠杆仓位，例如 sETHwBTC5x 代表以 WBTC 计价、5 倍杠杆做空 ETH。开仓时协议从对应的 iToken 池借钱，再通过 Kyber Network 兑换。据 The Block 2020 年 2 月 17 日的报道，bZx 当时锁仓约 1,550 万美元，在 DeFi 协议中排第七[11]。

bZx 没有单独的价格预言机，价格直接取自 Kyber 的报价。Kyber 是一个流动性聚合器，每笔兑换会被路由到报价最好的储备（reserve），bZx 只采用其中“许可储备”的价格。bZx 在 2020 年 3 月的复盘《Mea Culpa》里承认，2017 年白皮书设想的是取三个链上价格源的中位数，但足够可靠的链上价格源一直没有出现，于是选了 Kyber。Kyber 的开发者文档也写明，把它当链上价格源“容易被恶意方操纵价格”[5]。

bZx 认为这个风险可控，前提是每种资产在 Kyber 上至少有一个 Fed Price Reserve（FPR）。这类储备由做市商设定基准价和报价曲线，有人对着一个储备砸价时，其他储备会报出更有竞争力的价格，把操纵抵消掉。安全研究员 samczsun 此前报告过可以把套利价格“推进”价格源的问题，bZx 因此加了一道“价差检查”，同时比较买入和卖出两个方向的报价[5]。

闪电贷在当时也刚出现。按 arXiv 上 Qin 等人的论文，这个概念最早由 Marble Protocol 提出，dYdX 支持一种没有写进文档的闪电借款方式，Aave 从 2020 年 1 月起大力推广这项功能[1]。bZx 自己在 1 月初也加了一个闪电贷函数，共 40 行代码，未经审计就上线了。另一个团队发现它允许任意调用，先在主网上验证了漏洞，再告知 bZx；bZx 悄悄打了补丁，计划 2 月底再公开[5]。

此外，bZx 绝大多数改变状态的功能都放在 12 小时时间锁之后，由管理员密钥控制，但预言机代币注册表不在时间锁的保护范围内[4]。这个缺口后来成了 bZx 的暂停按钮。

漏洞原理

两次攻击的根源不同。第一次是合约实现上的错误，一道该做的检查没有执行；第二次的代码按设计运行，问题出在设计本身：抵押品的价格取自一个可以在同一笔交易里被推动的报价。

第一次：抵押检查被捷径条件跳过

在 Fulcrum 开一个 5 倍仓位，调用会经过几层合约：用户调用 pToken 的 mintWithEther，pToken 调用 iETH 的 marginTradeFromDeposit 从借贷池借出 ETH，再交给 bZx 核心合约的 takeOrderFromiToken 去 Kyber 兑换[2]。

  1. pToken 开仓攻击者存入 1,300 ETH，开 5 倍做空
  2. iETH 借出借出 4,337.62 ETH，提取额被设成等于借款额
  3. bZx 兑换经 Kyber 卖出 5,637.62 ETH，滑点约 200%
  4. 最终检查捷径条件成立，抵押检查没有执行

兑换完成后，takeOrderFromiToken 本应确认仓位的保证金仍高于维持保证金。负责判断的是 BZxOracle 的 shouldLiquidate，它比较当前保证金和 maintenanceMarginAmount。修复前，这道检查是这样写的（英文注释是原有的，中文注释是本站加的）：

// iTokens_loanOpeningFunctions.sol，takeOrderFromiToken 末尾（修复前）
_handleTransfersAndSwaps(...);   // 转账和 Kyber 兑换在这里完成，参数从略

require ((
        // 左边成立时整个条件为真，|| 右边的 shouldLiquidate 不会被调用
        loanDataBytes.length == 0 && // Kyber only
        sentAmounts[6] == sentAmounts[1]) || // newLoanAmount
    !OracleInterface(oracle).shouldLiquidate(
        loanOrder,
        loanPosition
    ),
    "unhealthy position"
);

来源：bZx-monorepo 镜像，提交 ce858d0（修复提交 cb54efa 的父提交），iTokens_loanOpeningFunctions.sol 第 145–153 行，去掉了两层缩进[9]。sentAmounts[1] 是新借款额，sentAmounts[6] 是实际提取给借款人的金额。

|| 左边是一个捷径：没有 loanDataBytes，并且提取额等于新借款额时，直接放行。按 bZx 事后的说法，这个分支本是给“超额抵押贷款”准备的，借款人整笔取走借款、中间不发生兑换，所以不需要最后的滑点检查[4]。

问题是保证金交易也满足这两个条件。iETH 在 _borrowTokenAndUse 里按存款额算出借款额以后，顺手把提取额设成同一个值；走 Kyber 的保证金交易又不带 loanDataBytes：

// LoanTokenLogicV4.sol，_borrowTokenAndUse（修复前）
if (amountIsADeposit) {   // marginTradeFromDeposit 传入 true
    (sentAmounts[1], sentAmounts[0]) = _getBorrowAmountAndRate( // borrowAmount, interestRate
        loanOrderHash,
        sentAmounts[1], // amount
        useFixedInterestModel
    );

    // update for borrowAmount
    sentAmounts[6] = sentAmounts[1]; // borrowAmount   // 提取额 = 借款额
}

来源：同上，LoanTokenLogicV4.sol 第 944–953 行，去掉了两层缩进[9]。

结果是一笔刚刚以约 200% 滑点完成兑换的保证金交易，被代码当成了“没有兑换的超额抵押贷款”，最终检查被跳过。PeckShield 的分析确认，攻击触发的正是 loanDataBytes.length == 0 && sentAmounts[6] == sentAmounts[1] 这个条件[2]。这里的毛病在于：安全检查执行与否，取决于输入参数的表面特征，与交易实际做了什么无关。“提取额等于借款额”被默认为只有无兑换的贷款才会出现，另一条代码路径恰好也算出了同一个等式。

第二次：预言机读的是可以被推动的即时报价

bZx 计算所需抵押品时，_getRequiredCollateral 调用预言机的 getTradeData，后者通过 _querySaneRate 向 Kyber 查询两个方向的 getExpectedRate，价差在 maxSpreadPercentage（3%）以内才取平均值使用：

// BZxOracle.sol（修复前），_getExpectedRateCall：直接读 Kyber 的即时报价
(bool result, bytes memory data) = kyberContract.staticcall(
    abi.encodeWithSignature(
        "getExpectedRate(address,address,uint256)",
        sourceTokenAddress,
        destTokenAddress,
        // 只查询许可储备
        requirePermissionedReserveForQuery ? sourceTokenAmount.add(2**255) : sourceTokenAmount
    )
);

// _querySaneRate：比较正反两个方向的报价
uint256 reversedRateModified = SafeMath.div(10**36, reversedRate);
uint256 maxSpread = maxSpreadPercentage;   // 3 * 10**18，即 3%
if (maxSpread != 0 && reversedRateModified < expectedRate) {
    uint256 spreadPercentage = expectedRate
        .sub(reversedRateModified);
    spreadPercentage = spreadPercentage
        .mul(10**20);
    spreadPercentage = spreadPercentage
        .div(expectedRate);
    require(                              // 只拦得住正反报价差距过大的情况
        spreadPercentage <= maxSpread,
        "bad price"
    );
}
saneRate = expectedRate
    .add(reversedRateModified)
    .div(2);

来源：bZx-monorepo 镜像，提交 ce858d0，BZxOracle.sol 第 1406–1413 行与第 1356–1375 行，去掉了两至三层缩进[9]。两次攻击之间的修复提交没有改动 _querySaneRate 和 getTradeData。

getExpectedRate 返回的只是此刻报价最好的储备给出的价格，没有时间维度，也没有外部参照。Kyber 永远选报价最好的储备，如果能抵消操纵的 FPR 被耗尽或者根本不存在，报价就只反映 AMM 型储备的当前状态。AMM 按自己的库存计算价格，谁在同一笔交易里先做一笔大额兑换，谁就直接改变了这个价格。

价差检查也拦不住这种情况。AMM 被推向一边以后，它的买入报价和卖出报价一起移动，两者之差只剩手续费和少量滑点，远低于 3%。这道检查原本针对的是“买入比卖出还便宜”的套利价格，它判断不了整体价格是否已经偏离市场。

bZx 事后的复盘印证了这一点：sUSD 在 Kyber 上有两个类似 Uniswap 的储备，攻击者操纵价格时因此通过了价差检查[5]。按 arXiv 论文附录的建模，这两个储备一个是 Uniswap 储备，一个是自动价格储备（APR），都按库存定价[1]。samczsun 随后又演示，只要储备池里存在 Uniswap 或 APR 储备，攻击者就可以反复与 FPR 交易，直到它停止报价，再随意操纵剩下的 AMM 储备。bZx 写道，到这时才确认继续用 Kyber 作价格源已经站不住[5]。

差距有多大，用数字看得最清楚。bZx 对 sUSD 抵押借 ETH 要求 150% 的抵押率。arXiv 按被操纵后的价格 108.44 sUSD/ETH 计算，有效借款比率是 162.66 sUSD 换 1 ETH[1]。按操纵前的公允价 268.30 sUSD/ETH，1,099,841 枚 sUSD 只值约 4,099 ETH，最多能借约 2,733 ETH；攻击者实际借走了 6,796 ETH，约为上限的 2.5 倍。bZx 后来清算这笔抵押品，换得 4,099.31 ETH，与按公允价的估算一致[5]。

为什么一个算漏洞、一个算设计缺陷

bZx 在《Mea Culpa》的根因分析里，把第一次攻击的直接原因定为“导致最终抵押检查被绕过的 bug”，把第二次定为“协议的根本设计缺陷”，并认为经济审计比代码审计更有可能提前发现后者[5]。第一次攻击依赖一个实现错误；第二次只依赖一个设计假设：DEX 的实时报价可以当价格源。即使代码一行不错，只要有人能在一笔交易里推动价格，这个假设就会失效，而闪电贷让推动价格所需的资金几乎没有成本。

攻击过程

第一次攻击：2020-02-15

下面按 arXiv 论文、PeckShield 和 bZx 的复盘转述攻击的结构和关键数字[1][2][4]，重点是 bZx 一侧哪一步没有拦住。

  1. 闪电贷拿到本金攻击者从 dYdX 闪电贷借出 10,000 ETH，整笔借款要在同一笔交易结束前归还。
  2. 先在别处借好 WBTC用其中一部分 ETH 在 Compound 抵押借出 112 WBTC。这笔借款留到交易之外，攻击者要承担被清算的风险。
  3. 让 bZx 用借贷池的钱高价买入攻击者在 bZx 的 Fulcrum 开了一个 5 倍杠杆的 ETH/WBTC 空单。bZx 从 iETH 借贷池借出约 4,338 ETH，连同保证金一起经 Kyber 卖进 Uniswap 的 WBTC/ETH 池。这个池子很浅，这笔交易的平均成交价约是市价的 3 倍，滑点超过 200%。正常情况下，仓位检查会让交易回滚，但上一节说的检查被跳过了。
  4. 在被抬高的池子里卖出攻击者把事先借来的 112 WBTC 卖进同一个池子，换回的 ETH 足够归还闪电贷，交易内还剩约 71 ETH。
  5. 事后收尾此后约两天，攻击者分批按接近市价的价格买回 WBTC，还清 Compound 的借款，取回抵押的 ETH。

arXiv 论文统计的合计获利约 1,193.69 ETH[1]，bZx 的 post-mortem 给出的也是约 1,193 ETH[4]。PeckShield 按 38.5 ETH/WBTC 的市价和约 4,300 ETH 的买回成本粗算，得出约 1,271 ETH[2]，这是估算口径的差别。真正的损失落在 bZx 的 iETH 借贷池上：仓位里只剩约 51 WBTC，对应的却是约 4,338 ETH 的借款。

第二次攻击：2020-02-18

第二次攻击在一笔交易里完成，没有利用代码漏洞，靠的是 bZx 把 Kyber 的即时报价当作抵押品价格[1][3][5]。

  1. 从 bZx 自己的池子闪电借款本金 7,500 ETH 来自 bZx 的 iETH 池，用的正是 bZx 1 月加上的闪电贷功能[5]。
  2. 在浅池里推高 sUSD攻击者用不到 1,000 ETH 在 Kyber 路由的两个 AMM 型 sUSD 储备里买入 sUSD，把 sUSD 的 ETH 价格抬高约 2.5 倍[1][3]。
  3. 在别处按公允价囤 sUSD攻击者另从 Synthetix Depot 按市价买入大量 sUSD，合计持有约 110 万 sUSD，PeckShield 估计约占当时 sUSD 总供应量的 20%[3]。这一步不受 Kyber 价格影响，作用是凑出足够多的抵押品。
  4. 以虚高的抵押品借款攻击者把这些 sUSD 存进 bZx 作抵押。bZx 的预言机读到被操纵的 Kyber 报价，按约 2.5 倍的价格给 sUSD 估值，允许借出 6,796 ETH。
  5. 还款离场归还 7,500 ETH 闪电贷后，攻击者净得约 2,378 ETH[1]。bZx 留下一笔抵押不足的贷款。

借款额和获利的数字在来源之间差约 3 ETH：arXiv 记为借出 6,799.27 ETH、获利 2,381.41 ETH[1]；PeckShield、bZx 和 CoinDesk 记为 6,796 ETH 和约 2,378 ETH[3][5][10]。来源没有解释差异的原因。

资金去向

攻击者拿走了什么

第一次攻击者在闪电贷交易里得到 71.41 ETH 和一个 Compound 仓位，随后两天花 4,377.72 ETH 买回 WBTC 还清 Compound，取回 5,500 ETH 抵押品，合计净得约 1,193 ETH[1]。第二次攻击者在一笔交易里拿走约 2,378 ETH。两次攻击的获利都是普通 ETH，没有可以冻结的中心化稳定币。

本页没有找到这些 ETH 后续流向的公开追踪记录，bZx、PeckShield 和 arXiv 都没有提到冻结或追回。bZx 在第一次 post-mortem 里写道，如果没有 Tornado Cash 和闪电贷，攻击者很难同时获得这样的匿名性和资金规模，但没有具体说明攻击者如何使用了 Tornado Cash[4]。

bZx 留下了什么

两次攻击都给 iETH 池留下了抵押严重不足的贷款。第一次的仓位里有 51.35 WBTC，bZx 撰文时它可兑换约 1,902.26 ETH，而仓位剩余本金为 4,698.02 ETH[4]。第二次留下的 1,099,841 sUSD 被清算成 4,099.31 ETH，作为利息流回 iETH 池。截至 3 月 9 日，两笔贷款的未偿本金合计 11,497.29 ETH，可用于支付利息的资金为 6,095.57 ETH[5]。bZx 没有马上确认这笔损失，后续处理见下文“后续处置”。

影响

闪电贷改变了攻击的成本

arXiv 论文分析了这两次攻击，称它们的投资回报率都超过 500,000%。论文指出，交易是原子的，初始状态完全确定，攻击者可以事先精确计算每一步参数对结果的影响；作者用自己的优化框架算出，第一次攻击若参数最优可获利 82.95 万美元，是实际的 2.37 倍，第二次可获利 110 万美元，是实际的 1.73 倍[1]。

在这之前，协议评估价格操纵风险，多半默认攻击者要动用自有资金，还要跨多个区块承担风险。bZx 在《Mea Culpa》里写道，它把跨区块的价格操纵当作主要威胁，并用 tx.origin == msg.sender 的要求挡住了单笔交易内的清算攻击[5]。这两次攻击说明，资金可以由闪电贷临时提供，真正要问的是：把价格推动一个区块需要多少钱。

常说的“第一次闪电贷攻击”没有权威定义。可以确定的是：闪电贷在此前已经存在；bZx 1 月的闪电贷漏洞在主网上被验证过，但没有造成损失；arXiv 论文把 2020 年 2 月的这两起作为分析对象，称闪电贷带来的攻击可能性“部分已在 2020 年 2 月被利用”[1]；CertiK 把它列为价格操纵成为主要威胁的起点[18]。本页没有找到更早的、以闪电贷为资金来源并造成实际损失的公开案例。

价格预言机成为攻击面

CertiK 2025 年的回顾把 2020 年初的 bZx 攻击列为价格操纵成为 DeFi 主要威胁的起点[18]。此后越来越多的借贷协议改用时间加权平均价、链下聚合报价或多源交叉校验，bZx 自己走的也是这条路。后来的价格操纵不再局限于推动 DEX 现货价，被扭曲的对象换成了金库份额价格、治理票数和永续合约浮盈，底层问题相同：协议把一个能在一笔交易或很短时间内被扭曲的数值当成了可信价格。

暂停按钮之争

bZx 两次都用不受时间锁约束的管理员权限暂停了交易，止住了更大的损失，也引来了“这样还算不算去中心化”的质疑。bZx 在 post-mortem 里回应说，经过深思熟虑设计的升级和暂停功能，可以是去中心化协议工具箱的一部分，它所做的也是一个 DAO 同样会做的事[4]。四年前的 The DAO 既不能暂停也不能升级，最后只能靠整条链硬分叉追回资金。协议该保留多少应急权力，这个问题此后一直没有统一答案；bZx 自己 2021 年的事故又说明，同一把钥匙也会成为攻击目标。

市场层面，The Block 指出 bZx 当时是锁仓量第七大的 DeFi 协议[11]。Cointelegraph 报道，DeFi 总锁仓价值从 2 月 18 日约 12 亿美元的高点回落了约 1.4 亿美元，锁仓的 ETH 减少约 20 万枚[12]。这是同期的市场数据，不能直接等同于攻击造成的损失。

后续处置

两次暂停，一次过快的重启

从第一次攻击交易上链到协议重新开放约 29 小时；重新开放后约 45 小时，第二次攻击发生，协议再次暂停。bZx 事后解释，暂停交易的同时也停掉了所有仓位的追加保证金和清算，交易者被困在仓位里，出借人的资金也暴露在风险中，所以第一次之后急于恢复服务。它在重启前与 samczsun、Lev Livnev 等白帽一起检查过补丁，但第二次攻击属于另一类问题[5]。

不立即确认的坏账

bZx 没有马上核销坏账，而是让两笔贷款继续存在，用剩下的抵押品慢慢支付利息。第一次攻击后，它按约 0.2% 的年利率测算，剩余的 WBTC 抵押品可以付约 202 年的利息[4]；第二次攻击留下的抵押品相对更多，这个期限反而延长到 265.14 年。公司和协议的现金流被导入保险基金，等这笔债在约公元 2285 年真正违约时再由基金覆盖。保险基金原本收取借款利息的 10%，bZx 计划再加上它作为 Kyber 联盟方的收入和协议的套利收入[5]。

bZx 表示用户不会承担这笔损失，只有 ETH 借贷池受到影响；CoinGeek 报道 Kistner 称损失由公司和利益相关方吸收[5][13]。bZx 还承诺补偿在暂停期间被困的交易者。本页没有找到 v1 iETH 池这笔坏账最终如何结清、是否在升级时迁入新版本的公开记录。

换预言机

《Mea Culpa》提出分三步更换预言机。第 0 阶段用 Chainlink 作参考价格，DEX 成交价与它偏离过大时交易回滚；第 1 阶段加入 Band Protocol；第 2 阶段再加上 Uniswap v2 的时间加权价格，三者取中位数。bZx 自己注明后两个阶段只是初步设想[5]。2020 年 9 月 2 日上线的 Fulcrum 2.0 在开仓、清算和发放奖励三处都使用 Chainlink 价格，保证金交易单笔上限暂定 1,500 ETH，理由是多数协议攻击都要靠闪电贷调动大额资金[7]。

流程上的承诺

bZx 承诺以后不再部署任何未经审计的代码，提高漏洞赏金并交给独立小组评定，为每种上架资产发布风险报告，并做经济审计。它承认 1 月把闪电贷函数未经审计就推上主网是一种失职[5]。

协议后来的事故与监管

重启后不到两周，iToken 的 transferFrom 被发现允许把代币转给自己并凭空增加余额，bZx 在 9 月 15 日宣布追回全部资金[8]。2021 年 11 月 5 日，一名开发者的私钥泄露导致 BSC 和 Polygon 部署被盗约 5,500 万美元[14]。以太坊部署已转为 DAO 治理，没有受影响；BSC 和 Polygon 部署的管理权还没有移交 DAO，开发者的私钥一失窃，攻击者就同时拿到了这两个部署的控制权[15]。2020 年 2 月帮助止损的管理员权限，在这次事故里成了单点。

监管方面，CFTC 2022 年与 bZeroX 及两名创始人和解，又在加州北区联邦地区法院起诉 Ooki DAO，2023 年 6 月由 William H. Orrick 法官作出缺席判决，罚款数额见时间线[16][17]。两案针对的是未注册经营杠杆交易和未做客户身份识别，与 2020 年 2 月的攻击无关。

教训与防御

给合约开发者
  • 交易之后的健康检查不要设基于输入参数的捷径。某种情形确实不需要检查，就让它走单独的代码路径，而不是用一个条件把检查短路掉。
  • 风险判断要看交易的实际结果：卖出了多少、换回了多少、仓位里现在有什么，而不是从参数的样子推断“这是哪种交易”。
  • 单笔规模上限和滑点上限是对付未知漏洞的最后一道防线。bZx 在第一次修复和 9 月重启时都加上了这一条。
给预言机和抵押品设计者
  • 不要用能在同一笔交易里被推动的价格给抵押品定价，无论它来自 AMM 池的即时价还是聚合器的报价。优先用时间加权价格或外部聚合价格，最好多源比对，偏离过大时回滚。
  • 买卖价差检查只能发现套利价格，发现不了整体价格被推走。
  • 评估一种抵押资产，要看它流动性最薄的那个价格来源。sUSD 同时有深度足够的 Synthetix Depot 和很浅的链上储备，攻击者正是在前者按公允价买入、在后者推高价格。
给协议设计者
  • 假设攻击者能在一笔交易里零成本借到市场上可借的全部流动性，按这个前提做经济审计。bZx 自己的结论是，经济审计比代码审计更有可能提前发现第二次攻击。
  • 再小的代码改动也要审计。bZx 1 月的闪电贷函数只有 40 行，未经审计上线，里面就有任意调用漏洞。
  • 暂停和升级权限要公开写明范围；这些密钥本身要按金库级别保护，2021 年的事故说明它们同样会被盯上。
