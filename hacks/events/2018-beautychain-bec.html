区块链被盗事件编年史

总览　/　2018 年　/　智能合约登场

BeautyChain（BEC）整数溢出

2018 年 4 月 22 日，攻击者调用 BEC 代币合约的批量转账函数，利用“人数 × 单笔金额”这一步的乘法溢出，没花一枚代币就给两个地址各记上约 5.8×10⁵⁸ 枚 BEC，而 BEC 的总量只有 70 亿枚。部分代币被转进 OKEx 抛售，项目方随即暂停合约转账，交易所回滚了异常成交，项目方换发了新合约。两天后同类漏洞在 SmartMesh（SMT）上重演，OKEx、火币等交易所一度暂停全部 ERC-20 代币的充值。

概要

BEC 合约在标准的 ERC-20 转账之外加了一个批量转账函数 batchTransfer：先用“收款地址数 × 每个地址的金额”算出总额，检查调用者余额够不够，再给每个地址加钱。合约里对余额和金额的加减都经过 SafeMath，唯独这一行乘法没有。Solidity 0.8 之前，uint256 乘法溢出不会报错，只会悄悄截断。攻击者传入 2 个地址、每个地址 2²⁵⁵ 个最小单位，乘积 2²⁵⁶ 恰好截断成 0，余额检查于是对任何地址都成立。

结果是调用者的余额减了 0，两个收款地址各多出约 5.79×10⁵⁸ 枚 BEC。PeckShield 的监控系统在 UTC 03:28 发现了这笔转账，把漏洞命名为 batchOverflow，编号 CVE-2018-10299[1][10]。攻击者把部分代币转进 OKEx 抛售，BEC 价格大跌[2][5]。美链暂停了合约的全部转账，OKEx 暂停 BEC 的提币和交易，事后把 4 月 22 日 13:18（香港时间）之后的 BEC 成交全部回滚，并给受影响用户 10% 的 USDT 补偿[4][5]。

美链随后部署了删掉 batchTransfer 的新合约，把攻击前的持仓 1:1 映射过去，攻击者地址的余额不予映射[4][25]。安全公司很快发现，以太坊上还有十几个合约带着同样的代码[1][2]。两天后，SmartMesh（SMT）等代币被人用相似的加法溢出攻击，OKEx、火币、Poloniex 等交易所一度暂停全部 ERC-20 代币的充值或充提[6][7][8]。攻击者身份至今没有公开。

背景

美链（Beauty Chain）自称“全球第一个基于区块链技术打造的美丽生态链平台”，打算用代币 BEC（官网中文名“美蜜”）奖励内容创作和社区参与。官网把自拍修图应用 BeautyPlus 列为“种子应用”；两位创始人 Ryan Cheung 和 Edward Chow 此前创办的 PressLogic 获得过美图的 A 轮投资[4][12]。当时的中文报道里也有“美图 BEC”的叫法[15]。

BEC 总量 70 亿枚，流通量 35 亿枚，2018 年 2 月 23 日开始流通，按基金会 30%、生态发展 10%、团队 10%、社区奖励 50% 分配，项目注册地是新加坡，OKEx 的项目资料里预售和公募各项都填着“N/A”[14]。同一天，OKEx 作为全球首家交易所上线 BEC，开通 BEC/BTC、BEC/ETH、BEC/USDT 三个现货交易对[13]。攻击发生前，BEC 的价格约为 0.3 美元[2][9]。

BEC 合约的源码在 Etherscan 上公开验证，编译器版本 0.4.19[3]。它的结构是当时常见的代币模板：SafeMath 库，加上 BasicToken、StandardToken、Ownable、Pausable、PausableToken 一层层继承，最后由 BecToken 设定名称、精度和总量。其中 Pausable 与 zeppelin-solidity 1.3.0（OpenZeppelin Contracts 的早期版本）中的同名合约逐行相同，PausableToken 里的 transfer、transferFrom、approve 三个包装函数也与模板一致[24]。batchTransfer 是项目方自己加进 PausableToken 的。它不属于 ERC-20 标准，作用是用一笔交易给最多 20 个地址各转同样数量的代币。

漏洞原理

batchTransfer 接收两个参数：收款地址数组 _receivers 和每个地址收到的数量 _value。下面是 Etherscan 上已验证源码中的这个函数[3]，行号与 PeckShield 文中引用的一致[1]：

// BecToken.sol，PausableToken 合约中的 batchTransfer（第 255–267 行）
function batchTransfer(address[] _receivers, uint256 _value)
    public whenNotPaused returns (bool) {
  uint cnt = _receivers.length;
  uint256 amount = uint256(cnt) * _value;     // 裸乘法，没有用 SafeMath
  require(cnt > 0 && cnt <= 20);
  require(_value > 0 && balances[msg.sender] >= amount);  // amount 为 0 时恒成立

  balances[msg.sender] = balances[msg.sender].sub(amount);  // 扣的是截断后的 amount
  for (uint i = 0; i < cnt; i++) {
      // 加的是完整的 _value，每个地址一份
      balances[_receivers[i]] = balances[_receivers[i]].add(_value);
      Transfer(msg.sender, _receivers[i], _value);
  }
  return true;
}

来源：Etherscan 上已验证的 BecToken 合约（0xc5d105e63711398af9bbff092d4b6769c82f793d）源码第 255–267 行。去掉了一层缩进，函数签名折成两行，中文注释是本站加的。

uint256 能表示 0 到 2²⁵⁶ − 1。Solidity 0.8 之前，加、减、乘的结果超出这个范围时不会报错，只保留结果的低 256 位，相当于对 2²⁵⁶ 取模；0.8 以后这种行为只在 unchecked 块里保留[22]。所以只要 cnt × _value 恰好是 2²⁵⁶ 的整数倍，amount 就是 0。攻击者用的是最简单的一组：2 个地址，_value = 2²⁵⁵，十六进制是 0x8000…0000（8 后面 63 个 0）[1][2]。

攻击发生时，函数里每一行的实际取值如下：

行这一步取值说明
256取人数 cnt2两个攻击者控制的地址
257算总额 amount0数学上应为 2²⁵⁶，溢出截断成 0，不报错
258人数检查通过只限制人数，不限制金额
259余额检查通过任何余额都 ≥ 0，调用者不需要持有 BEC
261调用者扣款减 0调用者余额不变
263收款地址入账各加 2²⁵⁵循环两次，代币凭空出现

合约里其实有 SafeMath

同一个文件的开头就定义了 SafeMath。它的 mul 用除法反推来检测乘法溢出，transfer 里的加减法也都走 SafeMath[3]：

// BecToken.sol 第 7–12 行：SafeMath.mul，溢出时 assert 失败，整笔交易回滚
library SafeMath {
  function mul(uint256 a, uint256 b) internal constant returns (uint256) {
    uint256 c = a * b;
    assert(a == 0 || c / a == b);   // 截断后 c / a 不等于 b，就能发现溢出
    return c;
  }
  // ……（div、sub、add 从略）……
}

// 第 59–68 行：BasicToken.transfer，减和加都经过 SafeMath
function transfer(address _to, uint256 _value) public returns (bool) {
  require(_to != address(0));
  require(_value > 0 && _value <= balances[msg.sender]);
  // SafeMath.sub will throw if there is not enough balance.
  balances[msg.sender] = balances[msg.sender].sub(_value);
  balances[_to] = balances[_to].add(_value);
  Transfer(msg.sender, _to, _value);
  return true;
}

来源：同上，第 7–12 行和第 59–68 行，省略了 SafeMath 的其余三个函数和一个空行，去掉了一层缩进。英文注释是原有的。

写这份合约的人知道整数溢出，模板里的加减法都处理了，自己新加的那一行乘法却没有。SECBIT 当天的分析也指出了这一点。它找到的另外 12 个相同合约中，有些出自不同的开发团队，SECBIT 推测这些代码可能来自同一个作者[2]。

为什么要两个不同的地址，cnt ≤ 20 为什么挡不住

入账那一行用的是 SafeMath 的 add，它只在结果溢出时回滚。两个收款地址原本余额都是 0，各加一次 2²⁵⁵ 不会溢出，这道检查不起作用。如果把同一个地址填两次，第二次就是 2²⁵⁵ + 2²⁵⁵，add 会让整笔交易回滚。这是从代码推出的结论，与 PeckShield 看到的“同一合约转给两个不同地址”一致[1]。

cnt <= 20 只限制了人数。只要 cnt × _value 恰好等于 2²⁵⁶，乘积就会截断成 0，例如 4 个地址各 2²⁵⁴，或 16 个地址各 2²⁵²。这同样是从代码推出的，实际攻击只用了 2 个地址。

代币合约有一条隐含的不变量：所有地址的余额之和等于 totalSupply。transfer 减和加的是同一个数，天然守住这条规则。batchTransfer 减的是截断后的 amount，加的是 cnt 份完整的 _value，两者一旦不等，差额就凭空出现在收款地址上。batchTransfer 不改 totalSupply，所以攻击之后 totalSupply 仍是 70 亿枚，两个收款地址的余额加起来却约有 1.16×10⁵⁹ 枚。

正确的写法

把这一行乘法也交给 SafeMath 就够了，这也是 SECBIT 漏洞清单给出的建议写法[18]。到了 Solidity 0.8 以后，同样一行裸乘法会因为溢出直接回滚[21]：

// 示意：两种不会溢出的写法
// Solidity 0.4.x：乘法也走 SafeMath，溢出时 assert 失败，整笔交易回滚
uint256 amount = uint256(cnt).mul(_value);

// Solidity 0.8 及以后：算术运算默认检查溢出，溢出时以 Panic(0x11) 回滚
uint256 amount = cnt * _value;

示意代码，不是美链的补丁。美链的实际做法是在新合约里把 batchTransfer 整个删掉，见“后续处置”。

攻击过程

攻击者没有公开身份，也没有发表过任何说明。下面的步骤依据 PeckShield 和 SECBIT 对攻击交易的分析[1][2]。

  1. 不需要本金扣款额因为溢出变成 0，发起交易的地址不必持有任何 BEC，只要付以太坊的手续费。PeckShield 的说法是，两个收款地址的余额增加了天量的 _value，攻击者却“without costing a dime”[1]。
  2. 构造参数准备两个收款地址，_value 填 2²⁵⁵。按 ABI 编码，交易输入依次是函数选择器 0x83f12fec、数组的偏移位置、_value、数组长度 2 和两个地址[2]。
  3. 一次调用，两条转账记录batchTransfer 执行后发出两条 Transfer 事件，金额都是 2²⁵⁵ 个最小单位，即约 5.79×10⁵⁸ 枚 BEC。PeckShield 在 UTC 03:28 报警的，就是这两笔金额相同、来自同一合约、收款地址不同的转账[1]。SECBIT 文中链接的攻击交易是 0xad89ff16fd1ebe3a0a7cf4ed282302c06626c1af33221ebe0d3a470aba4a660f[2]。
  4. 转进交易所抛售攻击者把一部分 BEC 转进交易所卖出，OKEx 在香港时间 13:00 前后发现异常交易[5]。具体卖了多少、换成了什么，美链和 OKEx 都没有公布。SECBIT 的说法是，在项目方暂停合约之前，攻击者卖出的不多[2]。
  5. 合约被暂停美链宣布暂停 BEC 的一切交易和转账[4]，SECBIT 的描述是项目方暂停了合约[2]。BEC 继承了 Pausable：owner 调用 pause() 后，带 whenNotPaused 修饰符的 transfer、transferFrom、approve 和 batchTransfer 全部失效，漏洞也就无法再被利用。
// BecToken.sol 第 205–208 行、第 221–224 行：Pausable 合约
modifier whenNotPaused() {
  require(!paused);            // 暂停后，带这个修饰符的函数一律回滚
  _;
}

function pause() onlyOwner whenNotPaused public {   // 只有 owner 能调用
  paused = true;
  Pause();
}

来源：同上。batchTransfer 的声明里带着 whenNotPaused（第 255 行），所以暂停对它同样生效。

一笔交易还是两笔

PeckShield 写的是“两笔”各 2²⁵⁵ 的大额转账，CryptoSlate 写的是增发分“两笔交易”完成[1][9]。从代码看，_value 为 2²⁵⁵ 时 cnt 必须是偶数，每次调用至少留下两条转账记录，所以这两条记录应来自同一次调用，这与 SECBIT 解析的交易输入（数组长度为 2）一致[2]。本站没有做链上核对。

资金去向

这起事件里没有真实资产被直接转走。攻击者拿到的是合约账本上凭空多出来的余额，要变现只能卖给别人。所以资金去向取决于两件事：攻击者在交易所卖出了多少，这些成交后来有没有被撤销。

  1. 凭空增发两个地址各多出 2²⁵⁵ 个最小单位，合计约 1.16×10⁵⁹ 枚 BEC
  2. 转进 OKEx 抛售香港时间 13:00 前后出现异常成交，BEC 价格大跌
  3. 暂停与回滚合约停止转账；OKEx 撤销 13:18 之后的 BEC 成交，按当天 USDT 价格结算并补偿 10%
  4. 新合约映射攻击前的持仓 1:1 转到新合约，攻击者的余额不予映射，旧合约停用

公开了的

增发数量，PeckShield、SECBIT、CoinDesk 给出的数字一致[1][2][8]。攻击前的价格，约 0.3 美元[2][9]。OKEx 回滚的基准时间和补偿比例[4][5]。新合约地址和映射规则[4]。

没有公开的

攻击者实际卖出了多少 BEC，换回了多少 USDT、BTC 或 ETH。这些资产有没有在暂停之前从交易所提走。回滚让 OKEx 和成交对手承担了多少成本。攻击者是谁。

当时有报道把增发数量直接乘以市价，算出天文数字的“损失”。CryptoSlate 按每枚 0.32 美元算出约 3.7×10⁶⁰ 美元，可是按它自己给出的数量和单价相乘只有约 3.7×10⁵⁸[9]。CertiK 则把两个地址合计的 2²⁵⁶ 个最小单位写成了“2²⁵⁶ 枚代币”[19]。这类数字没有意义：凭空增发的代币不可能按市价全部卖出，真实损失只取决于攻击者实际卖出并提走的部分，而这部分从未公开。本站因此不给这起事件标注被盗金额。

影响

交易所成了实际的防线

PeckShield 在披露时写道，以太坊讲“代码即法律”，合约部署后不能修改，也没有传统软件那样的安全响应机制；它作为第三方安全公司，无权让交易所暂停可疑代币的交易[1]。能拦住损失的是交易所。

4 月 25 日 SMT 出事后，OKEx 暂停全部 ERC-20 代币的充值，理由是攻击者能凭空生成大量代币充进正常地址、操纵价格[7]。火币 Pro 一度暂停所有币种的充提，后收窄为 ERC-20 代币；Poloniex、Changelly、Quoine、HitBTC 也暂停了 ERC-20 相关服务，CoinDesk 发稿时 Poloniex 已经恢复[8]。据 CryptoSlate 转述，火币的公告还提到，其系统检测到了 SMT 攻击者的充值，没有入账[9]。PeckShield 同日指出，部分受影响的代币仍能在 gate.io、HitBTC、YoBit、CoinExchange 交易[6]。这与 CoinDesk 关于 HitBTC 已暂停的说法不一致，可能对应的是不同时刻。

漏洞不止一个合约

PeckShield 在 4 月 22 日就说扫描到十几个 ERC-20 合约存在同样问题[1]。SECBIT 按函数选择器比对，找出 12 个与 BEC 相同的合约[2]。在 SECBIT 后来维护的问题代币清单里，batchTransfer 溢出一类列了 13 个地址，其中包括 BEC，清单的说明文字却写“至少还有 10 个合约”，两处口径不一致[18]。

漏洞与溢出位置已知受影响的合约
batchOverflow（CVE-2018-10299），batchTransfer 的乘法BEC 及另外 12 个相同合约，含 AMMBR[2][18]
proxyOverflow（CVE-2018-10376），transferProxy 的加法MESH、UGToken、SMT、SMART、MTC、FirstCoin、GG Token、CNY Token、CNYTokenPlus[6][11]
2018-06 披露的 CVE-2018-11687 等 5 个，多种整数溢出，本站未逐条核对SECBIT 称扫描两万多个合约，发现 800 多个有同样问题[18]

从 SafeMath 到 Solidity 0.8

BEC 已经引入了 SafeMath，只是没有用在每一处运算上。所以事后的建议集中在“每一处都要用”。SECBIT 的小标题就是“Use REAL SafeMath”[2]。NCC Group 发起的 DASP Top 10（2018）把 batchOverflow 和 proxyOverflow 列为“算术问题”一类的真实案例[20]。CertiK 用 BEC 举例说明，给函数加上“不溢出”的后置条件，形式化验证几秒钟就能给出反例[19]。

结构性的改变发生在两年多以后。2020 年 12 月发布的 Solidity 0.8.0 把溢出检查做进了编译器：算术运算默认检查溢出，溢出时以 Panic(0x11) 回滚；要用旧的回绕行为，必须写进 unchecked 块[21]。SafeMath 因此大多不再需要，OpenZeppelin 在 2023 年的 Contracts 5.0 中删掉了它[23]。用 0.8 编译 BEC 那一行裸乘法，攻击交易会直接失败。

溢出并没有消失

编译器的检查只管加减乘除这类算术运算。Solidity 文档写明，位移运算从不做溢出检查，结果总是截断；把整数显式转换成更小的类型时，高位会被直接丢掉；unchecked 块里的运算按设计回绕[22]。Solidity 以外的链，则要看各自的语言和数学库。

事件溢出在哪里后果

后续处置

交易所回滚成交

4 月 24 日，OKEx 宣布把 BEC/BTC、BEC/ETH、BEC/USDT 三个交易对的数据回滚到 4 月 22 日 13:18（香港时间），只回滚这个时刻之后的 BEC 成交，其他币种不受影响[5]。按美链 5 月 2 日的通报，回滚在 4 月 28 日完成，统一按成交当天的 USDT 价格结算，另给用户 10% 的 USDT 补偿[4]。这次回滚只改了交易所自己的内部账本。The DAO 之后以太坊的硬分叉改的是整条链的状态，需要全网升级，两者不在一个层面。

换发新合约

旧合约的代码不能修改，美链只能另部署一个合约，把攻击前的持仓 1:1 映射过去，攻击者地址的余额不予映射。映射从 4 月 25 日开始，因为持币地址分散、以太坊网络拥堵，到 5 月 2 日凌晨（香港时间）才完成[4]。

新合约的版本号是 1.0.1，用 0.4.23 编译[25]。对比 Etherscan 上新旧两份已验证源码，功能上唯一的差别是 batchTransfer 被整段删掉，SafeMath、暂停开关和 owner 权限原样保留[3][25]。新合约的构造函数仍把 70 亿枚全部记在部署者名下，映射应是项目方逐笔转账完成的。这是本站根据代码和公告做的推断，美链没有说明具体做法。

安全公司与交易所的后续动作

PeckShield 和 SECBIT 披露漏洞时都表示已联系受影响合约的项目方[1][2]。SECBIT 随后在 GitHub 上建立问题代币合约清单，按漏洞类型归类，batchTransfer 溢出编为 A1 类[18]。Quantstamp 为 Binance 审计了已上线的 ERC-20 代币，结论是没有一个受这两个溢出漏洞影响，并表示已联系所有受影响的代币项目，愿意按成本价协助修复[17]。SmartMesh 则把“交易所完成 ERC-20 审计所需的时间”列为恢复 SMT 充提的条件之一[16]。

攻击者与项目现状

截至 2026 年 10 月，本站没有查到任何机构公开攻击者的身份，也没有查到执法或司法方面的进展。美链官网 beauty.io 在 2020 年 7 月 18 日之后就没有再被 Internet Archive 正常抓取到，之后先返回 502，2021 年 6 月起返回 404[26]。本站也没有找到 OKEx 关于恢复 BEC 交易或将其下架的公告。

教训与防御

给合约开发者
  • 每一处运算都要防溢出，包括“看起来不会溢出”的乘法。BEC 合约里，涉及用户传入金额的运算只有这一行没走 SafeMath。
  • 用 0.8 以上的编译器，把 unchecked 块、位移和向更小类型的转换当作审查重点。
  • 先校验再计算。批量转账可以先要求 _value <= balances[msg.sender] / cnt，或者在循环里逐笔用 sub 扣款。
  • 对外部传入的数值测边界：0、1、2²⁵⁵、2²⁵⁶ − 1，以及数组里出现重复地址的情况。
  • 把“余额之和等于 totalSupply”写成不变量，用模糊测试或形式化验证去检查。
给项目方
  • 在成熟模板上新加的代码风险最高，应该单独审计。BEC 的 Pausable 与模板逐行相同，漏洞在项目方自己加的 13 行里。
  • 暂停开关当天止住了损失，也意味着 owner 能冻结所有人的代币。这种权限应该在上线前向持有人说明。
  • 同一份代码常被多个项目复用。一个合约出事，应尽快按函数选择器或代码相似度扫描同类合约并通知交易所，SECBIT 当天就是这样找到另外 12 个合约的[2]。
给交易所
  • 上币前审查合约里的非标准函数和 owner 权限，batchTransfer 这类 ERC-20 标准之外的函数尤其要看。
  • 入账前做合理性检查。单笔充值超过代币总量这类明显的异常，系统应自动拒绝；SMT 事件中，火币的系统就检测到了攻击者的充值，没有入账[9]。
  • 接入链上异常转账监控。PeckShield 的系统在 UTC 03:28 报警，比 OKEx 发现异常成交早约一个半小时[1][5]。
