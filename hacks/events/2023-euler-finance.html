总览　/　2023 年　/　国家级黑客与人的弱点

Euler Finance 被盗 1.97 亿美元

2023 年 3 月 13 日，攻击者利用借贷协议 Euler 新增的 donateToReserves 函数没有检查账户健康度这一点，先把自己的账户做成坏账，再用另一个地址以 20% 的折扣清算它，在几十分钟里取走约 1.97 亿美元。这段代码是八个月前一次经过审计的治理升级加进去的。三周后，攻击者道歉并归还了资金。

概要

Euler 是以太坊上的借贷协议。存款人拿到计息的 eToken 作为抵押凭证，借款人背上 dToken 作为债务。每个账户的抵押与债务之比叫健康分，低于 1 就可以被清算。凡是会减少抵押的操作，函数末尾都要检查一次健康分；2022 年加入的 donateToReserves 允许用户把自己的 eToken 捐给协议储备，抵押因此减少，函数里却没有这次检查。

攻击者从 Aave 闪电贷借出 3,000 万 DAI，用 Euler 的 mint 在一个账户里叠出约 10 倍的自抵押杠杆，然后捐出 1 亿 eDAI，把这个账户的健康分压到约 0.75。另一个账户随即以最高 20% 的折扣清算它，拿走全部剩余抵押，只承接了一部分债务，留下约 1.36 亿 dDAI 的坏账。清算后的账户抵押多于债务，可以把池子里的 DAI 全部取走[6][7]。同样的操作在 DAI、USDC、WBTC、stETH 和 WETH 几个市场重复了几次。

此后的三周里，Euler 一边在链上给攻击者留言施压，一边与执法和链上分析机构合作。攻击者在 3 月 18 日到 4 月 3 日之间分多次归还了约 95,556 枚 ETH 和约 4,306 万 DAI，并留言道歉[5]。ETH 在这段时间上涨，归还时的美元价值超过了被盗时的金额，Euler 因此称资金“100% 追回”；不过按币数算，转进 Tornado Cash 的 1,100 枚 ETH 和转给 Ronin 攻击者地址的 100 枚 ETH 没有回来[1][5]。攻击者的身份至今没有公开。

背景

Euler V1 于 2021 年 12 月部署在以太坊上，主打“无许可上币”：只要某个代币在 Uniswap V3 上有可用的定价池，任何人都能为它开一个借贷市场[1]。用户存入资产得到 eToken，借款时记一笔 dToken 债务。它还提供一个 mint 函数，同时给账户铸出等量的 eToken 和 dToken，相当于“用自己存的钱借给自己”。这种自抵押贷款的抵押率上限是 95%，普通贷款是 75%，所以自抵押可以叠出很高的杠杆[7]。

清算采用“软清算”：账户的健康分跌破 1 后，跌得越深，清算人能拿到的折扣越大，最高 20%。清算人替违约账户承接一部分债务，换取折价的抵押品[2][7]。出事前，Euler 的总锁仓约 2.64 亿美元，官网列出六家安全审计机构，还设有 100 万美元的漏洞赏金和 1,000 万美元的保险[1][9][10]。

2022 年 7 月 6 日，Euler 的开发者 Doug Hoyte 在治理论坛发布 eIP 14，把多个模块的改动打包升级。EToken 模块的说明里写着：新增 donateToReserves，允许用户把一部分 eToken 捐给储备，“可能对某些封装合约有用”，也可以用来清掉账户里的零头[4]。这个函数最早出现在 2022 年 6 月 21 日的提交 85abe8d 里，同一次提交让新市场的储备从一个非零初始值起步[3]。Euler 事后解释，这组改动是为了修复近一年前通过 Immunefi 报告的一个问题：新市场的第一个存款人可以操纵 eToken 的兑换率[1]。

论坛上有人问这些改动是否经过审计。Hoyte 回复说，Chainlink 相关的改动已由 Omniscia 审计，其余改动正由 Sherlock 等几方审阅；8 月 9 日他又补充，Sherlock 的审计员 WATCHPUG 完成了另一轮审计。8 月 18 日 Snapshot 投票通过，升级随即执行[4]。Cyfrin 后来的复盘称，donateToReserves 只被审计过一次，之后几轮审计都没有把它纳入范围[7]。

漏洞原理

Euler V1 的安全靠一条不变式：任何操作结束时，账户的健康分都不能低于 1。健康分等于按风险折算后的抵押价值除以按风险折算后的债务价值，由 checkLiquidity 按预言机价格重新计算，低于 1 就让整笔交易回滚。取款、借款（mint）、还款（burn）和 eToken 转账，都在函数末尾调用它[2]。下面是取款函数：

// EToken.sol，withdraw()
function withdraw(uint subAccountId, uint amount) external nonReentrant {
    (address underlying, AssetStorage storage assetStorage, address proxyAddr,
        address msgSender) = CALLER();
    address account = getSubAccount(msgSender, subAccountId);
    // ……（计算可取金额、检查池子余额）……
    pushTokens(assetCache, msgSender, amount);            // 把底层资产转给用户
    decreaseBalance(assetStorage, assetCache, proxyAddr, account, amountInternal);
    checkLiquidity(account);                              // 抵押减少后检查健康分
    logAssetStatus(assetCache);
}

来源：euler-xyz/euler-contracts 仓库 master 分支，contracts/modules/EToken.sol 第 180–200 行，中间几行从略，第一条语句按长度折行。

eIP 14 加入的 donateToReserves 同样会减少调用者的 eToken 余额，效果和取款一样是抵押变少，只是减掉的部分记进了协议储备，而不是转给用户：

// EToken.sol，donateToReserves()，eIP 14 加入
function donateToReserves(uint subAccountId, uint amount) external nonReentrant {
    (address underlying, AssetStorage storage assetStorage, address proxyAddr,
        address msgSender) = CALLER();
    address account = getSubAccount(msgSender, subAccountId);

    updateAverageLiquidity(account);
    emit RequestDonate(account, amount);

    AssetCache memory assetCache = loadAssetCache(underlying, assetStorage);

    uint origBalance = assetStorage.users[account].balance;
    uint newBalance;

    if (amount == type(uint).max) {
        amount = origBalance;
        newBalance = 0;
    } else {
        require(origBalance >= amount, "e/insufficient-balance");
        unchecked { newBalance = origBalance - amount; }
    }

    assetStorage.users[account].balance = encodeAmount(newBalance);   // 抵押减少
    assetStorage.reserveBalance = assetCache.reserveBalance =
        encodeSmallAmount(assetCache.reserveBalance + amount);           // 记入储备

    emit Withdraw(assetCache.underlying, account, amount);
    emitViaProxy_Transfer(proxyAddr, account, address(0), amount);

    logAssetStatus(assetCache);
    // 到这里就结束了：没有 checkLiquidity(account)，健康分低于 1 也不会回滚
}

来源：同上，EToken.sol 第 359–386 行。第一条语句和储备赋值按长度折行；最后一行注释是本站加的，原文没有这一行。

如果捐赠走的是普通的 eToken 转账，transferFrom 会对转出方调用 checkLiquidity（同一文件第 345 行）。donateToReserves 直接改写余额，绕开了这条路径[6]。漏洞本身就这么一行。

为什么能从清算里获利

只靠这个缺口，用户能做的只是把自己的账户弄得资不抵债，捐出去的抵押进了储备，对自己没有好处。让它变成攻击的是清算折扣的设计：账户健康分跌得越深，清算人拿到的折扣越大。

// Liquidation.sol，常量
uint public constant UNDERLYING_RESERVES_FEE = 0.02 * 1e18;
uint public constant MAXIMUM_DISCOUNT = 0.20 * 1e18;

// computeLiqOpp()：折扣 = 2% + (1 - 健康分)，再乘激励系数，最多 20%
uint baseDiscount = UNDERLYING_RESERVES_FEE + (1e18 - liqOpp.healthScore);
uint discountBooster = computeDiscountBooster(liqLocs.liquidator, liabilityValue);
uint discount = baseDiscount * discountBooster / 1e18;
if (discount > (baseDiscount + MAXIMUM_BOOSTER_DISCOUNT))
    discount = baseDiscount + MAXIMUM_BOOSTER_DISCOUNT;
if (discount > MAXIMUM_DISCOUNT) discount = MAXIMUM_DISCOUNT;

// Limit yield to borrower's available collateral, and reduce repay if necessary
// 抵押不够时，清算人拿走全部抵押，承接的债务按折扣后的价值相应减少
if (collateralBalance < liqOpp.yield) {
    liqOpp.repay = collateralBalance * 1e18 / liqOpp.conversionRate;
    liqOpp.yield = collateralBalance;
}

来源：euler-xyz/euler-contracts 仓库 master 分支，contracts/modules/Liquidation.sol 第 13–16、91–98、139–150 行，节选，一处长行折行。

健康分为 0.75 时，基础折扣是 2% + 25% = 27%，被封顶在 20%。清算人按八折拿抵押：每承接 0.8 份债务，就换到 1 份抵押。正常情况下，这个差价是给第三方清算人承担风险的补偿。可当违约账户和清算人都是攻击者自己时，抵押超出债务的那部分就成了可以直接取走的利润，而违约账户里剩下的债务没有任何抵押支撑，成了由其他存款人承担的坏账[7]。

两处设计叠在一起才出事

Cyfrin 的复盘把根因归为两点：捐赠后没有检查健康分；清算人的收益可以超过他承接的债务，所以清算账户不需要额外资金就能把利润取走[7]。单独存在时，前者只能让用户伤害自己，后者只是给清算人的正常激励。高倍自抵押杠杆又把规模放大了：2,000 万 DAI 本金撑起了 3.9 亿 dDAI 的债务。

修复只需要在函数末尾补上取款时已有的那次检查。下面是示意写法。Euler V1 事后没有重新开放，事发当天的处置是直接禁用这个模块，见“后续处置”。

// 示意：与 withdraw 保持一致，捐赠后也检查健康分
    emit Withdraw(assetCache.underlying, account, amount);
    emitViaProxy_Transfer(proxyAddr, account, address(0), amount);

    checkLiquidity(account);   // 健康分低于 1 时整笔交易回滚

    logAssetStatus(assetCache);
}

示意代码，并非 Euler 发布的补丁。

攻击过程

Euler、CertiK 和 Cyfrin 的复盘对 DAI 市场那一次攻击的描述一致，可以概括为四个阶段，数字取整[1][6][7]。这里只转述结论，重点是每个阶段为什么没有被拦下。

  1. 借来本金攻击者从 Aave 闪电贷借出 3,000 万 DAI，并准备了两个合约，一个用来制造坏账（复盘里称为违约账户），一个用来清算它。闪电贷必须在同一笔交易里还清，所以整个过程都发生在一笔交易之内。
  2. 叠出高杠杆违约账户存入 2,000 万 DAI，再借助 mint 的自抵押贷款把头寸放大到约 4.1 亿 eDAI 抵押、3.9 亿 dDAI 债务，健康分约 1.02。自抵押的抵押率上限是 95%，每一步都在规则之内，检查全部通过。
  3. 捐出抵押违约账户通过 donateToReserves 捐出 1 亿 eDAI，健康分跌到约 0.75。这是整个过程里唯一越界的一步，因为函数里没有健康检查，交易没有回滚。
  4. 自我清算清算合约以 20% 的折扣清算违约账户，拿走它的全部抵押，只承接了约 2.59 亿 dDAI，留下约 1.36 亿 dDAI 的坏账。清算合约的抵押多于债务，于是取走池中剩余的约 3,890 万 DAI，还掉闪电贷后，这一次净得约 888 万 DAI。

CertiK 列出的受害市场共五个：eDAI、eWETH、eWBTC、ewstETH 和 eUSDC，攻击者对每个市场重复了同样的流程[6]。DAI 市场的那一笔是第一笔，被一个自称 MEV 机器人的地址抢先执行了，所得约 880 万美元的 DAI 几个小时后又转给了攻击者的地址[1]。CertiK 发现，这个“机器人”的启动资金来自一个此前在 BSC 上利用通缩代币漏洞获利的地址[6]；rekt.news 和研究者 ZachXBT 也指出，与攻击者关联的地址此前在 BSC 上作过案，并把所得转进了 Tornado Cash[9][10]。

哪一步本可以拦住
  • 第 3 阶段：donateToReserves 末尾调用一次 checkLiquidity，交易就会回滚，后面的阶段都无从谈起。
  • 第 4 阶段：清算收益如果以承接的债务为上限，自我清算就不再有利润。
  • 第 2 阶段：如果自抵押杠杆有总量上限，单次攻击能撬动的规模会小得多。

“100% 追回”是按美元算的

Euler 在 2024 年的复盘里称被盗资金 100% 追回，标题里的金额是 2.4 亿美元，原因是谈判期间 ETH 价格上涨[1]。按币数算，约 1,200 枚 ETH 没有回来，这是 Euler 自己在兑付方案里列出的[5]。两种说法都成立，本页并列写出。

影响

Euler 自身

事发后 Euler 的总锁仓从约 2.64 亿美元跌到约 1,000 万美元，EUL 代币当天下跌超过 50%[9]。协议在禁用 eToken 模块后停摆，用户的资产只能等兑付方案出来后领取。

沿着集成扩散

更大的影响来自其他协议。不少协议把自己的资金存在 Euler 里赚利息，Euler 被掏空，它们的资产也跟着被锁住或受损。Cointelegraph 报道称受影响的协议超过 11 个[11]。rekt.news 在事发后列出的主要受影响方如下，数字是当时各方披露的风险敞口，不是最终损失[9]。这些协议在 Euler 里的存款后来也纳入了兑付范围，智能合约账户由 Euler Foundation 逐个处理[5]。

对行业

CertiK 在事发当天估计，这一起就占了 2023 年当时全部被盗金额的约 70%[6]。这次事件让两个问题受到关注。一是升级的审计范围：一次只审阅改动部分的审计，很难看出新函数和原有清算逻辑叠在一起会出什么问题。二是可组合性的代价：一个借贷协议出事，十几个把钱存在里面的协议同时受影响。

谈判追回也成了一个常被引用的先例：链上留言、悬赏、执法合作和私下沟通几种手段并用，最后几乎全额追回。不过同一年的 Curve / Vyper 等事件里，并不是每个攻击者都愿意谈。借贷协议被操纵清算的更早案例，可以对照 bZx 和 Mango Markets。

后续处置

止损

Euler 禁用了有漏洞的 eToken 模块和捐赠功能，存款随之停止，同时联系执法部门以及 TRM Labs、Chainalysis 等链上分析机构协助调查[11]。Euler V1 此后没有重新开放。

谈判

谈判几乎全程在链上公开进行，Euler 把留言写进交易的附加数据里[1][9]：

  1. 3 月 13 日：开口第一条留言写道：“我们知道今天早上对 Euler 平台的攻击是你干的”，并邀请对方谈下一步。
  2. 3 月 14 日：施压如果 24 小时内不归还 90%，就悬赏 100 万美元，征集能让攻击者被捕、资金全部追回的线索。
  3. 3 月 15 日：给台阶把 90% 的 DAI 和 ETH 还到 EulerDAO 金库，调查即可停止，资金可以直接分给用户，不必走法律途径。
  4. 3 月 18 日起：归还攻击者先还了 3,000 ETH，3 月 20 日提议建立加密通讯，此后在邮件中署名“Jacob”，3 月 25 日一次归还 51,000 ETH。
  5. 3 月 28 日：道歉攻击者留言：“Jacob here. I don't think what I say will help me in any way but I still want to say it.” 他后来私信 Euler 的联合创始人，称自己不知道可以走漏洞赏金渠道，“经验不够”。
  6. 4 月 3 日：还清最后几笔归还完成，最终归还的不是谈判时提出的 90%，而是攻击者控制的几乎全部资金。

谈判期间还有一段插曲：3 月 21 日，被美国财政部 OFAC 归因于朝鲜 Lazarus 的 Ronin 跨链桥攻击者地址，给 Euler 的攻击者发去一条加密消息，附带一个“解密工具”。Euler 认为这是想反过来黑掉他，提醒他不要使用[1]。此前攻击者转给这个地址的 100 ETH，Chainalysis 认为可能是故意制造与朝鲜有关的假象[8]。Ronin 事件见 Ronin 跨链桥被盗。

“Jacob”只是攻击者自己留下的称呼。截至 2026 年 10 月，本站没有查到针对此案攻击者的公开执法行动或起诉。

审计方赔付

审计平台 Sherlock 承认在审阅 eIP 14 时漏掉了这个问题，批准了 450 万美元的理赔，3 月 14 日先付了 330 万美元[9][11]。Euler 的兑付方案显示，金库中来自 Sherlock 保险赔付的资产为 3,396,964 USDC 和 1,007,321 DAI，这部分也用于兑付[5]。

用户兑付

Euler Foundation 在 4 月 5 日发布方案初稿，4 月 12 日发布修订版[5]。做法是：以协议被禁用时的区块为准，模拟每个子账户用资产偿还全部债务；剩余资产按事先公布的兑付区块的价格折算成净值；追回的 ETH、DAI 和 USDC 按净值比例分配。修订版增加了一条：如果按兑付时的价格，分到的资产超过净值的 1.005 倍，超出部分改分给那些因协议停摆而错过行情的持仓用户。普通地址和多签钱包签署条款后，通过 merkle 分发合约领取；141 个受影响的智能合约账户逐个处理。

2024 年 1 月，Euler Labs 发布长文复盘这次追回的经过。Euler 后来以 V2 的形式重新推出协议，同一篇文章的编者按称 V2 已完成 50 多次审计[1]。

教训与防御

给合约开发者
  • 凡是会减少抵押或增加债务的函数，都要经过同一个健康检查。与其指望每个函数记得调用，不如把检查放在所有入口共用的位置，并用不变式测试验证：任何外部可调用的函数执行完，账户健康分都不低于 1。
  • 新增一个“看起来无害”的函数时，要问它改了哪些状态，再查这些状态的每一个使用方。donateToReserves 改的是余额，而余额是清算的输入。
  • 清算激励要防自我清算：清算人的收益不应随违约程度无上限地增长，测试里要包括“违约者和清算人是同一人”的场景。
给协议和审计方
  • 升级的审计不能只看 diff。eIP 14 的改动被拆给不同的审计方，新函数和原有清算逻辑的交互没有人完整看过；Cyfrin 指出，这个函数之后几轮审计都不在范围内[7]。
  • 用存款和借款上限限制单个市场、单个账户的规模。高倍自抵押杠杆会把一个小缺口放大成上亿美元的坏账。
  • 事先准备好应急流程：能禁用的模块、能联系的执法与分析机构、给攻击者的谈判条件。Euler 在一天之内完成了止损和第一轮施压。
  • 集成其他协议的一方，要把对方的风险算进自己的风险里。这次有十几个协议同时被波及。
